## 一、文档定位与边界

### 1.1 zom workspace 中的 zom-desktop

zom 是一个 Cargo workspace，由六个 crate 组成。本文之外的 crate 各自独立设计与文档化：

```
zom-engine      纯 Rust 文本编辑底座（已冻结）
zom-workspace   "有什么"：buffer 与文件生命周期；拥有 Buffer 实例
zom-view        "我怎么看它"：view/pane/滚动/本视图 selection 与 fold
zom-command     命令派发脊柱 + 键位模型；"所有操作均是命令"
zom-ai          AI 抽象：provider trait + request/proposal 模型
zom-desktop     GPUI 外壳 + 组合根；本文档的主体
```

依赖图（无环）：

```
                                ┌─→ zom-engine
                                │
zom-desktop ─→ zom-command ─────┼─→ zom-workspace
            ─→ zom-view    ─────┤
            ─→ zom-workspace────┘
            ─→ zom-engine
            ─→ zom-ai ──────────→ zom-engine
```

`zom-ai` 与 `zom-command` 无依赖边；P4 接入 AI 命令闭环时，二者在 `zom-desktop` 组合根相遇。

### 1.2 本文档的合法领地

| 该规定 | 不该规定 |
|---|---|
| L1-L4 视觉层（外壳组件分层） | 命令系统语义（在 `zom-command`） |
| 颜色 / 尺寸 / 主题 / 字号 / i18n | 键位类型与解析（在 `zom-command`） |
| 桌面端 settings（视觉、用户偏好、键位文件） | 编辑事务 / Buffer / Snapshot（在 `zom-engine`） |
| OS 事件 → 归一化 KeyChord 的解码 | AI provider 抽象（在 `zom-ai`） |
| 组合根：如何接入并组装 5 个底层 crate | Buffer / 文件生命周期（在 `zom-workspace`） |
| Dock / Panel / EditorGrid 视觉模型 | view 状态 / fold / viewport 数学（在 `zom-view`） |
| 平台抽象（窗口控制、菜单、文件对话框） | 跨 crate 的依赖图（在根 `TODO.md`） |

遇到本文未覆盖的情形，**先确认它属于 desktop 还是某个底层 crate**：如果属于底层 crate，去对应 crate 的 docs；属于 desktop 才补本文或对应子册。

## 二、组合根

`zom-desktop` 是整个 zom workspace 的**组合根（composition root）**。底层五个 crate 各自提供 public API，desktop 负责把它们装在一起并接到 GPUI 上。

### 2.1 服务持有

desktop 持有以下顶层实例（全局或按窗口，详见《桌面端运行时手册》第二章）：

| 实例 | 来自 | 范围 |
|---|---|---|
| `Workspace` | `zom-workspace` | 每窗口绑一个（《桌面端运行时手册》§二.3） |
| `ViewSet` | `zom-view` | 每窗口绑一个 |
| `CommandRegistry` | `zom-command` | 进程单例 |
| `Keymap` | `zom-command` | 进程单例（从 settings 加载） |
| `AiProvider`（接入时） | `zom-ai` | 进程单例 |
| `ThemeRegistry` / `LocaleRegistry` / `SettingsRegistry` | 本 crate | 进程单例 |

GPUI 侧把"会变的状态"包装为 `Entity<T>`，提供 observe；不变的注册表也可包装为 Entity 以便统一 observe 接口。

### 2.2 启动序列

```
1. 加载 settings（用户级 settings.toml）
2. 启动 ThemeRegistry / LocaleRegistry（基于 settings）
3. 创建 CommandRegistry，注册内建命令
   - 安装 `zom-command::commands::editor` / `workspace` 等 catalog
   - 安装会 emit `HostEffect` 的 UI catalog（panel.toggle.xxx、window.xxx 等）
   - 若启用 AI：注册需要 AiProvider 句柄的命令（在组合根捕获）
4. 解析 settings.keymap → 构造 zom-command 的 Keymap 实例
5. 创建首个 Workspace + ViewSet（默认空白 buffer 或上次会话恢复）
6. 启动首个 GPUI Window，装配 WorkbenchFrame
```

### 2.3 命令注册的分工

| 命令类别 | 注册者 | 例 |
|---|---|---|
| 编辑命令 | `zom-command::commands::editor::install` | `editor.insert_text` / `editor.undo` / `editor.move_selection` |
| UI / 外壳命令 | `zom-command::commands::*`，handler emit `HostEffect` | `panel.toggle.file_tree` / `window.minimize` / `settings.open` |
| AI 命令 | desktop 组合根（handler 捕获 AiProvider） | `ai.propose-edit` / `ai.accept-proposal` |
| 将来插件命令 | 插件 host 调用 `CommandRegistry::register` | 任意 |

**desktop 不重新发明 CommandId / CommandArgs / Keymap**——这些已在 `zom-command` 设计完毕。desktop 的责任是：

- 注册自己负责的那一类命令
- 解码 OS 事件为 `KeyChord` 喂给 keymap（详见《桌面端运行时手册》第三章）
- 实现命令面板等 UI 入口（详见《桌面端运行时手册》第四章）

### 2.4 模块分区

desktop crate 内部分两大模块：

```
zom-desktop/src/
  shell/       视觉层与平台层（本手册的主战场）
    workbench/   L4 窗口级外壳区域、Dock 状态与 panel 固定归属
    features/    L3 功能切片；dock panel 收在 features/panels/
    surfaces/    浮面 portal 外壳：定位、层级、关闭与焦点归还
    bubble/      气泡提示层：统一轻量提示模型
    shared/      L2 视觉原语、资源、主题 token
    platform/    平台差异收纳（《桌面端运行时手册》第三章）
    ...
  app/         命令装配、Workspace / ViewSet / Keymap 编排、IME 状态投影
    command.rs   命令派发与 HostEffect 收集
    ime.rs       输入法桥接
    ...
```

`shell` 不依赖 `app`；`app` 装配 `shell` 并接入底层 crate。

## 三、组件层级

桌面端组件代码必须按四层组织。**每一层的所有权规则不同**，混淆层级是后续所有腐烂的起点。

```
L4  Region      ── TopBar / BottomBar / EditorGrid / Dock
                  窗口级外壳区域。强存在感、几乎不复用、由 app 层组装。
L3  Composite   ── CommandPalette / FileTree / TabStrip / StatusItem / EditorView
                  业务组件。有领域状态、有交互语义、有专属文案与图标。
L2  Primitive   ── Button / Glyph / Tooltip / Popover / Frame
                  视觉原语。无领域语义、可被多处复用。
L1  Token       ── gray.s03 / blue.a04 / space.s4 / radius.r4 / type.f13
                  视觉刻度。只是命名常量。
```

### 3.1 各层所有权

| 层 | 必须自己拥有 | 必须从下层取 | 不能拥有 |
|---|---|---|---|
| L4 Region | 区域内 layout 决策、专属 placement、专属 actions | 视觉原语、token | 不能直接画图形（要复用 L2） |
| L3 Composite | 视觉状态、交互语义、专属 icon / 文案 / actions | L2 + L1 | 不能定义新的复用型颜色或尺寸；不能持有领域状态（领域状态在 workspace / view） |
| L2 Primitive | 视觉算法（圆角、阴影、布局）、变体枚举 | L1 | 不能持有业务状态、不能知道自己被谁用 |
| L1 Token | 一组命名常量 | — | 不能引用任何上层 |

### 3.2 L3 与领域状态的边界

L3 视觉组件**不拥有领域状态**——领域状态在底层 crate：

| 领域状态 | 真正归属 | desktop L3 怎么用 |
|---|---|---|
| Buffer 内容、dirty、path | `zom-workspace::WorkspaceBuffer` | EditorView 透过 `Entity<Workspace>` 句柄读 |
| View 的光标、滚动、fold | `zom-view::View` | EditorView 透过 `Entity<ViewSet>` 句柄读 |
| 命令注册表 | `zom-command::CommandRegistry` | CommandPalette 透过句柄读列表 |
| AI 提案 | `zom-ai::AiProposal` | AI 面板透过 provider 句柄读 |

L3 自己拥有的"视觉状态"只是：折叠展开标志、搜索框输入文本、当前 hover 项、滚动位置缓存（非视图本体）、表单临时填写值等**纯 UI 状态**。

### 3.3 "组件自给自足"的精确含义

"组件掌控自身资源"这条原则**只在 L3 严格成立**。L4 太大、L2 太通用、L1 本身就是资源。

一个 L3 组件的目录应当长成这样：

```
shell/features/panels/file_tree/
  mod.rs              对外只导出 FileTree 与其 Props
  view.rs             render 逻辑（小组件可直接写在 mod.rs）
  state.rs            可选。纯 UI 状态（折叠、hover、scroll cache 等非领域状态）
  actions.rs          组件专属 UI action 枚举
  copy.rs             组件专属文案，每条用 match cx.locale() 给出多语言（见《桌面端视觉系统》§五）
  tests.rs            必需。至少覆盖一次主要 UI 状态转移（见第六章）
  logic.rs            可选。纯算法（fuzzy 匹配、树折叠等），可裸单测
  preview.rs          可选。playground 用的典型状态 variants
  styles.rs           可选。组件本地视觉常量（仅当不是 token 复用时）
```

注意组件目录**没有** `assets/` 与 `theme/` 子目录：视觉 token 不属于任何单个组件，资源文件（svg / 字体）由根资源目录统一管理。

### 3.4 是否新增视觉常量的判定

L3 组件经常会想"我这个特殊场景需要一个 token 里没有的值"。判定准则只有一条：

> **改了这个值，会影响其他组件吗？**
>
> - 会 → 它属于 token，必须进 L1。
> - 不会 → 它属于组件本地常量，写在组件目录里。

典型的组件本地常量：红绿灯三色（模仿系统、拒绝主题改写）、品牌徽标的精确尺寸、组件内特殊图形的几何参数。

## 四、依赖方向

### 4.1 desktop 内部单向依赖图

```
L4 Region ─────┐
               ├──> L2 Primitive ──> L1 Token ──> Platform
L3 Composite ──┘
```

严禁的反向依赖：

- L2 不能 `use crate::app::*`（原语不能知道领域）
- L3 不能 `use crate::shell::region::*`（组件不能知道自己住在哪个区域）
- L1 不能 `use` 任何上层
- 同层之间不准互相 `use`（同层组件互相不可见，要复用就下沉到下一层）

### 4.2 跨 crate 依赖

desktop 对底层 crate 的依赖：

```
zom-desktop ─→ zom-engine
            ─→ zom-workspace
            ─→ zom-view
            ─→ zom-command
            ─→ zom-ai
```

**所有跨 crate 调用只走 public API**。不允许使用其他 crate 的私有路径、源码 import、测试细节。

底层 crate 之间的依赖方向由根 `TODO.md` 与各 crate README 锁定，desktop 不打破它。

### 4.3 用模块可见性强制

依赖方向必须在编译期强制，不靠人审。

- L1 token 模块：`pub(crate)`，全 crate 可见
- L2 primitive 模块：`pub(crate)` 导出原语类型；内部实现 `pub(super)`
- L3 composite 模块：`pub(crate)` 只导出组件类型与 Props；其余一律 `pub(super)` 或私有
- L4 region 模块：仅 `app` 层可见，对外 `pub(super)`
- `app/` 是组合根，可以 import `shell/`；反之**禁止**

**第一版就要把模块树切对**。事后切的代价是十倍。

## 五、状态注入

### 5.1 组件只接受两种输入

L3 组件不准在内部主动去全局拿状态。只接受两种输入：

```
A. 数据   通过构造函数 / Props 传入（不可变快照、显式 Entity 句柄、显式 crate 服务句柄）
B. 行为   通过回调 / action handle 传入
```

禁止形式：

```rust
// 反例：组件内部直接读全局
let workspace = cx.global::<Workspace>();
```

正确形式：

```rust
// 正例：调用方注入显式句柄
pub struct EditorView {
    workspace: Entity<Workspace>,   // 来自 zom-workspace
    view_set: Entity<ViewSet>,       // 来自 zom-view
    view_id: ViewId,                 // 标识本视图
    on_request_command: Box<dyn Fn(CommandId, CommandArgs, &mut App)>,
}
```

### 5.2 透明传播的全局例外

下列全局通过 `cx.xxx()` 透明访问，**不算违反 5.1**：

| 入口 | 来自 | 用途 |
|---|---|---|
| `cx.theme()` | desktop ThemeRegistry | 当前主题色 |
| `cx.fonts()` | desktop FontRegistry | 当前字号配置 |
| `cx.locale()` | desktop LocaleRegistry | 当前语言 |
| `cx.settings()` | desktop SettingsRegistry | 当前 settings 快照 |

**例外清单由本手册维护，不允许扩展**。底层 crate 的服务（`Workspace` / `ViewSet` / `CommandRegistry` / `AiProvider`）**不在例外清单**——必须通过显式句柄注入。

### 5.3 GPUI 特有陷阱

- L2 / L3 不准调用 `cx.global::<App级状态>()`
- 跨层数据传递必须用 `&View<T>` / `Entity<T>` 显式传入，且 T 必须是该组件需要的最小子状态
- 跨组件通信走 action / event，不走"两个组件读同一个 global"
- 底层 crate 的 entity 句柄从 app 层一路 props 传到 L3，不走 cx global

### 5.4 收益是可替换、可测试、可预览

强制 5.1 的收益不是教条，而是三件具体的事：

- **可替换**：替换组件不需要改它的调用者以外的任何代码
- **可测试**：组件可以脱离完整 app 上下文独立测试
- **可预览**：组件可以放进 playground 单独渲染

## 六、测试要求

### 6.1 哲学

"可测试性"不等于"脱离 GPUI"。GPUI 提供 `TestAppContext`，可在测试里启动 headless app。zom-desktop 把"可测"的标准定义为**用 TestAppContext 能跑通**，而不是"代码不依赖任何 GPUI 类型"。

workspace 统一测试策略见 [`../agents/project.md`](../../agents/project.md)。底层 crate（`zom-engine` / `zom-workspace` / `zom-view` / `zom-command` / `zom-ai`）有各自的 contract test，**desktop 不重复测试它们的领域逻辑**。desktop 测试关注：

- L3 视觉组件的 UI 状态转移
- 组合根：服务注入是否正确、命令注册是否完整、Keymap 加载是否成功
- 跨 crate 接入的边界行为

### 6.2 L3 组件的硬规则

每个 L3 组件必须满足：

> **提供至少一个 `#[gpui::test]`，覆盖该组件的主要 UI 状态转移。**

没有测试的 L3 组件不允许合入。"主要 UI 状态转移"指：打开/关闭、激活/失活、用户交互导致的视觉状态变化。

视觉呈现（颜色、布局、icon 选择）**不在测试覆盖范围**，由 playground 人工 review 兜底。

### 6.3 state / view 是否分文件

**不强制**。L3 的纯 UI 状态可直接放在 `mod.rs` 或 `view.rs` 的 impl 块中。下列任一情况触发拆分：

1. 单文件超过约 300 行 → 拆 `view.rs`
2. `render` 函数超过约 80 行 → 拆视觉子组件
3. 复杂派生计算 → 抽 `logic.rs`（**纯 Rust 函数**，可裸单测）

`logic.rs` 是 desktop 唯一鼓励"脱离 GPUI"的场景——纯算法。

### 6.4 各层测试要求

| 层 | 测试要求 |
|---|---|
| L4 Region | integration 测试覆盖区域组装与面板挂载位置 |
| L3 Composite | 必须 `#[gpui::test]` 覆盖 UI 状态转移；纯算法抽 `logic.rs` 裸单测 |
| L2 Primitive | 关键变体 `#[gpui::test]`；layout 算法可裸单测 |
| L1 Token | 不需要测试 |
| app（组合根） | 启动 smoke test：能成功启动、命令注册无缺漏、keymap 解析无错 |

### 6.5 视觉回归：playground 优先

第一版**不引入 snapshot 截图对比**。视觉回归走 playground 人工 review。

组件可选提供 `preview.rs`：

```rust
pub fn variants() -> Vec<(&'static str, FileTreeUiState)> {
    vec![
        ("empty", FileTreeUiState::empty()),
        ("one-folder", ...),
        ("deep-nested", ...),
    ]
}
```

playground 是 desktop 内部开发工具，遍历所有组件的 `variants()` 渲染网格。

### 6.6 测试不该做的事

- **不测视觉细节**（颜色值、像素 padding）
- **不测 token 取值**
- **不测 GPUI 内部行为**（render 被调用了几次、layout pass 顺序）
- **不重测底层 crate 的领域逻辑**（buffer 怎么 undo 是 engine 的契约测试覆盖的，desktop 不重复）

## 七、扩展性

### 7.1 第一版不做通用插件系统

zom-desktop 第一版**不发布**任何通用插件 API。理由：

- 插件 API 是**单向门**——1.0 发布后所有变更都要兼容旧插件
- MVP 阶段没有用户、没有插件作者
- 设计错误会污染整个核心架构，且无法事后剥离

通用插件系统推迟到**第三版及以后**。

### 7.2 但第一版就具备的"插件友好"基础设施

下列设施对第一版自己也有价值，同时为将来插件铺路：

- **命令系统**：`zom-command` 提供的 `CommandRegistry` 本身就是开放注册表（类型擦除 handler）。插件将来注册命令是同一个 API
- **键位外置**：用户已经能改键位、未来插件能注册键位
- **AI 意图入口**：`AiAction` 已经走"翻译为命令"的路径，与插件命令同形
- **主题驱动**：主题就是配置驱动的内容扩展（见《桌面端视觉系统》第二章）
- **语言支持配置**：第二版将引入 `languages/<name>/` 目录配置

### 7.3 L3 形态：具体类型，不抽 trait

L3 视觉组件第一版采用**具体结构体**形态，在 app 层硬编码注册。**不为不存在的插件预先抽 trait + 注册表**。

```rust
// 第一版
pub struct FileTree { ... }
pub struct CommandPalette { ... }

// shell/workbench 层硬编码组装
fn build_workbench(...) -> Workbench { ... }
```

但 L3 的 **Props / 对外接口必须按 trait 思维设计**：命名清晰、参数稳定、不漏内部实现。将来加扩展时是机械重构。

### 7.4 长期：WASM 沙箱

第三版引入通用插件系统时，采用 **WASM 沙箱** 方案。

选 WASM 而非其他架构的理由：

| 候选 | 否决理由 |
|---|---|
| 动态库 (dylib) | 插件崩了带崩主进程；平台特定二进制 |
| 内嵌 Lua / JS | 被锁死在脚本生态；解释器内嵌增加二进制体积 |
| 子进程 IPC | 适合 LSP 这种重交互场景；通用插件开销太大 |
| **WASM** | **跨平台分发统一、强隔离、性能接近 native、语言中立、Zed 的实际选择** |

API 通过 WIT（WebAssembly Interface Types）定义、版本化。

### 7.5 插件能力锁定

无论何时引入插件系统，能力锁定在以下范围：

| 能力 | 是否允许插件 |
|---|---|
| 注册命令 | 允许 |
| 注册键位 | 允许（通过用户 settings.keymap 引用插件命令） |
| 注册语言支持（LSP / grammar） | 允许 |
| 编辑器装饰（诊断、inlay hint、代码动作） | 允许 |
| **注册自己的 dock panel** | **明确禁止** |
| **画任意 UI** | **明确禁止** |
| **修改外壳布局** | **明确禁止** |

理由：UI 是变化最快的层，锁定 UI 接口 = 主程序失去演化自由。允许的能力覆盖 80% 真实插件需求。

### 7.6 API 兼容承诺

- **第一版**：无公开扩展 API
- **第二版**：语言支持配置 schema 是稳定 API，遵循 semver
- **第三版**：WASM 插件 API 是永久承诺；破坏性变更必须主版本号 + 迁移期

| 持久化时机 | 状态变化 debounced 1s；workspace 切换 / 窗口关闭 / 正常退出强制 flush；panic 不写持久化（只走 crash-recovery） | 运行时 §九.4 |
| 持久化 schema | 强 schema + serde；未知字段警告不阻塞；缺失用默认；内嵌 `schema_version` 便于将来 migration | 运行时 §九.6 |
| 持久化失败 | 失败用默认 + toast + 日志；绝不影响关键路径 | 运行时 §九.8 |
| 与 crash-recovery 关系 | 互补：持久化存元数据 / crash-recovery 存 dirty 文本；下次启动顺序：先 layout 再检测 crash dump | 运行时 §九.9 |
| Buffer 内容不进 desktop 持久化 | layout 只存 buffer 路径；内容归 workspace 保存 / crash-recovery；避免重复与未保存数据泄漏 | 运行时 §九.10 |
| 关闭入口收敛 | 所有关闭入口（命令 / 键位 / 信号 / 平台事件）派发同一 `app.quit` 命令 | 运行时 §十.1 |
| 关闭流程 | 单一 handler 走完整序列：dirty check → flush persist/settings → 销毁窗口 → 清理子进程 → 退出；幂等 | 运行时 §十.2 |
| Workspace 切换 | `workspace.open`（当前窗口替换）vs `workspace.open_in_new_window`（新窗口）；前者必须 dirty check + flush | 运行时 §十.3 |
| 系统信号 | SIGINT/SIGTERM/macOS Cmd-Q/Windows shutdown 等都收敛到 `app.quit`；handler 必须 async-signal-safe | 运行时 §十.5 |
| 首次启动 | 创建配置目录但不主动创建 `settings.toml`；加载内置默认；首个 workspace 按 CLI → 默认空 workspace | 运行时 §十.6 |
| CLI 参数 | 第一版：`zom` / `zom <path>...` / `zom --new-window [path]` / `--version` / `--help`；用 clap 解析 | 运行时 §十一.1 |
| 路径解析 | 目录视为 workspace 根；文件视为打开目标（workspace 走文件最近 git root 或 cwd）；不存在路径当新文件处理 | 运行时 §十一.2 |
| 实例策略 | **第一版多实例**；每次启动新进程；第二版升级单实例 + IPC；CLI 表面不变 | 运行时 §十一.3 |
| 退出码 | 0 正常 / 1 panic / 2 CLI 参数错 / 3 配置严重错误 | 运行时 §十一.4 |
| 平台集成 | 第一版只保证命令行 `zom <path>` 工作；GUI 文件关联、URL handler（`zom://`）、stdin pipe 全部推迟到第二版 | 运行时 §十一.5、§十一.6、§十一.7 |
| 焦点唯一真相源 | `AppFocus` 是 desktop 焦点系统唯一语义源；所有命令、快捷键、IME、剪贴板、状态栏查询都从它派生；不允许 `ViewSet.active` / Dock active panel / 组件本地"激活态"并行 | 运行时 §十二.1、§十二.2 |
| FocusStore 持有焦点 | 每窗口一个 `FocusStore { current, previous }`；`previous` 只有一层,用于 Surface 关闭后焦点复位 | 运行时 §十二.3 |
| 焦点边界 | 显示状态 ≠ 焦点状态：active view / active panel / 文件树 selected / panel 可见性都不是焦点 | 运行时 §十二.4 |
| 文本路由由焦点派生 | EditorRouter 不再按 owner 顺序找第一个 active；`router.owner_for(app.focus().current())`；`TextTargetId` 由 `AppFocus` 叶子节点替代 | 运行时 §十二.5 |
| FocusProjection 是 shell 投影层 | `AppFocus <-> FocusHandle` 双向桥接；不决定业务焦点；旧 `FocusRouter` 名字废弃 | 运行时 §十二.6 |
| 焦点切换走命令 | 所有焦点变化通过 `HostEffect::Focus(AppFocus::..)` 表达；不允许直接操作 `FocusHandle` | 运行时 §十二.7 |
| 焦点旧概念迁移 | `FocusRole` / `FocusTarget` / `FocusRegistry` / `FocusRouter` / `TextTargetId` / 组件本地 active 都按运行时 §十二.8 表替换或删除；新代码不准引入旧概念 | 运行时 §十二.8 |
| 焦点不持久化 | 第一版不持久化当前焦点；重启由布局恢复逻辑默认到 active editor | 运行时 §十二.11、§九.5 |
