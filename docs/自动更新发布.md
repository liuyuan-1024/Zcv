# 自动更新发布

Zcv 从 GitHub Releases 获取更新。应用每次启动时自动检查一次，本次运行期间不再查询；
发现新版本后自动下载并验证，准备完成时才在 TopBar 设置按钮左侧显示“重启以更新”。

当前只支持安装为 `Zcv.app`、且内置更新公钥的 macOS 构建。直接运行的二进制通常不具备
这些发布条件，因此不会检查更新。代码不按 debug/release 模式分流；只要构建具备相同条件，
开发构建也执行同一套启动检查。

更新信任锚固定为公钥 `btPdamnS0mdny0zsaJA3qM/Du/XGAGXKQq93GC81Q0k=`，为公开信息；
只有清单签名私钥必须保密。安全根是 Ed25519 私钥：私钥不泄漏时，即使 GitHub 账号被接管，
攻击者也无法制作合法更新（只能重放旧签名清单，而应用只接受严格更高的版本）。

零费用方案使用 ad-hoc 代码签名，没有 Developer ID 与公证。后果：

- 用户第一次从 GitHub 安装时，macOS 会提示“无法验证开发者”，需要在
  “系统设置 → 隐私与安全性”中点击“仍要打开”。Apple 允许用户手动建立这一例外。
- 应用内更新不经过 LaunchServices 启动，且安装副本会清理下载元数据，因此通常静默完成；
  但不同 macOS 版本的安全策略行为有差异，发布前必须实测（见下文“静默更新的前提”）。
- 没有 Apple 恶意软件扫描、证书身份与公证撤销能力；公司管理的 Mac 可能禁止运行。

## 一、发布流程

1. 确认版本号已在 `Cargo.toml` bump 且高于线上版本，当前 HEAD 已打 `v<version>` 标签。
2. 运行发布脚本（打包 → 生成清单 → 签名 → 核对公钥）：

   ```text
   scripts/release-update /安全位置/zcv-update-key.pkcs8.b64
   ```

   产物输出到 `target/aarch64-apple-darwin/release/`：`latest.json`、`latest.json.sig` 和 zip。
   已打过包时可加 `--no-build` 跳过构建；脚本内部调用 `scripts/bundle-mac`
   （ad-hoc 签名 + hardened runtime）生成 `Zcv.app`。
3. 建立 `v<version>` 的 GitHub Release 草稿，上传 zip、`latest.json` 和 `latest.json.sig`。
4. 核对清单 URL、文件大小、SHA-256、版本和公钥后发布，使其成为 GitHub 的 latest Release。
5. 用上一正式版启动应用，验证自动下载、TopBar 提示、重启替换和新版本启动确认。

不要先发布缺少清单或签名的 Release。网络暂时不可用时，本次检查静默结束并在下次启动重新
尝试；签名、摘要、版本或压缩包结构不合法会通过错误 Toast 提示，不会执行替换。

### 使用 CI 自动发布（可选）

仓库已提供 `.github/workflows/release.yml`：push 以 `v` 开头的 tag 后，CI 自动完成
版本核对、构建打包、清单签名和 GitHub Release 创建。使用前先配置签名私钥：

1. 打开仓库 Settings → Secrets and variables → Actions → New repository secret。
2. Name 填 `ZCV_UPDATE_PRIVATE_KEY`，Value 填私钥文件内容（`cat /安全位置/zcv-update-key.pkcs8.b64` 的输出）。
3. 发布时：本地 bump 版本、提交推送、打 tag 并推送：

   ```text
   git tag v0.8.19 && git push origin v0.8.19
   ```

CI 在 Apple Silicon runner（`macos-14-xlarge`）上运行，public 仓库按 4 倍扣减免费分钟数；
产物与清单不一致（tag 版本 ≠ Cargo.toml 版本、私钥公钥 ≠ 内置公钥）会中止发布。
tag 已存在但需要重跑时，可用 Actions 页面的手动触发。

**信任模型变化**：CI 方式下私钥进入 GitHub Actions secrets，不再只保存在本地；GitHub 账号
被完全接管时，攻击者可修改 workflow 调用私钥签名。这是自动发布的固有代价，手动发布则
没有这一风险。

## 二、Release 资产契约

每个正式 GitHub Release 必须包含：

```text
latest.json
latest.json.sig
Zcv_<version>_darwin_arm64.zip
```

当前只发布 Apple Silicon（arm64），不提供 Intel（x86_64）产物。

`latest.json` 是 stable 通道的唯一版本事实，示例：

```json
{
  "schema_version": 1,
  "channel": "stable",
  "version": "0.8.19",
  "published_at": "2026-08-29T12:00:00Z",
  "assets": {
    "macos-aarch64": {
      "url": "https://github.com/liuyuan-1024/Zcv/releases/download/v0.8.19/Zcv_0.8.19_darwin_arm64.zip",
      "size": 12345678,
      "sha256": "小写十六进制 SHA-256"
    }
  }
}
```

应用始终读取：

```text
https://github.com/liuyuan-1024/Zcv/releases/latest/download/latest.json
https://github.com/liuyuan-1024/Zcv/releases/latest/download/latest.json.sig
```

因此 GitHub 上的 latest Release 必须是当前 stable 版本，且两个固定名称的文件必须随每次发布一起替换。

## 三、签名密钥管理

建立密钥（只执行一次）：

```text
cargo run -p zcv-update --bin zcv-update-keygen -- /安全位置/zcv-update-key.pkcs8.b64
```

命令把 Base64 编码的 Ed25519 PKCS#8 私钥写入指定文件，并在标准输出打印公钥。
私钥不得提交到仓库或附加到 Release；公钥固定在 `zcv/src/auto_update.rs` 的
`UPDATE_PUBLIC_KEY`，当前值为 `btPdamnS0mdny0zsaJA3qM/Du/XGAGXKQq93GC81Q0k=`。应离线备份
私钥。不能直接更换公钥，否则已安装版本将无法验证新清单；密钥轮换需要先发布能够同时信任
新旧密钥的过渡版本。

## 四、静默更新的前提（发布前实测）

Gatekeeper 只拦截带下载元数据（`com.apple.quarantine` / `com.apple.provenance`）且经
LaunchServices 启动的应用。本方案对静默更新做了两处保障：

- 更新 zip 由应用自身下载、用 ditto 解压，正常路径不会携带下载元数据；
- helper 在原子切换前会清理已验证副本上的下载元数据，避免后续手动双击再次触发提示。

仍应在目标 macOS 版本上实测完整更新流程（旧版本 → 重启替换 → 新版本双击启动），确认
没有 Gatekeeper 提示。如果某版本行为异常，优先检查下载/解压路径是否引入了下载元数据。

另外，用户如果直接从“下载”文件夹双击运行首次安装的 ad-hoc 应用，macOS 会把它转译到
只读临时路径（App Translocation）。转译状态下自动更新会被禁用（写入转译路径会在重启后
丢失），请提示用户把 `Zcv.app` 移到“应用程序”文件夹。
