# 架构决策记录

本文只记录会影响多个 crate、且未来维护者可能重新讨论的长期决策。当前模块职责与使用方式写在对应 crate README 中。

## 1. Git 能力使用具体类型

**决定**：`zcv-git` 直接提供当前本地 Git 实现所需的具体类型，不为不存在的第二实现预建 backend trait。

**理由**：当前只有一个真实消费模型。抽象接口会复制能力边界并增加转发层，不能带来实际解耦。

**重新评估条件**：出现第二个已确认的 Git 实现，且两者共享稳定的行为集合。

## 2. 语言能力由 Tree-sitter 驱动

**决定**：语言配置、语法高亮、语法节点识别和基础语法感知由 `zcv-language`、Tree-sitter 与 `.scm` 查询维护；编辑器实现通用输入行为。

**理由**：当前范围不包含 LSP 或语言插件系统。提前建立这些抽象会让尚不存在的消费方决定核心边界。

**重新评估条件**：项目正式引入 LSP 或外部语言扩展，并有明确生命周期与隔离需求。

## 3. 组合文档统一使用 MultiBuffer

**决定**：项目搜索结果、Git 差异等由多个文本片段组成的编辑视图，统一建立在 `zcv-multi-buffer::MultiBuffer` 上。

**理由**：选择、滚动、显示投影和编辑行为应消费同一种文档边界，不为每个功能维护一套平行编辑器模型。

**重新评估条件**：出现无法由摘录与缓冲区组合表达、且具有不同编辑语义的真实文档类型。

## 4. 所有文档统一由一个 Editor 展示

**决定**：Zcv 从始至终只有一个 `Editor`。普通文档、组合文档以及差异、搜索等文档形态，不是不同的编辑器，也不是不同的编辑逻辑；它们只是 `Editor` 所展示的内容组织与显示投影不同。所有文档都通过同一套选择、滚动、输入、编辑、折叠、命中测试和渲染管线展示。

**理由**：文档形态属于编辑器的显示差异，不能反向切分编辑器的状态、交互语义和生命周期。统一编辑器可以保持行为单一、状态所有权明确，并避免为普通文档和组合文档维护平行逻辑。

**实现约束**：业务层不得按文档形态复制 `Editor` 或建立普通文档与组合文档两套编辑流程；差异应由文档内容映射、可编辑性、源坐标映射或显示投影承载。`Editor` 的不同构造入口只表达输入场景或内容来源，不代表不同编辑器。

**重新评估条件**：不预设。除非未来出现具有不同编辑语义、状态生命周期和交互契约的真实编辑能力，否则不得以新的文档形态拆分编辑器。

## 5. 文本事实与编辑器视图状态分离

**决定**：`zcv-text::Buffer` 保存文本事实；语言状态、组合文档、编辑器交互状态和显示投影分层持有。

**理由**：文本、语法、选择、滚动和布局具有不同生命周期。分层使每项事实只有一个可写所有者，也避免 UI 成为第二份文档模型。

**重新评估条件**：不预设。新增能力应先放入拥有其生命周期的现有层；只有职责无法清晰归属时再调整分层。

## 6. 自动更新使用签名清单与独立 helper

**决定**：应用使用内置 Ed25519 公钥验证 Release 清单，按清单校验完整平台安装目录，并由独立 helper 在应用退出后执行替换、启动确认和回滚。macOS 使用 app bundle 原子交换；Windows 在目录级备份与切换后保留同样的启动确认和回滚协议。

**理由**：HTTPS、SHA-256 或 ad-hoc 代码签名单独都不能证明更新发布者身份；Ed25519 清单建立独立信任根。运行中进程也不应直接覆盖自身 bundle。

当前免费分发采用 macOS ad-hoc 签名，不依赖 Developer ID、Team ID、公证或强制 Gatekeeper 评估；Windows 包使用版本标记文件和清单哈希校验。发布者身份由签名清单保证。

**重新评估条件**：发行渠道或外部兼容要求明确要求 Apple Developer ID、公证或其他平台安装机制。即使改变分发身份，清单验证与事务替换仍应作为独立边界评估。

## 7. 跨平台差异按能力域收敛

**决定**：每个跨平台能力域提供一个平台无关的语义入口；平台路径、系统调用、权限、进程模型、文件系统行为和资源释放由该能力域的私有平台后端负责。更新、终端进程、Git 进程树、文件监听、设置路径和项目文件操作分别维护自己的边界，不建立聚合所有系统能力的全局 `Platform` 抽象或 `zcv-platform` crate。

**理由**：平台差异的共同点在于生命周期和语义，不在于系统 API 本身。共享业务流程可以保证 macOS、Windows 与其他平台的行为一致；把不相关的系统能力集中到一个平台层会降低内聚，并让一个能力的变化影响其他能力。只有多个能力域确实共享稳定的语义、所有权和错误契约时，才提取共享平台原语。

**实现约束**：调用方不直接判断平台布局或拼接平台流程；统一入口拥有状态机和错误语义，后端拥有系统资源的完整生命周期。平台无关测试覆盖共同流程，平台测试覆盖后端与操作系统边界。新增平台时应增加后端实现，而不是复制一套业务编排。

**重新评估条件**：出现多个能力域真实共享同一平台原语，且共享后的所有权、生命周期和错误契约已经稳定；或新增平台无法在现有能力域边界内表达而需要重新划分职责。

## 8. 跨平台边界通过登记表和持续门禁维护

**决定**：使用[跨平台能力边界](跨平台能力边界.md)登记统一入口、平台后端、状态所有者、资源生命周期和验证层次；由 `scripts/check-platform-boundaries` 检查变更中新增的平台实现是否离开后端或原生测试边界，并在持续集成中运行平台无关契约测试和 macOS/Windows 原生后端检查。

**理由**：能力域边界只在一次重构中成立是不够的。登记表提供当前架构的唯一维护入口，自动门禁阻止明显的平台实现泄漏，分平台检查则把“能编译”与“已完成运行时验证”分开。门禁不替代对状态所有权、生命周期和真实平台行为的人工审查。

**重新评估条件**：能力域重新划分、持续集成平台变化，或门禁规则出现稳定误报/漏报时，先更新登记表和验证矩阵，再调整脚本或工作流。

## 9. 路径按语义类型跨平台收敛

**决定**：引入窄的 `zcv-path` 路径语义 crate，区分操作系统原生绝对路径、项目相对路径和稳定路径身份。原生路径保留给文件系统与进程边界；绝对路径在进入工作区时使用兼容形式规范化；相对路径内部固定使用 `/`；Git revision spec 和持久化身份分别在其能力域内转换。

**理由**：Windows 的 `\\?\` 是文件系统 API 的合法扩展路径形式，不能全局删除；但它不应泄漏到 Git、缓存、工作区身份和 UI。单一 `PathBuf` 同时承担系统调用、路径比较、协议字符串和持久化键会让平台差异重新散落到调用方。Zed 的 `AbsPathBuf`、`RelPathBuf` 和 `dunce::canonicalize` 证明了值类型与边界转换可以收敛这类差异，但 Zcv 不复制 Zed 的远程路径和完整文件系统抽象。

**实现约束**：`zcv-path` 只提供路径值语义，不聚合窗口、终端、Git 或更新等平台后端。文件系统大小写和符号链接行为仍由实际文件系统能力提供；不得用全局小写或无条件移除 `\\?\` 代替运行时语义。路径尚不存在时，只有在删除事件等已定义场景才允许保留其简化后的原生形式，不能把失败静默当作规范化成功。

项目内部 Git 状态快照使用 `RelativePathBuf`；文件监听事件和版本控制树节点使用 `AbsolutePathBuf`。只有进入 Git 命令、文件系统操作或打开文件的边界才转换为 `PathBuf`，路径键、事件过滤和树展开状态不得重新退回裸路径。

**重新评估条件**：出现明确的非 UTF-8 项目相对路径需求，或多个能力域需要共享超出当前绝对/相对/身份语义的稳定路径契约时，先补充行为和所有权证据，再调整 `zcv-path` 的类型边界。
