# 交互架构

> 描述 zcv 中用户输入的路由模式、快捷键分层与组件类型边界。
> 本文是规范，代码和后续开发应遵守本文定义的规则。

---

## 1. 总则

输入设备只有两类：**键盘**和**鼠标**。任一操作可能由两者共同触发。

### 1.1 键盘只有一条路

键盘输入在 GPUI 中只有一种路径：

```text
按键 ──► bind_keys ──► dispatch_action ──► .on_action(handler) ──► 业务
```

没有其他选择。所有键盘快捷键最终都交给 `on_action` handler。

### 1.2 鼠标有两条路，由决策条件决定

鼠标点击有两条路径：

```text
点击 ──┬── dispatch_action ──► .on_action(handler) ──► 业务  （有键盘等效时）
       └── 直接 handler                                    （无键盘等效，指向具体数据时）
```

决策条件只有一个：**这个点击有没有对应的键盘快捷键？**

```
点击发生
  ├── 有键盘等效（toggle panel / 退出 / 设置 / 保存）
  │     └── dispatch_action → 与按键合流 → 同一 on_action handler
  │
  └── 无键盘等效，且指向具体数据（选中第 3 行 / 关闭 tab 5）
        └── 直接 handler（数据在闭包里，action 帮不上忙）
```

### 1.3 核心规则

**同一种行为，不允许存在两套实现。**

- 按键 `cmd-shift-e` 触发 `ToggleProjectTree`，那么鼠标点击同一个"项目树"图标必须走 `dispatch_action` 命中同一个 `on_action` handler。不允许图标点击再写一套直接逻辑。
- 没有键盘等效的操作（树行选中、关闭指定 tab），数据在闭包里，直接处理。

### 1.4 澄清：什么是"有键盘等效"？

"有键盘等效"不是"键盘也能做类似的业务动作"，而是**"同一个 action 类型、同一个 handler 就能覆盖，不需要额外参数"**。

以项目树为例验证这条边界：

| 操作 | 选中目标 | handler 能否共用？ |
|------|---------|------------------|
| 鼠标点击第 5 行 | 选中路径 `/src/main.rs` | 数据来自闭包捕获的 `path` |
| 键盘 `down` | 从当前选中行移到下一行 | 数据来自 `state.selected` + 偏移量 |

**鼠标和键盘表面上都做了"选中 + 展开/折叠"，但它们的 handler 无法共用。** 鼠标需要知道具体点了哪个 `path`，键盘需要基于当前选中行做相对移动。强行合流只会让 handler 里的 `if` 分支膨胀。所以鼠标走直接 handler、键盘走 `on_action` 是正确的分工。

**判断标准：** 问自己一个问题——"把这个点击改成 `dispatch_action` 后，现有的 `on_action` handler 需要改代码才能支持它吗？"

- 不需要改 → **有键盘等效**，走 `dispatch_action`
- 需要改（加参数、加分支、加新逻辑）→ **不是同一个命令**，走直接 handler

## 2. 输入路由规范

### 2.1 有键盘等效的鼠标点击 → dispatch_action

鼠标点击与键盘快捷键触发**同一命令**时，必须走 `dispatch_action` 合流。

```rust
// ✅ 正确：点击 dispatch_action，与按键合流

// 组件模块定义 action 和快捷键
actions!(window_controls, [QuitWindow, MinimizeWindow, ToggleMaximizeWindow]);

pub(crate) fn key_bindings() -> Vec<gpui::KeyBinding> {
    vec![
        KeyBinding::new("cmd-q", QuitWindow, None),
        KeyBinding::new("cmd-m", MinimizeWindow, None),
        KeyBinding::new("cmd-shift-m", ToggleMaximizeWindow, None),
    ]
}

// 点击 → dispatch_action（产生与按键相同的 action 类型）
pub(crate) fn render(window: &Window) -> gpui::Stateful<gpui::Div> {
    div()
        .child(pip(Pip::Close, active)
            .on_click(|_, window, cx| window.dispatch_action(Box::new(QuitWindow), cx)))
        .child(pip(Pip::Minimize, active)
            .on_click(|_, window, cx| window.dispatch_action(Box::new(MinimizeWindow), cx)))
        .child(pip(Pip::Maximize, active)
            .on_click(|_, window, cx| window.dispatch_action(Box::new(ToggleMaximizeWindow), cx)))
}

// keyboard → bind_keys 命中同一 action → 同一 on_action handler
window.dispatch_action(Box::new(QuitWindow), cx)
```

handler 定义在组件模块中，在 Workspace 注册：

```rust
// Workspace::render 中注册 handler
.on_action(window_controls::handle_quit)
.on_action(window_controls::handle_minimize)
.on_action(window_controls::handle_toggle_maximize)
```

**规则：** 任何有键盘快捷键的命令，其鼠标点击必须使用 `dispatch_action`，不得直接调用业务方法。

### 2.2 无键盘等效、指向具体数据的点击 → 直接 handler

点击天然携带指向信息（点击了第几行、哪个文件），且没有键盘等效要合流，在 `on_mouse_down` / `on_click` 中直接处理。

```rust
// ✅ 正确：树行点击直接处理
.on_mouse_down(MouseButton::Left, move |_, window, cx| {
    let mut s = state.borrow_mut();
    if is_dir { s.toggle_expand(&path); }
    s.select(&path);
    window.refresh();
    cx.stop_propagation();
})
```

**规则：** 无键盘等效的点击不经过 action。数据由闭包捕获，action 路由不提供额外价值。

### 2.3 决策表

| 场景 | 有键盘等效？ | 路由 |
|------|------------|------|
| 底栏「项目树」图标点击 | ✅ cmd-shift-e | `dispatch_action` → `on_action` |
| 顶栏「设置」图标点击 | ✅ cmd-, | `dispatch_action` → `on_action` |
| 窗口控制关闭圆点点击 | ✅ cmd-q | `dispatch_action` → `on_action` |
| 底栏「终端」图标点击 | ✅ cmd-j | `dispatch_action` → `on_action` |
| 文件树行点击 | ❌ 指向具体行 | `on_mouse_down` → 直接 handler |
| 标签栏 tab 关闭按钮点击 | ❌ 指向具体 tab | `on_click` → 直接 handler |

## 3. 快捷键注册规范

### 3.1 全局快捷键

全局快捷键不依赖焦点上下文，在任何时候都生效。

**定义位置：** 组件模块暴露 `key_bindings()` 函数。
**注册位置：** Workspace::new 中收集所有 `key_bindings` 后一次性 `cx.bind_keys()`。
**handler 注册：** Workspace::render 中 `.on_action()`。

```rust
// 组件模块 —— 定义 action + 快捷键 + handler
actions!(dock, [ToggleProjectTree, ToggleVersionControl, ...]);

pub(crate) fn key_bindings() -> Vec<gpui::KeyBinding> {
    vec![
        KeyBinding::new("cmd-shift-e", ToggleProjectTree, None),  // context: None = 全局
        KeyBinding::new("cmd-shift-g", ToggleVersionControl, None),
        // ...
    ]
}

pub(crate) fn handle_toggle_project_tree(...) {
    // 通过事件或 Workspace 方法修改布局
}

// Workspace —— 收集 + 注册
// Workspace::new
let mut bindings = Vec::new();
bindings.extend(window_controls::key_bindings());
bindings.extend(top_bar::key_bindings());
bindings.extend(dock::key_bindings());
bindings.extend(project_tree::key_bindings());
cx.bind_keys(bindings);

// Workspace::render
.on_action(dock::handle_toggle_project_tree)
```

### 3.2 上下文快捷键

上下文快捷键仅在组件聚焦时生效，用 `key_context` 避免快捷键冲突。

```rust
actions!(project_tree, [TreeUp, TreeDown, TreeLeft, TreeRight, TreeSpace]);

pub(crate) struct ProjectTree {
    focus: gpui::FocusHandle,
    state: Rc<RefCell<ProjectTreeState>>,
    scroll_handle: UniformListScrollHandle,
}

impl ProjectTree {
    pub(crate) fn new(root: PathBuf, cx: &mut Context<Self>) -> Self {
        let focus = cx.focus_handle();
        cx.bind_keys(vec![
            KeyBinding::new("up", TreeUp, Some("FileTree")),
            KeyBinding::new("down", TreeDown, Some("FileTree")),
            KeyBinding::new("left", TreeLeft, Some("FileTree")),
            KeyBinding::new("right", TreeRight, Some("FileTree")),
            KeyBinding::new("space", TreeSpace, Some("FileTree")),
        ]);
        Self { focus, state: Rc::new(RefCell::new(ProjectTreeState::new(root))), scroll_handle: Default::default() }
    }
}

impl Render for ProjectTree {
    fn render(&mut self, _window: &mut Window, cx: &mut Context<Self>) -> impl IntoElement {
        div()
            .size_full()
            .track_focus(&self.focus)
            .key_context("FileTree")
            .on_action(cx.listener(Self::handle_tree_up))
            .on_action(cx.listener(Self::handle_tree_down))
            .on_action(cx.listener(Self::handle_tree_left))
            .on_action(cx.listener(Self::handle_tree_right))
            .on_action(cx.listener(Self::handle_tree_space))
    }
}
```

`key_context` 的作用是避免冲突而非解决焦点丢失。"down" 在编辑器里是下一行，在文件树里是下一项——焦点在哪就用哪套绑定。没有自己焦点的组件不需要上下文，它们的快捷键永远是全局的。

### 3.3 两种注册方式对比

| | 全局快捷键 | 上下文快捷键 |
|---|---|---|
| 适用范围 | 始终生效 | 仅组件聚焦时生效 |
| 注册时机 | Workspace::new 收集后一次性注册 | 组件自己的 `new()` 中注册 |
| key_bindings 定义位置 | 组件模块的 `key_bindings()` 函数 | 组件 `new()` 中内联 |
| handler 类型 | 自由函数，Workspace 注册 | `cx.listener(Self::method)`，组件自注册 |
| handler 访问状态 | 通过 Workspace 方法或 Window API | 通过 `&mut self` |
| `key_context` | 不需要（`None`） | 组件 Render 中 `.key_context("...")` |

### 3.4 快捷键注册流程

```text
组件模块定义 action 类型 ──► 组件模块暴露 key_bindings() ──► Workspace::new 中
  (actions! macro)              (return Vec<KeyBinding>)         extend + cx.bind_keys()
       │
       ▼
GPUI 焦点树路由到 on_action handler
       │
       ├─► 全局快捷键 → Workspace::render 中 .on_action(自由函数 handler)
       └─► 上下文快捷键 → 组件 Render 中 .on_action(cx.listener(Self::method))
```

每个组件模块负责：
- 定义自己的 action 类型（`actions!`）
- 定义自己的快捷键映射（`key_bindings()`）
- 定义自己的 handler（自由函数或 `cx.listener` 方法）

Workspace 负责：
- 收集所有 `key_bindings` 一次性注册
- 在 render 中注册全局 action 的 `on_action` handler

## 4. 组件类型与交互能力

### 4.1 各类型允许的交互能力

| 组件类型 | actions! | key_bindings | handler 类型 | 焦点 | 跨帧状态 |
|---|---|---|---|---|---|
| **Entity** | ✅ | ✅ 全局或上下文 | 自由函数或 `cx.listener` | ✅ 可选 | ✅ |
| **函数式** | ✅（仅全局） | ✅（全局，由 Workspace 注册 handler） | 自由函数 | ❌ | ❌ |
| **Builder** | ❌ | ❌ | 通过 `on_click` 参数内联 | ❌ | 构建期持有 |

**关键规则：** 函数式组件可以有 `actions!` + `key_bindings` + handler（如 `window_controls`），这不改变它的分类。因为函数式组件也可能有按键交互，这些交互必须使用 action 来实现点击和按键统一。只要不引入 struct 和 Render/IntoElement trait，依然是函数式组件。

### 4.2 zcv 各组件的交互能力

| 组件 | 类型 | actions! | key_bindings | handler 位置 | 焦点 | 状态模式 |
|---|---|---|---|---|---|---|
| `Workspace` | Entity(root) | ❌ | 集中注册 | 内联 + 子模块函数 | ✅ | `Rc<RefCell<LayoutController>>` |
| `TopBar` | Entity | ✅ | 全局 | Workspace 注册 | ❌ | 字段直存 |
| `StatusBar` | Entity | ❌ | ❌ | 父组件直接调用 | ❌ | 字段直存 |
| `ProjectTree` | Entity | ✅ | 上下文 | 自有 `cx.listener` | ✅ | `Rc<RefCell<State>>` |
| `WindowControls` | 函数式 | ✅ | 全局 | Workspace 注册 | ❌ | ❌ |
| `Glyph` | Builder | ❌ | ❌ | 调用方通过 `on_click` 传入 | ❌ | 构建期持有 |
| `tree` 辅助 | 函数式 | ❌ | ❌ | ❌ | ❌ | ❌ |
| `frame` 辅助 | 函数式 | ❌ | ❌ | ❌ | ❌ | ❌ |
| `workspace/mod` 的布局渲染辅助 | 函数式 | ❌ | ❌ | ❌ | ❌ | ❌ |

## 5. Entity 状态管理

Entity 的状态管理有三种模式：

| 模式 | 方案 | 适用场景 | zcv 实例 |
|---|---|---|---|
| **A** | 直接 struct 字段 | 状态只在本组件 Render 中读取 | TopBar、StatusBar |
| **B** | `Rc<RefCell<T>>` | 状态需在多个闭包/回调中共享 | ProjectTree（`uniform_list` 闭包 + `on_mouse_down` 闭包） |
| **C** | Controller + Snapshot | 状态逻辑复杂，需独立单元测试 | `LayoutController` + `LayoutSnapshot` |

**`Rc<RefCell<T>>` 的使用边界：** 只在 GPUI 列表渲染器（`uniform_list`）的闭包需要与外部事件闭包共享状态时使用。这是 GPUI 自身 API 约束导致的必要妥协，不是推荐的状态管理方式。非 uniform_list 场景不使用 `Rc<RefCell>`，直接用 struct 字段。
