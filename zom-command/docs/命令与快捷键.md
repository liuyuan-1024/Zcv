# 命令与快捷键系统设计

`zom-command` 是 zom 宿主层的命令与快捷键基础设施。本文沉淀命令注册、参数解析、键位解析、`HostEffect` 边界，以及「加新命令该改哪儿」的操作手册。

设备输入如何统一收敛为 `HostIntentRequest`、`CommandRequest`、`KeyRequest` 或交互意图，见 `zom-desktop/docs/桌面端输入意图.md`。本文只描述其中的**命令管线**与**快捷键解析**。

---

## 1. 核心原则

> **可命名的离散动作是命令**。键盘快捷键、按钮、菜单和命令面板可以把同一个动作表达成 `(CommandId, CommandArgs)`，再经命令执行器处理。

命令不是所有输入设备事件的总入口。鼠标拖拽、滚动、resize、窗口焦点投影等高频交互走 desktop 的输入意图 / 交互管线；IME 的系统回调先进入 `HostIntent::Ime`，再在边界层翻译成编辑命令。

四个直接推论：

1. **单一命令派发边界**：命令执行器只接受 `(CommandId, CommandArgs)`，每条命令在自己模块里 `TryFrom<CommandArgs>` 解析强类型参数 —— 字段名只在命令模块出现一次（参数模型方案 A）。
2. **内建注册表**：`CommandRegistry` 保存当前产品内建命令，不为插件或未知调用方提供动态注册承诺。
3. **命令系统不直接接触宿主**：handler 拿到的 `CommandContext` 只暴露 `Workspace / ViewSet / CommandQueue / EffectQueue`。需要 GPUI 或 shell 布局时，发出一个 `HostEffect`，由宿主翻译。
4. **键位是命令的一种入口**。desktop 把物理键归一化成 `KeyChord` 后交给 `Keymap`；匹配成功才派发命令，未匹配必须放行给系统 IME。`Keymap` 反查 `CommandId → KeySequence` 是 UI 显示快捷键的唯一真理源。

## 2. 模块边界

```text
zom-command/
├── src/
│   ├── lib.rs               门面：模块编排 + crate 根重导出（不持有任何定义）
│   ├── core.rs              CommandId / CommandArgs / NoArgs / Command / Invocation
│   ├── registry.rs          CommandHandler / CommandRegistry / CommandBuilder
│   ├── executor.rs          CommandContext / EditTarget / CommandOutcome / CommandQueue / CommandExecutor
│   ├── keymap.rs            KeyChord / KeySequence / KeyBinding / KeyContext / Keymap / KeymapResolution
│   ├── error.rs             CommandError
│   ├── effects.rs           HostEffect 闭合枚举 + EffectQueue
│   ├── keymap_format.rs     chord → 平台快捷键文案投影
│   └── commands/            命令目录（catalog）
│       ├── mod.rs           总安装入口 + 对外重导出
│       ├── args.rs          catalog 共享参数解析 helper
│       ├── features/        按产品 feature 组织的命令
│       │   ├── editor.rs
│       │   ├── file_tree.rs
│       │   ├── terminal.rs
│       │   ├── settings.rs
│       │   └── ...
│       └── system/          非 feature 的 shell / 平台命令
│           ├── dismiss.rs
│           └── window.rs
└── tests/command_contract.rs
```

`core / registry / executor / keymap / error` 都是私有模块（`mod`）；类型在 `lib.rs` 经 `pub use` 在 crate 根重导出 —— 对外只有 `zom_command::CommandId` 一条路径，不暴露内部模块名。`lib.rs` 自身只做模块编排，不持有任何定义。

### 2.1 谁可以依赖谁

- `zom-command` → 依赖 `zom-engine / zom-workspace`（这是它要编辑 / 调度的资源）。
- `zom-command` → **不依赖** `zom-desktop / gpui`。任何反向依赖都是设计错误。
- 宿主（`zom-desktop` 等）→ 装载 `zom-command`，注册 catalog，翻译 `HostEffect`。

### 2.2 feature 命令模块的边界

命令按产品 feature 组织，快捷键按上下文解析。`commands/features/` 下每个 feature 一个子模块，**同处**声明该 feature 的全部命令资产 —— id 常量、typed args、typed builders、handler、默认键位，以及 feature 专属的键位上下文类型。

「feature 多大」由一条硬规则卡死：

> **一个 feature 模块里的焦点态快捷键，应当落在同一个 `KeyContext` 里。** 一旦想在一个模块里同时放 `text_edit` 与 `file_tree` 的焦点态绑定，这个模块就太大了 —— 拆。

`KeyContext` 是运行时键盘上下文（`Global` / `TextEdit` / `FileTree`，将来更多），由当前焦点面决定；`Keymap::resolve` 按上下文优先级解析按键。推论：

- **判据**：有独立键盘焦点的交互面（编辑器、文件树，将来的命令面板 / 终端）就是一个 feature。用户会说「我现在在 X 里操作」，X 即一个 feature。
- **同一物理键、不同领域不是冲突**。方向键对编辑器和文件树都有效但命令不同：`editor` 模块绑 `up → editor.move_selection`（`text_edit` 上下文），`file_tree` 模块绑 `up → file_tree.move_selection`（`file_tree` 上下文）。同 chord、两条绑定、零冲突 —— 因为上下文不相交。模块拆分跟着上下文走。
- `Global` 是「没有专属焦点面」的兜底上下文。feature 入口命令也归对应 feature，例如 `panel.toggle.file_tree` 放在 `features/file_tree.rs`，而不是集中到 `panels.rs`。窗口控制、浮面关闭这类非 feature 命令放在 `commands/system/`。

两条不变量：

1. **模块名 == 用户心智里的 feature 名词**。命令归哪个模块，看它在**用户心智**里属于哪个对象 —— 与 handler 的依赖无关。例如 `panel.toggle.file_tree` 的 id 前缀是 panel，但它属于文件树 feature，所以放在 `file_tree.rs`。
2. **feature 专属的上下文负载类型与模块同处**。`editor::TextEditKeyContext`、`file_tree::FileTreeKeyContext` 跟各自模块走。`KeyContext` 枚举本身留在 `keymap` 模块当「所有键盘上下文的总登记处」，每加一个焦点面给它 +1 个 arm。

文件过大是另一回事，**不靠拆领域解决**：领域内开子目录分文件（`commands/editor/{mod,movement,editing,ime}.rs`），领域仍是一个（一个上下文、一个 id 前缀、一个 `install`）。

### 2.3 handler 落在哪个 crate（与领域归属正交）

§2.2 决定命令归哪个**领域模块**；handler 落在哪个 **crate** 是另一根独立的轴，按"handler 需要什么"判断：

| handler 接触的资源 | handler 落点 |
|---|---|
| 只用 `Workspace / ViewSet / CommandQueue` | 本 crate，handler 直接操作 `CommandContext` |
| 需要 GPUI / shell 布局 / 平台 API | 本 crate，但 handler emit `HostEffect`，宿主翻译 |
| 需要宿主服务（如 LSP client） | 由 `zom-desktop` 组合根接线，走相同 catalog 模式 |

两根轴别混：**领域归属看用户心智，crate 落点看依赖**。`editor.save` 的 handler 只碰 `Workspace`（故可落本 crate、可无头测试），但它属于 `editor` 领域 —— 这两件事互不决定。

## 3. 数据模型

### 3.1 `CommandId` + `CommandArgs`

`CommandId` 是 `&'static str` 包装的稳定命令名，形如 `"editor.insert_text"`。

`CommandArgs` 是 `BTreeMap<String, String>` 的不透明键值袋。**字段名只在命令模块出现一次** —— 通过 typed args 结构体的 `From / TryFrom` 双向转换收拢：

```rust
pub struct InsertTextArgs { pub text: String }

impl From<InsertTextArgs> for CommandArgs { ... }
impl TryFrom<CommandArgs> for InsertTextArgs { ... }
```

命令调用方走 typed builder，不手拼字符串：

```rust
let invocation = editor::insert_text("hi");   // -> (CommandId, CommandArgs)
host_intent(HostIntent::Command(invocation), window, cx);
```

### 3.2 `Invocation`

> 类型定义参见 [`zom-command/src/core.rs`](../../zom-command/src/core.rs)。

"未提交的派发请求"。所有 typed builders 返回此类型，调用方一行 `app.dispatch(...)` 派发。

### 3.3 `CommandContext`

> 类型定义参见 [`zom-command/src/executor.rs`](../../zom-command/src/executor.rs)。

四件套：

- `workspace / views`：handler 直接读写编辑器状态。
- `queue`：handler 想触发子命令时 push，执行器排空（不重入）；宏直接记录同一条命令队列。
- `effects`：handler 给宿主提交"我做不了但你能做"的请求。详见 `HostEffect`。

### 3.4 `HostEffect`（闭合枚举）

> 类型定义参见 [`zom-command/src/effects.rs`](../../zom-command/src/effects.rs)。

**为什么闭合枚举**：

- 集中性 = `HostEffect` 一处枚举出"命令系统会找宿主做哪些事"。
- 类型安全 = 宿主的 `apply_host_effect` 是 match 表达式，漏写新变体就编译错误。
- 跨宿主一致 = 未来 web / cli / tui 等宿主必须实现同一组 effect 才能跑命令系统。

**代价**：新增宿主能力 = 修改 `effects.rs` + 宿主补 match 分支。这是集中性的必然代价，且代价可控（一次改两处，编译器引导）。

注意：`HostEffect` 是**命令执行后的宿主副作用**，不是 UI 输入事件入口。UI 输入入口在 desktop 侧是 `HostIntent::{Command, KeyChord, Ime, Interaction}`；连续设备输入在 `Interaction` 下细分为 `PointerIntent` 等领域意图。

### 3.5 `Keymap`

`Keymap` 是 `Vec<KeyBinding>` + 前缀 trie。承担三件事：

- 解析按键序列前缀 → `KeymapResolution::{Matched, Pending, NoMatch}`。
- 反查 `CommandId → KeySequence`（[`shortcut_for`]）。
- 反查 + 平台投影 → 给 UI 一行字符串（[`format_shortcut_for`]）。

UI 不维护"命令 → 快捷键"映射；统一从这里查。

### 3.6 `keymap_format`

把 `KeyChord` 字符串（`"mod shift z"`）投影成平台快捷键文案：

- macOS：`⇧ ⌘ Z`（HIG 顺序 `⌃⌥⇧⌘`，符号之间留空）
- Win / Linux：`Ctrl+Shift+Z`

平台差异封在两张数据表里（`MODIFIERS` / `SPECIAL_KEYS`），改文案只动这一个模块。

## 4. 注册：Catalog 模式

每个域一个子模块（catalog），**同处**声明四件事：

1. **`pub const ID_*`**：命令 id 常量（单一真理源，所有调用点引用）。
2. **typed args + 双向转换**：`From<Typed> for CommandArgs` + `TryFrom<CommandArgs>`。
3. **typed builders**：`pub fn xxx(...) -> Invocation`。
4. **`pub fn install(registry, keymap)`**：一口气注册 handler + 绑定默认键位。

### 4.1 install 链式 API

`CommandRegistry::install(...).key(...)` 是所有 catalog 的共用样板。**任何 catalog 都不该再自己实现"构造 CommandId → register → 构造 KeyBinding → bind"**。

```rust
let text_edit = KeyBindingContext::text_edit();

registry.install(keymap, UNDO, "撤销", Box::new(run_undo))
    .key_in("mod z", text_edit);

registry.install(keymap, MOVE_SELECTION, "移动选区", Box::new(run_move_selection))
    .key_with_in("left",  move_args(Previous, Grapheme, false), text_edit)
    .key_with_in("right", move_args(Next,     Grapheme, false), text_edit)
    .key_with_in("shift left",  move_args(Previous, Grapheme, true), text_edit)
    .key_with_in("shift right", move_args(Next,     Grapheme, true), text_edit);
```

特性：

- `key(chord)`：无参绑定，`Global` 上下文。
- `key_with(chord, args)`：带预设 args，`Global` 上下文（多变体共用同一命令，例如 `move_selection`）。
- `key_in(chord, context)`：无参绑定，指定 `KeyBindingContext`。
- `key_with_in(chord, args, context)`：带 args 且指定上下文 —— 编辑器 / 文件树等领域命令都走它。
- 错误处理：id / chord 都是源代码常量，错就 panic 让启动崩。**API 不返回 `Result`**，避免调用侧到处 `.expect(...)`。
- 冲突判定按"上下文重叠"而非"上下文相等"：同一序列在互不重叠的上下文里复用不算冲突（详见 §6）。

### 4.2 命令面变体策略

不要为每个变体注册一条命令（之前的 `editor.move_left / move_right / extend_left / ...` 8 条壳子）。**统一一条命令 + 多个 key_with**：

| 不要做 | 要做 |
|---|---|
| `editor.move_left` | `editor.move_selection { direction: previous, unit: grapheme, extend: false }` |
| `panel.toggle.file_tree` 写 7 条单独 register | `PANELS` 表 + 通用 handler |

## 5. 派发：执行流水线

### 5.1 执行器排空队列

```rust
let mut effects = EffectQueue::new();
let mut context = CommandContext {
    workspace: &mut self.workspace,
    views:     &mut self.views,
    queue:     &mut self.queue,
    effects:   &mut effects,
};
self.queue.dispatch(id, args);
executor.run(&registry, &mut context)?;   // 排空 queue，handlers 可入队子命令
```

特点：

- handler 入队子命令，执行器排空 —— **不重入**（`&mut` 借用会打架）。
- 执行器**不管历史**。`editor.undo` 只是一条命令，其 handler 调 `buffer.undo()`；undo 由 `zom-engine` 的事务系统记录。

### 5.2 宿主翻译 effects

```rust
for effect in effects.drain() {
    self.apply_host_effect(effect, &mut window_actions);
}

fn apply_host_effect(&mut self, effect: HostEffect, ...) {
    match effect {
        HostEffect::Quit            => ...,
        HostEffect::Minimize        => ...,
        HostEffect::ToggleMaximize  => ...,
        HostEffect::TogglePanel(panel) => self.toggle_panel(panel),
        HostEffect::ShowSettings    => ...,
        HostEffect::FileTreeMoveSelection(delta) => ...,
    }
}
```

**约定**：每次派发用一份新的 `EffectQueue`，副作用不跨派发泄漏。窗口动作返回给上层（`ShellView` 才能调 GPUI），Dock 类直接应用。

### 5.3 desktop 输入意图到命令

```rust
pub enum HostIntent {
    Command(Invocation),
    KeyChord(String),
    Ime(ImeIntent),
}
```

desktop shell 给组件的不是 registry 或 `Invocation`，而是窄口：

```rust
CommandBinding     // Glyph 的命令完整表达：id + lookup + request
CommandRequest     // 非 Glyph 组件的命令闭包：内部发 HostIntent::Command
KeyRequest         // on_key_down：内部发 HostIntent::KeyChord，返回 consumed
HostIntentRequest  // shell / editor 共享的离散出口
```

`zom-command` 不知道 `HostIntent`；它只提供 command / keymap 能力。desktop 的 `HostIntentRequest` 负责把 `Command`、`KeyChord`、`Ime` 统一翻译到命令执行器，并解释返回的 `HostEffect`。

### 5.4 按键派发

```rust
// shell on_key_down
if key_request(normalized_chord(&event.keystroke), window, cx) {
    cx.stop_propagation();   // 仅在 keymap 消费时拦截
}
```

App 侧：

```rust
if self.is_composing() {
    return consumed=false;   // 组合态完全让位给系统 IME
}

let contexts = self.key_contexts(); // 由当前 AppFocus 派生
match self.command.resolve_key(chord, &contexts) {
    Matched { command, args } => dispatch_command((command, args)); consumed=true
    Pending                   => consumed=true
    NoMatch                   => consumed=false
}
```

**关键陷阱**：在 macOS GPUI 中，无条件 `stop_propagation` 会让 `inputContext handleEvent:` 永远拿不到按键，系统输入法直接哑掉。**只有 keymap 真正消费时才能拦截**。

### 5.5 IME 与命令的分工

| 阶段 | 路径 |
|---|---|
| **confirm / commit / update** | `HostIntent::Ime` → `editor.ime_confirm / editor.ime_commit / editor.ime_update` |
| **IME 查询** | 系统输入法协议查询：`text_for_range`、`selected_range`、`bounds_for_range` 等，不进命令队列 |
| **普通按键** | 组合态下 `dispatch_key` 直接 `consumed=false`，交给系统 IME |

IME 写入最终仍落到编辑命令，因此能复用 undo / redo、selection 同步和搜索同步等命令尾部机制；查询类回调不是命令。

## 6. 键位约定

### 6.1 逻辑修饰键

第一版提供的逻辑修饰键如下：

| 逻辑键 | macOS | Win / Linux | 用途 |
|---|---|---|---|
| `mod` | ⌘ | Ctrl | 标准应用快捷键（保存、撤销、全选…） |
| `ctrl` | 物理 Ctrl（Emacs 语义） | Ctrl | 用户自定义可用；默认表尽量不用（mac 上与 `mod` 不同键，可移植性 OK） |
| `alt` | ⌥ Option | Alt | 按词 / 段编辑（mac 习惯，跨平台一致） |
| `shift` | Shift | Shift | 扩展选区 / 反向变体 |
| `fn` | Fn | Fn | 仅用于事件归一化映射 F-row 等键，用户级 keymap 通常不直接拼写 |

平台不对称需求走 `[keymap.darwin]` / `[keymap.linux]` 覆盖段。出现无法识别的修饰键由 keymap 解析阶段报错。

### 6.2 chord 字符串形态

底层 `KeyChord` 始终是逻辑字符串：`"mod shift z"` / `"shift alt left"` / `"backspace"`。GPUI 事件归一化 → chord 字符串由 `zom-desktop` 的 `normalized_chord` 完成。

UI 显示时调 [`Keymap::format_shortcut_for`]，自动投影到当前平台符号。

### 6.3 命令面板 / 菜单 / Glyph 怎么显示快捷键

Glyph 通过 `CommandBinding`（`id + title_lookup + shortcut_lookup + request`）绑定命令。渲染时自动反查 keymap 填 tooltip 与 hint，点击时派发 request。UI 不维护"命令 → 快捷键"映射，统一从 keymap 反查。

### 6.4 键盘上下文与冲突判定

快捷键按上下文解析。两套类型，分属解析的两端：

- **`KeyContext`** —— 运行时上下文，由当前焦点面决定：`Global` / `TextEdit { accepts_newline, composing }` / `FileTree { mode }`。派发方按优先级传一个 `&[KeyContext]`，`Keymap::resolve` 逐个上下文找匹配，第一个命中的上下文胜出。
- **`KeyBindingContext`** —— 绑定侧上下文，声明一条绑定**适用于什么条件**：`Global` / `TextEdit { requires_newline, composition }` / `FileTree { mode }`。

领域专属的负载类型（`TextEditKeyContext` 等）与命令模块同处（见 §2.2 不变量 2）；`KeyContext` 枚举本身留在 `keymap` 模块统一登记。

**冲突 = 上下文重叠，不是上下文相等。** `Keymap::try_bind` 拒绝的是「同一序列、且两条绑定会被某个运行时 `KeyContext` 同时命中」。所以：

- 同一 chord 在**不相交**的上下文里复用不是冲突 —— `enter` 可同时绑给文件树导航（`FileTree`）和编辑器换行（`TextEdit`）。
- `composition` 是用来**切分**上下文空间的：`Active` 与 `Inactive` 互斥，含 `Any` 的组合则重叠。一旦同一 chord 绑了重叠的两条（如 `Any` + `Active`），就是没切干净 —— `try_bind` 在启动期 panic 报错，而非让 `resolve` 靠注册顺序静默裁决。
- `requires_newline` 只是单向过滤、不切分空间，故不参与重叠判定。

## 7. 怎样加一条新命令

### 7.1 handler 只用 workspace / view / engine

放进 `zom-command::commands::editor`（或新建一个 catalog 子模块）。

1. 在 `editor.rs` 顶部加 `pub const FOO: &str = "editor.foo";`
2. 写 typed args 结构体（如果有参数），实现双向 `From / TryFrom<CommandArgs>`。
3. 写 typed builder：`pub fn foo(...) -> Invocation`。
4. 写 handler：`fn run_foo(ctx, args) -> Result<CommandOutcome, CommandError>`。
5. 在 `install` 里加一行：

```rust
registry.install(keymap, FOO, "标题", Box::new(run_foo))
    .key("mod shift ?");
```

### 7.2 handler 需要宿主资源

例如"打开设置面板"。

1. 在 `effects.rs` 的 `HostEffect` 加一个变体：

```rust
pub enum HostEffect {
    // ...
    ShowSettings,   // 新增
}
```

2. 在 `zom-command::commands::*`（按域归位，例如 `settings.rs`）写一个 emit handler：

```rust
pub const OPEN: &str = "settings.open";

pub fn install(reg, km) {
    reg.install(km, OPEN, "打开设置",
        Box::new(|ctx, args| {
            NoArgs::try_from(args)?;
            ctx.effects.push(HostEffect::ShowSettings);
            Ok(CommandOutcome::default())
        }))
        .key("mod ,");
}
```

3. 在宿主侧 `App::apply_host_effect` match 加一个分支。**漏写编译错误，闭合枚举的好处**。

4. App::new 里调用 `settings::install(&mut registry, &mut keymap);`。

### 7.3 多变体共用一条命令

不要再注册 `editor.move_left / right / word_left / word_right / extend_*` 这些壳。统一绑到 `editor.move_selection` + `key_with(chord, args)`：

```rust
registry.install(km, MOVE_SELECTION, "移动选区", Box::new(run_move_selection))
    .key_with("left",  move_args(Previous, Grapheme, false))
    .key_with("alt left", move_args(Previous, Word, false))
    .key_with("shift left", move_args(Previous, Grapheme, true))
    // ...
```

## 9. 反例：不要这样做

- ❌ 在 UI 组件里硬编码 `"editor.undo"` 字符串。由 shell bridge 引用 catalog 的 `pub const` 构造 `CommandBinding`，组件通过 Glyph 渲染时自动反查 keymap。
- ❌ 在 catalog 里自己实现"注册 + 绑键"样板。用 `registry.install(...).key(...)`。
- ❌ 把 GPUI Window / shell DockState 塞进 `CommandContext`。新增 `HostEffect` 变体。
- ❌ 给同一动作的不同变体注册多条命令。一条命令 + `key_with` 多个 args。
- ❌ 在 `on_key_down` 里无条件 `stop_propagation`。会让 IME 哑掉，只在 keymap 真消费时拦截。
- ❌ 把 drag / scroll / resize 这类连续输入塞进 command catalog。走 desktop 的 `HostIntent::Interaction` / `PointerIntent` 等交互管线。
- ❌ 在调用点拼接 `CommandArgs::new().with("field", val)`。用 typed builder 或 typed args + `From`。
- ❌ 在 UI 层手拼平台符号（`⌘`、`Ctrl+`）。用 `keymap_format::format_chord` / `Keymap::format_shortcut_for`。
