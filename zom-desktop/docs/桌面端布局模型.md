# 桌面布局模型

> 本文定义 `zom-desktop` 第一版稳定布局模型。布局模型描述区域、面板、悬浮层与提示层的语义边界，不规定具体视觉样式与实现机制。
>
> 具体视觉系统、组件分层与实现规则在 `桌面端设计手册.md`。两文档分工：布局模型说"是什么 / 在哪里 / 长什么语义"；设计手册说"怎么实现 / 怎么组装 / 怎么演化"。

## 设计目标

`zom-desktop` 的桌面界面采用稳定外壳 + 可停靠面板 + 主编辑区 + 临时浮层的分层模型。临时浮层分为两类：可交互的 **浮面（Surface）**，以及轻量提示用的 **气泡（Bubble）**。

核心目标：

- `TopBar` / `BottomBar` 作为 IDE 外壳的一部分，保持极高稳定性。
- `TopBar` / `BottomBar` 采用同一套 shell bar 视觉规则，上下镜像，保持对称。
- `LeftDock` / `RightDock` / `BottomDock` 只负责承载面板，不绑定具体面板实现。
- `EditorGrid` 独立建模，保留编辑器 tab、split、active editor 等专属规则。
- `SurfaceLayer` / `BubbleLayer` 是运行时临时层，不进入持久布局；二者同属悬浮层，但语义、生命周期与复用方式不同。
- 底部停靠区只位于中间列下方，不侵入左右停靠区下方。

## 视觉哲学

`zom-desktop` 采用灰度梯度作为主体视觉系统。界面层次主要依赖灰阶明度、边框与间距表达，彩色只用于状态、风险和行动反馈。

基础规则：

- 布局层次靠灰度，不靠彩色。
- 交互状态靠灰度微调，不靠大面积高饱和色。
- 语义状态才允许使用彩色，例如错误、警告、成功、运行中。
- 颜色、间距、圆角、字号必须优先来自 theme token。
- 不按组件命名颜色，例如 `topbar_bg`；使用语义或梯度 token，例如 `gray.g10`、`accent.danger`。

灰度梯度语义：

```text
gray.g00   最深浮层背景
gray.g05   主工作区背景
gray.g10   shell bar / chrome 背景
gray.g20   控件背景
gray.g40   边框 / 分隔线
gray.g60   次要文字
gray.g75   控件文字
gray.g90   主文字
gray.g95   强调文字
```

语义色只做点状使用：

```text
accent.danger   危险 / 退出 / 错误
accent.warning  警告 / 注意
accent.success  成功 / 可用 / 放大
accent.info     信息 / 提示
```

具体取值与三轴正交命名规则在 `桌面端设计手册.md` 第四章。

## 总体结构

```text
Window
├─ WorkbenchFrame
│  ├─ TopBar
│  ├─ Body
│  │  ├─ LeftDock
│  │  ├─ CenterColumn
│  │  │  ├─ EditorGrid
│  │  │  └─ BottomDock
│  │  └─ RightDock
│  └─ BottomBar
├─ SurfaceLayer
└─ BubbleLayer
```

视觉结构：

```text
┌────────────────────────────────────┐
│ TopBar                             │
├───────┬────────────────────┬───────┤
│ Left  │    EditorGrid      │ Right │
│ Dock  ├────────────────────┤ Dock  │
│       │    BottomDock      │       │
├───────┴────────────────────┴───────┤
│ BottomBar                          │
└────────────────────────────────────┘
```

`BottomDock` 指 `CenterColumn` 内的底部停靠区，不是窗口级底栏。窗口级底栏统一称为 `BottomBar`。

## 区域语义

### Shell Bar 对称性

`TopBar` 与 `BottomBar` 是同一种窗口外壳区域的上下两次使用。二者必须保持一致的高度、内边距、背景、字号、基础文字色与横向三槽布局。

它们只允许在以下方面不同：

- 所处位置：`TopBar` 在窗口顶部，`BottomBar` 在窗口底部。
- 分隔线方向：`TopBar` 的分隔线在下侧，`BottomBar` 的分隔线在上侧。
- 承载内容：`TopBar` 偏标题栏、命令入口与窗口控制；`BottomBar` 偏模式、任务、状态与摘要。

除非明确修改 shell bar 共同规则，否则不得只单独调整其中一条栏的厚度、颜色、字号或密度。

### Glyph

`Glyph` 是 shell 内复用的基础视觉标记组件。它可以承载文字、图标、图标加文字或纯视觉内容，并统一提供鼠标悬浮提示。

`Glyph` 不表达可点击语义，不持有命令系统，也不持有 Surface 锚点。它只是视觉原语；快捷键提示由调用方传入，若某个功能入口需要召唤 Surface，则由该功能入口自己包装 invoker。

基础规则：

- 每个 `Glyph` 必须有稳定 `id`。
- 每个 `Glyph` 必须有 tooltip 标题；需要展示快捷键或状态补充时，由调用方传入可选 hint。
- 组件外框不写死高度，高度由内容、字号与图标尺寸自然撑开。
- `Glyph` 不附带内外边距，所见即所得；标记之间的距离与栏内留白都由父级布局显式决定。
- 图标加文字的 `Glyph` 必须横向排列，先图标后文字，不额外增加背景色或胶囊外观；内部图标与文字的距离应小于不同 item 之间的距离，文字容器应与图标同高并通过布局居中，不使用固定像素偏移做视觉校正。
- 纯视觉标记可以规定内部图形尺寸，例如红绿灯圆点直径，但外层仍由内容撑开。
- tooltip 只用于短提示，由标题和快捷键两部分组成，例如「退出应用」「Cmd-Q」。
- tooltip 不承载确认、表单或复杂交互；需要交互时升级为 `SurfaceLayer`。
- tooltip 的实际提示框与鼠标点之间必须保留间距，避免遮挡触发它的 glyph。
- 文字标记、图标标记、图标加文字标记与窗口控制标记共享同一套 tooltip 行为。

### TopBar

`TopBar` 是窗口级顶部外壳，稳定存在，不作为普通 `Panel` 容器。

它可以承载工作区入口、命令入口、全局导航、窗口级操作、运行中任务摘要等 shell 级内容。具体内容可以演进，但区域本身不参与普通面板停靠、迁移或关闭。

`TopBar` 同时承担 `zom` 的统一自绘标题栏职责。窗口控制标记采用跨平台一致的 macOS 红绿灯设计，由 `zom-desktop` 自己绘制，不依赖 OS 原生标题栏承载信息架构。

`zom-desktop` 默认隐藏 OS 原生标题栏内容，并由 `TopBar` 承担窗口外壳视觉。平台只提供窗口能力，例如移动、最小化、放大、退出，不提供可见标题栏 UI。

第一版窗口控制标记：

```text
Close     红色，退出应用
Minimize  黄色，最小化当前窗口
Zoom      绿色，放大 / 还原当前窗口
```

窗口拖动、双击放大等平台行为属于 `shell` 适配层职责，不进入 `app` 布局模型。

### BottomBar

`BottomBar` 是窗口级底部外壳，稳定存在，不作为普通 `Panel` 容器。

它不预设为状态栏。它可以承载状态，也可以承载模式、任务入口、同步进度、AI 运行标记、诊断摘要、语言服务状态、账户或环境信息等全局内容。

第一版 `BottomBar` 使用图标项作为主要内容，从左到右依次为：

```text
文件树
版本管理
大纲
项目搜索
诊断 0
终端
调试
快捷键
```

这些图标项统一使用 `Glyph`，图标来自 `zom-desktop/assets/icons/panels/` 与 `zom-desktop/assets/icons/status/`，并通过 tooltip 显示名称。诊断项第一版先使用 `diagnostics_warn` 图标和占位数字，后续再接入真实 LSP 诊断数量。

`BottomBar` 中的面板切换图标是 `panel.toggle.<id>` 命令的视图（详见 `桌面端设计手册.md` 20.8）——`BottomBar` 本身不知道 panel 是什么，只派发命令。

### LeftDock 和 RightDock

`LeftDock` 与 `RightDock` 是左右停靠区域，贯穿 `Body` 高度。

它们适合承载工作区级导航与上下文面板，例如文件树、搜索、符号大纲、AI 会话、当前文件上下文等。区域负责显示、隐藏、折叠、尺寸和面板激活状态，不关心面板内部实现。

### BottomDock

`BottomDock` 是中间列底部停靠区域，只位于 `EditorGrid` 下方，与左右停靠区不重叠。

它适合承载当前编辑任务相关的输出与反馈，例如终端、问题列表、输出日志、测试结果、任务日志等。它的水平边界与 `EditorGrid` 对齐。

### EditorGrid

`EditorGrid` 是主编辑区，不作为普通面板处理。

它拥有独立的编辑器规则，包括 tab、split、active editor、dirty state、preview tab 等。这样可以避免普通面板模型过早污染编辑器核心行为。

`CenterColumn` 是 `EditorGrid` + `BottomDock` 的垂直容器；`EditorGrid` 占据上半部，`BottomDock` 占据下半部。

## 面板模型

面板通过停靠区域承载。面板自身描述能力与身份，位置由布局状态决定。

```rust
struct PanelDescriptor {
    id: PanelId,
    title: String,
    icon: Option<IconId>,
    kind: PanelKind,
    capabilities: PanelCapabilities,
}
```

```rust
struct PanelPlacement {
    panel_id: PanelId,
    area: DockAreaId,
    group: Option<PanelGroupId>,
    order: usize,
    active: bool,
}
```

第一版停靠区域采用单栈模型：

```rust
struct PanelStack {
    panels: Vec<PanelId>,
    active: Option<PanelId>,
}
```

需要支持区域内拆分时，再升级为分组树：

```rust
enum PanelGroup {
    Stack(PanelStack),
    Split {
        axis: SplitAxis,
        children: Vec<PanelGroup>,
    },
}
```

停靠区域标识：

```rust
enum DockAreaId {
    Left,
    Right,
    Bottom,
}
```

其中 `Bottom` 表示 `CenterColumn` 内的 `BottomDock`，不是窗口级 `BottomBar`。

desktop 端的具体实现（PanelHost、L3/L4 落位、命令注册）见 `桌面端设计手册.md` 第二十章。

## 编辑区模型

编辑区单独建模，采用 group + split tree：

```rust
struct EditorGrid {
    root: EditorNode,
    active_group: EditorGroupId,
}
```

```rust
enum EditorNode {
    Group(EditorGroup),
    Split {
        axis: SplitAxis,
        children: Vec<EditorSplitChild>,
    },
}
```

```rust
struct EditorGroup {
    id: EditorGroupId,
    tabs: Vec<EditorTab>,
    active: Option<EditorTabId>,
}
```

该模型支持单编辑器、左右拆分、上下拆分、多 tab group，以及未来的 tab 拖动迁移。

每个 `EditorTab` 对应 `zom-view::View` 的一个 `ViewId`；`EditorView`（叶子组件）的实现规则见 `桌面端设计手册.md` 第十九章。

## 浮面模型

`SurfaceLayer` 承载临时但可交互的悬浮面板，统一称为 **Surface / 浮面**。浮面不进入持久布局。

Surface 的共性只在外壳：召唤入口、定位、窗口边界吸附、层级、关闭策略与焦点归还。具体内容、功能、内部状态和焦点目标都由打开它的调用方决定，SurfaceLayer 不理解也不枚举业务内容。

典型浮面：

```text
CommandPalette / QuickPicker / ContextMenu / InlinePopover / InspectorPopover
```

浮面必须有明确召唤入口。默认情况下，浮面锚到召唤它的那个具体元素，而不是锚到 TopBar / BottomBar / Dock 这类容器：

```rust
enum SurfaceAnchor {
    Invoker(ElementId),
}
```

`SurfaceLayer` 不应演化成任意窗口系统。第一版只保留明确形态：命令面板、快速选择器、上下文菜单、内联弹出层、检查器弹出层。

desktop 端的具体实现（SurfaceManager、SurfaceShell、invoker 采集与定位、生命周期）见 `桌面端设计手册.md` 第二十一章。

## 气泡提示模型

`BubbleLayer` 承载轻量提示，不进入持久布局，也不承担复杂交互。

典型类型：

```rust
enum BubbleKind {
    Tooltip,
    DiagnosticHover,
    ParameterHint,
    Toast,
}
```

基础规则：

- `Tooltip` 只解释标记、图标和其他短语义对象。
- `DiagnosticHover` 跟随编辑器位置。
- `ParameterHint` 跟随光标。
- `Toast` 固定在窗口角落。

当气泡需要承载确认、表单、复杂 AI 回复或可持续交互时，应升级为 `SurfaceLayer` 中的浮面。

desktop 端的具体实现（BubbleManager、BubbleShell）见 `桌面端设计手册.md` 第二十一章。

## 持久化边界

第一版布局持久化只覆盖稳定工作区结构：

- `TopBar` / `BottomBar` 的 shell 级配置。
- `LeftDock` / `RightDock` / `BottomDock` 的显隐、折叠、尺寸、面板顺序与激活项。
- `EditorGrid` 的 split tree、tab group 与 active group。
- 每个 tab 的 buffer 路径、滚动位置、光标位置（不含 buffer 内容）。

不持久化：

- 当前打开的临时 `SurfaceInstance`。
- 当前显示的 tooltip、hover、parameter hint、toast。
- 鼠标位置、临时 invoker rect 等运行时几何信息。
- dirty buffer 的内容（走 crash-recovery，见 `桌面端设计手册.md` 17.6）。

具体存储方式（全局层 vs 窗口层 / TOML 格式 / debounced 写 / schema 兼容）见 `桌面端设计手册.md` 第二十四章。

## 第一版边界

第一版明确支持：

- 固定外壳：`TopBar`、`Body`、`BottomBar`。
- 三个停靠区：`LeftDock`、`RightDock`、`BottomDock`。
- 底部停靠区只属于中间列。
- `EditorGrid` 支持 split tree。
- 浮面层与气泡层作为运行时状态。

第一版暂不支持：

- 任意拖拽窗口系统。
- 面板浮动成独立窗口。
- 跨显示器布局。
- 完全自定义 workspace layout DSL。
- `BottomDock` 贯穿全窗口宽度。
- 面板跨 dock 拖动。
- 同一 dock 内多 panel 同时显示（PanelGroup tree 形态推迟到第二版）。
