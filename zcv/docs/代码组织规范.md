# 代码组织规范

> 三种组件类型各自采用统一的代码顺序，让人一打开文件就能按开发流程找到对应部分。

---

## 一、Entity 组件代码顺序

对应八步流程的顺序，自上而下：

```
// ═══ 1. actions!（第 1 步）══════════════════════════════
// 定义该组件所有的 action。
actions!(my_component, [ActionA, ActionB]);

// ═══ 2. key_bindings ═══════════════════════════════════
// 定义快捷键 → action 的映射。
// 注册由父级 AppView 统一收集后一次性 cx.bind_keys()。
pub(crate) fn key_bindings() -> Vec<gpui::KeyBinding> { ... }

// ═══ 3. 自由函数 handler（第 4 步，不需要 &mut self 的场景）══
// 通过 cx.try_global 等访问共享状态，不持有组件引用。
pub(crate) fn handle_action_a(...) { ... }
pub(crate) fn handle_action_b(...) { ... }
// handler 共用的私有辅助函数跟在它们后面
fn toggle(...) { ... }

// ═══ 4. Struct + constructor（第 2 步）══════════════════
// 组件定义：状态字段、焦点句柄、子 Entity。
pub(crate) struct MyComponent { ... }
impl MyComponent {
    pub(crate) fn new(cx: &mut Context<Self>) -> Self { ... }
    // 需要 &mut self 的 handler 方法放在这里
    fn handle_action_c(&mut self, ...) { ... }
}

// ═══ 5. Render 实现（第 3 步）═══════════════════════════
impl Render for MyComponent { ... }

// ═══ 6. 私有渲染辅助函数（第 3 步的产出）════════════════
// 被 Render 调用的构建函数。
fn leading_slots() -> Vec<AnyElement> { ... }
fn cluster(items) -> Div { ... }
```

### 规则
- 自由函数 handler 放在 struct 之前（它们不依赖 struct）
- `cx.listener()` 方式的 handler 放在 `impl MyComponent` 块中
- 私有渲染辅助函数统一放在 Render 之后
- `#[cfg(test)]` 模块放在文件末尾

## 二、函数式组件代码顺序

```
// ═══ 1. 模块文档、use ══════════════════════════════════
// ...

// ═══ 2. actions!（可选，有键盘交互时）══════════════════
actions!(my_module, [ActionA]);

// ═══ 3. key_bindings（可选，有快捷键时）════════════════
pub(crate) fn key_bindings() -> Vec<gpui::KeyBinding> { ... }

// ═══ 4. 自由函数 handler（可选）════════════════════════
pub(crate) fn handle_action_a(...) { ... }
pub(crate) fn handle_action_b(...) { ... }

// ═══ 5. 公开渲染函数 ═══════════════════════════════════
// 组件的主渲染入口。
pub(crate) fn render(...) -> Div { ... }

// ═══ 6. 私有渲染辅助函数 ══════════════════════════════
// 被公开渲染函数调用的子构建函数。
fn helper_a(...) -> Div { ... }
fn helper_b(...) -> Div { ... }

// ═══ 7. 内部类型定义（可选）════════════════════════════
// 仅在本模块使用的枚举/struct。
enum InternalEnum { ... }
impl InternalEnum { ... }
```

### 规则
- 公开函数在前，私有函数在后
- 内部类型定义放在文件末尾
- 无 actions/key_bindings/handler 时跳过对应章节，不空占位置

## 三、Builder 组件代码顺序

```
// ═══ 1. 模块文档、use ══════════════════════════════════
// ...

// ═══ 2. 内容变体枚举 ═══════════════════════════════════
enum ContentEnum { ... }

// ═══ 3. Struct 定义 ════════════════════════════════════
pub(crate) struct MyBuilder { ... }

// ═══ 4. impl MyBuilder（工厂 + Builder 方法）═══════════
impl MyBuilder {
    // 工厂构造函数
    pub(crate) fn variant_a(...) -> Self { ... }
    pub(crate) fn variant_b(...) -> Self { ... }
    // 私有构造函数（设默认值）
    fn new(...) -> Self { ... }
    // Builder 方法
    pub(crate) fn option_x(mut self, ...) -> Self { ... }
    pub(crate) fn option_y(mut self, ...) -> Self { ... }
}

// ═══ 5. IntoElement 实现 ═══════════════════════════════
impl IntoElement for MyBuilder { ... }

// ═══ 6. 内部 Entity（可选）═════════════════════════════
struct InternalTooltip { ... }
impl Render for InternalTooltip { ... }
```

## 四、新旧文件对照

| 文件 | 是否对齐 | 需要调整 |
|---|---|---|
| `shared/glyph.rs` | 是 | 符合 Builder 顺序 |
| `shared/tree.rs` | 是 | 符合函数式顺序 |
| `bars/frame.rs` | 否 | 内部类型（BarEdge、BarRegionAlign）应移到底部 |
| `bars/window_controls.rs` | 否 | `Pip` 枚举应移到底部的"内部类型"区 |
| `bars/top_bar.rs` | 是 | 符合 Entity 顺序 |
| `bars/bottom_bar.rs` | 否 | `dispatch!` macro 位置错误；`join_groups` 应紧随 `leading_slots`/`trailing_slots` |
| `layout/render.rs` | 是 | 符合函数式顺序 |
| `project_tree.rs` | 否 | 内部类型 `ProjectTreeRow`、`ProjectTreeState` 应移到底部 |
