# Zcv 性能与内存优化

以可复现的用户体验退化和可比较的数据为依据，找出 Zcv 的真实 CPU、I/O、等待或内存瓶颈，并做最小、正确的架构修复。性能分析本身不授权修改代码；“优化”“修复性能回归”等明确实现请求才授权在已确认范围内改动。

## 建立基准

1. 先完整读取仓库与目标目录的 `AGENTS.md`，再检查工作树、相关模块的职责、调用方、状态所有者和现有测试。保留用户已有改动。
2. 用能代表问题的固定场景定义成功条件：输入数据或项目规模、操作路径、观察指标和可接受阈值。性能至少记录端到端耗时、主线程卡顿或吞吐；内存至少记录常驻集（RSS）、峰值、活跃分配或可确认的缓存/队列大小。记录构建配置、缓存状态和测量方法，避免把不同条件直接比较。
3. 先获取修改前基线；优先使用现有测试、诊断和分析工具。没有现成基准时，只为当前回归建立最小的可重复测量，不默认引入全局遥测或长期采样基础设施。
4. 对存在波动的耗时或内存数据多次测量，报告中位数和离散范围；区分首次运行、预热后、异步任务完成后以及空闲稳定后的数据。不要依据一次偶然测量宣称优化有效。

## 定位瓶颈

- 先区分端到端等待、主线程卡顿、CPU、I/O、锁等待、分配速率、峰值内存和长期保留；测量只说明“慢或占在哪里”，还需沿调用链确认“为什么”。
- 从用户操作追踪到实际数据流和所有权。检查是否存在重复解析、复制、物化、排队、缓存、订阅或任务生命周期，尤其关注数据是否在操作结束后仍被不必要地保留。
- 对缓存、索引、后台任务和结果通道同时检查容量、失效条件、取消路径和释放时机。区分真实泄漏、过宽生命周期、峰值工作集和有意缓存，不能把暂时的异步峰值误判为泄漏。
- 涉及 Zed 已成熟的编辑器能力时，研究 `/Users/liuyuan/project/zed` 对应实现的分层、生命周期和边界条件，只移植与 Zcv 目标一致的设计。
- 先确认热路径再优化。循环、缓存、批量处理、异步化或减少分配的名称和直觉不是证据；不要在未测得的路径上做推测性微优化。

## 实施约束

1. 优先消除根因，例如重复计算、错误的数据投影、过宽的失效范围、不必要的同步工作、无界队列或错误的对象生命周期；不要为了数字好看而跳过必要工作、降低结果完整性或引入隐式降级。
2. 缓存、增量计算或后台处理必须有明确的权威数据源、失效条件、容量/生命周期和所有者。缓存是可重建的派生数据，不能成为第二份可写事实；内存优化也不能通过泄漏、静默丢结果或永久保留旧快照来换取速度。
3. 优先减少不必要的物化、复制和长期持有；只有在基线证明保留数据能改善端到端指标时才增加缓存，并同时定义上限和回收路径。不要把所有值都改成可配置项。
4. 不为单一优化点预建抽象、配置项或兼容路径。若瓶颈揭示底层抽象错误，应修正唯一正确路径，并同步更新调用方、测试和文档。
5. 不引入实时协作、远程开发或 LSP；语法相关优化继续遵循 Tree-sitter 路径。调整 `Cargo.toml` 的构建配置、依赖或全局运行策略前，先证明问题确实由该层造成。

## 验证与交付

- 以相同场景和方法比较修改前后，同时报告性能和内存指标；若一个指标改善而另一个退化，明确说明权衡，不把单项改善描述成整体优化。
- 内存验证至少覆盖操作中的峰值和任务稳定后的保留量；涉及缓存、任务或订阅时，验证取消、替换、关闭视图和重复操作后对象能够释放或回到预期规模。
- 按风险补充最小的编译、格式、Lint 和行为回归验证；不运行全量测试，除非用户明确要求。无法执行的测量或验证需说明尝试、限制和仍未确认的范围。
- 交付时说明：用户可感知的问题、性能与内存基线及优化后数据、已确认的根因、修改如何消除根因、正确性和释放路径验证，以及尚未验证的场景或风险。
