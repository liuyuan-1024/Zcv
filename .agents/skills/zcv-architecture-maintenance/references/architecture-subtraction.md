# 架构减法

架构减法用于删除已经没有必要或正在掩盖错误边界的概念，让系统回到一条明确的数据和调用路径。它不是以删行数为目标，也不是普通代码清理。

## 候选来源

优先审查已经有证据的候选：

- 无真实消费者的重导出、配置、扩展点和公共接口；
- 只转发调用或类型、没有独立职责的 wrapper 和兼容门面；
- 单一消费方专用逻辑被放在共享层形成的伪抽象；
- 同一业务事实的影子状态、缓存式权威副本、双写和同步逻辑；
- 旧实现与新实现并行存在的分支、别名、适配器和 fallback；
- 为理论上不可能的受控类型状态增加的运行时恢复；
- 从 Zed 搬入但只服务远程、协作、LSP 或尚不存在消费者的基础设施；
- 已被新边界替代，但调用方、测试或文档仍维持的旧概念。

## 删除前证明

对每个候选确认：

1. 所有定义、导出、构造点和调用方已经找到。
2. 当前行为由哪个权威实现承担。
3. 删除后保留的唯一数据源和规范调用路径是什么。
4. 它是否承担真实的依赖方向、协议、异构分发或生命周期边界。
5. 是否存在用户明确要求的外部兼容对象。

不能仅凭未使用警告或文本搜索无结果删除反射、宏、配置驱动或外部 API；先确认其发现机制。反之，不要用“可能有外部调用方”为内部错误设计保留兼容层。

## 实施顺序

1. 确定正确的职责所有者、权威数据源和规范入口。
2. 把真实调用方一次性迁移到正确路径。
3. 删除旧状态、接口、分支、适配器和同步逻辑，不保留双轨。
4. 删除由本次修改直接产生的死代码、失效测试和过时文档；行为仍有效的测试应迁移到新边界。
5. 为改变的外部可观察行为补充或更新测试。

如果删除会跨越用户指定能力域、涉及大量文件，或存在多个会显著改变架构方向的正确方案，先报告证据并请求确认。

## 验证减法是否成立

- 旧概念、旧路径和兼容分支的搜索结果应归零，除非存在明确记录的外部兼容要求。
- 编译检查证明所有真实静态调用方已经迁移。
- 相关行为测试证明用户可观察行为保持正确或按需求变化。
- 状态类修改应证明只剩一个权威数据源，不再需要双写或补偿同步。
- 格式和相关 Lint 检查通过，且没有用抑制属性隐藏问题。

最终说明删除了哪些架构概念、保留了哪条唯一路径、净减少了哪些状态或同步责任，以及仍未验证的部分。不要把文件数量或代码行数当作成功标准。
