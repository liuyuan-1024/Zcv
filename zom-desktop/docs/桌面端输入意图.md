# 桌面端输入意图

> 本规范规定 `zom-desktop` 如何把键盘、鼠标、IME、命令面板、Glyph 点击与 feature 内部按钮统一收敛为**输入意图**，再由 shell / feature runtime 翻译到命令管线或交互管线。它只规定 desktop 边界；命令 ID、命令参数、键位解析仍归 `zom-command`。代码里统一离散出口命名为 `HostIntentRequest`。

## 一、定位

输入意图是 UI 与运行时之间的窄协议：UI 层只上报"用户想做什么"，不直接决定"用哪个命令 ID、改哪个 runtime 状态、触发哪个 `HostEffect`"。

它解决三类泄漏：

- L2 / L3 组件知道 `CommandId`、`Invocation` 或 command registry。
- 鼠标 / IME / 键盘路径各自发明派发入口。
- 高频交互被过度命令化，或离散功能入口绕过命令管线。

## 二、分层原则

输入设备事件只允许在 shell 边界被解码：

```text
设备事件 / UI 事件
    ↓
输入意图
    ↓
shell / feature runtime 翻译
    ↓
命令管线 或 交互管线
```

各层职责：

| 层 | 可以做 | 不可以做 |
|---|---|---|
| L2 视觉原语 | 持有 `CommandBinding`（id + lookup + request），渲染时自动反查 keymap | import `zom_command`；拼 command id；读取 app |
| L3 业务组件 | 产出领域意图，如 `SearchIntent` | 直接 dispatch command；持有 command registry |
| L4 区域 | 组装 `CommandBinding` / intent handler | 执行业务能力；复制 app 状态 |
| shell view / feature runtime | 把意图翻译为命令或交互 handler | 让组件反向依赖命令系统 |
| app | 执行 `Invocation`，产出 `HostEffect` | 接触 GPUI、窗口、像素、焦点 handle |

## 三、三条管线

### 3.1 命令意图

离散、可命名、应出现在快捷键 / 命令面板 / undo 语义中的用户动作走命令管线。

```text
CommandBinding → Glyph.command() 绑定
    ↓
render 时自动从 title_lookup / shortcut_lookup 拉取展示文案
    ↓
点击时通过 binding.request 进入 HostIntent::Command(Invocation)
    ↓
App::dispatch_command / App::dispatch_key
    ↓
Vec<HostEffect>
    ↓
shell 解释
```

规则：

- `HostIntentRequest` 是唯一真实离散派发出口；UI 子组件不直接拿它。
- Glyph 通过 `CommandBinding` 拿到 `id + title_lookup + shortcut_lookup + request`，渲染时自己查 keymap，点击时派发 request。
- `Invocation -> CommandRequest -> HostIntent::Command` 的绑定集中在 shell bridge，例如 `shell/view/actions.rs` 与 `ShellView` 组合根。
- 键盘路径必须保留 `consumed=false` 的分支，让系统 IME 接管未被 keymap 消费的按键。

适合命令管线的例子：

- 打开设置、切换面板、关闭 tab。
- 搜索下一项、替换下一项。
- 编辑器插入、删除、undo / redo。

### 3.2 Feature 意图

当 L3 组件知道的是功能语义，而不是全局命令语义时，先产出 feature intent，再由 feature runtime 或 shell view 映射到命令 / 交互。

```text
SearchIntent::FindNext
    ↓
SearchIntentRequest
    ↓
shell view 映射到 search.find_next Invocation
    ↓
命令管线
```

规则：

- feature intent 类型放在 `shell/features/<feature>/`，由该 feature 拥有。
- intent → command id 的映射集中在 runtime / shell bridge，不散落到按钮、列表行、状态栏。
- 展示元数据通过 `CommandTitleLookup` + `ShortcutLookup` 注入，组件不维护第二套标题 / 快捷键表。`CommandBinding` 把这两个 lookup 和 request 打包，Glyph 渲染时自行反查。

适合 feature 意图的例子：

- `SearchIntent`：大小写、整词、正则、上一个、下一个、替换。
- `ProjectPickerIntent`：移除最近项目这类只在项目选择器语境成立的动作。

### 3.3 交互意图

连续、高频、通常不应进入命令目录的输入走交互管线。

```text
InteractionRequest<Event>
    ↓
shell / feature runtime handler
    ↓
局部 UI 状态或 feature runtime 状态
```

规则：

- drag、scroll、resize、focus 这类事件不强行建 command。
- 组件只提交领域事件，例如 `DockResizeEvent`；真正状态修改由持有 runtime 的 handler 完成。
- 交互管线不能偷偷承载本该能被快捷键 / 命令面板触发的离散功能。

适合交互管线的例子：

- Dock resize drag。
- 鼠标拖选。
- 滚动 viewport。
- 纯窗口焦点投影。

## 四、文本与 IME

IME 是输入意图中最容易越界的路径。规范如下：

- 查询类回调，如 `text_for_range`、`selected_text_range`、`bounds_for_range`，是系统输入法协议查询，不算命令意图。
- commit / confirm / cancel 这类会改变文本或组合态终局的动作，应翻译为编辑命令，进入 undo / redo 语义。
- preedit update 若只是组合态临时刷新，可以走受控直接通道；若实现选择走命令，也必须保持它不会污染普通编辑历史。
- keymap 未消费的按键不得 stop propagation，必须放行给系统 IME。

## 五、命名约定

当前共享原语：

| 名称 | 含义 |
|---|---|
| `HostIntentRequest` | shell / editor 之间唯一真实离散派发出口 |
| `HostIntent` | 命令、按键、IME 写入、交互这四类离散宿主意图 |
| `CommandBinding` | Glyph 持有的命令完整表达：command id + title/shortcut lookup + 点击 request。渲染时自动反查 keymap，点击时派发 |
| `CommandRequest` | 给非 Glyph 组件使用的命令闭包；内部发 `HostIntent::Command` |
| `InteractionRequest<Event>` | 连续交互出口（resize、scroll、selection drag） |
| `FocusRequest` | 焦点类交互出口 |
| `KeyRequest` | 键盘事件窄口；内部发 `HostIntent::KeyChord`，返回 consumed 决定是否 stop propagation |
| `<Feature>IntentRequest` | feature 领域意图出口 |

如果某个意图已经稳定成为全局命令语义，优先直接提供 `CommandBinding`，不要再包一层 feature intent。

`CommandBinding` 把命令 id、展示查表（title/shortcut lookup）和派发 request 打包为一个值，Glyph 通过 `.command(binding)` 一次性拿到它需要的一切。统一派发、剪贴板 scope、`HostEffect` 解释、刷新策略仍集中在 `HostIntentRequest`。

## 六、验收规则

新增或迁移输入入口时逐项确认：

- 命令、按键、IME 写入最终都落到 `HostIntentRequest`。
- L2 primitive 不 import `zom_command`。
- L3 组件不直接 dispatch command。
- 离散功能入口走 `CommandBinding` 或 feature intent。
- 高频设备交互走 `InteractionRequest<Event>`，不进入 command catalog。
- intent → command id 映射只有一个集中位置。
- 快捷键展示由 Glyph 通过 lookup 自行反查，不由组件手写快捷键字符串。
- 按键路径只在 keymap 消费时停止传播。
