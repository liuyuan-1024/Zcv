# 编辑器架构审计与规划

用于只读审计、问题解释、迁移规划和代码评审。目标是判断当前实现是否满足 `docs/编辑器架构.md` 的目标契约，并给出可以直接实施和验证的差距，而不是罗列风格偏好。

## 建立事实图

先从实际定义、构造点、调用方、订阅和测试建立事实，再与目标对照。对每个涉及层记录：

| 维度 | 需要回答的问题 |
| --- | --- |
| 职责 | 该层现在负责什么；哪些职责应属于相邻层 |
| 权威状态 | 谁创建、持有、修改；是否存在第二份可写副本 |
| 快照 | 快照固化了哪个下层版本；文本与元数据是否一致推进 |
| 坐标 | 输入、输出和长期位置各用什么类型；在哪个快照上解析 |
| 增量 | 消费什么 edit/patch/event；向上产出什么；谁是唯一推进入口 |
| 生命周期 | 实体、订阅、缓存和后台任务何时创建、取消、替换、销毁 |
| 依赖 | crate/module 依赖是否只从上层指向下层 |
| 验证 | 哪个测试或检查能直接证明对应不变量 |

沿一条完整的状态变化路径取证，避免只看静态类型。例如文本编辑至少追踪 `Editor → MultiBuffer → Buffer → MultiBuffer → DisplayMap → Editor → EditorElement`；语法更新追踪解析任务的基准版本、安装入口、元数据版本和上层快照推进。

## 与目标和 Zed 对照

1. 先用架构文档确定目标层、稳定不变量和已登记差距。
2. 再读 Zcv 当前实现，判断为“符合、缺失、偏离或合理实现差异”。
3. 对缺失或偏离读取 Zed 对应能力，确认原型的状态所有权、数据流和生命周期。
4. 用架构文档第 17 节判断协作、远程、LSP 裁剪；不要自行扩大裁剪。
5. 第 18 节已有差距仍要用当前代码复核，不能把登记项当作已确认的现状；发现新差距时说明是否应登记，已消除的条目应在实施时删除。

Zed 与 Zcv 名称不同不构成差距；只有职责、所有权、依赖、坐标、版本、增量或生命周期语义不同才构成差距。

## 优先检查的结构性问题

- 同一文档形态是否绕开或复制唯一 `Editor` 管线。
- 文本、excerpt、显示行、选择、滚动或装饰是否形成影子权威。
- 长期状态是否保存旧快照的 offset/point/display point，或重建后复用旧投影坐标。
- 不同坐标空间是否混用裸整数，转换是否缺少快照、`Affinity`、`Bias` 或失败处理。
- 快照链是否混入不同版本；语法、diff、设置等纯元数据变化是否会漏推进。
- 某层是否绕过直接下层，读取更低层批次、全文或私有状态。
- 增量入口是否在推导失败、边界不匹配或缓存缺失时静默回退到全量重建（整层 edit、整份投影、整体装饰重建），而不是修正推导或让不变量失败。
- 全量路径是否只作为命名的显式边界操作存在（构造、整体替换、配置切换、低频重命名），还是散落在增量协议中充当兜底；每条保留的全量都应能说明它对应的边界语义。
- edit 是否被误当作精确差量，而非需要失效的旧/新区间。
- 同一派生状态是否同时由订阅回调、显式刷新或多个缓存推进。
- 事务、undo/redo、输入法或程序化编辑是否存在旁路写入。
- 后台任务是否缺少取消、基准版本校验或唯一安装入口。
- Project/Workspace/UI 是否上移了编辑器领域状态，或底层反向依赖上层。
- 是否因裁剪协作、远程或 LSP 而误删仍服务本地编辑的版本、Anchor、历史或增量协议。

## 发现与规划格式

每条发现包含：

1. 严重度与简短标题。
2. 最窄的文件和行范围。
3. 当前实际的数据流、状态所有者或依赖证据。
4. 违反的架构文档章节与不变量编号。
5. 用户可观察错误、增量失效、状态分叉或长期维护影响。
6. 目标边界：唯一所有者、规范入口、上下游协议和需要删除的旧路径。
7. 必须一起迁移的调用方、测试与文档。
8. 能直接证明修正成立的定向验证。

迁移计划按架构依赖从下往上组织，但每个阶段都要形成内部完整的协议边界，不能长期保留新旧双轨。无法证明实际影响或不变量违反的想法不列为发现。没有问题时，明确已检查的层、路径和未覆盖边界。
