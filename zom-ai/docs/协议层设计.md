# zom-ai 协议层设计

> `zom-ai` 是面向 chat 与 agentic（多轮 + 工具调用）的协议层。本文记录当前抽象的目标、数据模型、接口边界与后续扩展点。

## 1. 定位

`zom-ai` 只描述一次模型请求与流式响应的协议形状，不持有会话、不执行工具、不应用编辑，也不绑定任何具体厂商 SDK。

它提供四类稳定词汇：

1. `Message / Content`：对话上下文。
2. `ToolDef / ToolCall / ToolResult`：工具定义、调用与回包。
3. `ChatRequest / Options`：一次请求的模型、消息和工具配置。
4. `StreamEvent / AiError`：流式事件与可恢复错误分类。

## 2. 目标与非目标

### 2.1 目标

- 提供能直接承载 **chat 面板**与 **agentic loop** 的协议层数据模型。
- 提供 **async + 流式**的 `AiProvider`，并以 stream 的 drop 作为唯一取消语义。
- **零网络、零厂商**。具体 SDK / 鉴权 / HTTP 留给独立 provider crate（如未来的 `zom-ai-anthropic`）实现。
- **零会话状态**。`zom-ai` 不持有 conversation；裁剪、压缩、持久化由调用方决定。
- **零编辑能力**。"读 buffer / 应用编辑 / 跑命令"等具体能力以 **tool** 的形式由上层注册，`zom-ai` 不认识这些工具的语义。

### 2.2 非目标（本轮不做）

- 多 Provider 多态 / 能力位（capabilities）。目前只服务 chat + agentic 这一种形态，"能力位"暂不抽。
- Agent loop 本身。`while not stopped { provider.stream → 执行 tool → 续轮 }` 由上层组合，不下沉到 `zom-ai`。
- 任何具体厂商适配。
- 任何 UI / panel 状态机。

## 3. 边界与依赖

```text
zom-ai → zom-engine
zom-ai → futures-core      （流式协议）
zom-ai → async-trait       （async trait 写法）
zom-ai → serde_json        （tool 的 input_schema / input / 结果）
```

仍然不依赖：网络栈、tokio、`zom-command`、`zom-workspace`、任何厂商 SDK。

`serde_json::Value` 是行业既定事实：Anthropic、OpenAI、MCP 的 tool 入参/出参都是 JSON。让 schema、`ToolCall.input`、`ToolResult.content` 同质，避免上层反复 parse。

## 4. 数据模型

### 4.1 Message 与 Content

```rust
pub enum Role { System, User, Assistant, Tool }

pub enum Content {
    Text(String),
    ToolUse(ToolCall),
    ToolResult(ToolResult),
}

pub struct Message {
    pub role: Role,
    pub content: Vec<Content>,
}
```

`Content` 是**有序数组**。assistant 消息可能同时包含 text 段与一个或多个 tool_use 段（这是 Claude / OpenAI 现实形状），不能压成"要么文本要么工具"的二选一。

Conversation 直接以 `Vec<Message>` 表达，不另封类型 —— 上层（panel / agent）才知道什么时候截断、压缩、落盘，`zom-ai` 只对"一次请求"负责。

### 4.2 Tool 协议

```rust
pub struct ToolDef {
    pub name: String,
    pub description: String,
    pub input_schema: serde_json::Value,   // JSON Schema
}

pub struct ToolCall {
    pub id: String,
    pub name: String,
    pub input: serde_json::Value,
}

pub struct ToolResult {
    pub call_id: String,
    pub content: String,
    pub is_error: bool,
}
```

`zom-ai` 不规定有哪些工具。"读 buffer"、"应用编辑"、"跑命令"等都由上层注册成 `ToolDef`，把 buffer id、版本号、范围等通过 `input_schema` 显式约束。

### 4.3 请求

```rust
pub struct ChatRequest {
    pub system: Option<String>,
    pub messages: Vec<Message>,
    pub tools: Vec<ToolDef>,
    pub options: Options,
}

pub struct Options {
    pub model: String,
    pub max_tokens: u32,
    pub temperature: Option<f32>,
}
```

`Options` 只放跨厂商通用字段。任何厂商私有参数留在该厂商的 provider crate 内部，不污染抽象层。

## 5. Provider 接口

```rust
use core::pin::Pin;
use futures_core::Stream;

pub type EventStream =
    Pin<Box<dyn Stream<Item = Result<StreamEvent, AiError>> + Send>>;

#[async_trait::async_trait]
pub trait AiProvider: Send + Sync {
    async fn stream(&self, request: ChatRequest) -> Result<EventStream, AiError>;
}
```

为什么是 async + Stream：

- chat / agentic 必须能边到边渲染，长响应必须能中途取消。
- `stream()` 本身是 async，便于把"建立连接 / 鉴权"这种可失败步骤与"消费事件"分开 —— 连接阶段的错误立刻 `Err` 返回，进入 stream 后才有 per-event 错误。
- 取消语义统一为 **drop stream**：上层 drop 掉 `EventStream`，具体 provider 在 stream 的 drop 实现里关闭底层连接。不引入第二条取消通道。

`Pin<Box<dyn Stream>>` 而不是 `impl Stream`，是为了让 trait object 可用，方便上层把不同 provider 装进同一容器（即便目前只做一种形态，trait object 的代价小到可以现在就付）。

## 6. 流式协议

```rust
pub enum StreamEvent {
    MessageStart { role: Role },
    TextDelta { text: String },
    ToolUseStart { id: String, name: String },
    ToolInputDelta { id: String, json_fragment: String },
    ContentBlockStop { index: u32 },
    MessageStop { stop_reason: StopReason, usage: Usage },
}

pub enum StopReason {
    EndTurn,
    ToolUse,
    MaxTokens,
    StopSequence,
    Cancelled,
}

pub struct Usage {
    pub input_tokens: u32,
    pub output_tokens: u32,
}
```

形状对齐 Anthropic SSE 事件流，OpenAI 的 delta 也能映射进来。`ToolInputDelta.json_fragment` 是累积型片段，由上层拼成完整 JSON 后再 parse —— 这与厂商对 tool input 分块下发的现实一致。

UI 可直接以 `StreamEvent` 为驱动单元，无需自行设计中间事件类型。

## 7. 错误层

```rust
pub enum AiError {
    Network(String),
    Auth,
    RateLimited { retry_after: Option<std::time::Duration> },
    Timeout,
    ContextTooLong { limit_tokens: u32 },
    Cancelled,
    ToolProtocolViolation(String),   // provider 输出的 tool_use 不合规
    ProviderUnavailable,
    Other(String),
}
```

每个变体对应一种 UI 决策路径：

| 错误 | UI 决策 |
| --- | --- |
| `Auth` | 引导换密钥 |
| `RateLimited` | 退避重试，必要时显示等待时间 |
| `Timeout` | 重试或建议拆短请求 |
| `ContextTooLong` | 触发上下文压缩或截断 |
| `Cancelled` | 静默或回到 idle |
| `ToolProtocolViolation` | 上报为 bug，不可对用户隐藏 |
| `Network / ProviderUnavailable` | 重试或提示稍后 |
| `Other` | 兜底展示原文 |

## 8. 文件结构

```text
zom-ai/src/
├── lib.rs           // 重新导出
├── message.rs       // Role / Content / Message
├── tool.rs          // ToolDef / ToolCall / ToolResult
├── request.rs       // ChatRequest / Options
├── stream.rs        // StreamEvent / StopReason / Usage
├── provider.rs      // AiProvider trait / EventStream
└── error.rs         // AiError
```

每个文件单一职责，符合协作规范中的"高内聚低耦合"。多 provider 的实现 crate 将来另起（如 `zom-ai-anthropic`），不在本 crate 内部分模块承载。

## 9. 接入约束

- 上层 panel / agent loop 只依赖 `AiProvider + ChatRequest + StreamEvent + AiError`。
- buffer 读取、编辑应用、命令执行等能力都通过 tool schema 显式建模。
- provider crate 负责厂商参数、鉴权、网络栈和事件映射，不把这些细节扩散进 `zom-ai`。
- README、crate 描述和代码接口必须同步更新，避免文档与实现错位。

## 10. 留待后续

以下事项本轮不做，记录以避免遗失：

- **多 Provider / capabilities。** 出现第二个真实形态（如 inline completion）时再抽。
- **Agent loop 的标准实现。** 若多个上层重复实现同一套 loop，再考虑下沉到 `zom-ai` 或新 crate。
- **结构化编辑提案的复用类型。** 当前由各 tool 自行定义 input/output schema；若多个 tool 重复定义"编辑"形状，再抽公共类型（例如 `EditTarget { buffer_id, version, range }`）到一个共享层，但不预建。
- **Tracing / 观测。** provider 内部观测先由各 provider 自决；待出现跨 provider 统一需求再抽。
- **持久化与序列化。** `Message / ToolCall / ToolResult` 是否实现 `serde::Serialize` 由后续 panel 持久化需求驱动，本轮不加。

## 11. 验证标准

本设计达成的判据：

- `zom-ai` 的依赖仍只含 `zom-engine + futures-core + async-trait + serde_json`，无网络、无 tokio、无厂商 SDK。
- 用一个 mock provider 能跑通：单轮 chat 流式输出、tool_use 事件、tool_result 续轮、中途 drop stream 取消。
- 上层 panel 仅依赖 `AiProvider + ChatRequest + StreamEvent + AiError` 即可拼出 chat 与 agent 两种形态，无需再回头改 `zom-ai`。
