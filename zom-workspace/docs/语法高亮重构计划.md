# 语法高亮 render-time query 改造计划

> 上一轮把 confirmed layer 切到 `Stickiness::Expand` 后，边界插入不再露默认前景色，
> 但仍存在"先以旧 tree 颜色显示、worker reparse 回包后再纠正"这一帧的色跳。本计划
> 把架构从"预算 layer + worker 投递 ReplaceRange/All"切换到"主线程持有 `Arc<Tree>`
> + paint 阶段按 viewport 现查 tree-sitter Query"，从根上消除 layer 与 tree 之间的
> 一致性窗口。

## 目标

最终态：layer 抽象在 syntax 子系统消失，worker 仅负责后台 reparse 替换 tree；
颜色 = 当前 tree 在 viewport 上的纯函数，没有任何缓存可以滞后。

## Phase 0：测量与定标（0.5 天）

不动代码，先回答两个问题：

1. **viewport query 实测耗时**：取
   `zom-workspace/src/syntax/providers/common.rs` 的 `collect_spans` 路径，
   做一份 micro-bench —— 在 16 MiB rust 文件上，对随机 viewport（~50 行 ≈ 2-4 KiB）跑 `QueryCursor::captures` 加上 `SnapshotTextProvider` 全链路，统计 p50 / p95 / p99。
2. **incremental reparse 实测耗时**：同样规模下
   `Parser::parse_with_options(..., Some(&old_tree), timeout=None)` 对"单字符 edit"后的 reparse 耗时。

**决策点**：

- query p99 < 0.5 ms → 直接 render-time（不缓存）。
- query p99 在 0.5-2 ms → 加一层"viewport spans cache"，失效条件：tree 变了 /
  viewport 移了。
- query p99 > 2 ms → 改造前先优化 query 本身（可能需要更小粒度的 capture cache），
  否则 render-time 会拖帧。

bench 进 `zom-bench`，跟现有 syntax bench 同位置。

## Phase 1：新共享态（1 天）

引入 `BufferSyntaxTree`（放 `zom-workspace/src/syntax/tree.rs`）：

```rust
pub struct BufferSyntaxTree {
    config: Arc<SharedConfig>,     // language + query + lookup
    tree: Arc<Tree>,               // 当前 tree（可能是 interpolate 过的）
    snapshot: Arc<Snapshot>,       // 与 tree 对应的 buffer 快照
    version: BufferVersion,
}
```

挂在 `WorkspaceBuffer` 上（替换现在的 `BufferSyntaxState` + `MetadataLayers<HighlightSpan>`
这套）。`Arc<Tree>` 让 worker 后台算完后能 `Arc::swap`，主线程读永远不阻塞。

**worker 改造**：

- `Job::Attach` 改成传 provider + snapshot，worker 跑首次 parse，把 `Arc<Tree>` 写
  回主线程（用 `Arc<AtomicCell<Option<BufferSyntaxTree>>>` 或类似的 lock-free swap；
  视情况退化成 Mutex 也可）。
- `Job::Edit` 改成只做 reparse + swap，**不再 push sink**。
- `Job::Detach` 还在，清掉共享态。
- `SetViewport` / `apply_pending_edit` / coalesce 路径**全部删除**——viewport 由
  render 端现取，coalesce 由"每次 swap 都拿最新 snapshot"自动覆盖。

主线程编辑入口（`BufferSyntaxState::handle_edit` → 新结构）：

- 同步调 `tree.edit(InputEdit)`（O(log N)，已经在 provider common.rs 里有
  `translate_edits` 逻辑可复用）。
- 异步投 `Job::Edit` 给 worker 跑 reparse。
- **不写 layer**。

## Phase 2：render 路径切换（1 天）

替换 `zom-desktop/src/editor/highlight/producers/syntax.rs`：

```rust
pub(crate) fn push(
    syntax_tree: Option<&BufferSyntaxTree>,
    snapshot_lines: &[SnapshotLine],
    out: &mut Vec<Decoration>,
) {
    let Some(st) = syntax_tree else { return };
    let Some(viewport) = viewport_byte_range(snapshot_lines) else { return };
    let mut cursor = QueryCursor::new();
    cursor.set_byte_range(viewport.start().get()..viewport.end().get());
    let spans = collect_spans(
        &st.config,
        &mut cursor,
        &st.tree,
        SnapshotTextProvider { snapshot: &st.snapshot },
    );
    for (range, span) in spans {
        out.push(Decoration {
            range,
            kind: Foreground,
            style: Named(StyleClass::Syntax(span.name.to_string())),
            priority: SYNTAX_CONFIRMED,
        });
    }
}
```

`push_syntax_layers` 入参从 `&MetadataLayers<HighlightSpan>` 改成
`Option<&BufferSyntaxTree>`，WorkspaceBuffer 给出 getter。`collect_spans` 已存在，
直接复用。

**关键细节**：`QueryCursor` 不要每帧 new——放 `RefCell<QueryCursor>` 缓存在
viewport 或 surface 上（thread-local 也行）。tree-sitter 这玩意儿构造一次还行但
每帧若干次会累积。

## Phase 5：bench / 验收（0.5 天）

跑 `zom-bench` 原有的 syntax bench——指标看：

- **主线程单键耗时**（目前 16 MiB rust ~3 µs）：render-time 改造后，主线程改成只
  跑 `tree.edit` + 投 worker job + paint 时一次 query。query 进入主线程 critical
  path，目标 < 0.5 ms / 帧。
- **首屏冷启动**：全文 parse 仍然走 worker（同步路径只对增量 edit）。bench 应当
  和现在持平或略好（少了 sink 投递与 drain 一层）。
- **持续打字**：perceptually，wrong-color 闪烁应当消失——这点 bench 测不出，需要
  在 desktop 跑真实样本（自录 GIF 对比）。

## 风险与未知点

1. **共享 tree 的所有权模型**：`Arc<Tree>` 看似简单，但 worker 跑 reparse 时主线程
   可能正在 query。两种选项：
   - **(A) 双缓冲**：worker reparse 在自己的 tree 上跑，完成后 `Arc::swap` 整个
     `BufferSyntaxTree`。主线程拿快照后无锁读。需要 `arc-swap` crate 或自己撸。
   - **(B) Mutex**：主线程 query 拿读锁，worker reparse 时拿写锁。锁竞争在快节奏
     打字时可能拖帧。

   起手用 (A)，它的范式更符合"单写多读"。如果实现成本高再退到 (B)。

2. **incremental tree 的 query 结果**：`tree.edit` 后 tree 的 node 范围被推进，但
   node TYPE 仍是旧的。query 在 interpolate tree 上跑的结果可能在结构变化的位置
   出现错误（例如 `fn` → `fnx` 后 tree 还说它是 keyword 节点）。**这正是 "wrong
   color flash"** —— render-time 也救不了，直到 reparse 完成。

   两种思路：
   - 接受这个一帧错色，等 worker reparse（典型 < 5 ms）替换 tree → 下一帧颜色正确。
   - 主线程也跑一次带 budget 的 reparse（`Parser::set_timeout_micros`），小文件命中
     预算就直接拿到结构正确的 tree。这是 A 路径的剩余价值，可以叠加进 B。

   建议：**先不做主线程同步 reparse，看 Phase 5 实测感受**。如果用户感受仍然有
   wrong-color 痕迹，再加同步 reparse fast-path——B 架构下加这层很自然，只是多一
   个"主线程能不能 < 1 ms 拿到 reparsed tree"的判断。

3. **injections / nested grammar**：当前 provider common.rs 显式不处理 injections。
   render-time 改造不影响这点，但未来如果加 markdown 内嵌代码块、HTML 里 JS 这类，
   query 入口要支持多 layer。Phase 0 时就要把 `Arc<Vec<Arc<Tree>>>` 而非
   `Arc<Tree>` 留好结构。

4. **`tree_sitter::Tree` 是否 Send/Sync**：必须确认。如果不是，worker 把 tree 传回
   主线程的路径要走 `Arc<Mutex<...>>` 或专门的跨线程容器。

## 总工期估计

- 顺利：**3-4 天**（全职）

## 不在本次范围内

- Selection / diagnostics / AI proposal 的装饰系统（它们仍走 `MetadataLayers<T>`
  基础设施，只是 syntax 不再用这个抽象）。
- theme color 解析（还在 shell composer，不变）。
