# 桌面端组件实现

> 本手册规定 `zom-desktop` 的可见结构与组件实现：窗口外壳、停靠区、编辑面、浮面与气泡。"几何语义"（区域怎么排、面板模型是什么、Surface 锚到哪里）与"实现规约"（组件状态怎么持有、命令怎么进、扩展点怎么留）合写在一处，按"由外到内"的顺序：先 WorkbenchFrame 的几何，再 EditorGrid 与 EditorView，再 Dock 与 Panel，最后浮面与气泡。
>
> 本手册不规定视觉令牌（颜色 / 字号 / icon）的命名与取值，也不规定命令派发、键位解码、平台事件、焦点系统、异步执行器这些"应用怎么跑"的基础设施。本手册描述的组件在这两套基础设施之上长出来。

## 词汇预设

为让本手册自洽阅读，先把会反复出现的几个概念约定清楚。

### 组件层级

zom-desktop 内部组件分四层，本手册的主体只关心 **L3 / L4**：

```
L4  Region      ── TopBar / BottomBar / EditorGrid / LeftDock / RightDock / BottomDock
                  窗口级外壳区域。强存在感、几乎不复用、由 app 层组装。
L3  Composite   ── CommandPalette / FileTree / TabStrip / StatusItem / EditorView ...
                  业务组件。有领域语义、有交互、有专属文案与图标。
L2  Primitive   ── Button / Glyph / Tooltip / Popover / Frame ...
                  视觉原语。无领域语义、可被多处复用。
L1  Token       ── 颜色 / 尺寸 / 字号 命名常量。
```

**L3 不拥有领域状态**——领域状态在底层 crate（buffer 内容 / dirty 在 workspace、视图状态在 view、命令在 command、AI 提案在 ai）。L3 通过 `Entity<T>` 句柄读取；自己只持有 UI 局部状态（折叠展开标志、hover 项、当前输入文本等）。

### 模块分区

```
zom-desktop/src/
  shell/       视觉层与平台层
    workbench/   L4 窗口级外壳区域 (TopBar / BottomBar / Body / Dock)
    features/    L3 功能切片 (CommandPalette / FileTree / EditorView 等)
    surfaces/    浮面 portal 外壳：定位、层级、关闭与焦点归还
    bubble/      气泡提示层：统一轻量提示模型
    shared/      L2 视觉原语
    platform/    平台差异收纳
  app/         命令装配、Workspace / ViewSet / Keymap 编排、IME 状态投影
```

`shell` 不依赖 `app`；`app` 装配 `shell` 并接入底层 crate。

### 状态注入

L3 组件**不主动**去全局取业务状态。只接受两种输入：

```
A. 数据   通过构造函数 / Props 传入（不可变快照、显式 Entity 句柄、显式 crate 服务句柄）
B. 行为   通过回调 / action handle 传入
```

```rust
// 禁止：组件内部直接读全局
let workspace = cx.global::<Workspace>();

// 必须：调用方注入显式句柄
pub struct EditorView {
    workspace: Entity<Workspace>,
    view_set: Entity<ViewSet>,
    view_id: ViewId,
    on_request_command: Box<dyn Fn(CommandId, CommandArgs, &mut App)>,
}
```

**透明全局例外**：`cx.theme()` / `cx.fonts()` / `cx.locale()` / `cx.settings()` 四类视觉 / 偏好查询是允许的透明全局。底层 crate 的服务（`Workspace` / `ViewSet` / `CommandRegistry` / `AiProvider`）**不在例外清单**——必须显式注入。

### 测试要求

每个 L3 组件必须满足：

> **提供至少一个 `#[gpui::test]`，覆盖该组件的主要 UI 状态转移。**

"主要 UI 状态转移"指：打开 / 关闭、激活 / 失活、用户交互导致的视觉状态变化。视觉呈现（颜色、布局、icon 选择）**不在测试覆盖范围**，由 playground 人工 review 兜底。

L3 组件**不重测底层 crate 的领域逻辑**——SelectionSet 怎么 movement、Buffer 怎么 undo、Keymap 怎么解析，这些在底层 crate 的契约测试已覆盖。

字体度量、坐标 ↔ 位置转换这类**纯算法**抽到组件本地 `logic.rs`，作为纯 Rust 函数裸单测；不依赖 GPUI。

## 一、外壳与几何

### 1.1 设计目标

zom-desktop 的桌面界面采用**稳定外壳 + 可停靠面板 + 主编辑区 + 临时浮层**的分层模型。临时浮层分为两类：可交互的 **浮面（Surface）**，以及轻量提示用的 **气泡（Bubble）**。

核心目标：

- `TopBar` / `BottomBar` 作为 IDE 外壳的一部分，保持极高稳定性。
- `TopBar` / `BottomBar` 采用同一套 shell bar 视觉规则，上下镜像，保持对称。
- `LeftDock` / `RightDock` / `BottomDock` 只负责承载面板，不绑定具体面板实现。
- `EditorGrid` 独立建模，保留编辑器 tab、split、active editor 等专属规则。
- `SurfaceLayer` / `BubbleLayer` 是运行时临时层，不进入持久布局；二者同属悬浮层，但语义、生命周期与复用方式不同。
- 底部停靠区只位于中间列下方，不侵入左右停靠区下方。

### 1.2 WorkbenchFrame 总体结构

```text
Window
├─ WorkbenchFrame
│  ├─ TopBar
│  ├─ Body
│  │  ├─ LeftDock
│  │  ├─ CenterColumn
│  │  │  ├─ EditorGrid
│  │  │  └─ BottomDock
│  │  └─ RightDock
│  └─ BottomBar
├─ SurfaceLayer
└─ BubbleLayer
```

视觉结构：

```text
┌────────────────────────────────────┐
│ TopBar                             │
├───────┬────────────────────┬───────┤
│ Left  │    EditorGrid      │ Right │
│ Dock  ├────────────────────┤ Dock  │
│       │    BottomDock      │       │
├───────┴────────────────────┴───────┤
│ BottomBar                          │
└────────────────────────────────────┘
```

`BottomDock` 指 `CenterColumn` 内的底部停靠区，不是窗口级底栏。窗口级底栏统一称为 `BottomBar`。

### 1.3 Shell Bar 对称性

`TopBar` 与 `BottomBar` 是同一种窗口外壳区域的上下两次使用。二者必须保持一致的高度、内边距、背景、字号、基础文字色与横向三槽布局。

它们只允许在以下方面不同：

- 所处位置：`TopBar` 在窗口顶部，`BottomBar` 在窗口底部。
- 分隔线方向：`TopBar` 的分隔线在下侧，`BottomBar` 的分隔线在上侧。
- 承载内容：`TopBar` 偏标题栏、命令入口与窗口控制；`BottomBar` 偏模式、任务、状态与摘要。

除非明确修改 shell bar 共同规则，否则不得只单独调整其中一条栏的厚度、颜色、字号或密度。

### 1.4 Glyph 视觉原语

`Glyph` 是 shell 内复用的基础视觉标记组件。它可以承载文字、图标、图标加文字。

`Glyph` 通过 `.command(CommandBinding)` 绑定一条命令。绑定后：渲染时自动从 `CommandTitleLookup` / `ShortcutLookup` 拉取 tooltip 标题与快捷键 hint，点击时派发 `CommandBinding.request`。未绑命令时，`Glyph` 为纯展示元素（无 tooltip、无点击）。`Glyph` 不持有 Surface 锚点，若某个功能入口需要召唤 Surface，则由该功能入口自己包装 invoker。

基础规则：

- 每个 `Glyph` 必须有稳定 `id`。
- 绑定命令后 tooltip 标题和快捷键 hint 由 Glyph 自行通过 lookup 拉取，不由调用方传入。
- 组件外框不写死高度，高度由内容、字号与图标尺寸自然撑开。
- `Glyph` 不附带内外边距，所见即所得；标记之间的距离与栏内留白都由父级布局显式决定。
- 图标加文字的 `Glyph` 必须横向排列，先图标后文字，不额外增加背景色或胶囊外观；内部图标与文字的距离应小于不同 item 之间的距离，文字容器应与图标同高并通过布局居中，不使用固定像素偏移做视觉校正。
- 纯视觉标记可以规定内部图形尺寸，例如红绿灯圆点直径，但外层仍由内容撑开。
- tooltip 只用于短提示，由标题和快捷键两部分组成，例如「退出应用」「Cmd-Q」。
- tooltip 不承载确认、表单或复杂交互；需要交互时升级为 `SurfaceLayer`。
- tooltip 的实际提示框与鼠标点之间必须保留间距，避免遮挡触发它的 glyph。
- 文字标记、图标标记、图标加文字标记与窗口控制标记共享同一套 tooltip 行为。

### 1.5 TopBar 区域语义

`TopBar` 是窗口级顶部外壳，稳定存在，不作为普通 `Panel` 容器。

它可以承载工作区入口、命令入口、全局导航、窗口级操作、运行中任务摘要等 shell 级内容。具体内容可以演进，但区域本身不参与普通面板停靠、迁移或关闭。

`TopBar` 同时承担 `zom` 的统一自绘标题栏职责。窗口控制标记采用跨平台一致的 macOS 红绿灯设计，由 `zom-desktop` 自己绘制，不依赖 OS 原生标题栏承载信息架构。

`zom-desktop` 默认隐藏 OS 原生标题栏内容，并由 `TopBar` 承担窗口外壳视觉。平台只提供窗口能力，例如移动、最小化、放大、退出，不提供可见标题栏 UI。

第一版窗口控制标记：

```text
Close     红色，退出应用
Minimize  黄色，最小化当前窗口
Zoom      绿色，放大 / 还原当前窗口
```

窗口拖动、双击放大等平台行为属于 `shell` 适配层职责，不在本手册范围。

### 1.6 BottomBar 区域语义

`BottomBar` 是窗口级底部外壳，稳定存在，不作为普通 `Panel` 容器。

它不预设为状态栏。它可以承载状态，也可以承载模式、任务入口、同步进度、AI 运行标记、诊断摘要、语言服务状态、账户或环境信息等全局内容。

第一版 `BottomBar` 使用图标项作为主要内容，从左到右依次为：

```text
文件树
版本管理
大纲
搜索
诊断 0
终端
调试
快捷键
```

这些图标项统一使用 `Glyph`，图标来自 `zom-desktop/assets/icons/panels/` 与 `zom-desktop/assets/icons/status/`，并通过 tooltip 显示名称。诊断项第一版先使用 `diagnostics_warn` 图标和占位数字，后续再接入真实 LSP 诊断数量。

`BottomBar` 中的面板切换图标是 `panel.toggle.<id>` 命令的视图（详见 §三.9）——`BottomBar` 本身不知道 panel 是什么，只派发命令。

### 1.7 LeftDock 和 RightDock

`LeftDock` 与 `RightDock` 是左右停靠区域，贯穿 `Body` 高度。

它们适合承载工作区级导航与上下文面板，例如文件树、搜索、符号大纲、AI 会话、当前文件上下文等。区域负责显示、隐藏、折叠、尺寸和面板激活状态，不关心面板内部实现。

### 1.8 BottomDock

`BottomDock` 是中间列底部停靠区域，只位于 `EditorGrid` 下方，与左右停靠区不重叠。

它适合承载当前编辑任务相关的输出与反馈，例如终端、问题列表、输出日志、测试结果、任务日志等。它的水平边界与 `EditorGrid` 对齐。

### 1.9 EditorGrid 区域

`EditorGrid` 是主编辑区，不作为普通面板处理。

它拥有独立的编辑器规则，包括 tab、split、active editor、dirty state、preview tab 等。这样可以避免普通面板模型过早污染编辑器核心行为。

`CenterColumn` 是 `EditorGrid` + `BottomDock` 的垂直容器；`EditorGrid` 占据上半部，`BottomDock` 占据下半部。

### 1.10 第一版几何边界

明确支持：

- 固定外壳：`TopBar`、`Body`、`BottomBar`。
- 三个停靠区：`LeftDock`、`RightDock`、`BottomDock`。
- 底部停靠区只属于中间列。
- `EditorGrid` 支持 split tree。
- 浮面层与气泡层作为运行时状态。

明确不做：

- 任意拖拽窗口系统。
- 面板浮动成独立窗口。
- 跨显示器布局。
- 完全自定义 workspace layout DSL。
- `BottomDock` 贯穿全窗口宽度。
- 面板跨 dock 拖动。
- 同一 dock 内多 panel 同时显示（PanelGroup tree 形态推迟到第二版）。

## 二、EditorGrid 与 EditorView

### 2.1 EditorGrid 数据模型

`EditorGrid` 内部采用 group + split tree：

```rust
struct EditorGrid {
    root: EditorNode,
    active_group: EditorGroupId,
}

enum EditorNode {
    Group(EditorGroup),
    Split {
        axis: SplitAxis,
        children: Vec<EditorSplitChild>,
    },
}

struct EditorGroup {
    id: EditorGroupId,
    tabs: Vec<EditorTab>,
    active: Option<EditorTabId>,
}
```

该模型支持单编辑器、左右拆分、上下拆分、多 tab group，以及未来的 tab 拖动迁移。每个 `EditorTab` 对应 `zom-view::View` 的一个 `ViewId`；`EditorView`（叶子组件）实现规则见后续小节。

### 2.2 EditorView 定位

EditorView 是 desktop 最复杂的 L3 组件，串起四个底层 crate（engine / workspace / view / command）将文本编辑能力呈现给用户。本章定义其第一版最小可用形态，面向"OS 按键 → KeyChord → keymap → 命令、删除、移动光标、撤销 / 重做"闭环；P3（搜索 / 折叠 / 投影）与 P4（AI 提案）的接入点留出明确扩展槽，但本章不规定其内部细节。

```
EditorView (L3, in shell/workbench/regions/editor_area/editor_grid.rs)
  ├─ 显示：透过 zom-view 的 ViewportState、zom-workspace 的 Buffer 内容渲染文本
  ├─ 输入：转 GPUI 事件为 zom-command 的 (CommandId, CommandArgs) 派发
  └─ 状态：自身只持 UI 局部状态（焦点、IME 缓冲、鼠标拖拽、字体度量缓存）
```

EditorView **不持有领域状态**：buffer 在 workspace、视图状态在 view、命令派发在 command。

### 2.3 持有的句柄与状态

```rust
pub struct EditorView {
    // 句柄：由调用方注入，EditorView 不主动去全局取
    workspace: Entity<Workspace>,
    view_set: Entity<ViewSet>,
    view_id: ViewId,

    // 行为通道：所有"要让别人做的事"都走回调
    on_request_command: Box<dyn Fn(CommandId, CommandArgs, &mut App)>,

    // 自己的 UI 状态（局部、可序列化为 PreviewVariant）
    focus_handle: FocusHandle,
    composition: Option<CompositionUiState>,
    drag: Option<DragUiState>,
    metrics: FontMetricsCache,
}
```

EditorView 必须接受**最小子状态**：拿 `Entity<ViewSet>` 而非 `Entity<App>`；拿 `ViewId` 而非"由我决定哪个是活动 view"。

### 2.4 与 EditorGrid / ViewSet 的关系

- **EditorView 是叶子组件**——对应一个 `ViewId`。多视图（分屏）由 EditorGrid 通过 split tree 装配多个 EditorView，每个实例持有不同 `ViewId`。
- **EditorView 不挑活动 view**——`active view` 状态由 `ViewSet` 维护。EditorView 获得 focus 时通过命令（如 `editor.activate_view`）通知 ViewSet 更新 active。
- **EditorView 不知道 split tree**——split 决策、尺寸分配、聚焦切换都在 EditorGrid 层。EditorView 内部只关心"我这一个视图怎么显示和响应"。

### 2.5 渲染策略（第一版最小可用）

第一版按 viewport 渲染：

```
1. 从 view_set 取出 view（ViewId 索引）
2. 读 view.ViewportState 决定可见行范围
3. 从 workspace 取 Buffer，调 zom-engine 的 viewport slicing API 取可见文本
4. 渲染层次（自底向上）—— 6 阶段绘制契约：
   1) 行背景        active line / diff hunk 整段背景
   2) 范围背景      selection / search match / AI 提案区间
   3) 字符层        字色 / 字重 / 斜体 / 下划线 / 波浪线
   4) 字符叠加      inline ghost text / inlay hint
   5) cursor / IME composition
   ─（与文本层并列的独立竖列）─
   6) gutter        行号 + 行级装饰图标（断点 / git diff / 诊断 glyph 等）
5. 字体度量缓存按 ui_font_size / buffer_font_size 失效
```

阶段顺序固定，阶段之间是绘制顺序（后画的覆盖前画的）；阶段内部不同 layer 来源之间才谈 z-order。

第一版必填：阶段 1（仅纯背景色 / 无 diff）、阶段 2 的 selection、阶段 3（仅字色 / 无字重斜体下划线波浪线）、阶段 5、阶段 6（仅行号 / 无装饰图标）。其余（搜索 / AI 区间、字符叠加、gutter 装饰图标）是 P3+ 扩展槽位，**槽位本身必须在第一版就留出**——第一版不实现，但渲染管线的 6 阶段结构不能等接入时再改。

所有装饰来源遵循"语义键 + theme 解析"契约：layer payload 只携带语义键（如 `SyntaxToken { kind }`、`DiagnosticMark { severity }`），desktop 侧统一查 theme 解析为颜色 / 字重 / 下划线 / inline 文本等具体绘制指令。换主题不重算 layer；跨平台（如未来的终端版）能复用同一份 payload。

**observe 哪些 entity 触发 re-render**：

- `workspace`（buffer 内容变化 + buffer 上挂载的 metadata layer 变化 + buffer.search 状态变化）
- `view_set`（光标 / 滚动 / fold 变化）

P3 接入 fold / projection 时，第 3 步从 `ViewportSlice` 升级为 `ProjectedRange`——这是一处单点替换。

### 2.6 键盘输入路径

```
GPUI key event
    ↓
shell::platform::keyboard 解码为 KeyChord
    ↓
EditorView.on_key_down 接到 KeyChord
    ↓
向上派发：调用 on_request_command（实际由组合根的 Keymap 解析）
    ├─ 匹配 Command       → CommandQueue → handler
    └─ 不匹配 + 可打印字符 → 包装为 editor.insert_text 命令 → CommandQueue
    ↓
CommandExecutor 排空队列，handler 调 workspace/view/engine API
    ↓
对应 Entity notify
    ↓
EditorView observe 触发 re-render
```

**EditorView 不持有 Keymap 实例**——Keymap 是组合根服务，EditorView 通过回调机制将 KeyChord 上抛后由组合根派发。

### 2.7 IME 接入

按最小闭环：

| IME 事件 | 通道 |
|---|---|
| `start` | 命令 `editor.composition_start` |
| `update` | **直接通道**：EditorView 直接调用 `view.composition_mut().update(...)`；不走命令队列以避免每次按键都排队 |
| `commit` | 命令 `editor.composition_commit` |
| `cancel` | 命令 `editor.composition_cancel` |

GPUI IME event → `shell::platform::ime` 适配 → 上述命令 / 直接通道。

`CompositionUiState`（EditorView 自己持有的局部状态）只承载渲染所需的临时显示信息（如下划线区段）；权威的 composition 状态在 `zom-view::View` 中。

### 2.8 鼠标输入

第一版三类鼠标交互：

| 交互 | 通道 | 说明 |
|---|---|---|
| 点击 → 移动光标 | 命令 `editor.set_cursor` | 鼠标坐标 → 字符位置由 desktop 算（字体度量缓存） |
| 拖拽 → 选区 | 命令 `editor.set_selection`（高频可改直接通道，第一版先走命令） | drag 起始 / 终止位置打包 |
| 滚轮 → 滚动 | **直接通道**：EditorView 直接改 `view.viewport_mut()` | 与 IME update 同理，高频不走命令 |

**字体度量**：desktop 缓存当前 `buffer_font_size` 下的字符宽度表（等宽字体下是单一值；变宽字体需按 grapheme cluster 缓存）。字号变化时缓存失效。坐标 ↔ 字符位置转换抽到 `logic.rs`，可裸单测。

### 2.9 滚动权威

`view.ViewportState` 是**唯一权威**。GPUI 的 scroll handle 只是 UI 触发源。

```
用户滚轮  → GPUI scroll event → 直接通道改 view.ViewportState → re-render
命令 / 代码改 ViewportState → re-render → GPUI 渲染到新位置
```

不允许两个权威。GPUI 的内部滚动状态被 EditorView 视为"无状态的事件源"，所有"当前滚到哪了"的真相只在 view。

### 2.10 留给 P3 / P4 的扩展点

| 阶段 | 接入方式 | EditorView 侧的改动 |
|---|---|---|
| P3 fold / projection | viewport 切片从 `ViewportSlice` 改为 `ProjectedRange`（zom-engine 已有） | 2.5 第 3 步单点替换；新增 fold 命令 handler 不在 EditorView 写 |
| P3 语法高亮 | 宿主侧 highlighter 异步算 tokens，通过 `MetadataLayer<SyntaxToken>` 挂到 buffer 上；payload 只携带语义键（`TokenKind::Keyword` 等），desktop 查 theme 解析颜色 | 阶段 3（字符层）按可见区间查 syntax layer，逐 glyph 应用解析后的字色 / 字重 |
| P3 搜索高亮 | 由 `WorkspaceBuffer.BufferSearch` 持有 query / `SearchResult` / current hit（per-buffer 共享，分屏看同一 buffer 时多 view 共用）；engine 仅提供纯查询 API（`search_in_text` / `SearchResult::try_remap`）。**重算时机**：编辑期间仅 `try_remap` 推进现存命中，不主动发现新命中；query 变化、或 find-next 发现 result 落后于当前 buffer.version 时才同步 re-run | 阶段 2（范围背景）从 `buffer.search().result.ranges()` 取可见命中绘制；current hit 加强调样式 |
| P3+ gutter 装饰 | 复用 `MetadataLayer`，行级用零宽锚点（行首 + `Stickiness::After`），多行用真实 range；失效策略 `invalidate_when_touched_by_deletion`；payload 只携带语义键 | desktop 维护"路由到 gutter 的 layer kind"硬编码常量表（`breakpoint` / `git-diff` / `diagnostic-mark` / `bookmark` 等），阶段 6 按表渲染图标 |
| P4 AI 提案预览 | 透过 `MetadataLayer` 承载 ghost text / diff hunks；payload 只携带语义键 | ghost text 落阶段 4（字符叠加）；diff hunk 整段背景落阶段 2；按 layer kind 路由 |

**第一版 EditorView 必须已具备这些扩展点**：

- viewport 切片是单点函数调用（2.5 第 3 步），不内联到 render
- 渲染层次允许新增装饰层（2.5 第 4 步是有序列表，新增层只是插入新项）
- selection 渲染按 `SelectionSet`（zom-engine 模型），天然支持多 cursor

### 2.11 与其他 L3 组件的协作

| 组件 | 协作形式 |
|---|---|
| `TabStrip` | EditorView 不直接知道。TabStrip 操作 ViewSet active view；EditorView 跟随 |
| `FileTree` | EditorView 不直接知道。FileTree 点击文件触发命令（`workspace.open_file` + `view.create_for_buffer` 等组合），由组合根 handler 完成 |
| `StatusBar` | EditorView 不直接知道。StatusBar observe `ViewSet` / `Workspace` 自行读取当前 view 的光标位置、文件 dirty 状态等 |
| `CommandPalette` / `FindReplace` 等 Surface | EditorView 不直接知道。Surface 通过命令派发；EditorView 因 Buffer / View 变化自动 re-render |

**所有跨 L3 协作都通过共享底层 entity 完成**——没有 L3 之间的直接调用，没有 EditorView 持有其他 L3 的句柄。

### 2.12 测试要求

EditorView 是 L3 组件，必须 `#[gpui::test]` 覆盖以下场景：

| 场景 | 验证 |
|---|---|
| 基本渲染 | 给定 Buffer + ViewportState，渲染输出包含可见行文本 |
| 光标移动命令 | 派发 `editor.move-left` → view 的 SelectionSet 更新 → EditorView 触发 re-render |
| 文本输入 | 派发 `editor.insert_text` → buffer 更新 → EditorView 显示新文本 |
| IME 闭环 | start → update → commit 后，buffer 包含提交文本，CompositionUiState 已清空 |
| 滚动 | 改 `view.ViewportState` 后渲染可见行范围变化 |

**字体度量、坐标 ↔ 位置转换**抽到 `logic.rs`，纯函数裸单测；不依赖 GPUI。

EditorView **不重测底层 crate 的领域逻辑**——SelectionSet 怎么 movement、Buffer 怎么 undo、Keymap 怎么解析，都是底层 crate 的 contract test 已覆盖的。

### 2.13 第一版不做的事

- **分屏 split 内部布局**（属 EditorGrid 的 split tree）
- **跨 view 的状态协调**（属 ViewSet / 组合根）
- **fold / 投影 / 语法高亮 / 搜索高亮 / gutter 装饰图标 / AI 提案的具体实现**（P3 / P4）
- **mini-map / 缩略图**（推迟）
- **行内插件 / 代码动作 UI**（推迟到插件系统）
- **代码折叠按钮 / gutter 装饰的扩展点**（与 P3 一起设计）

## 三、Dock 与 Panel

### 3.1 面板模型

面板通过停靠区域承载。面板自身描述能力与身份，位置由布局状态决定。

```rust
struct PanelDescriptor {
    id: PanelId,
    title: String,
    icon: Option<IconId>,
    kind: PanelKind,
    capabilities: PanelCapabilities,
}

struct PanelPlacement {
    panel_id: PanelId,
    area: DockAreaId,
    group: Option<PanelGroupId>,
    order: usize,
    active: bool,
}

enum DockAreaId {
    Left,
    Right,
    Bottom,   // 指 CenterColumn 内的 BottomDock，不是窗口级 BottomBar
}
```

第一版停靠区域采用**单栈模型**：

```rust
struct PanelStack {
    panels: Vec<PanelId>,
    active: Option<PanelId>,
}
```

需要支持区域内拆分时，再升级为分组树（第二版）：

```rust
enum PanelGroup {
    Stack(PanelStack),
    Split {
        axis: SplitAxis,
        children: Vec<PanelGroup>,
    },
}
```

### 3.2 整体落位

```
L4 Region        LeftDock / RightDock / BottomDock
                 容器：持有 PanelStack（panel id 列表 + active）
                 持有 Dock 自身的折叠 / 尺寸状态
                 按 active panel id 取实例渲染

L3 Composite     每个 Panel（FileTree / Outline / Search / Terminal / ...）
                 普通 L3 组件
                 不抽 trait：具体结构体形态，shell 层硬编码组装

PanelHost        每窗口持有；保存该窗口所有 panel 实例（Entity）
                 由组合根创建；Dock 按 id 从此取实例
```

### 3.3 Panel 是 L3，不抽 trait

第一版 Panel 是普通 L3 组件。**不为不存在的插件预先抽 `PanelProvider` trait**。

Panel 的图标、命令与短 id 由 `PanelId` 集中维护，避免面板身份字符串散落：

```rust
// shell/features/panels/mod.rs
pub(crate) fn icon_path(self) -> &'static str {
    match self {
        PanelId::FileTree => "icons/panels/file_tree.svg",
        // ...
    }
}
```

PanelId 由 desktop 定义为闭合 enum；需要给命令系统传递短字符串时，通过 `PanelId::command_str_id()` 显式投影。

### 3.4 PanelHost：每窗口持有所有 panel 实例

```rust
// shell/features/host.rs
pub struct PanelHost {
    file_tree: Entity<FileTreePanel>,
    outline: Entity<OutlinePanel>,
    search: Entity<SearchPanel>,
    terminal: Entity<TerminalPanel>,
    // ... 第一版硬编码列表
}

impl PanelHost {
    pub fn panel_element(&self, id: PanelId, cx: &mut App) -> Option<AnyElement> { ... }
}
```

`PanelHost` 由 app 组合根在创建窗口时一次性实例化全部 panel。Dock 按 PanelId 从 PanelHost 取元素。

**不引入 `PanelRegistry` 动态注册表**——第一版面板列表硬编码；注册表是为不存在的扩展付费。将来插件系统真要 panel 扩展时（**插件能力锁明确禁止插件 panel**）再演化。

### 3.5 PanelStack 切换语义

| 命令 | 行为 |
|---|---|
| `panel.toggle.<id>` | 若已 active 则置 None（关闭）；否则置 Some(id) |
| `panel.activate.<id>` | 无论之前是什么，置 Some(id) |
| `panel.close.<id>` | 若当前 active 是 id 则置 None；否则忽略 |

第二版升级为 `PanelGroup` tree（栈 + split），支持同 Dock 内多 panel 同时显示。

### 3.6 Panel 固定归属

第一版固定映射（用户不能拖动跨 dock）：

| Panel | 固定归属 Dock |
|---|---|
| FileTree | Left |
| VersionControl（第二版） | Left |
| Outline | Right |
| Search | Bottom |
| Terminal（第二版） | Bottom |
| Debug（第二版） | Bottom |

归属由对应 dock 模块声明：`left_dock.rs` 声明左侧 panel，`bottom_dock.rs` 声明底部 panel，`right_dock.rs` 声明右侧 panel。settings 可覆盖同 dock 内顺序，但不可改 panel 归属 dock（第一版）。

### 3.7 Dock 状态归属

| 状态 | 持有位置 |
|---|---|
| Dock 显隐（整个 Dock collapsed） | 每窗口（L4 Region 持有） |
| Dock 尺寸（宽 / 高） | 每窗口 |
| Dock 内 active panel | 每窗口（PanelStack 持有） |
| Dock 内 panel 顺序 | settings（用户级 / workspace 级覆盖） |

总原则：偏好类（panel 顺序）跨窗口共享；"当前在做什么"（active panel / 折叠 / 尺寸）按窗口持有。

### 3.8 折叠与尺寸交互

- **折叠**：通过 `panel.toggle.<id>` 命令切换 active 为 None；Dock 检测到 active 为 None 时自动 collapse
- **尺寸**：拖拽 Dock 边缘——L4 Region 内部交互；**不走命令**（高频拖拽）；直接改 `WorkbenchController` 里的 size 状态

### 3.9 BottomBar 与 Panel 的关系

BottomBar **不是 Dock**——它是窗口级外壳（见 §一.6）。

BottomBar 里的"面板切换 slot"（`bottom-bar-file-tree` / `bottom-bar-outline` 等）是 `panel.toggle.<id>` 命令的视图：

```
用户点击 BottomBar 里的 file_tree icon
    ↓
派发 panel.toggle.file_tree
    ↓
zom-command handler：emit HostEffect::TogglePanel("file_tree")
    ↓
ShellView：交给 WorkbenchController 找到所在 Dock → 更新 PanelStack.active / collapsed
    ↓
窗口 refresh → re-render
```

**BottomBar 不知道 panel 是什么**——它只知道 CommandId。这条切割让 BottomBar 与 Dock 完全解耦。

### 3.10 EditorGrid 与 Dock 的边界

EditorGrid **不是 Dock**，不走 Panel 模型。它独占 CenterColumn 上半部（见 §一.9）：

```
TopBar
─────────────────────────────────────────────
LeftDock │ EditorGrid              │ RightDock
         │ ─────────────────────── │
         │ BottomDock              │
─────────────────────────────────────────────
BottomBar
```

BottomDock 只占中间列下半部，不侵入左右 Dock。

EditorGrid 内部是 split tree + tab group（§二.1），由 EditorGrid L4 自己实现。EditorView（§二.2）是 EditorGrid 内的叶子。

### 3.11 第一版具体 Panel 清单

| Panel | 固定归属 Dock | 第一版功能 |
|---|---|---|
| FileTree | Left | 显示 workspace 文件树；点击触发 `workspace.open_file` |
| Outline | Right | 占位骨架；LSP 接入后填充符号大纲 |
| Search | Bottom | 当前文件与跨文件搜索 UI（绑定 zom-engine 的搜索能力，P3） |

推迟到第二版及以后：VersionControl / Terminal / Debug / KeyboardShortcuts。

第一版完整实现的 Panel 数量保持小（3 个）；新增 Panel 不需要修改其他 Dock 的代码——只需在 PanelHost 加字段、在目标 dock 模块的 `PANELS` 列表加入归属、注册 `panel.toggle.<id>` 命令。

### 3.12 注册流程

每窗口创建时：

```
1. 实例化 PanelHost（含全部 panel）
2. 创建 WorkbenchController
3. 创建 LeftDock / RightDock / BottomDock（按各 dock 模块的 PANELS 装入 PanelStack）
4. 应用 settings 覆盖（panel 顺序、初始 active、初始折叠 / 尺寸）
5. 注册 panel 命令 catalog；handler 只 emit HostEffect
6. ShellView 收到 HostEffect 后更新当前窗口的 WorkbenchController
```

panel 命令的**解释**是窗口范围的：同名 `HostEffect::TogglePanel` 在不同窗口里操作各自的 `WorkbenchController`。

### 3.13 第一版明确不做

- panel 跨 dock 拖动
- panel 浮动（脱离 dock）
- 同 dock 多 panel 同时显示（PanelGroup tree）
- 用户自定义 panel（等插件系统；但插件能力锁明确禁止插件 panel）
- panel 内拆分布局

## 四、SurfaceLayer 与 BubbleLayer

### 4.1 SurfaceLayer 语义

`SurfaceLayer` 承载临时但可交互的悬浮面板，统一称为 **Surface / 浮面**。浮面不进入持久布局。

Surface 的共性只在外壳：召唤入口、定位、窗口边界吸附、层级、关闭策略与焦点归还。具体内容、功能、内部状态和焦点目标都由打开它的调用方决定，SurfaceLayer 不理解也不枚举业务内容。

典型浮面：

```text
CommandPalette / QuickPicker / ContextMenu / InlinePopover / InspectorPopover
```

浮面必须有明确召唤入口。默认情况下，浮面锚到召唤它的那个具体元素，而不是锚到 TopBar / BottomBar / Dock 这类容器：

```rust
enum SurfaceAnchor {
    Invoker(ElementId),
}
```

`SurfaceLayer` 不应演化成任意窗口系统。第一版只保留明确形态：命令面板、快速选择器、上下文菜单、内联弹出层、检查器弹出层。

### 4.2 BubbleLayer 语义

`BubbleLayer` 承载轻量提示，不进入持久布局，也不承担复杂交互。

典型类型：

```rust
enum BubbleKind {
    Tooltip,
    DiagnosticHover,
    ParameterHint,
    Toast,
}
```

基础规则：

- `Tooltip` 只解释标记、图标和其他短语义对象。
- `DiagnosticHover` 跟随编辑器位置。
- `ParameterHint` 跟随光标。
- `Toast` 固定在窗口角落。

当气泡需要承载确认、表单、复杂 AI 回复或可持续交互时，应升级为 `SurfaceLayer` 中的浮面。

### 4.3 Surface 与 Bubble 的区分

Surface 中文称为 **浮面**，Bubble 中文称为 **气泡**。二者都属于悬浮层，但不是同一种组件：

- Surface 是可交互悬浮面板。框架只提供外壳能力：入口定位、层级、关闭策略与焦点归还；内容、状态、功能和焦点目标完全由打开方持有。
- Bubble 是轻量提示。框架统一它的内容模型、视觉样式与生命周期；调用方只提供文本、级别、少量动作和超时等数据。

| 维度 | Surface | Bubble |
|---|---|---|
| 可交互 | 是 | 否 |
| 承载焦点 | 是 | 否 |
| 关闭机制 | Esc / 显式 close / 失焦 | 自动 / 鼠标移开 / 超时 |
| 同时活跃 | 第一版最多 1 个 | 多个（不同类型可并存） |
| 例 | 命令面板、context menu、内联弹窗、inspector | tooltip、diagnostic hover、parameter hint、toast |

升级判定：Bubble 需要承载确认 / 表单 / 复杂交互时升级为 Surface。

### 4.4 渲染层次与 z-index

```
[10] WorkbenchFrame    含 TopBar / BottomBar / Body（Dock + EditorGrid + BottomDock）
[20] SurfaceShell      SurfaceManager 当前活跃的 Surface
[30] BubbleShell       BubbleManager 当前活跃的所有 Bubble
```

z-index 是 desktop 内固定常量，不暴露给 L3 组件。

### 4.5 SurfaceManager / BubbleManager

每窗口持有一对 Manager：

```rust
pub struct SurfaceManager {
    active: Option<ActiveSurface>,    // 第一版单 Surface 独占
}

pub struct BubbleManager {
    bubbles: HashMap<BubbleId, ActiveBubble>,   // 多 Bubble 并存
}
```

Manager 是 GPUI Entity；observe 触发对应 Shell re-render。

**第一版同时最多 1 个 Surface**——打开新 Surface 自动关闭旧的（"模态独占"）。第二版考虑允许嵌套，但需评估能否避免"无限堆叠"问题。

### 4.6 SurfaceShell / BubbleShell

两个 Shell 都是 desktop 内的特殊渲染层，挂在 WorkbenchFrame 之上：

- 从对应 Manager 读 active 状态
- 解析 invoker → 屏幕坐标
- 渲染 Surface / Bubble 实例

Shell 不是 L4 Region——它们不参与 WorkbenchFrame 的 layout，是独立 portal 层。

### 4.7 Surface 内容由调用方拥有

CommandPalette / QuickPicker / ContextMenu / InlinePopover / InspectorPopover 等都是普通 L3 组件。**它们不知道自己是 Surface**——只是普通组件。

功能模块创建或复用这些 L3 实例，并提供 `SurfaceRequest`。`SurfaceRequest` 携带 id、召唤入口、placement 与最终要渲染的 element。SurfaceShell 不按固定枚举匹配业务内容，也不直接 import 某个 feature 模块。新增一种 Surface 不应修改 SurfaceShell。

Bubble 不走这条规则。Tooltip / Toast / DiagnosticHover / ParameterHint 由 BubbleManager 接收结构化数据，统一渲染为气泡。

### 4.8 Anchor 解析

| SurfaceAnchor | 屏幕坐标计算 |
|---|---|
| `Invoker(ElementId)` | 通过 anchor registry 查询该入口元素的渲染矩形 |

入口几何采集在 `shell/surfaces/anchor_registry.rs`，入口元素通过 `track_surface_anchor` 标记自己。SurfaceShell 只消费这些入口矩形，不要求 TopBar / BottomBar / Dock 依赖 Surface 语义。

Bubble 的位置规则：

| BubbleKind | 跟随 |
|---|---|
| Tooltip | hover 目标 element 附近 |
| DiagnosticHover | EditorPosition |
| ParameterHint | 当前光标位置（EditorPosition） |
| Toast | 窗口角落（固定，多 toast 纵向堆叠） |

### 4.9 Surface 生命周期

```
1. 派发命令 surface.<id>.open（如 command-palette.open）
2. handler 创建或复用 Surface 实例 → SurfaceManager.active = Some(...)
3. Manager notify → SurfaceShell re-render → Surface 显示并获得焦点
4. 用户交互
5. 关闭触发：
   - Esc 键（全局键位 → 命令 surface.dismiss）
   - 显式命令（如选择命令面板的某项后自派发 surface.dismiss）
   - 失焦（窗口失焦或点击 Surface 之外区域）
6. SurfaceManager.active = None → SurfaceShell re-render → Surface 隐藏
```

Surface 关闭时焦点回到先前 focus 目标（SurfaceManager 在打开时记录）。

### 4.10 Bubble 生命周期

| 触发 | 关闭 |
|---|---|
| Tooltip：hover 进入 element | hover 离开 |
| DiagnosticHover：鼠标停留在编辑器位置 N ms | hover 离开 / 光标移动 |
| ParameterHint：编辑函数调用括号内 | 光标退出参数区 |
| Toast：程序派发 `toast.show` | 超时（默认 3 秒）/ 显式 dismiss / 数量上限替换 |

### 4.11 与 GPUI 内建 Tooltip 的关系

zom-desktop 现有 Glyph tooltip 通过 GPUI 内建 `Tooltip` 实现。第一版**两套并存**：

| 场景 | 选择 |
|---|---|
| 图标 hover 短文本 | GPUI 内建 Tooltip |
| 跨函数生命周期 / 程序化触发 / invoker 解析 | BubbleManager |

第二版若 BubbleManager 稳定，再考虑统一。

### 4.12 与 EditorView 的协作

Surface 中与 EditorView 位置强绑的（如 InlinePopover、ContextMenu）通过对应的召唤入口获取屏幕位置；需要按编辑器位置召唤时，由 EditorView 或相关功能提供一个临时 invoker rect。

**EditorView 不知道 Surface 存在**——它只提供可被定位的入口或几何信息，Surface 侧按 request 消费。

### 4.13 第一版不做

- 模态独立窗口（与 Surface 不同；推迟）
