# 架构体检

架构体检默认是只读任务。目标不是罗列风格偏好，而是找出已经造成错误依赖、重复事实、生命周期不清或维护成本的结构性问题。

## 建立目标边界图

围绕用户指定范围建立一份紧凑事实图：

- 模块或 crate 的稳定职责；
- 提供方与真实消费方；
- Cargo 和 Rust 模块依赖方向；
- 状态由谁创建、拥有、修改和消费；
- 生命周期从何时开始、由谁结束；
- 每项业务事实的权威数据源及派生数据；
- action、event、callback、subscription 和异步任务如何跨边界流动。

优先沿实际调用和类型关系阅读，不根据文件名猜测。涉及 Zed 已解决的编辑器能力时，对照其模块职责、所有权和生命周期，但同时记录 Zcv 范围不同之处。

## 检查维度

### 边界与依赖

- UI 是否持有本应属于模型或项目层的业务事实。
- 底层 crate 是否反向依赖具体产品能力或视图。
- 单一消费方代码是否被提前提升到共享层。
- 多个真实消费方是否反而复制相同原语或彼此依赖。
- 门面是否暴露内部组织，或用中间转发掩盖错误归属。

### 状态与生命周期

- 同一事实是否存在多个可写副本、双写、双向同步或补偿修复。
- 派生数据是否被当成第二权威源并能反向修改模型。
- 所有者是否无法说明，或依赖全局状态、隐式注册、临时桥接。
- subscription、task、focus 或资源句柄是否绕过正常创建和销毁生命周期。
- 默认策略是否藏在执行路径深处，而非由负责决策的模块显式确定。

### 抽象与范围

- 抽象是否没有第二个真实消费者、实现或当前需求。
- 接口是否只是单一调用方需求的镜像，没有形成稳定边界。
- fallback、兼容路径和特殊分支是否在维持错误抽象。
- 是否复制了 Zed 中只服务协作、远程、LSP 或其他 Zcv 未引入能力的基础设施。
- 配置、扩展点或错误恢复是否仅服务推测中的未来场景。

不要因为 trait 只有一个实现就自动判定多余。若它明确承担依赖倒置、异构类型擦除、稳定协议或生命周期隔离，应按其实际边界价值判断。

## 发现标准

每条发现必须包含可定位的代码证据和当前影响。按以下顺序组织：

1. 严重度与简短标题。
2. 文件和最窄行范围。
3. 当前数据流或依赖事实。
4. 架构根因，而不只是表面症状。
5. 最小修正方向及需要一并更新的调用方、测试或文档。

无法证明实际影响的想法放弃，不用“可能”“也许”填充报告。若没有结构性问题，明确说明已检查范围和未发现问题；同时列出因环境或范围限制未覆盖的部分。
