# 纯粹底层编辑引擎能力

> 目标：定义 `zcv-engine` 作为工业级、单机、纯文本编辑引擎底座应承担的长期能力边界。

`zcv-engine` 提供可靠的纯文本编辑核心，维护文本、坐标、事务、版本、历史、快照、
通用区间追踪和底层验证等事实。

本文只写稳定能力边界和架构方向，不记录实现阶段、细碎清单或完成流水账。当前状态和建议命令见 `docs/STATUS.md`。

## 判断标准

一项能力进入本 crate，必须至少满足以下判断：

- 它直接维护编辑引擎不变量。
- 它属于文本存储、文本编辑、坐标、事务、历史、快照、通用追踪、逻辑文本读取切片或底层验证。
- 它是宿主无关的通用底层事实，而不是某个产品层功能。

只是“宿主可能会用到”的能力，不默认进入 `zcv-engine`。

## 负责范围

- 文本存储与局部编辑。
- `ByteOffset` / `TextRange` 为核心的强类型坐标模型。
- 事务提交、变更映射、Delta 事件和原子失败。
- Undo / Redo、历史节点、事务记录与回放。
- 只读快照、版本绑定和本地读写边界。
- Selection / SelectionSet 数据原语、PositionMap 映射与纯文本边界查询。
- Anchor、Mark、TrackedRange、VersionedResult、VersionedRangeSet 等通用区间追踪原语。
- 逻辑文本 Viewport slicing。
- 单 Buffer 同步匹配、替换和版本化结果承载。
- 文件文本进入和离开 Buffer 时的编码、换行、保存点和 reload 边界。
- 大文件策略、历史预算、防御性错误处理、property / fuzz 等验证能力。

## 边界

本 crate 不承载 UI、产品业务、项目编排、协议集成、任务调度和网络协作。宿主可能
使用某项能力，不足以成为它进入引擎的理由；只有直接维护纯文本内核不变量的通用事实
才属于这里。

## 核心架构原则

- `ByteOffset` 是唯一权威、持久的核心编辑坐标。
- `CharOffset`、`Utf16Offset`、`Line`、`LogicalColumn`、`DisplayColumn`、grapheme 边界都是派生坐标或视图坐标。
- Public API 不用裸 `usize` 表达领域坐标。
- `TextRange` 必须保持 `start <= end`。
- `Transaction` 必须绑定 `base_version`，提交时必须校验版本。
- 事务失败必须保持原子性，不部分修改文本、版本、dirty、history 或订阅状态。
- Buffer 只保存共享文本状态，不保存调用方的当前选区或其他局部交互状态。
- engine 只接收已经形成的文本编辑，不解释编辑操作的产品来源。
- `ChangeSet` / `Delta` / `PositionMap` 只能由已验证编辑构造。
- `Snapshot` 必须只读、低成本、绑定 `BufferVersion`，并可跨线程读取。
- 生产存储使用 `RopeyStorage`，不自研 Rope / Piece Table / Piece Tree。
- 测试 reference model 可以使用简单字符串模型，但不进入生产存储核心。
- 目录模块是实现分层；长期 public API 由 crate root 统一导出。

## 能力域

### 文本存储与文件边界

引擎负责把外部文本安全载入 Buffer，并以适合大文件和局部编辑的结构保存、读取和修改文本。文件路径、编码、BOM、换行风格、保存点、dirty 状态、reload 和只读策略属于底层边界；文件监听、冲突交互和保存 UI 不属于本 crate。

### 坐标与文本数学

核心编辑语义以 UTF-8 byte offset 表达。其他坐标只通过显式转换进入编辑模型。坐标系统需要保护 UTF-8、UTF-16、CRLF、tab 展开、display column、word / subword / symbol boundary 以及可恢复错误边界。

### 编辑事务与变更映射

所有文本变异应归一化为已排序、不重叠的 edit 列表，并通过事务提交。普通事务提交统一返回 `TransactionOutcome`，承载事务身份、历史归属、Delta 和 ChangeSet；提交同时产生版本推进、PositionMap、changed ranges 和可选历史记录。引擎不关心事务来源是键盘、鼠标、格式化器还是外部系统。

### 历史、快照与版本

Undo / Redo 负责恢复文本并返回被回放历史节点的规范 `TransactionId`。
HistoryEntry 和 TransactionRecord 只保存文本事务事实，不绑定调用方局部状态。
历史节点、历史预算、事务记录、回放和版本化结果都围绕已提交文本事务展开。
Snapshot 是只读版本事实，用于并发读取、搜索和外部结果过期判断。

### 光标与选区原语

Selection / SelectionSet、归一化、PositionMap 映射以及 word / subword / symbol 边界
是宿主无关的数据与纯算法。Buffer 只接收已形成的 Transaction，不保存当前选区，
也不解释移动、删除或缩进等用户操作语义。

### 区间追踪与外部结果承载

任何需要跟随文本变化的位置或范围，都不应只是裸 offset。Anchor、Mark、
TrackedRange、VersionedResult 和 VersionedRangeSet 负责表达版本绑定、范围跟随、
失效策略、payload 承载和 UTF-16 边界转换。业务类别应保留为泛型 payload 或
自定义 kind，不在引擎中膨胀成专用 adapter。

### 读取切片与变更订阅

引擎提供版本绑定的 `Snapshot`、逻辑文本 Viewport slicing、`Anchor` /
`TrackedRange`，以及每个消费者独立累积的 `TextSubscription` / 可组合
`TextPatch`。事件只负责唤醒；消费者读取当前 Snapshot，再消费自己的 Patch。
不同消费者可以按各自节奏推进，同时保持连续版本和变更坐标语义。

### 单 Buffer 搜索与替换

当前 Buffer 内同步 literal / regex 匹配、结果版本绑定、range tracking、单次替换和
replace all 原子事务属于文本编辑底座。跨 Buffer 编排不进入本 crate。

### 防御、性能与验证

工业级底座必须对异常输入、巨大文本、超长行、超大事务、历史内存增长、版本冲突和边界坐标保持可诊断、可测试、可恢复。验证应覆盖机器契约、随机编辑、差分测试、性能基准和必要的可观测指标。
