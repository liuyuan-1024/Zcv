## 1. 单 VCS（git）设计贯穿数据层与 UI

- **状态**：接受（有意绑定）。
- **决策**：UI（项目树、版本控制面板）直接消费 `zcv-git` 的具体类型——
  `FileStatus` / `StatusCode` / `RepositorySnapshot`，不引入 VCS 抽象层。
  同一原则适用于 `zcv-multi-buffer` 直接依赖 `zcv-language`、`editor` 直接依赖
  `zcv-multi-buffer` / `zcv-project` 的具体类型，不做 trait 擦除。
- **背景**：Zed 同为单 VCS 设计（git only）。抽象层（VCS trait + 查询 API 泛化）的
  收益完全建立在"第二个 VCS"上，该需求不存在；为不存在的消费方预付抽象成本，违反
  "不为一次性使用的代码编写抽象"原则。单一真实消费者时，接口层 = 该消费者需求的
  镜像，没有抽象价值。
- **替代方案被否**：VCS trait + 查询 API 泛化——为不存在的第二个 VCS 预付抽象成本。
- **触发重构的条件**：出现第二个 VCS 需求时，第一步先**收敛 UI 到 `Project` 查询
  API**（`git_statuses_for_rows` 是现成雏形），让 UI 只依赖 Project 的查询边界，
  再引入后端抽象；而不是先铺抽象层。

## 2. 输入级编辑行为用「语言配置数据 + 编辑器内建行为引擎」，不建插件钩子

- **状态**：接受（对齐 Zed）。
- **决策**：自动闭合括号/引号等输入行为由语言数据表声明（`AutoClosePair`：start/end/close/surround），
  编辑器在 `replace_text` 输入枢纽内建行为解释器（自动补全、跳过已存在闭合符、包裹选区、退格删对）。
  新增一种配对 = 语言数据表加一行，不碰编辑器代码。
- **背景**：Zed 的扩展系统没有输入级钩子（插件只能贡献语言配置数据），行为代码不可扩展；
  vim 的 keystroke observer 是 gpui 内部机制。Zed 用 `[[brackets]]` 配置表 + `handle_input` 单一行为枢纽解决同类需求。
- **替代方案被否**：通用「输入转换规则表」（`{ typed, insert, cursor, skip }`）——`not_in` 语法上下文、
  换行行为等语义字段表达力更强，通用规则表会把复杂场景逼回代码；wasm/动态库插件钩子——Zed 自己都没有，现阶段过度设计。
- **触发重构的条件**：出现语法树驱动的特例行为（如 JSX 标签自动闭合）时，
  对齐 Zed 作为独立内建模块挂在输入枢纽末尾，仍不引入插件机制。

## 3. MultiBuffer 承载项目搜索与 Git 项目差异

- **状态**：接受（第二阶段已落地）。
- **决策**：Editor 始终持有 `zcv-multi-buffer::MultiBuffer`，DisplayMap 统一接收
  `MultiBufferSnapshot`；文件编辑使用 singleton，项目搜索结果使用只读 ordered excerpts，
  Git 项目差异使用按路径排序、由 hunk 扩展上下文得到的可编辑 excerpts。
  excerpts 保留来源文档、上下文范围、真实命中范围，以及组合坐标到源文件坐标的映射。
  Workspace Item 把标签身份路径、活动路径、文档能力和保存行为拆开，
  不再用单个 `file_path + buffer` 隐式定义所有 Item。`Item::multi_buffer` 与
  `PreviewDocument::multi_buffer` 是 Workspace 和 Preview 唯一的文本实体接口；Editor
  不缓存底层 `Entity<Buffer>` 或独立 `SyntaxSnapshot`，组合快照和变化订阅均由
  MultiBuffer 提供。GitStore 的状态快照是项目差异文件集合的唯一数据源；Project/BufferStore
  继续拥有真实文件文档，项目差异 Item 只组合并定位这些文档。行级 hunk 仍由 GitStore
  按源路径持有，Item 在注入 Editor 前投影到组合坐标，不复制一套 Git 状态。
- **背景**：项目搜索是首个多文档消费者。其核心链路对齐 Zed：Project 后台搜索
  各文件并产出范围，合并上下文后写入 MultiBuffer ordered excerpts，再由中心
  `zcv-search` 内的结果 Editor 展示。项目搜索 Item 与普通 Editor 共同实现
  `SearchableItem`。对齐 Zed，BufferSearchBar 与 ProjectSearchBar 是两个独立状态机，
  只复用 `search_bar.rs` 的 UI/交互实现、快捷键上下文和查询协议；切换到结果文件不会把
  项目查询泄漏为文件内搜索。项目搜索声明为只读目标，SearchBar 保留替换 Button 以维持
  与文件内搜索相同的布局，但将其设为禁用且不展开替换行。Zcv 暂不加入远程、协作、
  include/exclude 查询过滤器、搜索历史或复杂 excerpt 编辑语义。Git 项目差异对齐 Zed
  `ProjectDiff` 的核心所有权与复用行为：源 Buffer 保持完整且由 Project 持有，MultiBuffer
  只投影 hunk 与两行上下文；版本管理面板激活任一条目时复用同一个 Item 并定位文件；
  当前不移植 split diff、按 hunk 暂存、分支比较和 review 等尚无消费方的能力。
- **替代方案被否**：完整移植 Zed MultiBuffer——引入没有消费者的状态与复杂度；只在未来
  消费者出现时再改 Editor——把组合文档边界继续泄漏到显示与 Workspace 层。
- **触发重构的条件**：项目差异需要按 hunk 暂存/恢复或 split diff 时，再把每源 diff 元数据
  提升为 MultiBuffer 的一等变换；不提前加入协作、远程、LSP 或诊断状态。

## 4. 文本内核与 Editor 视图状态分离

- **状态**：接受（边界收敛）。
- **决策**：原 `zcv-engine` 更名为 `zcv-text`，只负责文本存储、不可变快照、坐标、
  事务、历史、搜索、diff、加载和跟踪原语。`Selection`、`SelectionSet`、选区锚点跟随
  与选区事务历史归属 `zcv-editor`。Editor、Workspace 和 Preview 的长期文档实体只能是
  `Entity<MultiBuffer>`；应用装配层不直接依赖 `zcv-text`。
  文件内搜索与项目搜索共用唯一的 `zcv_text::SearchQuery` 和
  `SearchQuery::search(&Snapshot)` 匹配入口；各消费者直接从 `zcv_text` 导入，不由
  Workspace、Project 或 Search crate 重导出。Editor 继续持有版本化结果、活动匹配与替换
  状态，Project 只负责文件遍历、数量限制和 excerpts 聚合。
- **背景**：`engine` 名称没有表达稳定职责，且把纯文本事实和视图选区放在同一 crate，
  容易让上层把底层 `Buffer` 当成编辑器文档模型。Zcv 当前没有独立编辑引擎产品或插件
  消费者，真正稳定的复用边界是文本原语；选区则随 Editor 视图独立存在。
- **替代方案被否**：让 `zcv-multi-buffer` 重导出全部文本类型——会把组合文档变成万能
  门面；让 Selection 留在文本内核——会把视图 primary、goal 与事务恢复语义继续错误地
  固化到底层。
- **触发重构的条件**：只有出现不依赖 Editor 的第二个 Selection 消费者时，才重新评估
  独立 selection crate；不能仅为缩短 import 路径移动职责。

## 5. 自动更新使用签名清单与退出后 helper

- **状态**：接受（macOS 第一阶段）。
- **决策**：应用每次启动时由应用级 `UpdateManager` 自动读取一次 GitHub Release 中固定名称的
  `latest.json` 与 `latest.json.sig`，不依赖 GitHub API。应用验证 Ed25519 清单签名后，
  按平台下载 zip，并校验清单声明的大小、SHA-256、app bundle 代码签名有效性和版本号。
  零费用方案使用 ad-hoc 签名，没有 Developer ID 与公证；信任锚就是应用内置的 Ed25519 公钥。
  下载及验证状态由 `UpdateManager` 单独持有；TopBar 只观察该状态，并在设置按钮左侧显示下载进度或“重启以更新”；
  失败通过一次性 Toast 提示，不长期占用 TopBar。应用不提供手动检查入口。
  用户确认重启后，应用保存工作区并退出；已复制到 `~/.zcv/updates` 的
  `zcv-update-helper` 在进程退出后把新旧 `Zcv.app` 原子交换，并在切换前清理已验证副本
  的下载元数据。新版本必须回写启动确认，否则 helper 原子恢复旧版本并重新启动。是否具备
  更新能力只由 macOS app bundle 与内置公钥这些发布条件决定，不按 debug/release 构建模式
  分流；从转译路径运行时自动更新被禁用。
- **背景**：应用无法安全覆盖正在运行的自身 bundle；只信任 GitHub Release 的 HTTPS 或
  SHA-256 也不能防止发布账号被接管后同时替换清单和产物。签名清单把发布信任锚固定在
  应用内，系统代码签名再约束最终执行的 bundle。ad-hoc 签名不提供身份，但能保证本地
  完整性校验；免费方案以私钥安全为信任根，代价是首次安装需要用户手动建立 Gatekeeper
  例外。helper 只负责退出后的最小文件事务，不拥有检查策略或 UI 状态。
- **替代方案被否**：只调用 GitHub Releases API 并信任下载地址——没有独立发布签名；
  应用进程内直接覆盖自身——失败边界和回滚生命周期不可靠；仅在下次启动时替换——会让
  启动器承担半完成事务，并延长旧版本继续运行时间；把更新状态注入底部状态栏——不符合
  更新作为应用级操作的位置与既定 TopBar 交互。
- **触发重构的条件**：增加 Windows 或 Linux 发布时，为对应平台实现独立替换策略，继续
  复用签名清单与事务模型；引入稳定/预览多通道时，再把通道选择提升为明确配置，不能在
  下载路径中隐式推断。
