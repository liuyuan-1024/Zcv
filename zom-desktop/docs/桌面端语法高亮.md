# 语法高亮设计手册

> **本手册在高亮系统中的位置**：zom 桌面端整体采**渲染层统一、生产层分散**的高亮架构（见 [`桌面端高亮架构.md`](桌面端高亮架构.md)）——选区、搜索匹配、diagnostics、AI 提案等各自是独立 producer，由 `HighlightComposer` 统一合成。**语法高亮是这一架构的第一个 producer**。本手册只规定该 producer 内部的产出机制；与其他高亮的叠加、优先级、上屏合成规则不在本手册，全部在高亮架构手册。
>
> **设计立场**：zom 不做语法高亮，只消费工业界已验证的高亮源——首选 [tree-sitter](https://tree-sitter.github.io/)，其次 LSP semantic tokens。本手册定义的全部内容都是「把这些外部系统装进 zom 所需的最小宿主壳」，不引入任何 zom 私有的词汇表、scope 规则、theme 约定或高亮算法。
>
> 由此推论：
>
> - 不自研高亮算法（包括 regex / TextMate scope 引擎）。
> - 不定义 token 词汇表；name 取值域 = tree-sitter highlight name 命名空间。
> - 不规定 theme 必须覆盖哪些 name；theme 生态对齐 tree-sitter 上游（Helix / Zed 兼容口径）。
> - 本手册主体是 trait、sink、版本对齐、调度——「最小宿主壳」本身。
>
> 编辑面在字符层怎么消费这些 span 是渲染端的事，不在本手册范围。

## 参考

- [`桌面端高亮架构.md`](桌面端高亮架构.md)：高亮系统全局架构。本手册的 syntax producer 落入该架构的「第一个 producer」位置；与其他高亮（选区 / 搜索 / diagnostics / ...）的合成规则、装饰协议、优先级档位都在那本手册。
- [`引擎能力.md`](../../zom-engine/docs/引擎能力.md)：本手册反复引用的 `MetadataLayer<T>` / `BufferVersion` / `ChangeSet` 由 `zom-engine` 提供，类型定义与不变量见此。
- [tree-sitter highlight names](https://tree-sitter.github.io/tree-sitter/syntax-highlighting#highlights)：本手册采纳的 name 命名空间的上游规范。

## 一、定位与边界

- **是什么**：宿主侧的可插拔 producer 子系统。按 buffer 喂语言识别 → 选 provider（tree-sitter 或 LSP）→ 把高亮产物以 `MetadataLayer<HighlightSpan>` 写回 buffer。
- **不是什么**：
  - 不在 `zom-engine` 实现。Engine 只提供 `MetadataLayer<T>` 这个承载底座，不知道「语法高亮」这个业务类别。
  - 不绑定任何特定 parser 实现细节。Provider 形态是 trait，tree-sitter / LSP / 占位实现都通过同一 trait 接入；trait 只是这两类 provider 的最小公共面。
  - 不解析颜色 / 字重 / 字号。Provider 只产 name + 修饰位，theme 在 desktop 端解析为样式。
- **在分层中的位置**：

```text
┌─────────────────────────────────────────────────────┐
│ zom-desktop      theme 按 tree-sitter name 解析样式  │  阶段 3（字符层）
├─────────────────────────────────────────────────────┤
│ 高亮调度层       per-buffer actor：触发 / 版本对齐      │  本手册主体
│ HighlightProvider 实现（tree-sitter / LSP）          │
│ Language Registry（识别 + 选 provider）               │
├─────────────────────────────────────────────────────┤
│ zom-workspace    BufferId / WorkspaceBuffer 句柄     │
│ zom-engine       MetadataLayer<HighlightSpan> 承载   │
└─────────────────────────────────────────────────────┘
```

调度层与 provider 实现当前统一寄存在 `zom-workspace`；后续若拆出独立 crate `zom-syntax`，不影响下游 API。

## 二、Token name

Token name 的取值域 = **tree-sitter highlight name** 命名空间（点分小写，如 `keyword.control.import` / `function.builtin` / `string.special.url`）。

- **本手册不维护词汇表，不裁剪子集，不规定别名**。具体取值由各语言的 `highlights.scm` 决定，是 tree-sitter 上游的事。
- LSP provider 内部把 `SemanticTokenType + modifiers` 映射到 tree-sitter name，用公开的标准映射表实现；映射表落在 LSP provider 模块内，不外溢。
- 渲染端按完整 name → 点分前缀 → 默认前景色逐级回退查询 theme。**回退链是本子系统的不变量**——任意 name 必有 fallback，绝不漏渲染。
- Theme 是否覆盖某个 name 不归本手册管：覆盖得多就细，覆盖得少就糙，都合法。

携带类型见 §三。

## 三、HighlightSpan

写入 `MetadataLayer` 的 payload。

```rust
pub struct HighlightSpan {
    pub name: HighlightName,           // tree-sitter highlight name，&'static str newtype
    pub modifiers: TokenModifiers,     // bitset：static / readonly / deprecated / async / ...
}

pub struct HighlightName(&'static str);
```

- 不带颜色、不带字体；纯 name + 修饰位。
- 区间靠 `MetadataRange<HighlightSpan>` 自己携带的 `TextRange` 表达。
- `modifiers` 用 bitset 平铺（主要服务 LSP token modifiers），theme 端按需叠加样式（如 `deprecated` → 下划线 + 半透明）。tree-sitter provider 默认产 0 修饰；少数语言在 highlight name 里编码了类似信息（如 `variable.builtin`），按 name 直接表达，不强行拆到 modifier。

层 kind 统一：

```rust
MetadataLayerKind::custom("syntax")
```

不允许把语法高亮挂到别的 kind 上；编辑面的字符层渲染按这个固定 kind 取 layer。

## 四、HighlightProvider trait

这是 tree-sitter 与 LSP 两类 provider 的最小公共面。trait 本身不假设语言学语义，只规定生命周期与产物投递方式。

```rust
pub trait HighlightProvider: Send + Sync {
    fn language(&self) -> LanguageId;

    /// 把一个 buffer 挂上来开始供应高亮。
    /// provider 自行决定首次产物什么时候、以什么粒度推 sink。
    fn attach(&mut self, buffer: BufferHandle, sink: HighlightSink);

    /// buffer 发生编辑后调度层通知 provider。
    /// tree-sitter provider 可在此调用内同步算完并推 sink；
    /// LSP provider 只更新内部版本号，真正推送来自 server 异步回包。
    fn on_edit(&mut self, buffer: BufferHandle, change: &ChangeSet, version: BufferVersion);

    /// buffer 关闭 / 切换语言 / provider 卸载时调度层调用。
    /// provider 必须释放与该 buffer 相关的全部资源；调用后不得再向 sink 推任何内容。
    fn detach(&mut self, buffer: BufferHandle);
}
```

**关键点**：

- **订阅模型，不是拉模型**。`on_edit` 不返回值；产物始终走 `sink`。这是为了把 LSP 这类「外部异步推」的 provider 装进同一 trait —— 拉模型只装得下同步 provider。
- **provider 不持有 `Buffer`**。它通过 `BufferHandle` 借调度层提供的只读 snapshot 接口，禁止直接持有 engine 内部句柄。
- **provider 内部状态归 provider**。tree-sitter 的语法树、LSP 的请求队列都封装在 provider 实现里，不外溢。

## 五、HighlightSink 契约

```rust
pub struct HighlightSink { /* 调度层私有句柄 */ }

impl HighlightSink {
    /// 全量替换：用新 snapshot 覆盖该 buffer 的整个 syntax layer。
    pub fn replace_all(&self, version: BufferVersion, spans: Vec<(TextRange, HighlightSpan)>);

    /// 局部替换：覆盖给定区间内的所有 span。区间外保持不变。
    /// 用于 tree-sitter 增量 / LSP delta；不会的 provider 一直用 replace_all。
    pub fn replace_range(&self, version: BufferVersion, range: TextRange, spans: Vec<(TextRange, HighlightSpan)>);
}
```

**版本对齐规则（不可绕过）**：

- 每次推 sink 必带 `BufferVersion`。调度层在写入前比对当前 `buffer.version()`：
  - 等于：正常落 `MetadataLayer`。
  - 更旧：**静默丢弃整批**。Provider 算的是过期版本，结果不能落，但不算错。
  - 更新：**panic**。Provider 不可能拿到比 buffer 当前更新的版本，出现即逻辑错误。
- Provider 不需要自己 remap 已推送的 span。落到 `MetadataLayer` 后，engine 的 `update_through_delta_event` 会按 edit 事件自动 remap，新一轮 provider 推送时已是新版本。
- 调度层在 sink 写入侧做 coalesce：同一 buffer 的连续 `replace_all` 只保留最后一份。

## 六、Language Registry

```rust
pub struct LanguageId(&'static str); // "rust" / "typescript" / "markdown" / ...

pub struct LanguageRegistry { /* ... */ }

impl LanguageRegistry {
    pub fn register(
        &mut self,
        id: LanguageId,
        detectors: Vec<LanguageDetector>,
        provider_factory: Box<dyn Fn() -> Box<dyn HighlightProvider> + Send + Sync>,
    );

    /// 优先级：用户显式声明 > shebang > mode-line > 扩展名 > 默认 plain。
    pub fn detect(&self, buffer: &BufferHandle) -> LanguageId;

    pub fn make_provider(&self, id: LanguageId) -> Option<Box<dyn HighlightProvider>>;
}

pub enum LanguageDetector {
    Extension(&'static [&'static str]),       // [".rs"]
    Shebang(&'static str),                    // "python"
    ModeLine(&'static str),                   // "-*- mode: ruby -*-"
    Filename(&'static [&'static str]),        // ["Makefile", "Dockerfile"]
}
```

- 一个 `LanguageId` 对应**一个**默认 provider 工厂。当前不做多 provider 叠加（tree-sitter + LSP 合成）；trait 不阻止，调度层暂不实现。
- 注册接口只接 `Box<dyn HighlightProvider>` 工厂闭包，**不在编译期把 provider 集合写死**。这是后续可换 dynamic loading 的关键 —— 静态注入与动态注入对 registry 而言无差别。

## 七、调度层（per-buffer actor）

```text
            ┌───────────────── HighlightCoordinator ─────────────────┐
            │  per BufferId：state、provider、pending、coalesce queue │
            └────────────────────────────────────────────────────────┘
                  ▲                       │                       │
   buffer.events  │                       │ attach / on_edit      │ replace_all / replace_range
                  │                       ▼                       │
            zom-workspace          HighlightProvider          MetadataLayers
                                  (tree-sitter / LSP)         (engine 承载)
```

调度层职责：

1. **生命周期**：监听 workspace 的 `open_file` / `close_buffer` / language change，做 `attach` / `detach` 配对。每个 buffer 最多 1 个活跃 provider。
2. **编辑订阅**：订阅 buffer 的 `Transaction` commit，把 `ChangeSet` 转发给 provider 的 `on_edit`。
3. **版本守护**：sink 写入侧做版本比对（见 §五）。Provider 不需要自己防过期。
4. **背压与 coalesce**：高频编辑下，pending sink 写入只保留最后一份未落地版本；编辑率快于 provider 出产时，旧版本主动丢弃。
5. **降级**：provider panic / 长时间无响应 / 文件超阈值 → detach 并切到 plain（无 syntax layer）。降级是调度层的事，不让 provider 自报。
6. **线程模型**：调度层主线程只持前台句柄；tree-sitter provider 由 `SyntaxWorker` 后台线程串行承载，结果通过 sink 回送；LSP provider 可自管 task / IO，遵守同一 sink 契约。

## 八、Provider 形态

trait 同一，内部差异完全封装。当前只接入 tree-sitter native 与 plain，**不接入 regex / TextMate scope 引擎**。

| Provider 形态 | 触发模型 | 增量能力 | 失败模式 |
|---|---|---|---|
| tree-sitter（native，Tier 1） | 后台 worker 处理 `on_edit` | 内部 `InputEdit`；有 viewport hint 时 `replace_range` 推可见区间 | parse 错误：全量重解析或落 plain，不阻塞主线程 |
| tree-sitter（wasm，Tier 2 语言包） | 后续接入 | 同上 | 同上；额外：装载失败 / ABI 不匹配 → 整体落 plain |
| LSP semantic tokens | `on_edit` 只更新内部版本号 | 协议 `SemanticTokensDelta`；首次全量 | server 未就绪 / 超时 / 协议错：保持现状，不主动清空 |
| plain（占位） | 永远不推 | — | — |

native 与 wasm 两种 tree-sitter provider 对调度层透明——同一 trait、同一 sink 契约，差异封装在 provider 实现内部（详见 §十）。

**所有 provider 必须遵守**：

- `attach` 后任何线程拿到的 sink 句柄都是轻量 clone，**不持有 buffer 引用**。
- `detach` 调用返回后**绝不再推 sink**。异步 provider 内部需要在自己的 task 里检查 detach 标记。
- 不在 trait 方法内做阻塞 IO；需要 IO 的 provider 自起 task。
- 产出的 name 必须落在 tree-sitter highlight name 命名空间内（LSP provider 在内部做映射）。

## 九、生命周期

```text
open_file(path)
    │
    ▼
workspace 创建 Buffer + BufferId
    │
    ▼
HighlightCoordinator::on_open
    │  language = registry.detect(buffer)
    │  provider = registry.make_provider(language)
    │  provider.attach(buffer_handle, sink)
    ▼
buffer 编辑 → coordinator 收 Transaction → provider.on_edit
    │
    ▼
provider 推 sink → 版本对齐 → 写 MetadataLayer
    │
    ▼
编辑面 re-render（字符层读取该 buffer 的 syntax layer）

──── 切换语言 ────
coordinator.detach(old) → provider.detach() → 清空 syntax layer → attach(new)

──── 关闭 buffer ────
coordinator.on_close → provider.detach() → 释放 MetadataLayer
```

**不变量**：

- 任意时刻每个 `BufferId` 最多挂一个 provider。
- `syntax` layer 在 detach 后清空；切换语言不允许「旧高亮残留 + 新高亮叠加」。
- buffer 未挂 provider 时 `syntax` layer 不存在；渲染层不能假设它一定存在。

## 十、可插拔机制与语言规模

「内置几种」只能撑到 ~20 门语言；超过后会同时撞二进制体积、CI 时间、发版耦合三堵墙。为兼顾「常用语言开箱即用」与「长尾语言不拖体积」，语法接入分两层。

### Tier 1：内置语言（compile-in）

- 范围：zom 保证开箱可用的核心集（约 15–25 门，具体清单由主仓维护）。
- 交付：tree-sitter grammar 与对应 provider 作为普通依赖直接编进 `zom-desktop`，启动期在组合根遍历内置 provider 调 `registry.register(...)`。
- 准入维度：使用频率、grammar 上游稳定度、对二进制体积的影响。
- LSP provider 同属此层（按 workspace 配置连接对应 language server）。

### Tier 2：语言包（WASM，on-demand）

- 范围：Tier 1 之外的全部 tree-sitter 语言。
- 交付：每门语言独立打包为「语言包」，runtime 通过 tree-sitter 官方 WASM runtime 装载。**不**采用 dylib——跨平台分发、沙箱隔离、零用户侧工具链依赖三项综合下来 WASM 是更合理的默认；性能损失（约 native 2–3×）在桌面端 syntax 高亮场景可接受。
- 对调度层透明：registry 工厂闭包返回 `Box<dyn HighlightProvider>`，内部是 native tree-sitter 还是 wasm tree-sitter 不外露；trait / sink / coordinator 完全不区分。
- 用户路径：打开未识别文件 → workspace 上报未知扩展 → 状态栏建议安装语言包 → 用户确认后装入 → registry 注册新工厂 → 已打开 buffer 触发重新 detect & attach。

### 语言包格式

最小内容：

```text
<pack-id>/
  pack.toml          # id / display name / version / ts-abi-version / detectors
  grammar.wasm       # tree-sitter parser 的 wasm 产物
  queries/
    highlights.scm
```

- `ts-abi-version` 必须与 zom 内嵌的 tree-sitter wasm runtime ABI 匹配；不匹配则装载失败，该语言落 plain。
- `detectors` 与 §六 `LanguageDetector` 同构，pack 自描述识别规则。
- 其余 query 文件（`locals.scm` / `injections.scm` 等）第一版忽略，留作未来扩展。

### Queries 与 grammar 解耦（不变量）

无论 grammar 是 Tier 1 内置还是 Tier 2 wasm，**queries 永远允许被外部资源覆盖**：

- 查询查找顺序：用户配置目录 > 语言包内 `queries/` > Tier 1 内置默认。
- 收益：修高亮规则不需要发 zom 版本，也不需要重发语言包。
- Grammar 二进制是另一维：Tier 1 随 zom 发版，Tier 2 随语言包独立发版。

### 装载器接口

```rust
pub trait LanguagePackLoader: Send + Sync {
    fn list_installed(&self) -> Vec<InstalledPack>;
    fn load(&self, pack_id: &str) -> Result<Box<dyn HighlightProvider>, LoadError>;
}
```

- 装载器在组合根注入 registry，与 Tier 1 的内置 provider 工厂在 registry 内并列。
- 包的获取、缓存、签名校验、版本升级、磁盘存放路径都是装载器内部职责，不在本手册规定。
- `registry.register` 已经只接 `Box<dyn HighlightProvider>` 工厂，本接口加入不破坏既有签名。

### 不在本手册规定的事

- 语言包的**分发渠道**（仓库 URL / 镜像 / 签名信任锚）——属发行工程范畴，单独成文。
- 语言包的**作者工作流**（从 tree-sitter grammar 源码产出符合本格式的 pack 的流程）——单独写作者手册。
- 包管理 UI（安装 / 卸载 / 升级界面）——desktop 端 UX 章节。

## 十一、与渲染契约的对接

本手册只规定 syntax producer 把产物投递到哪里、以何种形态投递。**多 producer 的合成、叠加规则、优先级档位不在本手册**——全部在 [`桌面端高亮架构.md`](桌面端高亮架构.md)。

对接点：

1. syntax provider 经 `HighlightSink` 把产物落入 `MetadataLayer<HighlightSpan>`（版本对齐由 §五 保证）。
2. `HighlightComposer` 在合成前按 viewport 行范围调 `layers.ranges_for_kind_in_line_window(Custom("syntax"), window)` 读取该 buffer 的 syntax layer。
3. composer 把每个 `HighlightSpan` 翻译成一条 `Decoration { kind: Foreground, style: theme(name + modifiers), priority: 0..100 }`，进入合成（详见高亮架构手册 §四 / §五 / §六）。
4. theme 端按完整 name → 点分前缀 → 默认前景色逐级回退查询（**回退链是本子系统的不变量**）。theme 查表逻辑统一抽到 desktop `shared/theme.rs`；theme 内容对齐 tree-sitter 生态（Helix / Zed 兼容口径），不在本手册定义。
5. 其他 producer（选区 / 搜索 / diagnostics / ...）**不读 syntax layer、不写 syntax layer**——它们以同样的 `Decoration` 形态投递 composer，与 syntax 在合成层汇合。

字符背景（搜索高亮 / 选区）会盖在 syntax 字色之上的 cell，但 syntax 字色仍生效——`Foreground` 与 `Background` 在 composer 内正交（详见高亮架构 §五）。

## 十二、降级与边界条件

| 触发条件 | 调度层行为 |
|---|---|
| `registry.detect` 命中 `plain` | 不创建 provider；syntax layer 不存在 |
| `registry.make_provider` 返回 `None`（Tier 2 包未安装） | 同上；可由 UI 层提示「装语言包」 |
| Tier 2 语言包装载失败（ABI 不匹配 / 文件损坏 / grammar.wasm 缺失） | 装载器返回 `LoadError`，registry 不注册该语言；落 plain |
| 文件大小 > `MAX_HIGHLIGHT_BYTES`（默认 4 MiB） | 不 attach；状态栏可显示「高亮已停用」 |
| tree-sitter provider panic（native 或 wasm） | 调度层捕获 → detach → 切 plain |
| LSP server 未就绪 / 超时 / 协议错 | 保持现有 layer 不动；不主动 detach |
| 用户手动切换语言 | detach old → 清 layer → attach new |
| Buffer 关闭 | detach → 清 layer → coordinator 释放 entry |
| theme 未命中某 name | 走点分前缀回退，最终落默认前景色——**不算错** |

阈值常量集中维护，可在配置层覆盖；不允许 provider 内部各自设阈值。

## 十三、测试要求

按 [`agents/project.md`](../../agents/project.md) 的测试边界：

| 模块 | 测试形态 |
|---|---|
| `LanguageRegistry::detect` | 纯函数表驱动：extension / shebang / mode-line / filename 各类输入决定性 |
| `HighlightSink` 版本对齐 | 给定 stale / current / future version 三种推入，断言「丢弃 / 落地 / panic」 |
| Coordinator 生命周期 | attach / detach 配对：detach 后再推 sink 不落 layer；语言切换不残留旧 layer |
| theme 回退链 | 未命中完整 name → 命中前缀；未命中前缀 → 默认前景色；绝不缺省 |
| Provider 实现 | 在 provider 自己的模块内单测，trait 层只测 mock provider |

**不测**：

- engine `MetadataLayer` 自身行为（engine 自己有覆盖）。
- tree-sitter / LSP 上游正确性（外部已验证）。
- GPUI 渲染像素结果（由 desktop 端 element 测覆盖，见 [`桌面端组件实现.md`](桌面端组件实现.md) §一.11）。

## 十四、当前不做的事

明确划掉，避免范围漂移：

- **自研高亮算法**：包括 regex / TextMate scope 引擎在内的任何「我们自己写词法」路径，不接入、不留口。
- **自有 token 词汇表**：name 一律走 tree-sitter 命名空间，不另起。
- **dylib 形态的 Tier 2 装载**：Tier 2 只走 WASM，不并行支持 dylib。
- **多 provider 叠加**：tree-sitter + LSP 合成的双层产出。
- **跨语言嵌入**（injection / combined parsers）。
- **运行时切换 wasm runtime 版本**：ABI 版本随 zom 编译期固定，包不匹配即拒绝装载。
- **语言包的分发渠道 / 作者工作流 / 包管理 UI**：均在本手册范围外，各自单独成文。
- **mini-map / 缩略图的语法着色**（与 mini-map 一起推迟）。
- **token 自定义 modifiers 的运行时扩展**：modifiers 在编译期定 bitset。
