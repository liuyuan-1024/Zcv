# Zcv 测试架构维护

维护测试代码与生产代码之间清晰、可验证的边界。目标不是机械搬迁测试，而是让生产构建不携带测试专用状态、入口和依赖，同时让测试通过稳定的产品行为或明确的测试支持边界完成验证。

## 选择工作模式

- 用户只要求审计、检查、评估或给建议时，只读分析，不修改代码。
- 用户明确要求清理、迁移、重构或优化时，在指定范围内实施修改，并同步更新调用方、测试和 Cargo 配置。
- 如果迁移会改变产品 API、删除大量代码、引入新的 workspace crate，或存在多个无法由现有架构判断的方向，先报告证据并请求确认。

## 共同工作准则

1. 完整读取仓库与目标目录中的 `AGENTS.md`，再按范围读取相关模块、测试组织和 Cargo 配置；不要无条件读取整个 `docs/`。
2. 开始前检查工作树并保留用户已有修改。先建立测试代码、生产代码、测试支持代码和依赖之间的实际关系，不根据 `test_*` 等命名单独下结论。
3. 涉及编辑器核心能力、生命周期或测试架构时，研究 `/Users/liuyuan/project/zed` 的对应实现，理解其边界后再判断哪些设计适合 Zcv；不要机械复制 Zed。
4. 遵循 Zcv 的测试目录约定，优先把测试文件放在 `test` 目录；需要访问私有实现的单元测试可以就近保留，但必须说明其可见性边界。
5. 区分“测试使用了某个产品 API”和“某个 API 只为测试存在”。真实产品能力、真实状态和稳定的构造不变量不应仅因测试覆盖而被移除。
6. 测试专用能力不得进入正常生产模块的 API。禁止通过 `test-support` 等 feature、`#[cfg(test)]` 以外的生产条件编译路径，或测试专用 `pub` 函数、字段、构造器和状态入口，把 fixture、mock、非法状态构造或依赖注入暴露给生产 crate。正常生产构建不应包含或暴露这些入口。
7. 不使用生产路径中的 `is_test`、`force_*`、测试专用开关或隐式回退掩盖错误抽象。需要依赖注入时，先判断它是否是产品真实需求；若只是测试 fixture，应由测试代码自身持有，或放入明确的测试支持模块 / 独立测试支持 crate。
8. 只有存在真实生产调用方、属于正式产品契约的能力，才能保留在生产代码中；“被测试使用”本身不能证明生产归属。若测试是唯一消费者，应优先收回到测试边界，而不是扩大可见性。
9. 不引入实时协作、远程开发或 LSP；测试清理不得借机扩大产品范围。

## 审计流程

### 1. 建立证据清单

检查以下内容的实际调用关系：

- `#[cfg(test)]` 模块和函数；
- 生产结构体中的测试专用字段、构造器、状态记录和 mock 分支；
- `test_support`、fixture、快照、临时文件和测试资源；
- `src/test`、嵌套 `test` 模块以及现有集成测试入口；
- `Cargo.toml` 的 `[dependencies]`、`[dev-dependencies]`、features 和 workspace 继承；
- 只由测试、benchmark、example 或 fuzz 目标使用的 crate。

特别检查 `Cargo.toml` 中的 `test-support`、`test_support`、`cfg(test)` 相关 feature 和条件依赖，确认它们没有把测试专用 API 编译进正常生产依赖图。

每条发现都要能回答：谁调用它、谁拥有它、它是否进入正常生产构建、它是否是正式产品契约、删除或迁移后哪条行为会受影响。

### 2. 分类而不是统一搬迁

将候选代码分为：

- 仅供同一模块单元测试使用的辅助逻辑；
- 跨模块共享的测试 fixture 或测试支持能力；
- 只用于构造非法状态、伪造外部输入或控制测试时间的入口；
- 实际属于产品模型、产品状态或公开行为的代码；
- benchmark、example、fuzz 或构建脚本专用代码。

只有前几类中的“确实不属于产品语义”的部分才应迁移。对最后两类分别保持其目标边界，不把它们混入普通测试支持模块。测试唯一使用的生产 `pub` API、测试 feature 和生产测试开关，应优先视为测试架构问题处理，而不是因为已有测试调用就默认保留。

### 3. 选择迁移位置

- 私有实现的单元测试辅助代码：放在对应测试模块或相邻的测试文件中。
- 多个测试目标共享的 fixture：放入明确命名的测试支持模块；若跨 crate 共享且依赖内部实现，优先评估独立的 `test-support` crate。
- 仅集成测试需要的能力：由集成测试或测试支持 crate 持有，不通过生产 crate 的测试专用公共 API 暴露私有状态。
- 真实产品行为：保留生产代码，测试通过外部可观察结果、公开契约或正式构造器验证。
- 只被测试使用的 Cargo crate：移入 `[dev-dependencies]`，并检查它没有通过 workspace feature 泄漏到正常依赖图。

Rust 的单元测试和集成测试边界见 [references/rust-test-boundaries.md](references/rust-test-boundaries.md)；Cargo 依赖审计见 [references/cargo-test-dependencies.md](references/cargo-test-dependencies.md)。

## 修改要求

修改时遵守以下顺序：

1. 先建立或保留能暴露原问题的行为测试；
2. 迁移测试专用代码和依赖；
3. 删除由迁移直接淘汰的生产字段、入口、导入、feature 和分支；
4. 更新所有调用方、模块声明、Cargo 配置和必要文档；
5. 检查没有残留的测试专用生产 API、`test-support` 生产路径、重复 fixture 或新旧双轨逻辑。

不要为了测试放宽生产类型不变量，不要维护一份生产 fixture 和一份测试 fixture 的长期可写副本，也不要用 `#[allow(...)]` 隐藏迁移产生的警告。

## 验证与交付

验证范围必须与修改范围匹配，至少区分：

- 生产代码：目标 package 的正常编译或类型检查；
- 行为：本次影响的单元、集成或回归测试；
- 依赖：Cargo 依赖树确认测试 crate 未进入正常依赖；
- 边界：确认正常生产构建不包含测试专用 `pub` API、测试 feature、fixture、mock 或依赖注入入口；
- 质量：格式检查，以及修改涉及时的 Lint 检查。

不要默认运行全量测试。使用能直接证明目标行为的最小命令，并确认过滤条件确实执行了目标测试。若受平台、网络、依赖或沙箱限制无法验证，明确说明尝试的命令、阻塞原因和剩余未验证部分。

最终报告按影响排序，说明：迁移了什么、为什么属于测试边界、保留了什么以及为什么仍是产品能力、实际验证了什么、哪些问题超出本次范围。
