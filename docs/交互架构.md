# 交互架构

本文规定跨 crate 的键盘、鼠标与焦点路由。具体组件的按键清单和实现细节留在对应模块与测试中。

## 输入路由与状态所有权

按键与鼠标点击不要求共用同一条分发路径。应根据输入携带的信息和目标是否确定选择路由，但所有路径都必须直接到达对应状态所有者，不能在 UI 层维护第二份业务状态：

```text
内置 keymap ──> Action ──> 焦点链上的 on_action handler ──> 状态所有者方法
菜单         ──> Action 或已知目标的直接调用 ──────────────> 状态所有者方法
工具栏/按钮  ──> 已绑定的目标实体 ─────────────────────────> 状态所有者方法
鼠标位置交互 ──> 命中目标与即时数据 ───────────────────────> 状态所有者方法
```

规则：

- `zcv-actions` 定义跨模块共享的 Action；只在单个实现模块使用的 Action 留在实现附近。
- 适合统一入口执行的 Action 在同一声明处附带标题和简短说明；统一入口只消费由该声明生成的命令元数据，不从全部注册 Action 推断用户命令。
- `assets/keymaps/default-*.json` 只描述按键到 Action 的映射，不承载业务逻辑。
- `zcv-keymap` 负责加载、解析和注册内置 keymap，不决定具体命令行为。
- handler 由真实状态所有者或窗口根注册，不能通过第二套命令总线转发。
- 快捷键必须经 `Action` 与焦点链路由；不要伪造鼠标事件来复用按键处理。
- 鼠标控件已绑定明确目标时，应直接调用该目标的状态所有者方法，不应为了派发 `Action` 而改变焦点，也不应依赖当前焦点恰好位于目标之内。
- 菜单或按钮没有确定目标、语义确实由当前焦点决定时，可以 `dispatch_action`。
- 相同业务意图应收敛到同一状态所有者；若没有输入特有的数据或策略差异，优先复用同一个所有者方法，不复制业务步骤。

鼠标拖拽、点击位置、文本范围等携带即时数据的直接交互，应直接调用状态所有者方法。键盘命令需要相同行为时，应通过自身的 `Action` 路径到达相同所有者，而不是反向伪造鼠标事件。

## 焦点与上下文

键盘分发依赖焦点链与 `KeyContext`：

1. 可交互实体持有自己的 `FocusHandle`。
2. 渲染根节点设置与真实所有者对应的 `key_context`。
3. 该根节点注册相关 `on_action` handler。
4. 子输入控件需要继承外层命令时，外层上下文必须位于同一焦点链上。

面板的根焦点句柄用于标识焦点归属；激活目标必须是根焦点子树中的实际输入控件。Dock 根自身获得焦点时，由 Dock 转交给当前可见面板的激活目标。打开、切换和关闭面板等跨区域导航由 Workspace 决定：先更新 Dock 与 Panel 的生命周期状态，再立即聚焦激活目标。需要向内部状态机同步焦点的视图在首次渲染时读取 `Window` 的焦点状态。Panel 生命周期回调只负责资源与状态，不决定跨区域焦点转移。

上下文名称描述真实的聚焦所有者，例如编辑器、项目树或提交编辑区。不要用过宽的通用上下文掩盖所有权，也不要为同一所有者叠加含义重复的布尔上下文。

交互状态收尾与焦点转移是两个独立决策。`on_blur` 可以结束当前组件拥有的编辑状态，但不得因此默认重新聚焦该组件；焦点由明确请求目标的状态所有者设置。异步打开文档时，由 `Workspace` 在 Item 激活后聚焦编辑器，发起组件后续的失焦清理只能更新自身状态，不能覆盖目标焦点。

### 焦点归还契约

窗口当前焦点以 GPUI 的 `Window` 为唯一权威。每次交互由创建该交互的所有者确定退出目标，不建立全局焦点历史或让通用层猜测目标：

1. 临时浮层、顶栏统一入口等需要回到发起位置的交互，在取得焦点之前记录该次会话的原焦点；重复聚焦同一会话不得覆盖它。关闭或取消时，只有焦点仍由该交互持有才归还。切换到另一个浮层时，新的浮层继承最初的归还目标。
2. 搜索栏、行内编辑等附属于明确目标的交互，关闭时聚焦所属 Item、Editor 或容器。是否归还仍取决于焦点是否留在该交互内；失焦清理只结束自身状态。
3. 打开文件、切换标签或面板等明确导航，由目标的所有者在目标激活后聚焦它。先前交互的关闭和异步完成回调不得覆盖这个新焦点。
4. 当前焦点节点从渲染树消失时，由 `Workspace` 优先选择仍存在的焦点链祖先；没有可用祖先时聚焦当前工作区的活动 Item，空 Pane 则聚焦 Pane。此兜底只处理焦点丢失，不代替正常关闭路径的显式决定。

跨组件传递归还目标时使用焦点句柄，不复制一份可独立修改的“当前焦点”。目标生命周期可能短于交互时，保存弱句柄；归还时目标已经失效则交给工作区的焦点丢失处理。

| 交互 | 退出目标的决定者 | 归还目标 |
| --- | --- | --- |
| 顶栏统一入口、顶栏选择器 | 发起该次会话的入口组件或选择器层 | 进入前的焦点；选择器互切沿用最初目标 |
| 文档搜索、编辑器局部重命名、项目树行内编辑 | 各自的宿主 | 所属 Item、Editor 或项目树；创建文件后的导航由工作区聚焦新 Item |
| 面板关闭、标签关闭 | `Workspace` 或 `Pane` | 仍有效的活动 Item；空 Pane 聚焦 Pane |
| 焦点节点消失 | `Workspace` | 最近的可聚焦祖先，否则活动 Item 或 Pane |

搜索栏统一使用 `SearchBar`：普通 `Editor` Item 使用 Pane 持有的按需显示搜索栏；项目差异、项目搜索和提交图 Item 各自持有常驻搜索栏。`Editor` 从当前显示快照中的选区提供查询建议，`SearchBar` 拥有查询、选项和焦点。内容聚焦时由当前 Item 或 Pane 接收 Cmd-F，搜索输入框聚焦时由搜索栏接收，两条路径部署同一份会话。Pane 文档搜索栏只绑定直接打开的 `Editor`；差异视图以其内层 `Editor` 为目标，项目搜索与提交图以视图自身为目标。项目搜索结果只使用原有项目查询栏，不打开第二个文件搜索框。

## 视觉焦点不是分发焦点

`FocusHandle::contains_focused` 表示自身或后代持有焦点，适合判断一整块交互区域是否活跃。`FocusHandle::is_focused` 只表示该句柄本身持有焦点，适合选择边框、树导航和输入目标等精确视觉状态。

二者不能互换：

- 外层区域需要在内部编辑器聚焦时继续响应命令，可以使用 `contains_focused`。
- 只有树本体聚焦时才显示选择边框，应使用 `is_focused`。
- 如果视觉状态取决于焦点变化，状态所有者必须在 focus/blur 时触发重绘，不能只在其他数据变化时偶然更新。

## 注册位置

- 组件专属命令在组件根节点注册。
- 跨整个工作区可达的命令由 `Workspace` 根节点或宿主装配层注册。
- 具体业务 crate 负责自己的 Action 行为；工作区提供窗口级挂载位置和命令分发边界。
- 初始化函数只注册协议、keymap 或真实全局能力，不通过副作用隐藏普通业务调用。

## 修改检查

新增或调整交互前，确认：

1. 键盘输入是否通过 `Action` 与正确的焦点链到达状态所有者。
2. 鼠标点击是否已经绑定明确目标；若是，是否直接路由到该目标而不依赖或改变焦点。
3. 不同输入路径是否收敛到同一状态所有者，且没有维护 UI 影子状态。
4. `KeyContext` 是否与实际焦点链一致。
5. 视觉状态需要的是 `is_focused` 还是 `contains_focused`。
6. 测试是否覆盖目标焦点下按键可达、非目标焦点时鼠标仍能命中其绑定目标，以及焦点变化后的视觉更新。
