# 重导出规范

> 规定 workspace 内模块可见性、crate 根门面和重导出的使用原则。
> binary crate 的门面服务于内部架构；library crate 的根门面同时构成 public API。

---

## 一、核心原则

zcv workspace 采用：

> **实现模块默认私有，能力域或 crate 根选择性重导出，消费者只使用所属边界的规范路径。**

例如，`Editor` 定义在 `zcv-editor/src/view/mod.rs`，但宿主统一从
`zcv_editor::Editor` 导入，不依赖 `view/mod.rs` 这一内部文件路径：

```rust
// zcv-editor/src/lib.rs
mod view;

pub use view::Editor;

// zcv 宿主
use zcv_editor::Editor;
```

这里的 `zcv-editor` 是独立能力 crate，`lib.rs` 是公开门面，`view/` 是可调整的
实现细节。文件拆分、合并或重命名不应迫使宿主同步修改导入路径。宿主不保留
`crate::editor` 兼容模块，避免两条长期路径。

---

## 二、为什么使用能力域门面

### 2.1 隔离文件组织

消费者只依赖 `zcv_editor::Editor`、`crate::workspace::Pane`、
`crate::ui::Glyph` 等能力路径，不需要知道符号具体定义在哪个文件。

### 2.2 明确能力边界

`mod.rs` 中的重导出列表就是该能力域允许其他模块使用的接口清单。没有被重导出的
内部类型，不应被其他能力域穿透引用。

### 2.3 保持一条规范路径

实现子模块保持私有，因此同一符号不会同时出现：

Editor 的实现路径不公开，宿主只能使用 crate 根门面：

```text
zcv_editor::Editor
```

### 2.4 支持渐进拆分

能力域内部可以按职责拆文件，门面路径保持稳定。重构物理目录时，调用方不需要跟随
内部结构变化。

## 三、可见性规则

### 规则 1：实现子模块默认私有

能力域内的实现文件使用 `mod`，不使用 `pub(crate) mod`：

```rust
// workspace/mod.rs
mod dock;
mod pane;
mod toolbar;
```

只有当“子模块本身”就是需要被跨能力域访问的命名空间时，才提高模块可见性。不要仅仅
为了让外部取得其中一个类型，就公开整个实现模块。

### 规则 2：跨能力域接口在根模块选择性重导出

被其他能力域真实使用的主类型、trait、事件和 action，由能力域根模块统一重导出：

```rust
// workspace/mod.rs
pub(crate) use dock::{Dock, DockPosition, ToggleProjectTree};
pub(crate) use item::{ItemEvent, ItemHandle};
pub(crate) use pane::{CloseTab, Pane};
```

消费者统一从能力域根路径导入：

```rust
use crate::workspace::{CloseTab, Dock, Pane};
```

不要跨过门面引用 `crate::workspace::pane::Pane`。

### 规则 3：只重导出真实接口

重导出必须至少有一个能力域外的真实消费者。以下内容默认不重导出：

- 仅在当前文件使用的符号。
- 仅在同一能力域内部协作的 helper。
- 私有渲染函数和中间数据结构。
- 为未来功能预留、当前没有调用方的类型或方法。
- 只为缩短一处导入而增加的别名。

不要使用通配符：

```rust
// ❌ 暴露范围会随实现模块增长
pub(crate) use pane::*;

// ✅ 门面变化显式可审查
pub(crate) use pane::{CloseTab, Pane, PrevTab};
```

### 规则 4：根模块自用符号使用普通 `use`

`mod.rs` 自己需要使用、但其他能力域不需要的符号，只做私有导入：

```rust
mod toolbar;

// Workspace 自己装配 Toolbar，外部不需要取得 Toolbar 类型。
use toolbar::Toolbar;

// 其他能力域需要实现 ToolbarItemView，所以进入门面。
pub(crate) use toolbar::{ToolbarItemLocation, ToolbarItemView};
```

不得为了少写一条普通 `use`，把内部符号扩大为 `pub(crate) use`。

### 规则 5：定义位置不等于访问路径

类型应放在职责最匹配的叶子模块中；跨能力域访问路径由上层门面决定：

```text
定义位置：workspace/pane.rs
规范路径：crate::workspace::Pane
```

查找实现时使用编辑器跳转或文本搜索，不通过暴露物理文件路径来换取定位便利。

能力域的主聚合类型可以直接定义在 `mod.rs`。例如 `Workspace` 本身属于
`workspace` 根能力，不需要为了形式统一再创建一层 `workspace/view.rs`。

### 规则 6：嵌套能力域可以有自己的门面

复杂能力内部允许继续分层：

```rust
// editor/display_map/projection/mod.rs
mod core;
mod point;
mod range;

pub use core::Projection;
pub use point::ProjectedPoint;
pub use range::ProjectedRange;
```

这里使用 `pub use` 不代表符号对整个 crate 无限制公开。最终可见范围仍受父模块
`display_map` 和 `editor` 的可见性约束。

嵌套门面同样必须选择性暴露，不得把所有内部 helper 展平。

## 四、不同符号的处理方式

| 符号类别 | 跨能力域使用时 | 仅能力域内部使用时 |
|---|---|---|
| 主 Entity / Builder / 数据类型 | 在能力域根重导出 | 私有导入或直接使用 |
| Trait 与对应 Handle | 一起重导出 | 保持在实现模块内 |
| Event | 有外部订阅者时重导出 | 不重导出 |
| `actions!` 生成类型 | 由 keymap 或外部 handler 使用时重导出 | 不重导出 |
| 函数式渲染入口 | 确有跨域消费者时重导出 | 普通 `use` |
| Helper / 中间类型 | 不重导出 | 保持私有 |
| 测试辅助 | 优先留在测试模块 | 必要时用 `#[cfg(test)]` 限定 |

### 4.1 Action

Action 的命名空间由定义它的模块决定，Rust 导入路径不需要复制该物理路径。外部
keymap 或父组件需要 action 类型时，从能力域门面重导出：

```rust
// zcv-editor/src/lib.rs
pub use view::{MoveLeft, MoveRight, Undo};

// keymap/mod.rs
use zcv_editor::{MoveLeft, MoveRight, Undo};
```

### 4.2 Trait 与类型擦除 Handle

一组配套抽象应从同一个门面出现：

```rust
pub(crate) use panel::{Panel, PanelHandle};
```

不要让消费者分别穿透不同实现模块寻找 trait、handle 或事件。

### 4.3 测试

同文件单元测试可以通过 `use super::*` 访问私有实现，不应为了测试扩大生产可见性。

跨模块测试确实需要辅助入口时：

```rust
#[cfg(test)]
pub(crate) use test_support::make_editor;
```

测试专用重导出必须受 `#[cfg(test)]` 限定。

## 五、禁止的模式

### 5.1 公开实现模块后再重导出同一符号

```rust
// ❌ 产生两条可达路径
pub(crate) mod pane;
pub(crate) use pane::Pane;
```

应保持实现模块私有：

```rust
// ✅ 只有 crate::workspace::Pane
mod pane;
pub(crate) use pane::Pane;
```

### 5.2 把 `mod.rs` 变成全量符号仓库

门面只表达跨能力域契约，不追求把子模块所有内容展平。新增实现符号时，默认不修改
`mod.rs`；只有出现真实的跨能力域消费者时才增加重导出。

### 5.3 用重导出掩盖错误的模块归属

如果一个类型主要服务另一个能力域，不应只靠重导出制造表面上的整洁。先判断它是否
放错了目录，再决定门面位置。

### 5.4 保留未使用重导出

zcv 不使用 `#[allow(unused_imports)]` 隐藏 warning。出现未使用重导出时，应判断：

1. 符号是否只有根模块自己使用——改为普通 `use`。
2. 符号是否完全没有消费者——删除导入。
3. 功能是否尚未接入——等产生真实消费者时再重导出。

## 六、能力域示例

### 6.1 Editor crate

```rust
// zcv-editor/src/lib.rs
mod blink_manager;
mod display_map;
mod element;
mod scroll;
mod selection;
mod view;

pub use view::{Editor, EditorEvent, MoveLeft, MoveRight, Undo};
```

`Editor`、宿主订阅的事件和需要注册的 action 进入 crate 根门面。`element`、
`scroll`、`selection` 是内部实现，不向宿主暴露。`blink_manager`、`display_map`
即使拆成目录，也仍是 Editor crate 的内部实现；Projection 与 Fold 不从 crate 根
重导出。

### 6.2 Workspace

```rust
// workspace/mod.rs
mod dock;
mod item;
mod pane;
mod toolbar;

pub(crate) use dock::{Dock, DockPosition, ToggleProjectTree};
pub(crate) use item::{ItemEvent, ItemHandle};
pub(crate) use pane::{CloseTab, Pane};
pub(crate) use toolbar::{ToolbarItemLocation, ToolbarItemView};

use toolbar::Toolbar;
```

Workspace 门面对外提供编辑区装配所需的主类型和 action；只服务 Workspace 自身的
具体 Toolbar 实体保持私有。

### 6.3 UI

```rust
// ui/mod.rs
mod glyph;
mod icon;
mod list_item;
mod picker;

pub(crate) use glyph::Glyph;
pub(crate) use icon::SvgIcon;
pub(crate) use picker::Picker;
```

业务组件从 `crate::ui::{Glyph, Picker, SvgIcon}` 使用设计系统，不依赖 UI 原语的
文件拆分。

## 七、修改流程

新增或移动符号时按以下顺序判断：

1. 确认符号属于哪个能力域。
2. 把实现放进职责匹配的私有子模块。
3. 查找是否存在能力域外的真实消费者。
4. 有外部消费者时，在最近的能力域根选择性重导出。
5. 将消费者统一改为门面路径。
6. 确认实现模块没有同时对外开放，避免两条规范路径。
7. 运行 `cargo fmt` 和 `cargo check`，清除未使用重导出 warning。

审查时重点确认：

- 消费者是否只依赖能力域门面。
- 门面是否暴露了没有真实消费者的符号。
- 根模块自用符号是否误用了 `pub(crate) use`。
- 同一符号是否存在两条跨能力域可达路径。
- 文件重命名是否被限制在能力域内部。

## 八、适用边界

本规范适用于整个 workspace。`zcv/` binary crate 使用 `pub(crate) use` 建立内部
能力门面；独立 library crate 使用 `pub use` 建立公开门面。

`zcv-engine`、`zcv-editor`、`zcv-theme`、`zcv-project`、`zcv-ui`、`zcv-keymap` 是独立
library crate，`src/lib.rs` 是各自对宿主的 public API 门面。它们同样采用选择性重导出，
并需要遵守 public API、长期语义和 semver 约束。

- `zcv-project`：项目数据层（git 状态编排、文件系统监听、项目快照），对应 Zed 的
  `project` crate；`Project`/`GitStore`/`RepositorySnapshot` 等从根门面导出。
- `zcv-ui`：设计系统（Glyph/SvgIcon/Picker/Checkbox 与 `tree` 原语），对应 Zed 的
  `ui` crate；业务组件统一从 `zcv_ui` 根取原语。
- `zcv-keymap`：快捷键加载器（`KeyBindings`/`load`/`load_json`），keymap JSON 由本
  crate 的 `assets/keymaps/` 编译期嵌入。

Editor 消费者统一依赖 `zcv_editor` 的 crate 根能力路径：

```rust
use zcv_editor::{Editor, EditorEvent, MoveLeft, Undo};
```

`zcv` 不保留 `crate::editor` 兼容门面。Workspace 定义强类型 `Item` 与对象安全
`ItemHandle` 两层接口，并通过 `ItemHandle for Entity<T: Item>` 统一完成类型擦除。
`EditorEvent` 到 `ItemEvent` 的转换只在 `Item for Editor` 中完成，`zcv-editor`
不得反向依赖 Workspace。Workspace 只按需实现当前存在的 Item 能力，不预先照搬
Zed 的协作、序列化和搜索注册接口。

主题消费者统一依赖 `zcv_theme` 的 crate 根能力路径：

```rust
use zcv_theme::{color, radius, space, syntax, typography, Theme};
```

主题 TOML、调色板和字体 token 由 `zcv-theme` 自己持有；`zcv` 不再保留
`crate::theme` 兼容门面或重复资源。

## 九、配置文件排序约定

Rust 导入由 `rustfmt.toml`（edition / style_edition 2024，与 Zed 一致）保证组内字母序；
组间顺序按约定保持 `std` → 外部 crate → 本 crate 三组（`group_imports` 是 nightly-only 选项，stable rustfmt 不生效，组间靠人工维护）。
TOML / JSON 配置文件是人工维护的清单，排序约定如下：

- **Cargo.toml**：机器消费为主，`dependencies` 按用途分组（内部 crate /
  引擎底层 / 工作区层），组内一律按 crate 名字母序。
- **主题 TOML**：语法 token 按大类空行分组，组内父 token 在前、子 token 跟随（如 `function` → `function.builtin`），不按字母序。
- **settings / keymap JSON**：键按逻辑序组织——settings 把用户最常改的
  `theme` 放在前面；keymap 按键功能分组（编辑键 → 方向键 → 词移动 →
  选择 → 剪贴板）。加载器为 `serde_json_lenient` 的文件可以写注释。
