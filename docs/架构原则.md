# zom 架构原则

> 本文记录 `zom` workspace 的长期架构原则。它回答「代码应该往哪里放、依赖应该怎么连、哪些边界不能越过」。

## 总原则

`zom` 的核心目标是把编辑器拆成可独立理解、可无头测试、可长期替换的能力层。GUI、命令、工作区、视图状态、编辑引擎和 AI 协议各自拥有清晰边界，通过 public API 连接。

架构判断优先级：

1. 先守住职责边界，再追求局部便利。
2. 先让核心能力可无头验证，再把它接进桌面外壳。
3. 先稳定语义和测试契约，再扩大 public API。
4. 同一能力只能有一个权威入口；多个触发源必须汇入同一入口，不能各自实现一份语义。

## 单入口原则

同一能力不能出现多入口现象。这里的「入口」指拥有业务语义、状态变更或长期契约的执行入口，不是按钮、快捷键、菜单项、命令面板项或 AI 调用这样的用户触发源。

允许多个触发源，但它们必须只做参数收集和意图转换，随后汇入同一个权威入口：

```text
快捷键 / 菜单 / 命令面板 / AI / UI 按钮
                    ↓
              同一个能力入口
                    ↓
              同一份状态变更语义
```

禁止为了接入方便给同一能力开第二条执行路径。典型反例包括：UI 按钮直接改状态而命令 handler 走另一套逻辑、AI 工具绕过命令系统调用内部 helper、快捷键和菜单分别维护两份参数解析、测试专用 public API 成为事实入口。

如果现有入口无法承载新调用方，应扩展原入口的参数、返回值、错误模型或底层抽象；不要并排新增一个语义相近的入口。

## Workspace 分层

Workspace 各 crate 的职责与依赖图见 [`README.md`](../README.md)。

每个 crate 是一个黑盒能力单元。跨 crate 只能依赖 public API，不依赖源码布局、私有模块或测试专用细节。

## 依赖方向

`zom-engine` 位于底座，不知道 UI、命令、AI、项目或桌面外壳的存在。

宿主层按职责依赖底层能力：

```text
zom-workspace → zom-engine
zom-command   → zom-engine / zom-workspace
zom-ai        → 独立协议层，不依赖编辑宿主层
zom-desktop   → 组合根，认识并组装所有运行期边界
```

`zom-command` 与 `zom-ai` 不互相依赖。AI、菜单、快捷键、命令面板等入口最终都汇入命令派发路径；扩展域命令由 `zom-desktop` 组合根注册和接线。

## 状态归属

状态归属用一个判据判断：

```text
同一文件开两个分屏不会不同的状态 → zom-workspace
同一文件开两个分屏会不同的状态   → view 模块
```

因此，文件路径、来源、脏状态、只读、保存点和 `Buffer` 生命周期属于 `zom-workspace`。光标、selection、fold、viewport、滚动位置属于 `view` 模块。

`zom-engine` 提供可复用的数据结构、编辑算法和事务能力，但不拥有宿主层的文件生命周期或具体视图实例。

## 命令原则

可命名的离散动作都是命令。键盘快捷键、命令面板、菜单、AI 和宏都应该收敛成 `(CommandId, CommandArgs)`，经唯一派发路径进入执行器。

快捷键、命令面板、菜单、AI 和 UI 按钮可以是同一命令的多个触发源，但不能各自拥有一套执行语义。属于命令的能力必须以命令 handler 为权威入口。

命令系统是汇聚点，不是全局服务。输入源产出意图，由组合根喂给执行器；扩展域不进入 `CommandContext`，需要宿主接力的动作通过 `HostEffect` 表达。

历史不归命令执行器。`editor.undo` 是命令，真实事务、历史节点和回放语义由 `zom-engine` 记录。

## 组合根原则

`zom-desktop` 是二进制入口和组合根。它可以认识所有运行期边界，因为组装就是它的职责。

组合根负责：

- 创建并连接 `Workspace`、`ViewSet`、`CommandRegistry`、`Keymap` 和桌面 shell。
- 把 OS 原始输入解码成宿主层意图。
- 注册内建命令和扩展域命令。
- 落地 `HostEffect`、窗口、渲染、配置、资源和平台差异。

如果未来 `zom-desktop::app` 中出现稳定、可复用、需要无头测试的编排能力，再抽出新的宿主 crate；不预建空抽象。

## Public API 原则

新增 public API 前必须说明三件事：

1. 长期语义是什么。
2. 调用方会依赖什么行为。
3. 用什么测试覆盖外部契约。

不要为了测试把 `private` 或 `pub(crate)` 提升为 `pub`。需要验证私有 helper 时，优先在源码旁边写单元测试；需要验证外部契约时，放到 crate 的 `tests/` 目录，只通过 public API 观察行为。

目录结构是实现细节，不承诺长期 import path。外部使用者优先从 crate root 导入稳定 public API。

## 可测试性原则

编辑引擎、命令派发、视口数学、文件生命周期和协议抽象应尽量可脱离 GUI 测试。

测试分层遵循：

```text
src/**      模块内部不变量和私有 helper
tests/      crate public API 的外部契约
examples/   可选接入实验台和人工体感验证
```

视觉呈现和人工体感验证不能替代机器测试。GPUI 相关行为可以使用框架要求的 harness，但仍要保持「内部状态测内部，外部行为测契约」的分工。

## 文档维护

本文只记录长期架构原则、边界判据和依赖方向。阶段计划、当前状态、逐文件账本和临时实现细节不进入本文；确需记录时，放入相应 crate 的 `docs/STATUS.md`、能力文档或根目录规划文档。
