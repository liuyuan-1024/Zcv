# 交互架构

本文规定跨 crate 的键盘、鼠标与焦点路由。具体组件的按键清单和实现细节留在对应模块与测试中。

## 输入路由与状态所有权

按键与鼠标点击不要求共用同一条分发路径。应根据输入携带的信息和目标是否确定选择路由，但所有路径都必须直接到达对应状态所有者，不能在 UI 层维护第二份业务状态：

```text
内置 keymap ──> Action ──> 焦点链上的 on_action handler ──> 状态所有者方法
菜单         ──> Action 或已知目标的直接调用 ──────────────> 状态所有者方法
工具栏/按钮  ──> 已绑定的目标实体 ─────────────────────────> 状态所有者方法
鼠标位置交互 ──> 命中目标与即时数据 ───────────────────────> 状态所有者方法
```

规则：

- `zcv-actions` 定义跨模块共享的 Action；只在单个实现模块使用的 Action 留在实现附近。
- `assets/keymaps/default-*.json` 只描述按键到 Action 的映射，不承载业务逻辑。
- `zcv-keymap` 负责加载、解析和注册内置 keymap，不决定具体命令行为。
- handler 由真实状态所有者或窗口根注册，不能通过第二套命令总线转发。
- 快捷键必须经 `Action` 与焦点链路由；不要伪造鼠标事件来复用按键处理。
- 鼠标控件已绑定明确目标时，应直接调用该目标的状态所有者方法，不应为了派发 `Action` 而改变焦点，也不应依赖当前焦点恰好位于目标之内。
- 菜单或按钮没有确定目标、语义确实由当前焦点决定时，可以 `dispatch_action`。
- 相同业务意图应收敛到同一状态所有者；若没有输入特有的数据或策略差异，优先复用同一个所有者方法，不复制业务步骤。

鼠标拖拽、点击位置、文本范围等携带即时数据的直接交互，应直接调用状态所有者方法。键盘命令需要相同行为时，应通过自身的 `Action` 路径到达相同所有者，而不是反向伪造鼠标事件。

## 焦点与上下文

键盘分发依赖焦点链与 `KeyContext`：

1. 可交互实体持有自己的 `FocusHandle`。
2. 渲染根节点设置与真实所有者对应的 `key_context`。
3. 该根节点注册相关 `on_action` handler。
4. 子输入控件需要继承外层命令时，外层上下文必须位于同一焦点链上。

上下文名称描述真实的聚焦所有者，例如编辑器、项目树或提交编辑区。不要用过宽的通用上下文掩盖所有权，也不要为同一所有者叠加含义重复的布尔上下文。

## 视觉焦点不是分发焦点

`FocusHandle::contains_focused` 表示自身或后代持有焦点，适合判断一整块交互区域是否活跃。`FocusHandle::is_focused` 只表示该句柄本身持有焦点，适合选择边框、树导航和输入目标等精确视觉状态。

二者不能互换：

- 外层区域需要在内部编辑器聚焦时继续响应命令，可以使用 `contains_focused`。
- 只有树本体聚焦时才显示选择边框，应使用 `is_focused`。
- 如果视觉状态取决于焦点变化，状态所有者必须在 focus/blur 时触发重绘，不能只在其他数据变化时偶然更新。

## 注册位置

- 组件专属命令在组件根节点注册。
- 跨整个工作区可达的命令由 `Workspace` 根节点或宿主装配层注册。
- 具体业务 crate 负责自己的 Action 行为；工作区框架只提供通用挂载位置。
- 初始化函数只注册协议、keymap 或真实全局能力，不通过副作用隐藏普通业务调用。

## 修改检查

新增或调整交互前，确认：

1. 键盘输入是否通过 `Action` 与正确的焦点链到达状态所有者。
2. 鼠标点击是否已经绑定明确目标；若是，是否直接路由到该目标而不依赖或改变焦点。
3. 不同输入路径是否收敛到同一状态所有者，且没有维护 UI 影子状态。
4. `KeyContext` 是否与实际焦点链一致。
5. 视觉状态需要的是 `is_focused` 还是 `contains_focused`。
6. 测试是否覆盖目标焦点下按键可达、非目标焦点时鼠标仍能命中其绑定目标，以及焦点变化后的视觉更新。
