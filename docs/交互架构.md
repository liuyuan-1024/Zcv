# 交互架构

> 描述项目中用户输入的路由模式、快捷键分层与组件类型边界。
> 本文是规范，代码和后续开发应遵守本文定义的规则。

---

## 1. 总则

输入设备只有两类：**键盘**和**鼠标**。任一操作可能由两者共同触发。

### 1.1 键盘只有一条路

键盘输入在 GPUI 中只有一种路径：

```text
按键 ──► bind_keys ──► dispatch_action ──► .on_action(handler) ──► 业务
```

没有其他选择。所有键盘快捷键最终都交给 `on_action` handler。

### 1.2 鼠标有两条路，由交互性质决定

鼠标事件有两条路径，决策条件是**这个鼠标事件是"交互"还是"命令触发"**（对齐 Zed 的架构）：

```text
鼠标事件 ──┬── 命令触发（按钮 / 菜单 / 通知 / 手势触发命令）
          │     └── dispatch_action ──► .on_action(handler) ──► 业务
          │
          └── 交互（点击条目 / 文本 / 拖拽，指向具体数据）
                └── 直接调用 Entity 方法（listener / weak 引用）
```

- **命令触发**：鼠标作为命令的 UI 载体（按钮、菜单项、通知动作、双击手势触发现有命令）。
  点击只表达"执行这个命令"，没有其他参数 —— 走 `dispatch_action` 与键盘/菜单合流。
- **交互**：鼠标直接操作数据（点击第几行、选中哪个文件、拖到哪）。
  事件上下文（坐标、click_count、modifiers）与目标数据直接可用 —— 直接调用 Entity 方法。

### 1.3 核心规则

**先区分意图，再复用底层状态操作。**

- **Panel 键盘命令**：`FocusOrHidePanel { panel }` 表达“显示并聚焦 / 聚焦 /
  已聚焦时隐藏”的三态意图。
- **Panel Glyph 点击**：只表达可见性切换，直接调用 Workspace/Dock 方法，
  不分派键盘 Action。两条路径复用同一组 Dock 状态操作。
- **交互**：项目树 `enter` 与点击文件行都"打开文件" —— 鼠标直接调
  `activate_selected(...)`，键盘 `TreeActivate` handler 内部也调同一个方法。
  **方法复用，而不是 dispatch 合流**：鼠标交互携带的事件上下文（click_count、坐标）
  action 表达不了，dispatch 反而引入焦点链依赖。

### 1.4 键盘与鼠标共享实现的两种方式

| 合流方式 | 适用场景 | 机制 |
|---------|---------|------|
| **dispatch 合流** | 命令（按钮/菜单/通知） | 鼠标 `dispatch_action` → 与键盘命中同一 `on_action` |
| **方法复用** | 交互（条目点击/文本点击） | 鼠标直接调 Entity 方法；键盘 action handler 内部调用同一方法 |

**为什么交互不 dispatch 合流（Zed 的依据）：**

1. 交互需要事件上下文（点击坐标、click_count、modifiers），action 类型表达不了这些参数；
   强行合流会让 handler 里堆满 `if` 分支。
2. `dispatch_action` 沿**焦点链**分发 —— 鼠标交互依赖焦点链意味着"点击前必须先聚焦"，
   并在组件自身 action handler 的回调链里产生 read 冲突（见项目树点击的历史教训）。
3. Zed 的做法：`project_panel` 的条目点击 `cx.listener` 直接调 `open_entry`，
   键盘 `enter` 的 action handler 也调 `open_entry` —— **同一个方法，两个入口**。
   `editor` 的鼠标点击（`element/mouse.rs`）同样直接调 `editor.select(...)`。

**判断标准：** 问自己——"这个鼠标事件是**操作数据**（交互），还是**触发命令**（命令载体）？"

- 操作数据 → 直接调 Entity 方法；键盘等效通过共享方法合流
- 触发命令 → `dispatch_action` 与键盘合流

## 2. 输入路由规范

### 2.1 命令型鼠标事件 → dispatch_action

鼠标作为**命令的 UI 载体**（按钮、菜单项、通知动作、手势触发命令）时，
与键盘快捷键触发同一命令，必须走 `dispatch_action` 合流。

```rust
// ✅ 正确：点击 dispatch_action，与按键合流

// 组件模块定义 action（快捷键绑定在 keymap JSON，见 3.1）
actions!(window_controls, [QuitWindow, MinimizeWindow, ToggleMaximizeWindow]);

// 点击 → dispatch_action（产生与按键相同的 action 类型）
pub(crate) fn render(window: &Window) -> gpui::Stateful<gpui::Div> {
    div()
        .child(pip(Pip::Close, active)
            .on_click(|_, window, cx| window.dispatch_action(Box::new(QuitWindow), cx)))
        .child(pip(Pip::Minimize, active)
            .on_click(|_, window, cx| window.dispatch_action(Box::new(MinimizeWindow), cx)))
        .child(pip(Pip::Maximize, active)
            .on_click(|_, window, cx| window.dispatch_action(Box::new(ToggleMaximizeWindow), cx)))
}

// keyboard → keymap JSON 绑定命中同一 action → 同一 on_action handler
// {"bindings": {"cmd-q": "window_controls::QuitWindow", ...}}
window.dispatch_action(Box::new(QuitWindow), cx)
```

handler 定义在组件模块中，在 Workspace 注册：

```rust
// Workspace::render 中注册 handler
.on_action(window_controls::handle_quit)
.on_action(window_controls::handle_minimize)
.on_action(window_controls::handle_toggle_maximize)
```

**规则：** 任何命令型鼠标事件（按钮/菜单/通知），必须使用 `dispatch_action`，不得直接调用业务方法。

### 2.2 交互型鼠标事件 → 直接调用 Entity 方法

交互点击指向具体数据（点击了第几行、哪个文件），在 `on_mouse_down` / `on_click` 中
**直接调用 Entity 方法**；键盘等效通过共享方法合流（不是 dispatch）。

```rust
// ✅ 正确：树行点击直接调用 Entity 方法（对齐 Zed 的 cx.listener 路径）
// 键盘 enter 的 TreeActivate handler 内部调用同一个 activate_selected。
.on_mouse_down(MouseButton::Left, {
    let focus = render_context.focus.clone();
    let weak = render_context.weak.clone();
    move |event, window, cx| {
        window.focus(&focus);
        if let Some(tree) = weak.upgrade() {
            tree.update(cx, |tree, cx| {
                tree.state.borrow_mut().select(&path);
                match event.click_count {
                    1 => tree.activate_selected(false, window, cx), // 单击：预览
                    _ if is_dir => {}
                    _ => tree.activate_selected(true, window, cx),  // 双击：打开
                }
            });
        }
        cx.stop_propagation();
    }
})
```

**注意：** 交互闭包内对自身 Entity 的 update 链中，**不能再 read 自身**（同一帧内实体正在被 update）。
需要自身数据时用闭包捕获（state/focus/weak 引用），需要调方法时走 `weak.upgrade()` 后 `update`。

**规则：** 交互型点击不经过 action 分发。数据由闭包捕获；键盘等效的共享实现放在
Entity 的私有方法（如 `activate_selected`）中，鼠标与键盘 handler 都调用它。

### 2.3 决策表

| 场景 | 类型 | 路由 |
|------|------|------|
| 底栏「项目树」图标点击 | 命令（✅ cmd-shift-e） | `dispatch_action` → `on_action` |
| 顶栏「设置」图标点击 | 命令（✅ cmd-,） | `dispatch_action` → `on_action` |
| 窗口控制关闭圆点点击 | 命令（✅ cmd-q） | `dispatch_action` → `on_action` |
| 底栏「终端」图标点击 | 命令（✅ cmd-j） | `dispatch_action` → `on_action` |
| 文件树行点击 | 交互（指向具体行） | `on_mouse_down` → 直接调 Entity 方法，键盘等效走共享方法 |
| 标签栏 tab 关闭按钮点击 | 交互（指向具体 tab） | `on_click` → 直接 handler |

## 3. 快捷键注册规范

### 3.1 全局快捷键

全局快捷键不依赖焦点上下文，在任何时候都生效。

**定义位置：** `assets/keymaps/default-{platform}.json` 中**不带 `context` 的分组**（窗口控制、面板开关、项目选择器等）。
**加载位置：** Workspace::new 中 `keymap::load(cx)` 一次性解析 JSON 并 `cx.bind_keys()`（对齐 Zed 的 `assets/keymaps/default.json` 机制）。
**handler 注册：** Workspace::render 中 `.on_action()`。

```jsonc
// assets/keymaps/default-macos.json —— 无 context 的分组 = 全局
{
  "bindings": {
    "cmd-shift-e": ["dock::FocusOrHidePanel", { "panel": "project-tree" }],
    "cmd-shift-g": ["dock::FocusOrHidePanel", { "panel": "version-control" }],
    "cmd-s": "workspace::Save"
  }
}
```

```rust
// keymap/mod.rs —— JSON 解析 + 注册（组件模块不再写 key_bindings() 函数）
pub(crate) fn load(cx: &App) -> Result<KeyBindings> {
    // include_str 嵌入平台 JSON，按 action 名解析为 gpui KeyBinding
}

// Workspace::new —— 一次性加载注册
let keybindings = keymap::load(cx).expect("内置 keymap 应完整有效");
cx.bind_keys(keybindings.bindings.clone());
cx.set_global(keybindings);

// Workspace::render
.on_action(dock::handle_toggle_project_tree)
```

### 3.2 上下文快捷键

上下文快捷键仅在组件聚焦时生效：JSON 中声明 `context` 分组，组件 Render 用 `.key_context("...")` 提供上下文。

```jsonc
// keymap JSON —— 声明上下文分组
{
  "context": "ProjectTree && not_editing",
  "bindings": {
    "up": "project_tree::TreeSelectPrev",
    "down": "project_tree::TreeSelectNext",
    "space": "project_tree::TreeActivate"
  }
}
```

```rust
// 组件模块 —— 只定义 action 类型与 handler
actions!(project_tree, [TreeSelectPrev, TreeSelectNext, TreeActivate, ...]);

impl gpui::Render for ProjectTree {
    fn render(&mut self, window: &mut Window, cx: &mut Context<Self>) -> impl gpui::IntoElement {
        div()
            .size_full()
            .track_focus(&self.focus)
            .key_context(self.dispatch_context(window, cx))  // "ProjectTree && not_editing"
            .on_action(cx.listener(Self::handle_tree_select_prev))
            .on_action(cx.listener(Self::handle_tree_activate))
    }
}
```

`key_context` 的作用是避免冲突而非解决焦点丢失。"down" 在编辑器里是下一行，在文件树里是下一项——焦点在哪就用哪套绑定。没有自己焦点的组件不需要上下文，它们的快捷键永远是全局的（JSON 无 `context` 分组）。

### 3.3 两种绑定方式对比

| | 全局快捷键 | 上下文快捷键 |
|---|---|---|
| 适用范围 | 始终生效 | 仅组件聚焦时生效 |
| JSON 定义位置 | 无 `context` 的分组 | 带 `context` 的分组 |
| 注册时机 | Workspace::new 中 `keymap::load` 一次性注册 | 同左（JSON 统一加载） |
| 上下文提供 | 不需要 | 组件 Render 中 `.key_context("...")` |
| handler 类型 | 自由函数，Workspace 注册 | `cx.listener(Self::method)`，组件自注册 |
| handler 访问状态 | 通过 Workspace 方法或 Window API | 通过 `&mut self` |

### 3.4 快捷键注册流程

```text
组件模块定义 action 类型 ──► keymap JSON 声明绑定（context 分组）──► Workspace::new 中
  (actions! macro)              (assets/keymaps/default-*.json)      keymap::load + cx.bind_keys()
       │
       ▼
GPUI 焦点树（key_context）路由到 on_action handler
       │
       ├─► 全局快捷键 → Workspace::render 中 .on_action(自由函数 handler)
       └─► 上下文快捷键 → 组件 Render 中 .on_action(cx.listener(Self::method))
```

每个组件模块负责：
- 定义自己的 action 类型（`actions!`）
- 在 keymap JSON 中声明自己的快捷键绑定（按 `context` 分组）
- 定义自己的 handler（自由函数或 `cx.listener` 方法）

Workspace 负责：
- `keymap::load` 一次性加载并注册全部绑定
- 在 render 中注册全局 action 的 `on_action` handler

keymap 还提供 `display_shortcut(action_name)` 反向查询（按钮上显示快捷键提示，如 `⌘⇧E`）。

## 4. 组件类型与交互能力

### 4.1 各类型允许的交互能力

| 组件类型 | actions! | 快捷键绑定 | handler 类型 | 焦点 | 跨帧状态 |
|---|---|---|---|---|---|
| **Entity** | ✅ | ✅ 全局或上下文 | 自由函数或 `cx.listener` | ✅ 可选 | ✅ |
| **函数式** | ✅（仅全局） | ✅（全局，由 Workspace 注册 handler） | 自由函数 | ❌ | ❌ |
| **Builder** | ❌ | ❌ | 通过 `on_click` 参数内联 | ❌ | 构建期持有 |

**关键规则：** 函数式组件可以有 `actions!` + 快捷键绑定 + handler（如 `window_controls`），这不改变它的分类。因为函数式组件也可能有按键交互，这些交互必须使用 action 来实现点击和按键统一。只要不引入 struct 和 Render/IntoElement trait，依然是函数式组件。

### 4.2 各组件的交互能力

| 组件 | 类型 | actions! | JSON 绑定 | handler 位置 | 焦点 | 状态模式 |
|---|---|---|---|---|---|---|
| `Workspace` | Entity(root) | ❌ | 集中加载（`keymap::load`） | 内联 + 子模块函数 | ✅ | `Rc<RefCell<LayoutController>>` |
| `TopBar` | Entity | ✅ | 全局 | Workspace 注册 | ❌ | 字段直存 |
| `StatusBar` | Entity | ❌ | ❌ | 父组件直接调用 | ❌ | 字段直存 |
| `ProjectTree` | Entity | ✅ | 上下文（`ProjectTree`） | 自有 `cx.listener` | ✅ | `Rc<RefCell<State>>` |
| `WindowControls` | 函数式 | ✅ | 全局 | Workspace 注册 | ❌ | ❌ |
| `Glyph` | Builder | ❌ | ❌ | 调用方通过 `on_click` 传入 | ❌ | 构建期持有 |
| `tree` 辅助 | 函数式 | ❌ | ❌ | ❌ | ❌ | ❌ |
| `frame` 辅助 | 函数式 | ❌ | ❌ | ❌ | ❌ | ❌ |
| `workspace/mod` 的布局渲染辅助 | 函数式 | ❌ | ❌ | ❌ | ❌ | ❌ |

## 5. Entity 状态管理

Entity 的状态管理有三种模式：

| 模式 | 方案 | 适用场景 | 项目实例 |
|---|---|---|---|
| **A** | 直接 struct 字段 | 状态只在本组件 Render 中读取 | TopBar、StatusBar |
| **B** | `Rc<RefCell<T>>` | 状态需在多个闭包/回调中共享 | ProjectTree（`uniform_list` 闭包 + `on_mouse_down` 闭包） |
| **C** | Controller + Snapshot | 状态逻辑复杂，需独立单元测试 | `LayoutController` + `LayoutSnapshot` |

**`Rc<RefCell<T>>` 的使用边界：** 只在 GPUI 列表渲染器（`uniform_list`）的闭包需要与外部事件闭包共享状态时使用。这是 GPUI 自身 API 约束导致的必要妥协，不是推荐的状态管理方式。非 uniform_list 场景不使用 `Rc<RefCell>`，直接用 struct 字段。
