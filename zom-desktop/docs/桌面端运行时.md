# 桌面端运行时手册

> 本手册规定 `zom-desktop` 的**运行时基础设施**：设置、窗口、平台、命令键位接入、事件与通信、错误处理、资源、异步、持久化、生命周期、CLI、焦点系统。涵盖应用"怎么跑起来、怎么联起来、怎么收尾"的全部规约。

## 词汇预设

正文出现的几个常用术语：

- **L4 区域**：窗口级外壳区域，含 TopBar / BottomBar / EditorGrid / LeftDock / RightDock / BottomDock。窗口几何拓扑的最大单元。
- **L3 组件**：业务组件，含 CommandPalette / FileTree / TabStrip / EditorView / 等。每个 L3 组件有自己的 UI 状态与交互语义，但**不持有领域状态**（领域状态在底层 crate）。
- **L2 视觉原语**：Button / Glyph / Tooltip / Popover 等无领域语义的可复用 UI 原语。
- **应用域运行时**：`zom-desktop::app` 模块，负责装配底层 crate 实例（Workspace / ViewSet / CommandRegistry / Keymap / AiProvider）、配置、文本路由与后台拍点；不接触 GPUI、窗口、像素、焦点 handle、字体或布局。
- **GPUI 外壳**：`zom-desktop::shell` 模块，负责窗口、视觉、平台输入与 `HostEffect` 落地；只能把输入转成 `App` API 调用，不能读取 app 内部结构。

L3 / L4 的所有权与依赖矩阵、跨层依赖规则不在本手册范围。

## 一、设置系统

### 1.1 定位

设置系统是 zom-desktop 所有用户配置的母体。主题、locale、字号、键位——全部由设置系统承载。

设置文件是**单一事实源**：程序内任何变更都立即回写到文件；文件被外部编辑器修改时自动重载触发 observable。

### 1.2 文件位置与格式

格式统一为 **TOML**，与主题、language config 保持一致。

| 作用域 | 路径 |
|---|---|
| 用户级 | `~/.zom/settings.toml`（全平台一致） |
| Workspace 级 | `<project_root>/.zom/settings.toml` |

用户级目录与 workspace 级**同名 `.zom/`**，对称——一个挂在 `$HOME`，一个挂在项目根。**不走平台惯例路径**（mac `Application Support`、linux `~/.config`、windows `%APPDATA%`）；zom 面向开发者，对称性优先于 OS 惯例。

`~` 解析集中在 `shell::platform::paths`，避免 L2/L3 直接拼路径。

第一版**单文件**——所有配置（含 keymap）放同一个 `settings.toml`。

### 1.3 第一版 schema 草案

```toml
# ~/.zom/settings.toml

# 顶层：影响整个应用的全局偏好
theme  = "dark"
locale = "zh-CN"

# [ui]：UI 层偏好
[ui]
font_size = 13

# [editor]：编辑器偏好
[editor]
font_size = 14

# [keymap]：全局键位（用第三章定义的逻辑键；语义在 zom-command）
[keymap]
"mod-s"        = "editor.save"
"mod-shift-p"  = "command-palette.open"
"mod-1"        = "panel.toggle.file_tree"

# [keymap.context.<component>]：上下文键位（组件 focus 时生效）
[keymap.context.editor]
"alt-up"       = "editor.move-line-up"
"alt-down"     = "editor.move-line-down"

[keymap.context.file_tree]
"enter"        = "file_tree.open-selected"

# [keymap.darwin] / [keymap.linux]：平台特定覆盖
[keymap.darwin]
"cmd-,"        = "settings.open"

[keymap.linux]
"ctrl-comma"   = "settings.open"
```

### 1.4 命名空间约定

- **顶层**：影响整个应用的全局偏好（theme、locale）
- **分组 `[domain]`**：按作用域分组的偏好（ui、editor、keymap）
- **避免深度嵌套**：不超过两级
- 字段命名 snake_case；布尔字段避免否定语义（用 `enable_x` 而非 `disable_x`）

### 1.5 优先级与合并

```
内置默认  ←  用户级 settings.toml  ←  workspace 级 .zom/settings.toml
```

| 字段类型 | 合并规则 |
|---|---|
| Scalar | 后者覆盖前者 |
| Table | 递归合并，同 key 后者覆盖 |
| Array | 后者**整体替换**前者，不拼接 |

Array 整体替换是有意的——拼接语义会让用户难以"清空"某个数组。

### 1.6 强 schema + 类型安全 API

设置定义为 Rust struct + serde。组件通过 `cx.settings().theme` 访问，编译期保证字段存在。**禁止** `cx.settings().get("theme")` 这类字符串 key 访问。

未知字段**警告但不阻塞加载**——便于版本回退与多设备同步。

### 1.7 失败处理

| 失败类型 | 处理 |
|---|---|
| 文件不存在 | 全部默认；首次启动**不主动创建**文件 |
| 整文件解析失败 | 全部默认 + 持续 toast 报错 + 日志位置 |
| 单字段解析失败 | 该字段默认 + 一次性 toast + 日志 |
| 未知字段 | 警告日志，不报错 |
| Workspace 文件不存在 | 静默，只用用户级 |

**绝不静默忽略整文件失败**。

### 1.8 双向同步

外部文件变更：fs watch → SettingsRegistry reload → merge → 触发 observable。

程序内变更：`cx.settings_mut().set_theme(...)` → 立即触发 observable → 异步写回 settings.toml（debounced）。

写回时保留原文件的注释与格式（用 `toml_edit` 而非 `toml`）。**这条很重要**——用户在配置文件里写的注释是有价值的内容，不能被程序覆盖。

### 1.9 SettingsRegistry

`SettingsRegistry` 与 `ThemeRegistry` / `LocaleRegistry` 结构平行：

- 启动时加载用户级 + 当前 workspace 级 → merge → 提供 active settings 句柄
- 监听两份文件的变更，触发 reload
- 提供 `cx.settings()` 入口

切换 workspace 时重新 merge。

### 1.10 keymap 段的特殊处理

`[keymap]` / `[keymap.context.*]` / `[keymap.darwin]` / `[keymap.linux]` 是 desktop 解析的，**最终交给 zom-command 的 `Keymap`** 类型使用：

```
settings.toml [keymap.*] 段
    ↓
desktop 解析（含平台逻辑键映射，见第三章）
    ↓
构造 zom-command::Keymap 实例（前缀 trie）
    ↓
KeyChord 流入 → KeymapResolution → CommandId
```

`Keymap` / `KeyChord` / `KeymapResolution` 这些类型由 `zom-command` 提供，desktop 不重新发明，只负责"从配置文件构造它们"。

### 1.11 Workspace 级配置的信任

第一版**信任所有 workspace 级配置**——打开任何项目都直接加载 `.zom/settings.toml`，无信任提示。

将来必须补 workspace trust 机制（参考 VSCode "Workspace Trust"、Zed 同类机制）。第一版用户全部是项目作者本人，trust 是过度设计。

## 二、窗口模型

### 2.1 多窗口

zom-desktop 支持多窗口。所有窗口**对称**——不区分"主窗口"与"次窗口"。

### 2.2 跨窗口共享 vs 每窗口独立

| 全局单实例（跨窗口共享） | 每窗口独立 |
|---|---|
| `SettingsRegistry`（settings） | `WorkbenchFrame`（L4 region 树） |
| `ThemeRegistry`（active theme） | `EditorGrid`（split tree、tab group） |
| `LocaleRegistry`（active locale） | Dock 状态（显隐、尺寸、active panel） |
| 字号（`ui_font_size` / `buffer_font_size`） | 所有 L3 组件实例与其 UI state |
| `CommandRegistry`（来自 zom-command） | 临时层（SurfaceLayer、BubbleLayer） |
| `Keymap`（来自 zom-command） | `ViewSet`（来自 zom-view） |
| `AiProvider`（来自 zom-ai） | |

`Workspace`（来自 zom-workspace）的归属见 2.3。

### 2.3 Workspace 与窗口的关系

第一版**每窗口绑一个 workspace**。打开新 workspace 的两种方式：

- 在当前窗口打开（替换当前 workspace）
- 在新窗口打开（保留当前 workspace）

跨窗口允许打开同一 workspace。

### 2.4 跨窗口的资源共享

| 资源 | 共享粒度 |
|---|---|
| LSP 实例（将来） | per workspace（跨窗口共享同 workspace） |
| 文件监听 / file watcher | per workspace |
| 项目级索引（符号、文件路径） | per workspace |
| AI 会话 | per window |
| 最近文件 / 最近 workspace | 全局共享 |
| 命令面板使用频率（rank） | 全局共享 |

### 2.5 窗口关闭

- **关闭非最后窗口**：销毁该窗口的所有 UI state；窗口持久化由窗口持久化层处理（见 2.6）
- **关闭最后窗口**：默认退出。macOS 例外——按平台惯例保持进程、隐藏窗口、菜单栏仍激活

### 2.6 持久化边界

持久化整体由第九章规定。窗口模型侧只约定：

- 全局共享状态 → 全局持久化层（`settings.toml` 等）
- 每窗口独立状态 → 窗口持久化层，按 workspace 写快照
- 下次打开同 workspace 时恢复布局

详细规则见本手册第九章。

## 三、平台差异

### 3.1 处理原则

平台差异必须**集中收纳到尽可能少的地方**。其他模块编程时假装平台不存在。集中点：`shell::platform`。

L2 / L3 组件**不允许** `#[cfg(target_os = "...")]`。所有平台分支都在 `shell::platform` 一层内完成。

### 3.2 OS 事件 → KeyChord 解码

`zom-command` 只吃归一化的 `KeyChord`，**不处理 OS 事件**。OS 键盘事件到 `KeyChord` 的解码归 `shell::platform::keyboard`：

```
GPUI raw key event（含平台特定 keycode、modifier 标志）
    ↓
shell::platform::keyboard 归一化
    ↓
zom-command::KeyChord
    ↓
zom-command::Keymap::resolve → KeymapResolution
    ↓
CommandQueue
```

解码层处理的差异：

- macOS Cmd vs Linux/Windows Ctrl 的修饰键判定
- AltGr 在 Windows / Linux 上的特殊处理
- 数字小键盘按键映射
- 死键 / 组合键的归一化

KeyChord 的语义由 `zom-command` 定义，本手册不重复。

### 3.3 逻辑快捷键

键位定义中使用**逻辑修饰键**，第一版提供以下五个：

```
逻辑键    macOS         Windows / Linux
mod       Cmd           Ctrl
alt       Option        Alt
shift     Shift         Shift
ctrl      Control       Control
fn        Fn            Fn
```

`mod / alt / shift / ctrl` 是用户书写 keymap 时使用的四个修饰键；`fn` 仅由归一化阶段在事件链路中产出，用于映射 F-row 等需要 Fn 才能触发的物理键，用户级 keymap 通常不直接拼写。

平台不对称的快捷键需求走 3.4 的 `[keymap.darwin]` / `[keymap.linux]` 覆盖段。

`settings.keymap` 形如：

```toml
[keymap]
"mod-s"        = "editor.save"
```

逻辑键 → 实际键的映射在 `shell::platform::keymap_logical`。无法识别的修饰键由 keymap 解析阶段报错（参见 1.7 的字段失败处理）。

### 3.4 平台特定 keymap

少数非对称场景用平台段覆盖：

```toml
[keymap.linux]
"ctrl-comma"   = "settings.open"
```

合并规则：先加载通用段，再用当前平台段覆盖同 CommandId 的绑定。其他平台段静默忽略。

### 3.5 shell::platform 的职责边界

| 在 `shell::platform` 内 | 不在 |
|---|---|
| OS key event → KeyChord 解码 | KeyChord 语义（在 zom-command） |
| 逻辑键 → 实际键映射 | Keymap 解析（在 zom-command） |
| 窗口管理调用（最小化、最大化、全屏、关闭） | UI 渲染（GPUI 已抽象） |
| 文件选择对话框 | 文件 I/O（标准库 / 跨平台 crate） |
| 剪贴板平台差异适配 | 网络 |
| 平台路径（配置、缓存、日志目录） | 业务逻辑 |
| 菜单栏（如有） | 任何平台无关的代码 |

### 3.6 窗口控制按钮

zom-desktop 自绘窗口控制按钮，跨平台采用统一的 macOS 红绿灯设计。**不使用 OS 原生标题栏**。

理由：视觉一致、与 TopBar 融为一体、规避 Windows 标题栏扩展限制。

### 3.7 菜单栏

第一版**不引入原生菜单栏**。所有功能通过命令面板、键位、外壳按钮访问。

理由：菜单栏与命令系统职责重复（菜单是命令的视图）；跨平台菜单栏机制差异极大；现代 IDE 大量依赖命令面板。

第二版可能为 macOS 补最小菜单栏（应用名 / Edit / Window / Help）。

### 3.8 触控板 / 滚动 / 拖放

跟随 OS 行为，由 GPUI 抽象。`shell::platform` 不介入。如发现 GPUI 行为不一致，优先向 GPUI 上游修复。

## 四、命令与键位接入

本章规定 zom-desktop 作为组合根，如何接入 `zom-command` 的命令系统与键位模型。**不重复 zom-command 自己的设计**（CommandId 字符串约定、CommandArgs 模型、Keymap 前缀 trie、CommandContext 等在 zom-command 已定）。

### 4.1 命令注册的组合根

desktop 是命令注册的最终汇聚点，启动序列：

```
1. 创建空 CommandRegistry
2. 安装 `zom_command::commands::*` catalog
   ── 引入编辑命令（insert/delete/undo/movement 等）与会 emit HostEffect 的 UI 命令
3. shell 实现 HostEffect 翻译
   ── panel.toggle.<id> / window.minimize / window.toggle_maximize 等
4. 若启用 AI：desktop 注册 AI 命令
   ── handler 闭包捕获 AiProvider 句柄(这是 desktop 让 ai 与 command 在组合根相遇的形式)
5. 将来：插件 host 在此调用 CommandRegistry::register
```

**desktop 内的"UI 命令"是 desktop 必须自己写 handler 的那一类**：

| UI 命令 | handler 做的事 |
|---|---|
| `panel.toggle.file_tree` | 切换 Dock 中 FileTree 的显示 |
| `command-palette.open` | 打开命令面板 Surface |
| `theme.cycle` | 在 ThemeRegistry 中切换主题 |
| `settings.open` | 打开 settings 编辑界面 |

这些 handler 操作的是 desktop 自己的视觉状态，因此必须在 desktop 注册。

### 4.2 命令面板（CommandPalette）

CommandPalette 是 desktop 的 L3 组件，使用 `CommandRegistry` 提供的能力：

- 列出所有已注册命令（`registry.list()`）
- 按 fuzzy 匹配筛选（`logic.rs` 中的纯算法）
- 用户选择 → 派发 `(CommandId, CommandArgs::empty())`

命令的 `title` 通过 i18n 显示——见 4.5。

### 4.3 AI 意图到命令的翻译

`zom-ai::AiAction` 是 plain 意图（含 `command: String` + args）。desktop 组合根负责把它解析为 `(CommandId, CommandArgs)`：

```
AiProvider 返回 AiAction
    ↓
desktop 组合根的 AiActionTranslator
    ↓
(CommandId, CommandArgs)
    ↓
CommandQueue
```

`AiActionTranslator` 是 desktop 内的薄薄一层，捕获了"AI 知道的命令词表"。zom-ai 与 zom-command 仍然没有依赖边——它们只在 desktop 这里相遇。

### 4.4 键位三层模型

键位定义在 `settings.keymap`，desktop 解析后构造 `zom-command::Keymap` 实例。三层 dispatch 顺序：

```
1. 全局键位       [keymap]
                  不受 focus 影响

2. 上下文键位     [keymap.context.<component>]
                  组件 focus 时生效；目标必须是 Command

3. 文本输入 fallback
                  未被前两层捕获的可打印字符
                  转发给当前 focus 的文本输入目标
                  EditorView / 单行输入框 / 命令面板搜索框等共享
```

**上下文键位的目标也必须是 Command**——不允许绑组件本地 Rust 类型。组件如果想让某个局部行为可绑键位，必须先把它注册为 Command（如 `file_tree.expand-node`）。

文本输入 fallback：未匹配 keymap 的可打印字符，由 desktop 转换为 `editor.insert_text { text }` 命令（或同等的当前 focus 目标的命令），仍然走 `CommandQueue` 派发。**所有编辑动作都是命令**——这是 zom-command 的核心原则，desktop 不绕开。

### 4.5 命令的 i18n title

命令在用户界面显示时（命令面板、菜单、tooltip）需要 i18n title。desktop 维护一个 `CommandId → i18n_key` 表，由 desktop 的 `copy` 模块按 `cx.locale()` 解析：

```rust
// shell/commands/copy.rs
pub fn title_for(cx: &App, id: &CommandId) -> &'static str {
    match (id.as_str(), cx.locale()) {
        ("editor.save", Locale::ZhCN) => "保存",
        ("editor.save", Locale::EnUS) => "Save",
        ("panel.toggle.file_tree", Locale::ZhCN) => "切换文件树",
        ("panel.toggle.file_tree", Locale::EnUS) => "Toggle File Tree",
        // ...
    }
}
```

新增命令时 desktop 这里必须补翻译，否则 match 编译错——这是 desktop i18n 的"编译期穷举"原则：缺翻译永远是编译错，不是运行时漏文案。

底层 crate 的命令 title 由对应 catalog 维护；desktop 只负责把 keymap 反查结果和本地化展示接到 UI，不在组件里手拼命令字符串。

## 五、事件与通信

本章规定 zom-desktop **内部**的"行为传递"机制。跨 crate 的领域调用（修改 buffer、操作 view、派发命令）走对应 crate 的 public API，不在本章范畴。

### 5.1 通信机制决策树

```
我要传什么？
├─ 用户可名、可绑键位的功能              → Command（zom-command；见第四章）
├─ 组件自己 runtime 状态变化             → 组件/runtime 自己处理
├─ 组件动作 + workspace/session 副作用   → App 组合后产出 HostEffect
├─ 父→子组件的直接行为                    → 回调注入（5.2）
├─ desktop 内跨多层 / 跨兄弟组件的事件    → Entity Event（5.3）
├─ desktop 全局视觉状态变化               → Observable（5.4）
├─ 修改 buffer / view                    → 派发 Command 或直接调底层 crate API
└─ 监听底层 crate 状态变化                → observe 底层 crate 提供的 Entity 句柄
```

GPUI Action **不出现在决策树里**——它是 zom-command 内 Keymap dispatch 的实现机制，组件作者不直接接触。

`App` 不是所有组件动作的中转站。纯组件 runtime 状态（例如文件树选择、展开/折叠、临时重命名态、删除确认态）应由该组件直接处理；只有动作需要同时触碰组件意图与 `WorkspaceSession` / workspace / view 等应用域状态时，才进入 `App`，并通过窄端口返回声明式 `HostEffect`。

### 5.2 回调注入

L3 组件 Props 默认通过回调接收父级行为：

```rust
pub struct FileTreeProps {
    pub workspace: Entity<Workspace>,         // 来自 zom-workspace
    pub on_open: Box<dyn Fn(PathBuf, &mut App)>,
    pub on_request_command: Box<dyn Fn(CommandId, CommandArgs, &mut App)>,
}
```

判定准则：**父级想知道"子组件发生了某个具体动作"时用回调**。回调是显式的、类型安全的、可注入 mock 测试。

需要派发命令时，回调内调用调用方持有的 CommandQueue / CommandExecutor，而不是组件自己直接持有命令派发链路。

### 5.3 Entity Event

跨多层、跨兄弟组件通信时用 GPUI 的 Entity Event 机制：

```rust
pub enum FileTreePanelEvent {
    FileActivated(PathBuf),
}

impl EventEmitter<FileTreePanelEvent> for FileTreePanelState {}

cx.emit(FileTreePanelEvent::FileActivated(path));

cx.subscribe(&panel, |this, _, event, cx| { ... });
```

使用规则：

- **必须有明确的源 entity**：subscribe 时显式 `&entity_handle`，**禁止"无源订阅"**
- **事件携带 payload**：无 payload 用 Observable
- **Event 类型不跨 crate 暴露**：是组件实现细节；跨 crate 通信用 Command 或显式 Props

### 5.4 Observable

desktop 全局视觉状态变化用 observe：

```rust
cx.observe(&theme_registry, |this, _, cx| {
    cx.notify();   // 仅触发重渲染
});
```

判定准则：

- **有 payload 用 Entity Event**
- **无 payload、表达"状态变了、自己去读最新值"用 Observable**

例：主题切换 / locale 切换 / 字号变更都是 Observable。

底层 crate（workspace / view 等）的状态变化也以 observe 形式接入——desktop 把它们的 entity 句柄持有后 observe。

### 5.5 错误的呈现

底层 crate 的 `Display` / `Error` 用英文（它们没有 locale 概念）。desktop 在呈现给用户时翻译：

```rust
fn translate_workspace_error(cx: &App, err: &WorkspaceError) -> String {
    match (err, cx.locale()) {
        (WorkspaceError::FileNotFound(p), Locale::ZhCN) =>
            format!("文件不存在：{}", p.display()),
        (WorkspaceError::FileNotFound(p), Locale::EnUS) =>
            format!("File not found: {}", p.display()),
        // ...
    }
}
```

呈现层级（toast / banner / dialog）由 desktop 决定。技术细节同时进日志（不依赖 i18n）。

### 5.6 硬禁止全局事件总线

任何形式的全局 EventBus / MessageHub / GlobalDispatcher 都**不允许**出现在 zom-desktop。

理由：难追踪、难测试、容易腐烂。

跨组件通信只允许：

- **Entity Event**：必须有明确的源 entity
- **Command**：用户语义的全局动作，由 CommandRegistry 集中维护

### 5.7 键盘输入完整路径

```
GPUI raw key event
    ↓
shell::platform::keyboard 解码为 KeyChord
    ↓
zom-command::Keymap::resolve（三层 dispatch）
    ├─ 全局键位匹配 → CommandQueue
    ├─ 上下文键位匹配 → CommandQueue
    └─ 都不匹配 → 文本输入 fallback
                  ↓
              desktop 把字符包装成 editor.insert_text 命令 → CommandQueue
    ↓
zom-command::CommandExecutor 排空队列，handler 执行
    ↓
handler 调用 Workspace / ViewSet / Engine API 修改状态
    ↓
对应 Entity notify
    ↓
观察该 Entity 的 L3 组件 re-render
```

整条路径里 GPUI Action 只在 Keymap 内部 dispatch 时作为实现细节出现，组件作者从头到尾不直接接触。

## 六、错误处理

### 6.1 哲学

错误处理被切成两半：

```
底层 crate 错误（各自已定型，desktop 不重新发明）
  zom-engine     分层 thiserror（坐标 / 编辑 / 事务 / 存储 / 历史）
  zom-workspace  WorkspaceError / WorkspaceResult
  zom-command    CommandError
  zom-ai         AiError / ProposalRejected
        ↓ 通过 ? 上抛
desktop 的责任
  - desktop 自己的错误（settings 加载、theme 解析、I/O）
  - 把底层 crate 错误冒泡转化为用户可见呈现
  - panic hook + 数据救援
  - 日志（tracing）
  - i18n 化错误消息
```

desktop 只负责**中转、呈现、保护**，不重新定义错误模型。

### 6.2 错误风格

| 位置 | 风格 |
|---|---|
| 底层 crate | thiserror + 自定义 Error enum（已定，不动） |
| desktop 内部默认 | `anyhow::Result<T>` + `Context` |
| desktop 内工具模块 | 局部用 thiserror（如 `ThemeLoadError`、`SettingsParseError`、`KeymapParseError`），在 desktop 内被 anyhow 包装传播 |
| 跨 crate 转换 | 底层 Error 通过 `?` 自动 From 转入 anyhow，链路上下文保留 |

理由：desktop 是应用层，大部分错误只是"展示给用户"，弱类型 + 字符串链上下文足够；局部工具模块在 desktop 内仍想 match 分类处理时用 thiserror。

### 6.3 panic vs Result 的边界

| 场景 | 处理 |
|---|---|
| 编程错误（违反不变量、不可能状态、契约违反） | `panic!` / `unreachable!` / `debug_assert!` |
| 外部世界（文件、网络、解析、用户输入） | `Result` |
| 第三方 / 底层 crate 调用 | 必须 `?` 上抛或显式处理 |

**desktop 顶层（main）允许 panic**，但必须有 panic hook（6.6）。
**desktop 内部代码禁 `.unwrap()`**——测试代码、`// SAFETY:` 注释的"明确不可能"场景除外。CI 用 `clippy::unwrap_used` lint 强制。

### 6.4 用户可见错误的四级呈现

```
1. Inline    内联在相关元素旁、不打断
             例：保存按钮旁的"无效文件名"

2. Toast     窗口角落浮起、几秒后自动消失
             例：自动保存失败 / 主题加载 fallback

3. Banner    面板顶部常驻横幅，需用户主动关闭
             例：LSP 进程崩溃 / 文件被外部修改未同步

4. Dialog    模态对话框，必须用户操作
             例：未保存内容关闭确认 / 严重错误退出
```

判定准则：

- 阻塞继续操作 → Dialog
- 需用户知晓但可继续 → Banner
- 短暂提示、不关键 → Toast
- 与某个具体元素强绑 → Inline

四级呈现在 desktop 内各有 L2 / L3 组件支持：`InlineError` / `Toast` / `Banner` / `Dialog`。组件接收 `&str`（已 i18n 化的人话），不接收原始 Error 类型。

### 6.5 不静默原则

**任何错误必须留下痕迹**——至少一条 `tracing::warn!` / `tracing::error!`。

**禁止形式**：

```rust
let _ = risky_call();                                    // 禁
match risky_call() { Ok(_) => ..., Err(_) => () }         // 禁
risky_call().ok();                                        // 禁
```

唯一例外：明确写出 `// IGNORE_ERR: <原因>` 注释。例外用法稀有，code review 必看。

### 6.6 Panic hook 与数据救援

应用启动时安装 panic hook：

```
1. 完整记录 panic 详情到日志（含 backtrace、线程、文件位置）
2. 调用 Workspace::emergency_save_all
   ── 把所有 dirty buffer 直接 dump 到
      <cache_dir>/zom/crash-recovery/<timestamp>/
3. 退出进程
4. （第二版）显示崩溃对话框
5. （第二版）下次启动检测 crash-recovery 目录、提示用户是否恢复
```

第一版做 **1 + 2 + 3**：2 留接口，实现尽量简单（直接写文本）。第二版补 4 + 5。

panic hook 不依赖 desktop 的 GPUI 状态——hook 触发时 GPUI 可能已不可用，必须用纯 std I/O 完成数据保存。

### 6.7 错误的 i18n 化

底层 crate 的 `Display` 是英文（已隐含——它们没有 locale 概念）。desktop 在呈现给用户时翻译：

```rust
// shell/errors/translate.rs
pub fn translate_workspace_error(cx: &App, err: &WorkspaceError) -> String {
    match (err, cx.locale()) {
        (WorkspaceError::FileNotFound(p), Locale::ZhCN) =>
            format!("文件不存在：{}", p.display()),
        (WorkspaceError::FileNotFound(p), Locale::EnUS) =>
            format!("File not found: {}", p.display()),
        // ...
    }
}
```

每个底层 crate 一个翻译模块（`translate_workspace_error` / `translate_engine_error` / `translate_command_error` / `translate_ai_error`）。

**新增 Error 变体时 desktop 的 match 编译错**——强制补翻译，这是 desktop i18n 的"编译期穷举"原则。

技术细节同时进日志（保留英文原文），**日志不走 i18n**——日志面向开发者与机器，全英文便于检索、grep、贴 issue。

### 6.8 tracing 集成

第一版用 `tracing` crate。输出策略：

| 环境 | 输出目标 |
|---|---|
| 开发模式（`cargo run`） | stderr，彩色 |
| 发布模式 | 文件 `<cache>/zom/logs/zom-YYYY-MM-DD.log`，按日轮转，保留最近 7 天 |

跨平台 `<cache>` 路径走 `shell::platform::paths`（1.2）。

级别约定：

| 级别 | 用途 |
|---|---|
| `error!` | 用户或开发者必须知晓的错误 |
| `warn!` | 失败但已 fallback / 边界情况 |
| `info!` | 重要生命周期事件（启动、关闭、workspace 切换、theme 切换） |
| `debug!` | 开发期细节 |
| `trace!` | 极细节，仅 opt-in（`RUST_LOG=trace`） |

`tracing` 的 span 用于标记跨函数的操作上下文（如"打开文件 X"、"派发命令 Y"），便于日志检索。

### 6.9 错误处理的不变约束

| 约束 | 强度 |
|---|---|
| desktop 不重新定义错误模型 | 硬规则 |
| 底层 crate 的英文 Error 必须经翻译才呈现给用户 | 硬规则 |
| 任何错误必须至少一条 tracing 日志 | 硬规则 |
| desktop 内禁 `.unwrap()`（除测试与 `// SAFETY:` 注释） | 硬规则；CI lint 强制 |
| panic hook 必须救数据 | 第一版最低限度（dump dirty buffer） |
| 用户呈现走 inline / toast / banner / dialog 四级 | 推荐；新增级别需评审 |

## 七、资源管理 (assets)

### 7.1 资源根目录与组织

资源根目录：`zom-desktop/assets/`。

```
zom-desktop/assets/
  icons/
    app/               应用图标
    panels/            Panel 图标（与 PanelId::icon_path 对应）
    actions/           通用动作图标（close、settings、find/replace 等）
    navigation/        导航图标（chevron 等）
    files/             文件系统图标（file、folder 等）
    status/            状态图标(diagnostics、signal 等)
    window/            自绘窗口控制符号
    ...
  themes/
    dark.toml          内置主题（与用户主题同 schema）
    light.toml
  fonts/               第一版为空；见 7.6
```

按**语义类别**分目录：资源目录不绑定具体出现位置，组件仍在本地声明或内联自己使用哪个路径。

### 7.2 第一版用 embedded asset

第一版资源**编译进二进制**（embedded）：用 `include_bytes!` / `include_str!` 把 assets 打包进 desktop 可执行文件。

| 优点 | 代价 |
|---|---|
| 单一可执行文件分发 | 二进制体积略增（SVG 多在 <1KB / 个，全集 <100KB） |
| 不依赖文件系统路径 | 资源改动需重新编译 |
| 加载零延迟、零失败 | 不支持运行时替换 |
| 用户无法误删 | |

**用户主题除外**——用户主题在文件系统（`~/.zom/themes/*.toml`）。embedded 与文件系统并存：内置 asset embedded、用户产物在 `~/.zom/`。

### 7.3 GPUI AssetSource 接入

GPUI 通过 `AssetSource` trait 加载资源。desktop 实现一个 `EmbeddedAssetSource`：

```rust
pub struct EmbeddedAssetSource;

impl AssetSource for EmbeddedAssetSource {
    fn load(&self, path: &str) -> Result<Option<Cow<[u8]>>> {
        // 按 path 匹配 embedded bytes
    }

    fn list(&self, path: &str) -> Result<Vec<SharedString>> { ... }
}
```

启动时由 shell 启动路径注册到 GPUI App。所有 L3 组件通过 `svg().path("icons/...")` 等方式取资源，**不直接读文件**。

### 7.4 路径使用约定

图标路径用相对 assets 根的形式，**不带** `assets/` 前缀。多处复用的路径可以保留为组件本地常量；panel 图标由 `PanelId::icon_path()` 集中映射；只在一处使用的路径直接内联：

```rust
const FOLDER_ICON: &str = "icons/files/folder.svg";

svg().path("icons/actions/close.svg")
```

GPUI AssetSource 实现负责把 `"icons/..."` 路径映射到 embedded bytes。

### 7.5 资源命名

| 规则 | 例 |
|---|---|
| 文件名 snake_case | `file_tree.svg` |
| 按语义类别分目录 | `icons/panels/file_tree.svg` |
| 同图标多状态用后缀 | `chevron_right.svg` / `chevron_down.svg` |
| 不按视觉效果命名 | ❌ `red_circle.svg` ✓ `error_dot.svg` |
| 不按出现位置命名 | ❌ `topbar_settings.svg` ✓ `settings.svg` |

命名抗腐：将来同一图标可能被多处复用，按"是什么"命名不会过时。

### 7.6 字体策略

第一版**不内嵌字体**——使用系统字体。理由：

- 字体文件体积大（单个 1-10MB）
- 法律授权复杂（OFL / 私有协议各异）
- 用户对自己系统字体已熟悉

settings 提供字体配置，支持回退列表：

```toml
[ui]
font_family = ["Inter", "system-ui", "sans-serif"]

[editor]
font_family = ["JetBrains Mono", "Menlo", "Consolas", "monospace"]
```

GPUI 按列表顺序回退到第一个可用字体。

第二版可考虑内嵌 1-2 个推荐字体作为可选默认。

### 7.7 内置主题作为 asset

`themes/dark.toml` / `themes/light.toml` 是 embedded asset。ThemeRegistry 启动时通过 AssetSource 加载，与用户主题（文件系统加载）走相同 schema：

```
内置主题   AssetSource → embedded bytes → toml::from_str
用户主题   fs 读取 → toml::from_str
```

加载后路径不再区分，统一进 `name -> Theme` 表。

### 7.8 资源版本管理

资源跟随 desktop 二进制版本——升级 zom 自动获得新资源。**不存在"资源版本与代码版本不一致"**。这是 embedded 的另一项收益。

升级新增的 icon、修改的 token 取值都不会撕裂运行环境。

### 7.9 第一版不做

- 用户自定义 icon 包
- 动态资源热重载（修改 SVG 后即时生效；第二版若需要可加 fs watch + 文件系统 asset source 双轨）
- 远程资源加载
- 资源压缩 / 优化构建步骤（SVG 已经够小，不优化）
- 多分辨率 icon（@1x / @2x / @3x）；SVG 已矢量

## 八、异步与后台任务

### 8.1 GPUI 提供的工具箱

desktop **不引入自己的 async runtime**——直接使用 GPUI 提供的执行器：

| API | 作用 |
|---|---|
| `cx.spawn(async \|cx\| { ... })` | 前台任务：在主线程 await，可直接 update entity；返回 `Task<T>` |
| `cx.background_executor().spawn(async { ... })` | 后台任务：worker pool 执行；不能直接持有 Entity |
| `cx.foreground_executor().spawn(...)` | 显式提交到主线程的 task |
| `Task<T>` | 任务句柄；drop 即 cancel |

desktop 不直接 `use tokio` 或 `use async-std`——所有异步走 GPUI 的执行器，避免运行时双栈。

### 8.2 前台 vs 后台的分工

| 任务类型 | 执行器 | 例 |
|---|---|---|
| 短小、需 await 后立刻改 UI | foreground（`cx.spawn`） | 等待用户选择对话框结果 / 派发命令链 |
| 长时计算 / I/O 密集 | background | 文件读写、项目索引、搜索 |
| 网络请求 | background | LSP（将来）、AI 调用 |
| 实时小高频更新 | 不走 task | 滚动、IME update 走直接通道，绕开命令队列与异步 |

**判定准则**：会阻塞主线程超过 16ms（一帧）的事必须后台。

### 8.3 UI 状态修改的硬约束

后台任务**不能直接持有 GPUI Entity**——`Entity<T>` 是 `!Send`。后台结果必须通过 `cx.update_in` 切回主线程修改状态：

```rust
// 正确：后台读文件 → 切主线程更新 buffer
let task = cx.background_executor().spawn(async move {
    std::fs::read_to_string(&path)
});
cx.spawn(|workspace, mut cx| async move {
    let text = task.await?;
    workspace.update(&mut cx, |ws, cx| {
        ws.open_text(text, cx);
    })?;
    Ok::<_, anyhow::Error>(())
}).detach();
```

**禁止**：
```rust
// 错误：后台任务里直接 borrow entity
cx.background_executor().spawn(async move {
    workspace.update(&mut cx, ...);  // ← Entity 不能跨线程
});
```

### 8.4 取消语义

`Task<T>` drop 即 cancel。**取消的标准方式 = 让 Task 句柄随组件 drop**：

- L3 组件持有的 Task 在组件 unmount 时自动 cancel
- 显式取消：用户中断按钮 / Esc 时 drop 对应 Task

后台任务自身要写**取消检查点**——长循环要定期 `cx.background_executor().yield_now().await`，让 cancel 信号有机会传到。

```rust
for file in files {
    cx.background_executor().yield_now().await;   // 允许 cancel
    process(file);
}
```

### 8.5 超时

| 任务类别 | 超时策略 |
|---|---|
| 本地文件 I/O | 不主动超时（fs 本身有错误） |
| LSP 请求 | 默认 5s，可配置 |
| HTTP / AI 调用 | 默认 30s，必须 timeout，不允许无限等待 |
| 用户交互对话框 | 不超时（等用户） |

超时实现用 GPUI 的 `BackgroundExecutor::timer` 配合 `select!`，不引入 `tokio::time`。

### 8.6 并发限制

需要限制并发的场景用简单的 `Semaphore`（用 `tokio::sync::Semaphore` 或自实现的 GPUI 友好版本）：

| 场景 | 并发上限 | 理由 |
|---|---|---|
| 项目索引文件读 | 8（或 CPU 核数） | 防止打开过多 fd |
| LSP 请求（同一服务器） | 由 LSP 协议保证序列性 | 协议级 |
| AI 调用（同一 provider） | 1（顺序） | 防止配额耗尽 |
| 自动保存 | 1（按 buffer） | 防止重复保存 |

限制实现集中在各任务的入口处，**不引入全局任务调度器**。

### 8.7 错误传播

异步错误进第六章的错误处理流程：

```
后台 Task 内部 Err
    ↓
.await? 上抛到调用方
    ↓
调用方在 cx.spawn 内部接收 Err
    ↓
按场景：toast / banner / dialog（6.4）
    ↓
同时 tracing::error!(?err) 进日志
```

**任何被 `.detach()` 的 Task 必须处理错误**——detach 让 Task 后台跑，但错误不能丢。模式：

```rust
cx.spawn(|this, mut cx| async move {
    if let Err(err) = do_work(&mut cx).await {
        tracing::error!(?err, "...");
        show_toast(&mut cx, &err);
    }
}).detach();
```

### 8.8 长任务的进度反馈

| 进度形态 | 用法 |
|---|---|
| 静默 | 短任务（<200ms），无需反馈 |
| Spinner（不定量） | 中等任务（200ms–几秒），状态栏角落 |
| Progress bar（定量） | 长任务（>几秒），状态栏或专用 banner |
| Toast 结束通知 | 用户感知关键的（如"项目索引完成"） |

第一版只做静默 + spinner；progress bar 与结束 toast 推迟到第二版。

### 8.9 第一版的具体使用场景

| 场景 | 实现 |
|---|---|
| 文件保存 | `cx.background_executor` 写文件；完成后切主线程更新 dirty 状态 |
| 文件加载 | `cx.background_executor` 读文件；完成后切主线程 `workspace.open_text` |
| Workspace 切换 | foreground spawn 串联清理旧 + 创建新；按需后台预热索引（第二版） |
| LSP（推迟到第二版） | 子进程 + stdio；接收 → background task → 切主线程更新 view metadata |
| AI 调用（推迟） | background HTTP；超时 30s；结果切主线程 |

### 8.10 不做的事

- 自定义 async runtime
- 引入 `async-trait` crate（如果必须 async fn in trait，第一版评估时再决定）
- 流式响应（除 AI 第二版必须时）
- 跨 task 的复杂数据流（用 channel + spawn 解决，不引入 stream 抽象）
- 全局任务调度器（每场景就地写 Semaphore 已够）

## 九、持久化与状态恢复

本章规定 desktop 持久化的实现：文件位置、格式、时机、合并规则、跨版本兼容、与 crash-recovery 的协作。

### 9.1 持久化的两层

```
全局持久化层（跨窗口共享）
  └─ 用户偏好与会话级元数据
     - settings.toml             用户配置（第一章已定）
     - recent_workspaces.toml    最近 workspace 列表
     - command_usage.toml        命令使用频率（用于命令面板 rank）
     - themes/*.toml             用户主题

窗口持久化层（按 workspace 写）
  └─ <workspace_root>/.zom/layout.toml    本 workspace 的窗口布局快照
     - Dock 显隐 / 尺寸 / active panel / panel 顺序
     - EditorGrid 的 split tree
     - tab group 与 active editor
     - 每个 tab 的 buffer 路径、滚动位置、光标位置
```

`settings.toml`（已定）与 `layout.toml`（本章）**同目录但不同文件**：
- `settings.toml`：用户**意图**配置（要不要这个面板亮起、用哪个主题）
- `layout.toml`：当前**会话**布局快照（这次 dock 拖到了多宽、哪个 tab 是 active）

### 9.2 文件位置

全局持久化与 settings 同根（参见 1.2）：`~/.zom/`，全平台一致，不走 OS 惯例路径。`~` 解析走 `shell::platform::paths`。

完整文件清单：

```
~/.zom/
  settings.toml             第一章
  recent_workspaces.toml    本章
  command_usage.toml        本章
  themes/*.toml             用户主题
  logs/zom-YYYY-MM-DD.log   第六章 6.8
  crash-recovery/<ts>/      第六章 6.6
```

每窗口快照走 workspace 根：

```
<workspace_root>/.zom/
  settings.toml             第一章（workspace 级 settings 覆盖）
  layout.toml               本章（窗口布局快照）
```

### 9.3 文件格式：统一 TOML

与 settings、主题保持一致：所有持久化文件用 TOML。写回时用 `toml_edit` 保留注释（与 1.8 一致）——尽管 layout.toml 多为程序生成，预留注释空间便于用户手改。

### 9.4 持久化时机

| 触发 | 行为 |
|---|---|
| 状态变化 | debounced 1s 后写（与 settings 一致） |
| Workspace 切换 | 强制写出旧 workspace 的 `layout.toml`，再加载新 workspace |
| 窗口关闭 | 强制写出该窗口的 layout |
| 应用正常退出 | 强制 flush 所有 pending 写 |
| Panic / 崩溃 | **不写**持久化文件（不安全）；只走 crash-recovery（6.6） |

debounce 与强制写都通过 `cx.background_executor` 调度，**不阻塞 UI 主线程**（与 8.3 一致）。

### 9.5 持久化范围

**持久化**：
- shell 级配置（TopBar / BottomBar，第一版基本固定）
- Dock 状态：显隐 / 尺寸 / active panel / panel 顺序
- EditorGrid 的 split tree、tab group、active group
- 每个 tab：buffer path、滚动位置、光标位置
- 全局：recent_workspaces、command_usage

**不持久化**：
- 当前打开的 Surface / Bubble
- 鼠标位置、hover 状态
- 字体度量等渲染缓存
- dirty buffer 的内容（走 crash-recovery，见 9.9）
- IME composition 临时状态

### 9.6 强 schema + 跨版本兼容

layout.toml 也是 Rust struct + serde，规则与 settings（1.6）一致：

- 未知字段警告不阻塞（旧版 zom 能读懂新版生成的 layout）
- 缺失字段用默认值
- 破坏性字段重命名：旧版字段名保留并标 deprecated，新版双名读取至少一个大版本
- schema 内嵌 `schema_version: u32`（第一版 = 1），将来重大变更可按版本走 migration 函数

### 9.7 PersistenceRegistry

与 SettingsRegistry / ThemeRegistry / LocaleRegistry 结构平行：

```
启动时
  - 加载 recent_workspaces / command_usage（全局）
  - 加载首个 workspace 的 layout.toml（按 settings 决定首个 workspace）
运行时
  - observe 各组件状态变化 → debounced 写
切换 workspace 时
  - flush 旧 layout
  - 加载新 workspace layout
  - 触发 observable（panel / editor 跟随）
关闭窗口时
  - flush 本窗口 layout
```

`PersistenceRegistry` 是 GPUI Entity，每窗口持有自己的 layout 快照；全局 registry 持有跨窗口共享的内容。

### 9.8 失败处理

| 失败 | 处理 |
|---|---|
| layout.toml 不存在 | 使用内建 panel 固定归属与空窗口运行态；不报错（第一次打开 workspace 的正常状态） |
| layout.toml 解析失败 | 使用内建 panel 固定归属与空窗口运行态 + 一次性 toast + 日志（包含 backtrace） |
| 写失败（磁盘满、权限） | `tracing::error!` + 应用继续；不阻塞 UI |
| 跨版本 schema 不兼容 | migration 函数尝试转换；失败则用默认 + toast 通知 |

**持久化失败绝不影响关键路径**——持久化是优化，失败应用仍能跑。

### 9.9 与 crash-recovery 的关系

```
crash-recovery（6.6）         dirty buffer 文本内容
                              panic hook 紧急 dump
                              下次启动检测并提示恢复（第二版）

持久化（本章）                布局元数据 + 已保存文件的元信息
                              正常运行时 debounced 写
                              下次启动恢复布局
```

互补，不冲突。下次启动顺序：

```
1. PersistenceRegistry 加载 layout（恢复布局、打开上次 tabs）
2. CrashRecoveryRegistry 检查 crash-recovery 目录
   - 若有未消费的 dump → 提示用户"上次崩溃了，是否恢复未保存内容"
   - 用户同意 → 把 dump 内容载入新 buffer（不绑文件）
   - 消费后清理目录
```

### 9.10 buffer 内容不属于 desktop 持久化

打开的文件**内容**的持久化是 `zom-workspace` 的"保存"概念（已存盘的 buffer）。desktop 的 layout.toml **只存 buffer 路径**，不存内容。

dirty buffer 的两种归宿：

- 用户主动保存 → 落到磁盘的对应文件
- 崩溃前未保存 → crash-recovery dump（6.6）

desktop 持久化层**不复制 buffer 内容**——避免与 workspace 重复、避免泄漏未保存数据。

### 9.11 第一版不做

- 跨设备同步（云持久化）
- 持久化文件加密
- 持久化版本管理（git-like 多版本回滚）
- 多布局快照（用户切换不同"工作模式"）
- crash-recovery 的下次启动恢复提示（推迟到第二版，对应 6.6 的第 5 步）

## 十、生命周期

启动序列由组合根（app 模块）规定；本章管的是镜面对应的另一端：关闭、workspace 切换、资源清理、系统信号——围绕"用户的工作不丢失"展开。

### 10.1 触发关闭的入口

下列入口都派发同一个命令 `app.quit`，由唯一 handler 走完整流程：

| 入口 | 触发条件 |
|---|---|
| 命令面板 `app.quit` | 用户显式触发 |
| 全局键位 `mod-q` | macOS Cmd-Q / 其他平台 Ctrl-Q |
| 关闭最后窗口 | 2.5；macOS 例外（保持进程） |
| 系统信号（SIGINT / SIGTERM） | 见 10.5 |
| 平台 quit 事件 | macOS Dock quit / Windows shutdown |

收敛到单一命令避免多份关闭逻辑分叉。

### 10.2 关闭流程

```
app.quit handler
  1. 标记 quitting 状态（防止重入；二次触发直接 return）
  2. 收集所有窗口的所有 dirty buffer 清单
       若有 → 显示 SaveBeforeQuitDialog (Surface)
         - "保存所有" → 派发 editor.save_all → 等待完成
         - "全部丢弃" → 跳过
         - "取消"   → 解除 quitting 标记、中止流程
  3. flush PersistenceRegistry（写 layout / recent / usage）
  4. flush SettingsRegistry（确保 settings 已写）
  5. 关闭所有窗口（GPUI Window drop）
  6. 销毁每窗口 PanelHost / SurfaceManager / BubbleManager
  7. 关闭 LSP 子进程（第二版有 LSP 时）
  8. tracing::info!("zom shutdown complete")
  9. 进程退出
```

**幂等**：第 1 步的 quitting 标记保证重复触发不会重复弹 dialog 也不会重复 flush。

### 10.3 Workspace 切换

两个命令对应两种切换：

| 命令 | 行为 |
|---|---|
| `workspace.open` | 在**当前窗口**替换 workspace |
| `workspace.open_in_new_window` | 在**新窗口**打开；当前 workspace 不动 |

`workspace.open` 流程：

```
  1. 收集当前 workspace 的 dirty buffer
     若有 → 弹 Dialog 询问（同 10.2 第 2 步）
  2. flush 当前 workspace 的 layout.toml
  3. 销毁当前 Workspace / ViewSet（GPUI Entity drop）
  4. 创建新 Workspace 实例
  5. SettingsRegistry 重 merge 新 workspace 的 .zom/settings.toml
       触发 observable → 主题 / 字号 / locale 跟着切（若 workspace 覆盖）
  6. PersistenceRegistry 加载新 workspace 的 layout.toml
  7. 创建新 ViewSet（按 layout 恢复 split tree / tabs / 光标位置）
  8. WorkbenchFrame re-render
```

`workspace.open_in_new_window` 跳过 1-3 步，直接走 4-8 步（在新窗口）。

### 10.4 资源清理与 RAII

GPUI Entity 自动管理生命周期。desktop 不手动 Drop 大部分资源。

必须显式管理：

| 资源 | 显式处理 |
|---|---|
| LSP 子进程（第二版） | 显式 kill，避免 zombie |
| 文件 watcher | 随 Workspace Entity drop 自动释放 |
| 后台 Task | 组件 drop 即 cancel（与 8.4 一致） |
| 异步写文件的 pending flush | app.quit 第 3-4 步强制 await |

panic hook **不依赖 RAII**——崩溃时 GPUI 可能已不可用，必须用纯 std I/O 完成救援（6.6）。

### 10.5 系统信号

跨平台信号处理收纳在 `shell::platform::signals`（与 3.5 边界一致）：

| 信号 / 事件 | 处理 |
|---|---|
| SIGINT（terminal Ctrl-C） | 派发 `app.quit` |
| SIGTERM | 派发 `app.quit` |
| SIGKILL | 无法捕获；依赖下次启动 crash-recovery |
| macOS Cmd-Q / Dock quit | 派发 `app.quit` |
| Windows close 按钮 / shutdown 信号 | 关闭按钮 → `window.close`；最后窗口 → `app.quit` |
| Linux desktop session 结束 | 派发 `app.quit` |

信号 handler 必须 async-signal-safe——只做"把事件丢给主线程"，实际处理在 `app.quit` 命令 handler 内。

### 10.6 首次启动的特殊处理

首次启动（用户级配置目录不存在）：

```
1. 创建配置目录 ~/.zom/
2. 不主动创建 settings.toml（与 1.7 一致：用户首次改设置才创建）
3. 加载内置默认（dark 主题 / zh-CN locale / 默认字号）
4. 首个 workspace 来源决策：
   - CLI 参数指定 → 打开该路径
   - 否则 → 默认空 workspace（unnamed scratch buffer）
5. 启动后续步骤照常（组合根的启动序列）
```

第二版可补"首次启动欢迎页"（推迟）。

### 10.7 第一版不做

- 优雅重启（关闭并自动重启进程）
- 系统 sleep / wake 时的 buffer 保护
- 多用户切换处理
- 子进程清理超时强杀（第二版与 LSP 一起补）
- 关闭过程中的"取消未保存写"中断（assume flush 总能在合理时间完成）

## 十一、CLI 入口

zom-desktop 作为桌面应用，同时是命令行可调用的工具。本章规定 CLI 参数模式、路径解析、实例策略与平台集成边界。

### 11.1 第一版 CLI 参数

```
zom                              空 workspace 启动（默认 unnamed scratch buffer）
zom <path>                       打开文件或目录
zom <path1> <path2> ...          多目标（详见 11.2）
zom --new-window [path]          强制新窗口；与 10.3 的 workspace.open_in_new_window 等价
zom --version                    输出版本号后退出
zom --help                       输出帮助后退出
```

参数解析用 `clap`（或同类成熟 crate），**不自己手撸 parser**。

### 11.2 路径解析规则

| 输入 | 解析 |
|---|---|
| 单个目录 | 当 workspace 根打开；首个 buffer 由 layout 恢复（若有）否则空 |
| 单个文件（已存在） | workspace 根 = 文件所在目录的最近 git root；若无 git root → 文件所在目录；该文件作为初始 buffer 打开 |
| 单个路径（不存在） | 视为"新建文件"意图；workspace 根 = `cwd`；buffer 绑该路径但 dirty 直到首次保存 |
| 多个路径 | 第一个决定 workspace 根（按上述规则）；其余作为文件打开 |

**workspace 根判定的优先级**：CLI 显式 > 文件最近 git root > 文件所在目录 > cwd。

### 11.3 实例策略：第一版多实例

第一版**每次 `zom` 启动新进程**——多个进程独立运行、各自持有 settings/theme/locale 的拷贝（但全局共享的语义靠 OS 文件 inotify 自动同步，见 1.8）。

理由：

- IPC 实现跨平台复杂（macOS URL handler / Linux socket / Windows named pipe）
- 第一版用户量小，多实例性能成本可接受
- 让 desktop 第一版聚焦核心

第二版升级**单实例 + IPC**：

- 第一个进程是主进程
- 后续 `zom` 调用通过 IPC 把"打开 X"请求转给主进程
- 主进程决定走新窗口还是追加 tab

**CLI 表面在升级前后不变**——`zom <path>` 始终能工作，只是底下是否复用进程的差异。

### 11.4 退出码

| 码 | 含义 |
|---|---|
| 0 | 正常退出 |
| 1 | 内部错误（panic hook 设置；包括崩溃恢复后退出） |
| 2 | CLI 参数错误（clap 自带） |
| 3 | 配置文件严重错误且无法用默认（罕见；通常 settings 失败会走 1.7 fallback） |

### 11.5 平台集成（第一版只保命令行）

| 平台 | 第一版状态 | 第二版规划 |
|---|---|---|
| macOS | 命令行可用；Bundle 内不预注册文件类型 | Info.plist 注册文件类型；NSApplicationDelegate 处理 openFiles |
| Linux | 命令行可用；不自动注册 .desktop | .desktop 文件注册 MIME |
| Windows | 命令行可用；不自动改注册表 | 注册表关联文件类型 + cmd handler |

第一版用户想要"双击文件用 zom 打开"自己在系统设置里关联。

### 11.6 URL handler（推迟）

`zom://` 协议用于深链接（"打开远端文件"、"跳转到符号"、"插件入口"）推迟到第二版。届时设计：

```
zom://open?path=/abs/path&line=42
zom://workspace?root=/abs/workspace
```

第一版不实现；CLI 已覆盖大多数本地场景。

### 11.7 stdin / pipe（推迟）

第一版**不支持** `cat file | zom` 这类 stdin 输入。理由：

- 编辑器不是流式工具，pipe 输入语义模糊（要不要可编辑？保存到哪？）
- 命令行场景已被 `zom <path>` 覆盖

第二版可考虑 `zom --stdin` 显式接收 pipe 为只读 / 临时 buffer。

### 11.8 第一版明确不做

- 单实例 + IPC（第二版）
- URL handler `zom://`（第二版）
- stdin pipe（第二版）
- shell completion（`zom completion bash` 等；第二版）
- 文件关联自动注册（用户手动配；第二版可考虑安装脚本）
- macOS Quick Look 扩展
- 服务端模式（`zom --server`）

## 十二、焦点系统

一句话原则：**App 持有唯一的逻辑焦点；GPUI `FocusHandle` 只是这个逻辑焦点在窗口系统里的投影**。

### 12.1 定位

桌面端容易长出多套"激活态"概念——`ViewSet.active`、Dock 的 active panel、`FocusRole`、`FocusRegistry`、`FocusRouter`、`ProjectPicker.active`、`TextTargetId` 等各自决定"当前操作应该落到哪里"。这种多源真相会走向腐烂：命令派发、快捷键解析、IME 路由、状态栏读数、剪贴板目标会各挑一套,谁是"当前焦点"没人说得清。

本章规定 zom-desktop 焦点系统只允许**一个语义真相源**:`AppFocus`。所有命令、快捷键、IME、剪贴板、状态栏查询都从 `AppFocus` 派生,不再各自维护一套 active / role / target_id。

### 12.2 AppFocus

```rust
pub enum AppFocus {
    None,
    Editor(EditorFocus),
    Panel(PanelFocus),
    Surface(SurfaceFocus),
}
```

`AppFocus` 表达"当前用户操作应该落到哪里"。三层结构与 L4 区域 / Dock / Surface 的拓扑对齐:

- `Editor(EditorFocus)` —— 焦点在 EditorGrid 的某个 EditorView(对应一个 `ViewId`)
- `Panel(PanelFocus)` —— 焦点在某 Dock 的某个 Panel 内某个具体输入点
- `Surface(SurfaceFocus)` —— 焦点在浮面(CommandPalette / ContextMenu / InlinePopover 等)

叶子枚举(`EditorFocus` / `PanelFocus` / `SurfaceFocus`)由对应模块定义,可精确到"哪个 panel、哪个输入框"。

### 12.3 FocusStore

`FocusStore` 是 desktop 内唯一保存焦点状态的数据结构,每窗口一份(与 2.2"每窗口独立"一致):

```rust
pub struct FocusStore {
    current: AppFocus,
    previous: Option<AppFocus>,
}
```

`previous` 用于 Surface 关闭后焦点回到原位。它**不是任意深度的栈**——第一版同时只能有 1 个 Surface,一层 previous 已够。

App 暴露统一入口:

```rust
app.focus().current();          // 读当前焦点
app.focus().request(next);      // 请求切换到新焦点
app.focus().restore_previous(); // Surface 关闭时回到原焦点
app.focus().key_contexts();     // 当前焦点对应的上下文键位 key
app.focus().edit_target();      // 文本命令路由目标
app.focus().ime_target();       // IME 路由目标
app.focus().snapshot();         // 调试 / 日志用
```

这些 API 都是"当前唯一焦点的能力投影"——**不是新的焦点状态**。`edit_target` / `ime_target` / `key_contexts` 都是 `AppFocus::current()` 的派生函数,不允许独立写入。

### 12.4 焦点边界(关键反例)

焦点是**唯一**的,但很多状态**不是焦点**。混淆这两者是大多数焦点 bug 的根源。

| 不是焦点 | 真正归属 | 与焦点的关系 |
|---|---|---|
| `ViewSet.active` | zom-view | 当前编辑 view;不代表焦点在编辑器 |
| `WorkbenchController.active_panel` | desktop L4 | 当前显示的 panel;不代表焦点在 panel |
| 文件树 selected | FileTree L3 | 文件树内部游标;不是 app focus |
| Search 面板是否打开 | Dock | visibility;不是 focus |
| `ProjectPicker.active` | 旧代码 | **应删除**,改为从 `AppFocus::Surface(ProjectPicker(_))` 判断 |

具体地:用户可以"看着编辑器、但焦点在文件树"(按 ↓ 滚动文件列表),可以"打开了 Search 面板、但焦点仍在编辑器"。**显示状态 ≠ 焦点状态**。

### 12.5 文本输入路由

4.4 的"文本输入 fallback"需要知道写到哪里。原先用 `TextTargetId`,但它本质上回答的是"IME / 文本命令应该写到哪里"——这正是 `AppFocus` 已经回答的问题。

新模型:

```rust
// 旧:EditorRouter 按 owner 顺序找第一个 is_active()
// 新:直接从 AppFocus 派生
router.owner_for(app.focus().current())
```

这消除了 picker > file_tree > search > editor 这种隐式优先级——焦点值已经明确表达"现在文本去哪",不需要按 owner 列表猜。

### 12.6 FocusProjection(shell 投影层)

业务层只认 `AppFocus`,窗口系统只认 GPUI `FocusHandle`。二者之间由一个**薄的、shell-only** 的 `FocusProjection` 桥接:

```rust
// shell/focus/projection.rs
pub struct FocusProjection { /* AppFocus <-> FocusHandle 映射 */ }

impl FocusProjection {
    pub fn apply(&self, focus: AppFocus, window: &mut Window);
    pub fn sync_from_gpui(&mut self, handle: &FocusHandle, app: &mut App);
}
```

职责只有两件:

- App 请求焦点变化时,把 `AppFocus` 投影到对应 `FocusHandle`(`apply`)
- 用户点击或系统 focus 变化时,把 `FocusHandle` 反向同步成 `AppFocus`(`sync_from_gpui`)

**FocusProjection 不决定业务焦点**——它只做系统焦点桥接。任何"该焦点哪个组件"的语义判断都在 `FocusStore` 一侧。

旧名字 `FocusRouter` 已废弃:"路由"暗示语义决策,容易再次长出"按 owner 顺序找第一个活动者"的隐式逻辑。新名字 `FocusProjection` 强调只投影、不路由。

### 12.7 命令切焦点

切焦点动作**不允许直接操作 FocusHandle**,必须走语义焦点。命令 handler emit 一个 `HostEffect::Focus`:

```rust
HostEffect::Focus(AppFocus::Panel(
    PanelFocus::Search(SearchField::Query)
))
```

Shell 收到后:

```rust
app.focus().request(next);
focus_projection.apply(next, window);
```

所有焦点变化都有一个统一入口,可观测、可日志、可回放。这条规则与 5.1 通信机制决策树一致——焦点变化是命令的副作用,不是单独的通信通道。

### 12.8 迁移目标

旧概念应当被删除或替换:

| 旧 | 处置 |
|---|---|
| `FocusRole` | 删除 |
| `FocusTarget` | 并入 `AppFocus` |
| `FocusRegistry` | 替换为 `FocusProjection` 的反向映射 |
| `FocusRouter` | 替换为 `FocusProjection`(名字去掉"路由"语义) |
| `TextTargetId` | 逐步由 `AppFocus` 叶子节点替代 |
| `ProjectPicker.active` 等组件本地"激活态" | 删除,从 `AppFocus` 派生 |

迁移期内允许新旧并存,但**不允许新代码引入旧概念**——只允许在替换旧代码的同时整体下沉。

### 12.9 焦点的派生关系

| 派生项 | 由 AppFocus 决定的事 |
|---|---|
| 上下文键位匹配 | `[keymap.context.<key>]` 的 `<key>` 由 `app.focus().key_contexts()` 派生 |
| 文本输入 fallback | fallback 命令的目标由 `app.focus().edit_target()` 决定 |
| 编辑面 focus_handle | 每个 EditorView 持有的 `focus_handle` 由 `FocusProjection` 管理,不再各自维护 active 旗标 |
| IME 路由 | IME 路由目标由 `app.focus().ime_target()` 决定;权威 composition 仍在 view |
| Surface 关闭复位 | Surface 关闭时调用 `app.focus().restore_previous()` 把焦点送回原位 |
| 持久化（不参与） | 当前焦点**不持久化**——重启由布局恢复逻辑重新决定(默认到 active editor) |

### 12.10 一句收束

> **业务只认 `AppFocus`,窗口系统只认 `FocusHandle`,两者之间只通过 `FocusProjection` 映射。**

### 12.11 第一版不做

- 多层 Surface 焦点栈(第一版同时最多 1 个 Surface,单层 `previous` 已够)
- 跨窗口焦点跳转(每窗口独立 `FocusStore`,焦点不跨窗口)
- 焦点视觉指示的统一框架(各组件自己用 token 表达 focus 态;`color::*::s06` 已是 focus 边框档)
- 焦点持久化(9.5)
