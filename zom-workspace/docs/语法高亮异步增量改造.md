# 语法高亮异步 + 增量：设计决策

> 本文是 [`zom-workspace::syntax`](../src/syntax/) 当前实现的设计依据，配套
> [BASELINE](../../zom-bench/BASELINE.md) §4 性能红线、[桌面端语法高亮手册](../../zom-desktop/docs/桌面端语法高亮.md)。
>
> **形态**：异步 worker + tree-sitter 增量 + ReplaceRange 局部产物。主线程脱钩
> 文件大小，worker 端 viewport-scoped 后 16 MiB rust 单键 < 100 ms。改造覆盖
> `zom-workspace::syntax` 内部实现，不动 `HighlightProvider` trait 外部契约、
> 不动 sink 协议、不动 desktop 渲染层。
>
> 代码注释里若引用 §4.x，指的是下面"4. 关键架构决策"对应小节。

## 1. 性能红线

| 指标 | 当前目标 |
|---|---|
| 16 MiB rust 单键 viewport-scoped e2e | < 100 ms（worker 端） |
| 16 MiB rust 单键主线程时间 | < 5 ms |
| 16 MiB rust `parse` 冷启动 | ≤ 1.5 s（后台线程） |
| 1 / 4 MiB 现有数字 | 不允许劣化 |
| 64 MiB 一档 | **不追**：tree-sitter 走树本身 O(n) 不可避免，宿主提示用户跳过高亮 |

`MAX_HIGHLIGHT_BYTES = 16 MiB`，超出静默落 plain；具体阈值取舍见
[`MAX_HIGHLIGHT_BYTES`](../src/syntax/coordinator.rs) 的注释。

## 2. 总体方案

四条原则替换掉旧的"全文物化 / 全文 parse / 全集 Vec / 全层重建"：

| 旧的"全" | 替换为 | 兑现的红线 |
|---|---|---|
| 全文物化 String | `TextProvider` 按 chunk 流式喂给 tree-sitter | peak RSS |
| `Highlighter::highlight(bytes)` 全文 parse | `Parser::parse(text, Some(&old_tree))` 增量 reparse | parse / edit+hl 时间 |
| 全文 spans Vec | 按 viewport ± 缓冲区 `QueryCursor::matches` 局部产 | spans Vec 内存 |
| `replace_all` 全层重建 | `replace_range` 仅替换 viewport 段 | 编辑延迟 |

并把整条链路推到**后台 worker 线程**，主线程只投递 job + drain sink。

## 3. 关键架构决策

### 3.1 脱 `tree-sitter-highlight`，直接用 `tree-sitter`

**为什么**：`Highlighter::highlight()` 签名固定吃 `&[u8]` 从头 parse，**不接受
已有 Tree**——不可能做增量。这是 tree-sitter-highlight 的设计取舍，无法绕过。

**代价**：自己用 `tree_sitter::Query` + `QueryCursor::matches` 写 capture →
HighlightName 映射，复刻 tree-sitter-highlight 的"嵌套 stack + Source 段携带
栈顶 capture"逻辑（见 [`common.rs`](../src/syntax/providers/common.rs)）。
代码量 ~80 行 / 语言无关一份。

**收益**：拿到完整的 `Tree` 控制权——`Tree::edit()` +
`Parser::parse(_, Some(&old_tree))` 这条增量路径才能走。

### 3.2 Worker 线程模型：单全局 worker

**选项对比**：

| 方案 | 复杂度 | 并发度 | 内存 |
|---|---|---|---|
| 每 buffer 一线程 | 高（buffer 数 = 线程数，attach/detach 管理重） | 高 | 每线程一份 Parser/Tree |
| 每语言一线程 | 中（多线程常驻） | 中 | 同上 |
| **全局单 worker** | **低** | **低**（多 buffer 编辑串行） | **最省**（单 Parser pool） |

选**全局单 worker**：单用户编辑场景下"多个大文件同时频繁编辑"几乎不可能；
编辑器 60 fps 的主循环不会被 worker 阻塞，最坏情况 = 第二个 buffer 的高亮
延迟 50–100 ms 出，可接受。后续若证明是瓶颈再扩成线程池，**不影响 API**。

**线程内部结构**：

```rust
WorkerLoop {
    parsers: HashMap<LanguageId, Parser>,         // 复用，不重建
    trees: HashMap<BufferId, (BufferVersion, Tree)>,  // 每 buffer 最新树
    queries: Arc<LanguageRegistry>,               // 跨语言共享 query
    jobs: Receiver<Job>,
}

enum Job {
    Attach { buffer_id, language, snapshot, sink },
    Edit { buffer_id, edits: Vec<InputEdit>, new_snapshot, new_version, sink, viewport_hint },
    Detach { buffer_id },
}
```

### 3.3 任务投递与去抖（coalescing）

**问题**：用户连按 10 键，主线程发出 10 个 Edit job。worker 不可能 10 帧内
做完——必须丢掉中间 9 个。

**方案**：每 `(buffer_id, sink)` 维护一个"最新待处理 job"的原子槽。主线程
投递时**覆盖**槽而不是 append：

- 新 Edit 来了：取出旧 Edit（如果有），合并 `edits` 列表（旧的 InputEdit 仍
  有效，`Tree::edit` 可多次顺序调用），用新 snapshot/version 覆盖
- worker 完成当前 job 后从槽里**取走**最新待处理 job，开干

**好处**：天然合并连续按键、自动丢弃中间过期版本、不需要显式 cancellation。

**cancellation**：tree-sitter 的 `cancellation_flag` 作为兜底——worker 在每个
parse 调用前后检查"buffer 当前期望版本"是否仍 = 我手上这个 job 的版本，
否则把 flag 拉起来让 parse 中途退出。

### 3.4 ChangeSet → InputEdit 翻译

tree-sitter `InputEdit` 需要 6 个字段：

```rust
pub struct InputEdit {
    pub start_byte: usize,
    pub old_end_byte: usize,
    pub new_end_byte: usize,
    pub start_position: Point,      // (row, byte_column)
    pub old_end_position: Point,
    pub new_end_position: Point,
}
```

`ChangeSet` 暴露 `changed_ranges()` 但那是**新坐标**下的范围。tree-sitter 要的
是**旧坐标下的 start / old_end，加新坐标下的 new_end**。换源：用 `EditList`
（每条 `Edit` 有 `range`（旧）+ `replacement`（新文本））和老 Snapshot：

```rust
let start_byte = edit.range().start().get();
let old_end_byte = edit.range().end().get();
let new_end_byte = start_byte + edit.replacement().len();

let start_position = old_snapshot.byte_to_point(start_byte);
let old_end_position = old_snapshot.byte_to_point(old_end_byte);
let new_end_position = new_snapshot.byte_to_point(new_end_byte);
```

**关键工程点**：worker 同时持有 **本次 edit 之前的 snapshot**（算旧端 Point）
和**本次 edit 之后的 snapshot**（算新端 Point + 喂 TextProvider）。流程：

```
主线程 pump_post_edit:
  edit before = state.last_known_snapshot.clone()   // 极廉价（Arc 共享）
  edit after  = buffer.snapshot()
  events = buffer.take_pending_events()
  for event in events: translate to InputEdit using (before, after)
  push Job::Edit { edits, new_snapshot: after, new_version }
  state.last_known_snapshot = after
```

每个 Snapshot 都是轻量 clone（rope 内部 Arc + 几个 usize），多持一份不增加
显著内存。

`Snapshot::byte_to_point(ByteOffset) -> (Line, byte_in_line)` 是为此引入的
engine 公开方法——tree-sitter 要 byte column，`Position` 给的是 char column。

### 3.5 TextProvider：流式喂 rope chunks

tree-sitter `Parser::parse_with_options` 接受 `FnMut(usize, Point) -> impl AsRef<[u8]>`
——从指定字节位置开始拿一段 bytes，tree-sitter 自己迭代调用直到 EOF。实现：

```rust
fn provider(offset: usize, _: Point) -> &[u8] {
    snapshot.chunk_at_byte(offset).as_bytes()  // 借自 ropey
}
```

ropey 的 `Chunks` 是 zero-copy `&str` 迭代；engine 暴露
`Snapshot::chunk_at_byte(ByteOffset) -> (&str, ByteOffset)` 给"任意 byte offset
后第一段 chunk"的访问。

这一步等价兑现"不再物化全文"——peak RSS 的全文 String 分配消失。tree-sitter
内部需要把 bytes 拷进自己的扫描缓冲，但是分块的、有上限的（kB 级），不是
GB 级。

### 3.6 spans 局部产物：viewport ± 缓冲区

`QueryCursor::set_byte_range(start..end)` 限制查询范围。worker 拿到 desktop
上报的 viewport hint（line_range → byte_range），加 ± N 行缓冲（避免每次轻微
滚动都触发查询），跑 `cursor.matches(query, tree.root_node(), provider)`，
得到的只是 viewport 段的 spans。

通过 `sink.replace_range(version, viewport_byte_range, spans)` 投递，只覆盖
该段，远处的旧 spans 保留。

边界处理：viewport ± N 行缓冲是为了让跨可视区边界的 capture（多行字符串、
宏调用、属性）能被完整查询到，否则边缘行会缺色。N 取 32 行——视觉上 1 帧
约 30 行可视，padding 几乎一致，但保证语义完整。

### 3.7 Wake：每帧 drain

异步 worker 完工后产物落进 sink，但 sink 是**被动**的——必须有人调 `drain()`。
[`Workspace::pump_pending_highlights`](../src/lib.rs) 扫描所有 buffer，对有 sink
的调一次 drain；desktop 在每帧 `prepaint` 开始时调一次。每帧扫一次 hashmap +
空 drain（拿锁、看 empty、放锁）——主线程 1 µs 级别，60 fps 下完全可接受。

### 3.8 内存边界

| 单 buffer 持有 | 数量级（16 MiB rust） |
|---|---|
| Parser（在 worker，按语言共享） | 几 MB |
| `Tree`（latest only，每 buffer 一份） | tree-sitter Rust 实测约 5–7× 源 |
| spans Vec（在 MetadataLayers） | viewport 段几十 KB |
| Buffer 本身（ropey） | ~ 源大小 |
| 旧 Snapshot 缓存（worker 用作 InputEdit 旧端 Point） | 0（snapshot 是 Arc 共享，挂在 buffer 内） |

对比旧实现的峰值：消失的是全文 String 物化、tree-sitter-highlight 的短生命
周期 stack/cursor 缓冲、全文 spans Vec（百万 entries × 几十字节 = 几十 MB）。

## 4. 不做的事

- **不引入 `tokio` / async 运行时**。用 `std::thread` + `mpsc` 足矣，避免新依赖。
- **不做 LSP semantic tokens 并行**——本方案只覆盖 tree-sitter producer；LSP 是
  独立 producer，遵循同一 `HighlightProvider` trait 但内部线程模型不同
  （server 自带异步）。
- **不重写 `HighlightProvider` trait**。这个 trait 已经为异步设计
  （sink + version 协议），异步性完全在 worker 内部消化。
- **不动 desktop 渲染路径**。spans 落 `MetadataLayers` 后的消费链路完全不变。
- **不重排 cargo feature 拆分**（tree-sitter grammar feature gating）；正交事项。
- **不处理多 view 共享同 buffer 的 viewport 联合**——以最大并集为 hint，或只用
  active view 的 viewport，错过的远处 view 接受短暂"高亮缺失 → 1–2 帧后补齐"。

## 5. 对 engine 的入侵（最小集合）

| API | 用途 |
|---|---|
| `Snapshot::byte_to_point(ByteOffset) -> (Line, usize)` | ChangeSet→InputEdit 翻译，列单位为 UTF-8 byte |
| `Snapshot::chunk_at_byte(ByteOffset) -> (&str, ByteOffset)` | TextProvider 流式喂 tree-sitter，返回 chunk 和它在全文里的起点 |
| `MetadataLayers::replace_layer_ranges_in(kind, version, byte_range, spans)` | ReplaceRange sink 消费 |

三项都属于"派生 / 包装"，不动核心数据结构、不引入新错误模型。

## 6. 失败策略

- **增量 reparse 失败**（grammar bug、ABI 不匹配）：走全量重解析并复位
  `Tree = None`。
- **provider panic**：每条任务包 `catch_unwind`，出问题的缓冲区移除高亮条目，
  其他缓冲区继续工作；高亮线程不挂。
- **超 `MAX_HIGHLIGHT_BYTES`**：静默落 plain，不挂 provider。
- **不保留发布期切换路径**：只有当前 tree-sitter provider 路径；旧同步全量
  实现、环境变量切换、cargo feature 切换都不存在。若后续 bench 退化，按测试
  和性能基线修当前实现。
