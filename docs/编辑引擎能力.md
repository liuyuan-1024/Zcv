# 纯粹的底层编辑引擎能力清单

> 目标：定义一个面向编辑器宿主的**单机底层文本编辑引擎**能力边界。  
> 范围：文本存储、坐标转换、事务变异、历史系统、快照、版本、增量事件、位置映射、区间追踪、视口投影、版本化外部结果承载，以及错误防御、资源预算、benchmark / fuzz 等底层验证能力。  
> 非目标：不负责渲染、主题、字体测量、完整 LSP 协议、语法树、diagnostics / semantic tokens / inlay hints / code lens 生成、项目级索引、跨文件搜索、Command 语义层、宏录制、后台任务调度器或实时多人协作。

## 纯编辑引擎底线

后续阶段规划必须先判断一项能力是否属于编辑引擎核心。

保留范围：

- 文本存储、编辑、坐标、事务、历史、快照。
- 版本、Delta、PositionMap、TrackedRange、MetadataLayer 等通用协作原语。
- Fold / Projection、Viewport slicing、文件文本进入和离开 Buffer 的底层边界。
- 大文件策略、错误防御、property / fuzz / benchmark / 可观测指标。

移出范围：

- LSP / Tree-sitter provider。
- diagnostics / semantic tokens / inlay hints / code lens 的业务生成与专用 adapter。
- UI 渲染、fold placeholder 样式、像素 viewport。
- 快捷键、菜单、命令面板、Command / CommandExecutor。
- Macro Recording、用户操作录制与回放。
- 后台任务调度器、CancellationToken、线程池、优先级调度。

如果某项能力只是宿主层“可能会用”，但它不维护编辑引擎不变量，默认不进入 `zom-engine` milestone。

## 文档维护策略（低频）

- 本文档只维护稳定能力边界和长期路线，不维护逐文件清单与阶段进度快照。
- 阶段文件列表、当前完成度、命令清单统一写入 `docs/STATUS.md`。
- 只有“能力边界变化 / 路线调整 / 非目标变化”才更新本文档。

## 当前关键架构决策

- 编辑引擎的**核心编辑坐标**统一采用 `CharOffset`，即 Unicode scalar offset。
- `TextRange` 表示基于 `CharOffset` 的文本区间。
- `ByteOffset` 作为强类型保留，仅用于文件字节、编码边界、外部协议适配和显式坐标转换，不作为编辑 API 主坐标。
- 生产文本存储基于 `ropey`，不自研 Rope / Piece Table / Piece Tree。
- `StringStorage` 仅作为测试 reference model，与 `RopeyStorage` 做 differential testing；不进入 `src/storage/` 生产模块。
- 主选区模型为 `SelectionSet`，`Buffer` / `Transaction` / Undo / Redo 以完整选区集合恢复编辑状态。
- M6 统一承载用户编辑语义：M6A SelectionSet / 多光标，M6B Word / Subword / Symbol 移动，M6C IME 组合输入。
- `src/buffer/mod.rs` 仅保留 Buffer 状态聚合与公共入口；具体能力按领域拆分到子模块（坐标、编辑、历史、事务管线、composition 等）。
- 路线为 M0~M19，**全部阶段按纯编辑引擎标准取舍**；M13 之后明确移出 Command / Macro Recording / LSP 或 Tree-sitter provider / diagnostics 专用 adapter / 后台任务调度器 / 正式 UI 绘制。

# 推荐实现优先级

> 本优先级面向“独立编辑引擎库”的开发顺序。  
> 目标是先得到一个语义正确、可测试、可嵌入的核心，再逐步替换高性能存储结构，并向编辑器宿主暴露稳定接口。

# 判断标准

一个底层编辑引擎是否成熟，可以用下面的问题快速验证：

- [ ] 在 50MB 单行文本中间插入字符是否仍然可接受？
- [ ] 基于 Snapshot 的搜索或分析是否可以由宿主在 Buffer 外只读执行？
- [ ] 外部协议返回的 UTF-16 Position 是否能准确映射到 UTF-8 文本？
- [ ] Emoji、组合字符、复杂外文是否不会被光标切开？
- [ ] 多光标重叠删除是否能得到唯一合法结果？
- [ ] Undo 是否能恢复文本与选区？
- [ ] 撤销后再编辑是否能保留本地历史分支？
- [ ] 泛型外部 range payload 是否能通过 range tracking 随编辑稳定移动？
- [ ] CRLF 文件保存后是否不会被意外改成 LF？
- [ ] 超大文件、非法 UTF-8、超大粘贴是否不会拖垮引擎？
- [ ] CharOffset 是否作为核心编辑坐标，ByteOffset / Utf16Offset / DisplayColumn 是否只通过显式转换进入对应边界？
- [ ] tab width 改变后 display column 是否能重新计算？
- [ ] word movement 是否能区分 Unicode word、identifier、subword 和 symbol？
- [ ] 版本化外部结果过期后是否能被明确丢弃或 remap？
- [ ] dirty state 是否能通过 current_version 与 saved_version 可靠判断？
- [ ] 核心操作是否有稳定 benchmark 与内存统计？
- [ ] 文档中是否没有把完整 LSP、语法树、diagnostics、Command、宏录制、任务调度器或 UI 渲染误写成编辑引擎职责？
