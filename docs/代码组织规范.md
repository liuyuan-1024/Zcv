# 代码组织规范

本文只规定跨 crate 通用的源码组织方式。领域职责与架构边界记录在对应 crate README 中。

## 按所有权组织

文件位置由真实消费关系决定：

1. 只有一个消费方的代码放在消费方附近。
2. 存在两个或更多真实消费方时，才提取共享原语。
3. 共享层保存共同依赖的基础能力，不保存某个消费方的完整业务逻辑。
4. 没有真实复用时，不为目录整齐或未来可能性预建抽象。

模块变大时，先按职责拆分子模块，再考虑提升可见性。拆文件不等于建立新的架构层。

## 文件内顺序

Rust 文件通常按以下顺序组织：

1. 模块文档与属性。
2. 标准库、第三方 crate、内部 crate、当前 crate 的导入。
3. 常量、公共协议与核心类型。
4. 主要实现。
5. trait 实现与渲染接入。
6. 局部辅助函数。
7. 测试模块。

顺序服务于阅读，不要求为了形式统一打散紧密相关的定义与实现。

## 模块入口

- 每个 crate 通过 Cargo `lib.path` 指定的文件作为公共入口。
- 公共入口保持简短，只声明模块、重导出稳定 API 并完成必要初始化。
- 私有实现通过 `mod` 隐藏；可见性规则见[重导出规范](重导出规范.md)。
- crate 的职责、所有权、不变量和验证入口写在该 crate 的 `README.md`，不集中复制到 `docs/`。

## 注释与文档

- 注释说明非直观约束、不变量、外部协议或生命周期原因。
- 不逐字复述代码，不记录修改过程、review 对话或过时方案。
- 当前组件库存、文件清单和逐步迁移过程不作为长期文档维护。
- 改动职责、公共 API 或生命周期时，同步更新最近的 crate README。

## 测试位置

测试放在项目约定的 `test` 目录或同模块测试入口中，按可观察行为组织。不要为了测试公开内部实现，也不要让根模块堆积与领域无关的测试辅助代码。

## 修改检查

提交组织调整前，确认：

- 每个移动后的模块都有清晰所有者。
- 没有为了旧路径保留转发层。
- 公共入口没有暴露新的内部细节。
- README 和引用链接已同步。
- diff 中没有顺手整理的无关文件。
