# 桌面端设计手册

> 本文定义 `zom-desktop` 的架构与视觉系统设计原则。**本文只规定 `zom-desktop` 这一个 crate 的事**——视觉层、平台层、组合根、桌面端偏好系统。其他 crate（`zom-engine` / `zom-workspace` / `zom-view` / `zom-command` / `zom-ai`）有各自的 README 与 docs，本文不重复也不覆盖。
>
> 视觉的具体数值（色板、节拍刻度）以单独的 token 清单为准，本文只规定它们的命名规则与归属规则。

## 一、文档定位与边界

### 1.1 zom workspace 中的 zom-desktop

zom 是一个 Cargo workspace，由六个 crate 组成。本文之外的 crate 各自独立设计与文档化：

```
zom-engine      纯 Rust 文本编辑底座（已冻结）
zom-workspace   "有什么"：buffer 与文件生命周期；拥有 Buffer 实例
zom-view        "我怎么看它"：view/pane/滚动/本视图 selection 与 fold
zom-command     命令派发脊柱 + 键位模型；"所有操作均是命令"
zom-ai          AI 抽象：provider trait + request/proposal 模型
zom-desktop     GPUI 外壳 + 组合根；本文档的主体
```

依赖图（无环）：

```
                                ┌─→ zom-engine
                                │
zom-desktop ─→ zom-command ─────┼─→ zom-workspace
            ─→ zom-view    ─────┤
            ─→ zom-workspace────┘
            ─→ zom-engine
            ─→ zom-ai ──────────→ zom-engine
```

`zom-ai` 与 `zom-command` 无依赖边；P4 接入 AI 命令闭环时，二者在 `zom-desktop` 组合根相遇。

### 1.2 本文档的合法领地

| 该规定 | 不该规定 |
|---|---|
| L1-L4 视觉层（外壳组件分层） | 命令系统语义（在 `zom-command`） |
| 颜色 / 尺寸 / 主题 / 字号 / i18n | 键位类型与解析（在 `zom-command`） |
| 桌面端 settings（视觉、用户偏好、键位文件） | 编辑事务 / Buffer / Snapshot（在 `zom-engine`） |
| OS 事件 → 归一化 KeyChord 的解码 | AI provider 抽象（在 `zom-ai`） |
| 组合根：如何接入并组装 5 个底层 crate | Buffer / 文件生命周期（在 `zom-workspace`） |
| Dock / Panel / EditorGrid 视觉模型 | view 状态 / fold / viewport 数学（在 `zom-view`） |
| 平台抽象（窗口控制、菜单、文件对话框） | 跨 crate 的依赖图（在根 `TODO.md`） |

遇到本文未覆盖的情形，**先确认它属于 desktop 还是某个底层 crate**：如果属于底层 crate，去对应 crate 的 docs；属于 desktop 才补本文。

## 二、组合根

`zom-desktop` 是整个 zom workspace 的**组合根（composition root）**。底层五个 crate 各自提供 public API，desktop 负责把它们装在一起并接到 GPUI 上。

### 2.1 服务持有

desktop 持有以下顶层实例（全局或按窗口，详见第十三章）：

| 实例 | 来自 | 范围 |
|---|---|---|
| `Workspace` | `zom-workspace` | 每窗口绑一个（11.3） |
| `ViewSet` | `zom-view` | 每窗口绑一个 |
| `CommandRegistry` | `zom-command` | 进程单例 |
| `Keymap` | `zom-command` | 进程单例（从 settings 加载） |
| `AiProvider`（接入时） | `zom-ai` | 进程单例 |
| `ThemeRegistry` / `LocaleRegistry` / `SettingsRegistry` | 本 crate | 进程单例 |

GPUI 侧把"会变的状态"包装为 `Entity<T>`，提供 observe；不变的注册表也可包装为 Entity 以便统一 observe 接口。

### 2.2 启动序列

```
1. 加载 settings（用户级 settings.toml）
2. 启动 ThemeRegistry / LocaleRegistry（基于 settings）
3. 创建 CommandRegistry，注册内建命令
   - 安装 `zom-command::commands::editor` / `workspace` 等 catalog
   - 安装会 emit `HostEffect` 的 UI catalog（panel.toggle.xxx、window.xxx 等）
   - 若启用 AI：注册需要 AiProvider 句柄的命令（在组合根捕获）
4. 解析 settings.keymap → 构造 zom-command 的 Keymap 实例
5. 创建首个 Workspace + ViewSet（默认空白 buffer 或上次会话恢复）
6. 启动首个 GPUI Window，装配 WorkbenchFrame
```

### 2.3 命令注册的分工

| 命令类别 | 注册者 | 例 |
|---|---|---|
| 编辑命令 | `zom-command::commands::editor::install` | `editor.insert_text` / `editor.undo` / `editor.move_selection` |
| UI / 外壳命令 | `zom-command::commands::*`，handler emit `HostEffect` | `panel.toggle.file_tree` / `window.minimize` / `settings.open` |
| AI 命令 | desktop 组合根（handler 捕获 AiProvider） | `ai.propose-edit` / `ai.accept-proposal` |
| 将来插件命令 | 插件 host 调用 `CommandRegistry::register` | 任意 |

**desktop 不重新发明 CommandId / CommandArgs / Keymap**——这些已在 `zom-command` 设计完毕。desktop 的责任是：

- 注册自己负责的那一类命令
- 解码 OS 事件为 `KeyChord` 喂给 keymap（详见第十四章）
- 实现命令面板等 UI 入口（详见第十五章）

### 2.4 模块分区

desktop crate 内部分两大模块：

```
zom-desktop/src/
  shell/       视觉层与平台层（本手册的主战场）
    workbench/   L4 窗口级外壳区域、Dock 状态与 panel 固定归属
    features/    L3 功能切片；dock panel 收在 features/panels/
    surfaces/    浮面 portal 外壳：定位、层级、关闭与焦点归还
    bubble/      气泡提示层：统一轻量提示模型
    shared/      L2 视觉原语、资源、主题 token
    platform/    平台差异收纳（第十四章）
    ...
  app/         命令装配、Workspace / ViewSet / Keymap 编排、IME 状态投影
    command.rs   命令派发与 HostEffect 收集
    ime.rs       输入法桥接
    ...
```

`shell` 不依赖 `app`；`app` 装配 `shell` 并接入底层 crate。

## 三、组件层级

桌面端组件代码必须按四层组织。**每一层的所有权规则不同**，混淆层级是后续所有腐烂的起点。

```
L4  Region      ── TopBar / BottomBar / EditorGrid / Dock
                  窗口级外壳区域。强存在感、几乎不复用、由 app 层组装。
L3  Composite   ── CommandPalette / FileTree / TabStrip / StatusItem / EditorView
                  业务组件。有领域状态、有交互语义、有专属文案与图标。
L2  Primitive   ── Button / Glyph / Tooltip / Popover / Frame
                  视觉原语。无领域语义、可被多处复用。
L1  Token       ── gray.s03 / blue.a04 / space.s4 / radius.r4 / type.f13
                  视觉刻度。只是命名常量。
```

### 3.1 各层所有权

| 层 | 必须自己拥有 | 必须从下层取 | 不能拥有 |
|---|---|---|---|
| L4 Region | 区域内 layout 决策、专属 placement、专属 actions | 视觉原语、token | 不能直接画图形（要复用 L2） |
| L3 Composite | 视觉状态、交互语义、专属 icon / 文案 / actions | L2 + L1 | 不能定义新的复用型颜色或尺寸；不能持有领域状态（领域状态在 workspace / view） |
| L2 Primitive | 视觉算法（圆角、阴影、布局）、变体枚举 | L1 | 不能持有业务状态、不能知道自己被谁用 |
| L1 Token | 一组命名常量 | — | 不能引用任何上层 |

### 3.2 L3 与领域状态的边界

L3 视觉组件**不拥有领域状态**——领域状态在底层 crate：

| 领域状态 | 真正归属 | desktop L3 怎么用 |
|---|---|---|
| Buffer 内容、dirty、path | `zom-workspace::WorkspaceBuffer` | EditorView 透过 `Entity<Workspace>` 句柄读 |
| View 的光标、滚动、fold | `zom-view::View` | EditorView 透过 `Entity<ViewSet>` 句柄读 |
| 命令注册表 | `zom-command::CommandRegistry` | CommandPalette 透过句柄读列表 |
| AI 提案 | `zom-ai::AiProposal` | AI 面板透过 provider 句柄读 |

L3 自己拥有的"视觉状态"只是：折叠展开标志、搜索框输入文本、当前 hover 项、滚动位置缓存（非视图本体）、表单临时填写值等**纯 UI 状态**。

### 3.3 "组件自给自足"的精确含义

"组件掌控自身资源"这条原则**只在 L3 严格成立**。L4 太大、L2 太通用、L1 本身就是资源。

一个 L3 组件的目录应当长成这样：

```
shell/features/panels/file_tree/
  mod.rs              对外只导出 FileTree 与其 Props
  view.rs             render 逻辑（小组件可直接写在 mod.rs）
  state.rs            可选。纯 UI 状态（折叠、hover、scroll cache 等非领域状态）
  actions.rs          组件专属 UI action 枚举
  copy.rs             组件专属文案，每条用 match cx.locale() 给出多语言（见第十章）
  tests.rs            必需。至少覆盖一次主要 UI 状态转移（见第十一章）
  logic.rs            可选。纯算法（fuzzy 匹配、树折叠等），可裸单测
  preview.rs          可选。playground 用的典型状态 variants
  styles.rs           可选。组件本地视觉常量（仅当不是 token 复用时）
```

注意组件目录**没有** `assets/` 与 `theme/` 子目录：视觉 token 不属于任何单个组件，资源文件（svg / 字体）由根资源目录统一管理。

### 3.4 是否新增视觉常量的判定

L3 组件经常会想"我这个特殊场景需要一个 token 里没有的值"。判定准则只有一条：

> **改了这个值，会影响其他组件吗？**
>
> - 会 → 它属于 token，必须进 L1。
> - 不会 → 它属于组件本地常量，写在组件目录里。

典型的组件本地常量：红绿灯三色（模仿系统、拒绝主题改写）、品牌徽标的精确尺寸、组件内特殊图形的几何参数。

## 四、颜色系统

### 4.1 两轴正交：色相 × 档位

颜色 token 由两个正交维度决定：

```
轴 A  色相 hue     gray | blue | orange | red | green
轴 B  档位 step    01..09，跨色相含义固定（见 4.2）
```

token 命名形如 `hue.sNN` / `hue.aNN`，例：

```
gray.s01     app 底面背景
blue.s07     实心强调色（caret、按钮品牌色）
blue.s06     焦点边框
blue.a04     active UI 背景（半透明，叠在文本上）
orange.a05   次级强调高亮（半透明）
```

**关键设计**：**档位 step 跨色相含义固定**。`blue.s07` 与 `red.s07` 都是"该色相的实心强调档"——色相决定语气，档位决定角色。组件按"我要哪种视觉角色"反查档位，按"是不是要强调 / 是不是危险态"选择色相；两个维度独立做决定。

**不引入 usage 轴**。先前把"用法"作为命名维度（`xxx.fill` / `xxx.text` / `xxx.border`）的设计撤掉——usage 不是颜色的属性，是消费方的事；档位 step 已经隐含了该用在哪类元素上（见 4.2 表）。

### 4.2 9 档功能语义表

每个色相提供 9 档；档位**严格跨色相对齐**：

| 档 | 角色 | 典型用法 |
|---|---|---|
| 01 | app background | 最深底面（编辑区底） |
| 02 | surface | 抬升面（浮层底、bars 底） |
| 03 | ui-bg | UI 元素背景（常态） |
| 04 | ui-active | UI 元素背景（active / selected / hover 后） |
| 05 | border-subtle | 次级边框、分隔线 |
| 06 | border-focus | 焦点强调边框、hover 边框 |
| 07 | solid | 实心强调（caret、按钮 bg、链接色、品牌色填充） |
| 08 | text-muted | 次级 / 弱化文字 |
| 09 | text | 正文 / 强调文字 |

**档位含义不可更改**。一旦发布，每个数字代表的视觉角色就是用户主题作者的隐式 API（详见 5.6）——改它就破坏所有用户主题。

**关于 text 的强弱**：第一版只有 08 / 09 两档文字色。需要"比正文更强"的对比时，**靠 font_weight，不靠色阶**——给文字加 token 是逃避排版规则。

**gray 的 06/07 档**：填值以保持跨色相对称（无障碍 / 中性 solid 场景可能用到），但调用时优先考虑能否用 accent 色相。"中性焦点框"是 gray.s06 的少数合法场景；多数 focus / solid 应该走 blue。

### 4.3 solid 与 alpha 双阶梯

每个色相提供两条并行阶梯，档位语义同步：

```
hue.sNN    solid    不透明 RGB；用于边框、文字、实心填充
hue.aNN    alpha    半透明 RGBA；叠加在底色上的色块，让下层透过
```

| 形态 | 适合 | 不适合 |
|---|---|---|
| `sNN` | 文字、1px 边框、caret、按钮 bg、图标 | 跨文本的色块（会盖住 syntax 字色） |
| `aNN` | 选区背景、搜索高亮、hover 高亮、AI 提案区间 | 文字色（alpha 文字对比度不稳） |

**取色三步**：先选色相（语气）→ 再选档位（角色）→ 最后选 solid / alpha（叠加方式）。三个维度有清晰先后，调用方不需要"凭审美挑步数"。

举例：

```
caret 实心竖条        blue.s07    （蓝色相 × solid 强调档 × 不透明）
选区背景色块          blue.a04    （蓝色相 × active UI 档 × 半透明）
搜索普通命中          blue.a05    （蓝色相 × border-subtle 档 × 半透明）
搜索当前命中          orange.a05  （橙色相 × border-subtle 档 × 半透明）
错误文字              red.s07     （红色相 × solid 强调档 × 不透明）
危险按钮 hover 边框   red.s06     （红色相 × focus 边框档 × 不透明）
```

注意搜索两个命中**共用 a05 档**——同视觉角色，色相区分；这正是档位含义跨色相对齐的红利。

### 4.4 命名硬规则

1. **永远不按组件命名颜色**。`topbar_bg`、`status_item_color`、`caret_color` 都属于禁项。
2. **永远不按用法命名颜色**。`selection_bg`、`focus_border`、`link_text` 都属于禁项——用法在档位 step 里。
3. **永远只按"色相 + 档位"命名**。组件按视觉角色反查档位、按语气反查色相。
4. **组件本地色是例外、不是常态**。能进 token 的不进本地；进本地的必须在组件 doc 里写明"为什么不能复用 token"。

### 4.5 档位与色相的冻结纪律

档位含义（4.2 表）与色相列表（4.1）一旦发布即冻结：

- **不能改某档位的语义**。比如把 `s07` 从"solid 强调"改成"次强调"，会同时改写所有 5 个色相的同一档语义——这是用户主题作者的契约破坏。
- **新增档位是不可逆操作**。9 档之外要加（如 `s10`），所有内置 + 用户主题都得补值；走 5.6 deprecation 流程。
- **新增色相不影响档位语义**。要加 `purple` / `cyan` 等新色相时，按 9 档语义表完整填值就行——这是档位语义跨色相对齐的红利。
- **删除色相或档位是破坏性变更**。

### 4.6 颜色 token 的 API 形态

token 必须以函数形式暴露而非常量。函数签名固定为：

```rust
pub fn s07(cx: &App) -> Rgba { cx.theme().blue.solid.s07 }
pub fn a04(cx: &App) -> Rgba { cx.theme().blue.alpha.a04 }
```

组件代码不允许出现 `const BLUE_S07: Rgba = ...`，也不允许出现不接受 `cx` 的零参 token 函数。这是主题切换得以运行时生效的前提。

调用形如 `color::blue::s07(cx)` / `color::orange::a05(cx)`——色相是模块、档位是函数。括号始终在最后，与"组件 → 取色 token"的语法心智一致。

### 4.7 与主题的关系

颜色 token 的**集合定义**（5 色相 × 9 档 × 2 阶梯 = 90 个 token）由本章规定，**取值**由主题决定。换主题只能改取值，不能改集合。第五章规定取值如何被填充和切换。

第一版不区分"品牌色"。所有颜色 token 都参与主题切换。

## 五、主题系统

### 5.1 定位

主题是颜色 token 集合的一次完整填充。**主题不增减 token**，只决定每个 token 的具体取值。

只有颜色参与主题切换。**尺寸、字号、圆角、间距不参与主题**。

### 5.2 主题来源

```
内置主题   embedded 在二进制里
           themes/dark.toml
           themes/light.toml

用户主题   从用户目录加载
           ~/.config/zom/themes/*.toml（跨平台路径见第十四章）
```

第一版提供两套内置主题：`dark` 与 `light`。用户主题第一版即支持加载。

### 5.3 配置格式：TOML

主题文件采用 TOML。每个色相一个表，下分 `solid` / `alpha` 两个子表（对应 4.3 的双阶梯）：

```toml
name = "dark"
extends = "dark"   # 可选；继承的基底主题名

[gray.solid]
s01 = "#0d0f12"   # app background
s02 = "#13161b"   # surface
s03 = "#1b1f26"   # ui-bg
s04 = "#252a33"   # ui-active
s05 = "#3a4050"   # border-subtle
s06 = "#4a5266"   # border-focus
s07 = "#5e6678"   # solid
s08 = "#a8b0c0"   # text-muted
s09 = "#f2f4f8"   # text

[gray.alpha]
a01 = "#0d0f1219"   # alpha 各档对应 solid 同档语义，叠在背景上
a02 = "#13161b26"
# ... 9 档全填

[blue.solid]
s01 = "..."
# ... 9 档全填
s06 = "#5a8fd6"   # border-focus（焦点边框）
s07 = "#74ade8"   # solid（caret、品牌色）

[blue.alpha]
a04 = "#74ade83d"   # ui-active 档：选区色块
a05 = "#74ade866"   # border-subtle 档：搜索普通命中
# ... 9 档全填

# orange / red / green 同结构
```

颜色值统一用 `#RRGGBB` 或 `#RRGGBBAA`。**禁止**在主题文件里出现 token 名以外的自定义键。**每个色相的 solid 与 alpha 两套阶梯都必须各填 9 档**（除非 `extends` 覆盖，见 5.4）。

### 5.4 继承语义

用户主题通过 `extends` 字段声明基底，**只列要覆盖的差异**：

- `extends` 缺省时，主题必须**完整定义**所有 token；加载时若有遗漏直接报错并拒绝加载。
- `extends` 指向另一个主题时，缺失字段从基底继承；显式给出的字段覆盖基底同名值。
- 继承只允许一级，不允许链式。
- 基底只能是**内置主题**。强制内置主题永远是完整定义、永远是稳定锚点。

### 5.5 切换路径

```
settings.theme 改变
    ↓
ThemeRegistry 重算 active theme（解析 extends、合并字段）
    ↓
全局 observable 触发
    ↓
所有调用过 cx.theme() 的组件 re-render
```

组件**完全不感知主题切换**——只通过 `cx.theme()` 取值，GPUI observe 负责传播。主题加载失败一律 fallback 到 `dark`，**绝不静默忽略**。

### 5.6 主题作者的隐式 API

**token 命名与档位语义都是用户主题作者的 API**——一旦发布就极难改名 / 改义。这反向约束 4.1 的命名规则与 4.2 的档位语义：

- token 命名必须可读、稳定、与组件解耦
- **档位 step 的视觉角色含义不可悄悄改**——改 `s07` 的语义会同时改写所有色相的同一档
- 新增色相 / 档位是不可逆操作（用户主题不会自动覆盖新 token）
- 删除或重命名色相、档位是破坏性变更，需走显式 deprecation 流程

第一版起就要为 token 写一份"主题作者参考"——列出 5 色相 × 9 档 × 2 阶梯每个 token 的功能含义与示意取值。本文档不重复该清单。

## 六、尺寸系统

尺寸系统分为两个独立子系统：**距离类节拍尺**（固定）与**字号**（用户可配）。二者解耦。

### 6.1 距离类节拍尺

间距、圆角、icon 尺寸、控件 padding 必须落在同一根节拍尺上：

```
基础节拍 = 4px
半节拍   = 2px（仅供 hairline / 描边 / 圆点直径微调）
合法步长 = 2, 4, 6, 8, 12, 16, 20, 24, 32, 40, 48
```

距离类 token **完全固定**，不参与字号变化、不参与任何系数。Zed 风格——字号变化只让"文字行高自然变大"，节拍尺保持纯净。

### 6.2 命名风格：绝对像素

```
space.s2 / space.s4 / space.s6 / space.s8 / space.s12 / space.s16 ...
radius.r2 / radius.r4 / radius.r6 / radius.full
icon.i12 / icon.i14 / icon.i16 / icon.i20
```

相对档位命名抗腐性差。绝对像素命名看名字就知数值、不会膨胀。

允许在底层之上引入语义别名（`gap.inline = space.s4`），但别名永远是底层 token 的 alias、不允许独立赋值。

距离类 token 函数签名可以零参：

```rust
pub fn s8() -> Pixels { px(8.0) }
```

### 6.3 字号系统

字号是**唯一**对用户可配的尺寸维度。zom 不引入密度系统、不引入整体缩放。

字号分为两组独立可配的基础值：

```
ui_font_size       桌面外壳与所有 L2/L3 组件的基础字号，默认 13
buffer_font_size   编辑器缓冲区字号，默认 14
```

二者完全解耦。其他字号档位以基础值为锚点派生：

```
text.caption(cx)   ui_font_size - 1
text.body(cx)      ui_font_size
text.title(cx)     ui_font_size + 1
text.large(cx)     ui_font_size + 3

editor.body(cx)    buffer_font_size
editor.gutter(cx)  buffer_font_size - 1
```

字号 token 必须接受 `cx`，从 `cx.fonts()` 取基础值。

### 6.4 行高的派生

行高**不暴露为独立 token**，从字号按固定比例派生：

```
ui 行高     = ui_font_size × 1.5
editor 行高 = buffer_font_size × 1.4
```

行距比例是文档级常量，组件不感知。派生而非独立暴露的理由：行高与字号绑死才能保证视觉协调。

### 6.5 不引入密度系统

zom 明确不引入独立密度系统（无 compact / normal / comfortable 档位、无 density scale 系数）。理由：

- 用户调字号 → 行高跟着变 → 文字行天然变紧/变松 → 已覆盖大多数"密度感"需求
- 间距类完全脱钩字号变化 → 节拍尺保持纯净 → 视觉对齐永远精确到像素
- icon 尺寸固定 → 跨字号下控件结构稳定

**未来约束**：即使将来引入密度系统，作用域也只允许**全局一档**——禁止局部分区。理由是局部分区会让节拍尺失去"窗口内统一"的保证，且违反第七章依赖方向规则。

### 6.6 组件内禀尺寸

组件自身的"为什么是这个值"是组件设计决策，应当写在组件本地常量里，不进 token。例：红绿灯直径、品牌徽标尺寸、特殊图形几何参数。

## 七、依赖方向

### 7.1 desktop 内部单向依赖图

```
L4 Region ─────┐
               ├──> L2 Primitive ──> L1 Token ──> Platform
L3 Composite ──┘
```

严禁的反向依赖：

- L2 不能 `use crate::app::*`（原语不能知道领域）
- L3 不能 `use crate::shell::region::*`（组件不能知道自己住在哪个区域）
- L1 不能 `use` 任何上层
- 同层之间不准互相 `use`（同层组件互相不可见，要复用就下沉到下一层）

### 7.2 跨 crate 依赖

desktop 对底层 crate 的依赖：

```
zom-desktop ─→ zom-engine
            ─→ zom-workspace
            ─→ zom-view
            ─→ zom-command
            ─→ zom-ai
```

**所有跨 crate 调用只走 public API**。不允许使用其他 crate 的私有路径、源码 import、测试细节。

底层 crate 之间的依赖方向由根 `TODO.md` 与各 crate README 锁定，desktop 不打破它。

### 7.3 用模块可见性强制

依赖方向必须在编译期强制，不靠人审。

- L1 token 模块：`pub(crate)`，全 crate 可见
- L2 primitive 模块：`pub(crate)` 导出原语类型；内部实现 `pub(super)`
- L3 composite 模块：`pub(crate)` 只导出组件类型与 Props；其余一律 `pub(super)` 或私有
- L4 region 模块：仅 `app` 层可见，对外 `pub(super)`
- `app/` 是组合根，可以 import `shell/`；反之**禁止**

**第一版就要把模块树切对**。事后切的代价是十倍。

## 八、状态注入

### 8.1 组件只接受两种输入

L3 组件不准在内部主动去全局拿状态。只接受两种输入：

```
A. 数据   通过构造函数 / Props 传入（不可变快照、显式 Entity 句柄、显式 crate 服务句柄）
B. 行为   通过回调 / action handle 传入
```

禁止形式：

```rust
// 反例：组件内部直接读全局
let workspace = cx.global::<Workspace>();
```

正确形式：

```rust
// 正例：调用方注入显式句柄
pub struct EditorView {
    workspace: Entity<Workspace>,   // 来自 zom-workspace
    view_set: Entity<ViewSet>,       // 来自 zom-view
    view_id: ViewId,                 // 标识本视图
    on_request_command: Box<dyn Fn(CommandId, CommandArgs, &mut App)>,
}
```

### 8.2 透明传播的全局例外

下列全局通过 `cx.xxx()` 透明访问，**不算违反 8.1**：

| 入口 | 来自 | 用途 |
|---|---|---|
| `cx.theme()` | desktop ThemeRegistry | 当前主题色 |
| `cx.fonts()` | desktop FontRegistry | 当前字号配置 |
| `cx.locale()` | desktop LocaleRegistry | 当前语言 |
| `cx.settings()` | desktop SettingsRegistry | 当前 settings 快照 |

**例外清单由本手册维护，不允许扩展**。底层 crate 的服务（`Workspace` / `ViewSet` / `CommandRegistry` / `AiProvider`）**不在例外清单**——必须通过显式句柄注入。

### 8.3 GPUI 特有陷阱

- L2 / L3 不准调用 `cx.global::<App级状态>()`
- 跨层数据传递必须用 `&View<T>` / `Entity<T>` 显式传入，且 T 必须是该组件需要的最小子状态
- 跨组件通信走 action / event，不走"两个组件读同一个 global"
- 底层 crate 的 entity 句柄从 app 层一路 props 传到 L3，不走 cx global

### 8.4 收益是可替换、可测试、可预览

强制 8.1 的收益不是教条，而是三件具体的事：

- **可替换**：替换组件不需要改它的调用者以外的任何代码
- **可测试**：组件可以脱离完整 app 上下文独立测试
- **可预览**：组件可以放进 playground 单独渲染

## 九、文案与图标

### 9.1 文案

组件专属文案以函数形式写在组件本地 `copy.rs`，每条通过 `match cx.locale()` 给出多语言文本。详见第十章。

跨组件复用的标准文案（如"取消"、"确定"、"关闭"）下沉到 `shell::copy` 模块，按动作语义命名，不按出现位置命名。

### 9.2 图标

资源文件（svg）由根 `assets/` 统一管理，按语义类别分目录。组件只持有自己需要的相对路径，不带 `assets/` 前缀。

```rust
svg().path("icons/actions/close.svg")
```

多处复用的图标路径可以保留为组件本地常量；panel 图标统一由 `PanelId::icon_path()` 映射。只在一处使用的图标路径直接内联。

## 十、国际化

### 10.1 哲学

zom-desktop 第一版即引入 i18n 接口。理由：从字符串直接量迁移到 i18n 是机械重复但工作量巨大的事；"先做接口、再补翻译"的 ROI 远高于"先做直接量、将来全局替换"。

i18n 实现采用最轻量方案：**分散式 + enum locale + 零外部依赖**。不引入 fluent / gettext / rust-i18n 等库。

i18n 只影响 desktop 层。底层 crate 的 `Display`/错误消息**用英文**，由 desktop 在呈现时翻译为 locale 文本（详见 16.5）。

### 10.2 Locale 与切换

```rust
// shell/i18n.rs
#[derive(Clone, Copy, PartialEq, Eq)]
pub enum Locale {
    ZhCN,
    EnUS,
}
```

第一版固定支持 `ZhCN` 与 `EnUS`。每条文案两种语言都必须填写——`Locale` 是 enum，`match` 强制穷举，缺翻译直接编译错。

默认 locale 为 `ZhCN`。locale 通过 `settings.locale` 配置，运行时切换，机制与主题完全相同。

### 10.3 组件文案的写法

```rust
// shell/features/panels/file_tree/copy.rs
use crate::i18n::Locale;
use gpui::App;

pub fn empty(cx: &App) -> &'static str {
    match cx.locale() {
        Locale::ZhCN => "暂无文件",
        Locale::EnUS => "No files",
    }
}
```

调用方：`div().child(copy::empty(cx))`。

### 10.4 含变量的文案

涉及插值的文案用 `format!()`，返回 `String`：

```rust
pub fn found_n(cx: &App, n: usize) -> String {
    match cx.locale() {
        Locale::ZhCN => format!("找到 {n} 个匹配项"),
        Locale::EnUS => format!("Found {n} match{}", if n == 1 { "" } else { "es" }),
    }
}
```

复数 / 性别 / ICU 高级语法第一版不引入。

### 10.5 不翻译的内容

- 产品名（`zom`、`zom-desktop`）
- 技术专有名词（`LSP`、`Workspace`、`Editor`、`Panel`）
- 文件路径、命令 ID、快捷键文本
- 代码 / 标识符
- 底层 crate 的英文 Display 消息（直接在日志、技术对话框中保留原样）

判定准则：**翻译后用户更难看懂的，不翻译**。

### 10.6 跨组件标准文案

跨组件复用的标准文案下沉到 `shell::copy` 模块：

```rust
// shell/copy.rs
pub fn cancel(cx: &App) -> &'static str {
    match cx.locale() {
        Locale::ZhCN => "取消",
        Locale::EnUS => "Cancel",
    }
}
```

命名按动作语义，不按出现位置。

### 10.7 为什么不用 i18n 库

- **编译期穷举**：i18n 库走运行时表，缺 key 只有运行时暴露；enum match 缺翻译直接编译错
- **翻译跟随组件**：组件删除时翻译自然移除，不会留下"30% 死翻译"的腐烂表
- **零工具链**
- **重构友好**

代价是不支持第三方翻译平台。将来确需走 Crowdin / POEditor 时再迁移到集中式表，接口 `copy::xxx(cx)` 不变。

## 十一、测试要求

### 11.1 哲学

"可测试性"不等于"脱离 GPUI"。GPUI 提供 `TestAppContext`，可在测试里启动 headless app。zom-desktop 把"可测"的标准定义为**用 TestAppContext 能跑通**，而不是"代码不依赖任何 GPUI 类型"。

workspace 统一测试策略见 `../agents/project.md`。底层 crate（`zom-engine` / `zom-workspace` / `zom-view` / `zom-command` / `zom-ai`）有各自的 contract test，**desktop 不重复测试它们的领域逻辑**。desktop 测试关注：

- L3 视觉组件的 UI 状态转移
- 组合根：服务注入是否正确、命令注册是否完整、Keymap 加载是否成功
- 跨 crate 接入的边界行为

### 11.2 L3 组件的硬规则

每个 L3 组件必须满足：

> **提供至少一个 `#[gpui::test]`，覆盖该组件的主要 UI 状态转移。**

没有测试的 L3 组件不允许合入。"主要 UI 状态转移"指：打开/关闭、激活/失活、用户交互导致的视觉状态变化。

视觉呈现（颜色、布局、icon 选择）**不在测试覆盖范围**，由 playground 人工 review 兜底。

### 11.3 state / view 是否分文件

**不强制**。L3 的纯 UI 状态可直接放在 `mod.rs` 或 `view.rs` 的 impl 块中。下列任一情况触发拆分：

1. 单文件超过约 300 行 → 拆 `view.rs`
2. `render` 函数超过约 80 行 → 拆视觉子组件
3. 复杂派生计算 → 抽 `logic.rs`（**纯 Rust 函数**，可裸单测）

`logic.rs` 是 desktop 唯一鼓励"脱离 GPUI"的场景——纯算法。

### 11.4 各层测试要求

| 层 | 测试要求 |
|---|---|
| L4 Region | integration 测试覆盖区域组装与面板挂载位置 |
| L3 Composite | 必须 `#[gpui::test]` 覆盖 UI 状态转移；纯算法抽 `logic.rs` 裸单测 |
| L2 Primitive | 关键变体 `#[gpui::test]`；layout 算法可裸单测 |
| L1 Token | 不需要测试 |
| app（组合根） | 启动 smoke test：能成功启动、命令注册无缺漏、keymap 解析无错 |

### 11.5 视觉回归：playground 优先

第一版**不引入 snapshot 截图对比**。视觉回归走 playground 人工 review。

组件可选提供 `preview.rs`：

```rust
pub fn variants() -> Vec<(&'static str, FileTreeUiState)> {
    vec![
        ("empty", FileTreeUiState::empty()),
        ("one-folder", ...),
        ("deep-nested", ...),
    ]
}
```

playground 是 desktop 内部开发工具，遍历所有组件的 `variants()` 渲染网格。

### 11.6 测试不该做的事

- **不测视觉细节**（颜色值、像素 padding）
- **不测 token 取值**
- **不测 GPUI 内部行为**（render 被调用了几次、layout pass 顺序）
- **不重测底层 crate 的领域逻辑**（buffer 怎么 undo 是 engine 的契约测试覆盖的，desktop 不重复）

## 十二、设置系统

### 12.1 定位

设置系统是 zom-desktop 所有用户配置的母体。第五章主题、第十章 locale、第六章字号、第十五章键位——全部由设置系统承载。

设置文件是**单一事实源**：程序内任何变更都立即回写到文件；文件被外部编辑器修改时自动重载触发 observable。

### 12.2 文件位置与格式

格式统一为 **TOML**，与主题、language config 保持一致。

| 作用域 | 路径 |
|---|---|
| 用户级 | macOS: `~/Library/Application Support/zom/settings.toml`<br>Linux: `~/.config/zom/settings.toml`<br>Windows: `%APPDATA%\zom\settings.toml` |
| Workspace 级 | `<project_root>/.zom/settings.toml` |

跨平台路径通过 `dirs` 或同类 crate 抽象，集中在 `shell::platform::paths`。

第一版**单文件**——所有配置（含 keymap）放同一个 `settings.toml`。

### 12.3 第一版 schema 草案

```toml
# ~/.config/zom/settings.toml

# 顶层：影响整个应用的全局偏好
theme  = "dark"
locale = "zh-CN"

# [ui]：UI 层偏好
[ui]
font_size = 13

# [editor]：编辑器偏好
[editor]
font_size = 14

# [keymap]：全局键位（用第十四章定义的逻辑键；语义在 zom-command）
[keymap]
"mod-s"        = "editor.save"
"mod-shift-p"  = "command-palette.open"
"mod-1"        = "panel.toggle.file_tree"

# [keymap.context.<component>]：上下文键位（组件 focus 时生效）
[keymap.context.editor]
"alt-up"       = "editor.move-line-up"
"alt-down"     = "editor.move-line-down"

[keymap.context.file_tree]
"enter"        = "file_tree.open-selected"

# [keymap.darwin] / [keymap.linux]：平台特定覆盖
[keymap.darwin]
"cmd-,"        = "settings.open"

[keymap.linux]
"ctrl-comma"   = "settings.open"
```

### 12.4 命名空间约定

- **顶层**：影响整个应用的全局偏好（theme、locale）
- **分组 `[domain]`**：按作用域分组的偏好（ui、editor、keymap）
- **避免深度嵌套**：不超过两级
- 字段命名 snake_case；布尔字段避免否定语义（用 `enable_x` 而非 `disable_x`）

### 12.5 优先级与合并

```
内置默认  ←  用户级 settings.toml  ←  workspace 级 .zom/settings.toml
```

| 字段类型 | 合并规则 |
|---|---|
| Scalar | 后者覆盖前者 |
| Table | 递归合并，同 key 后者覆盖 |
| Array | 后者**整体替换**前者，不拼接 |

Array 整体替换是有意的——拼接语义会让用户难以"清空"某个数组。

### 12.6 强 schema + 类型安全 API

设置定义为 Rust struct + serde。组件通过 `cx.settings().theme` 访问，编译期保证字段存在。**禁止** `cx.settings().get("theme")` 这类字符串 key 访问。

未知字段**警告但不阻塞加载**——便于版本回退与多设备同步。

### 12.7 失败处理

| 失败类型 | 处理 |
|---|---|
| 文件不存在 | 全部默认；首次启动**不主动创建**文件 |
| 整文件解析失败 | 全部默认 + 持续 toast 报错 + 日志位置 |
| 单字段解析失败 | 该字段默认 + 一次性 toast + 日志 |
| 未知字段 | 警告日志，不报错 |
| Workspace 文件不存在 | 静默，只用用户级 |

**绝不静默忽略整文件失败**。

### 12.8 双向同步

外部文件变更：fs watch → SettingsRegistry reload → merge → 触发 observable。

程序内变更：`cx.settings_mut().set_theme(...)` → 立即触发 observable → 异步写回 settings.toml（debounced）。

写回时保留原文件的注释与格式（用 `toml_edit` 而非 `toml`）。**这条很重要**——用户在配置文件里写的注释是有价值的内容，不能被程序覆盖。

### 12.9 SettingsRegistry

`SettingsRegistry` 与 `ThemeRegistry` / `LocaleRegistry` 结构平行：

- 启动时加载用户级 + 当前 workspace 级 → merge → 提供 active settings 句柄
- 监听两份文件的变更，触发 reload
- 提供 `cx.settings()` 入口

切换 workspace 时重新 merge。

### 12.10 keymap 段的特殊处理

`[keymap]` / `[keymap.context.*]` / `[keymap.darwin]` / `[keymap.linux]` 是 desktop 解析的，**最终交给 zom-command 的 `Keymap`** 类型使用：

```
settings.toml [keymap.*] 段
    ↓
desktop 解析（含平台逻辑键映射，见第十四章）
    ↓
构造 zom-command::Keymap 实例（前缀 trie）
    ↓
KeyChord 流入 → KeymapResolution → CommandId
```

`Keymap` / `KeyChord` / `KeymapResolution` 这些类型由 `zom-command` 提供，desktop 不重新发明，只负责"从配置文件构造它们"。

### 12.11 Workspace 级配置的信任

第一版**信任所有 workspace 级配置**——打开任何项目都直接加载 `.zom/settings.toml`，无信任提示。

将来必须补 workspace trust 机制（参考 VSCode "Workspace Trust"、Zed 同类机制）。第一版用户全部是项目作者本人，trust 是过度设计。

## 十三、窗口模型

### 13.1 多窗口

zom-desktop 支持多窗口。所有窗口**对称**——不区分"主窗口"与"次窗口"。

### 13.2 跨窗口共享 vs 每窗口独立

| 全局单实例（跨窗口共享） | 每窗口独立 |
|---|---|
| `SettingsRegistry`（settings） | `WorkbenchFrame`（L4 region 树） |
| `ThemeRegistry`（active theme） | `EditorGrid`（split tree、tab group） |
| `LocaleRegistry`（active locale） | Dock 状态（显隐、尺寸、active panel） |
| 字号（`ui_font_size` / `buffer_font_size`） | 所有 L3 组件实例与其 UI state |
| `CommandRegistry`（来自 zom-command） | 临时层（SurfaceLayer、BubbleLayer） |
| `Keymap`（来自 zom-command） | `ViewSet`（来自 zom-view） |
| `AiProvider`（来自 zom-ai） | |

`Workspace`（来自 zom-workspace）的归属见 13.3。

### 13.3 Workspace 与窗口的关系

第一版**每窗口绑一个 workspace**。打开新 workspace 的两种方式：

- 在当前窗口打开（替换当前 workspace）
- 在新窗口打开（保留当前 workspace）

跨窗口允许打开同一 workspace。

### 13.4 跨窗口的资源共享

| 资源 | 共享粒度 |
|---|---|
| LSP 实例（将来） | per workspace（跨窗口共享同 workspace） |
| 文件监听 / file watcher | per workspace |
| 项目级索引（符号、文件路径） | per workspace |
| AI 会话 | per window |
| 最近文件 / 最近 workspace | 全局共享 |
| 命令面板使用频率（rank） | 全局共享 |

### 13.5 窗口关闭

- **关闭非最后窗口**：销毁该窗口的所有 UI state；窗口持久化由窗口持久化层处理（见 13.6）
- **关闭最后窗口**：默认退出。macOS 例外——按平台惯例保持进程、隐藏窗口、菜单栏仍激活

### 13.6 持久化边界

持久化整体由将来的「持久化」章节规定。窗口模型侧只约定：

- 全局共享状态 → 全局持久化层（`settings.toml` 等）
- 每窗口独立状态 → 窗口持久化层，按 workspace 写快照
- 下次打开同 workspace 时恢复布局

详细规则参考 `桌面端布局模型.md` 第 8 节，将来整合到本手册独立章节。

## 十四、平台差异

### 14.1 处理原则

平台差异必须**集中收纳到尽可能少的地方**。其他模块编程时假装平台不存在。集中点：`shell::platform`。

L2 / L3 组件**不允许** `#[cfg(target_os = "...")]`。所有平台分支都在 `shell::platform` 一层内完成。

### 14.2 OS 事件 → KeyChord 解码

`zom-command` 只吃归一化的 `KeyChord`，**不处理 OS 事件**。OS 键盘事件到 `KeyChord` 的解码归 `shell::platform::keyboard`：

```
GPUI raw key event（含平台特定 keycode、modifier 标志）
    ↓
shell::platform::keyboard 归一化
    ↓
zom-command::KeyChord
    ↓
zom-command::Keymap::resolve → KeymapResolution
    ↓
CommandQueue
```

解码层处理的差异：

- macOS Cmd vs Linux/Windows Ctrl 的修饰键判定
- AltGr 在 Windows / Linux 上的特殊处理
- 数字小键盘按键映射
- 死键 / 组合键的归一化

KeyChord 的语义由 `zom-command` 定义，本手册不重复。

### 14.3 逻辑快捷键

键位定义中使用**逻辑修饰键**：

```
逻辑键    macOS         Windows / Linux
mod       Cmd           Ctrl
meta      Cmd           Win / Super
alt       Option        Alt
shift     Shift         Shift
ctrl      Control       Control
```

`settings.keymap` 一律用逻辑键：

```toml
[keymap]
"mod-s"        = "editor.save"
```

逻辑键 → 实际键的映射在 `shell::platform::keymap_logical`。

### 14.4 平台特定 keymap

少数非对称场景用平台段覆盖：

```toml
[keymap.linux]
"ctrl-comma"   = "settings.open"
```

合并规则：先加载通用段，再用当前平台段覆盖同 CommandId 的绑定。其他平台段静默忽略。

### 14.5 shell::platform 的职责边界

| 在 `shell::platform` 内 | 不在 |
|---|---|
| OS key event → KeyChord 解码 | KeyChord 语义（在 zom-command） |
| 逻辑键 → 实际键映射 | Keymap 解析（在 zom-command） |
| 窗口管理调用（最小化、最大化、全屏、关闭） | UI 渲染（GPUI 已抽象） |
| 文件选择对话框 | 文件 I/O（标准库 / 跨平台 crate） |
| 剪贴板平台差异适配 | 网络 |
| 平台路径（配置、缓存、日志目录） | 业务逻辑 |
| 菜单栏（如有） | 任何平台无关的代码 |

### 14.6 窗口控制按钮

zom-desktop 自绘窗口控制按钮，跨平台采用统一的 macOS 红绿灯设计（已在 `桌面端布局模型.md` 规定）。**不使用 OS 原生标题栏**。

理由：视觉一致、与 TopBar 融为一体、规避 Windows 标题栏扩展限制。

### 14.7 菜单栏

第一版**不引入原生菜单栏**。所有功能通过命令面板、键位、外壳按钮访问。

理由：菜单栏与命令系统职责重复（菜单是命令的视图）；跨平台菜单栏机制差异极大；现代 IDE 大量依赖命令面板。

第二版可能为 macOS 补最小菜单栏（应用名 / Edit / Window / Help）。

### 14.8 触控板 / 滚动 / 拖放

跟随 OS 行为，由 GPUI 抽象。`shell::platform` 不介入。如发现 GPUI 行为不一致，优先向 GPUI 上游修复。

## 十五、命令与键位接入

本章规定 zom-desktop 作为组合根，如何接入 `zom-command` 的命令系统与键位模型。**不重复 zom-command 自己的设计**（CommandId 字符串约定、CommandArgs 模型、Keymap 前缀 trie、CommandContext 等在 zom-command 已定）。

### 15.1 命令注册的组合根

desktop 是命令注册的最终汇聚点，启动序列：

```
1. 创建空 CommandRegistry
2. 安装 `zom_command::commands::*` catalog
   ── 引入编辑命令（insert/delete/undo/movement 等）与会 emit HostEffect 的 UI 命令
3. shell 实现 HostEffect 翻译
   ── panel.toggle.<id> / window.minimize / window.toggle_maximize 等
4. 若启用 AI：desktop 注册 AI 命令
   ── handler 闭包捕获 AiProvider 句柄（这是 desktop 让 ai 与 command 在组合根相遇的形式）
5. 将来：插件 host 在此调用 CommandRegistry::register
```

**desktop 内的"UI 命令"是 desktop 必须自己写 handler 的那一类**：

| UI 命令 | handler 做的事 |
|---|---|
| `panel.toggle.file_tree` | 切换 Dock 中 FileTree 的显示 |
| `command-palette.open` | 打开命令面板 Surface |
| `theme.cycle` | 在 ThemeRegistry 中切换主题 |
| `settings.open` | 打开 settings 编辑界面 |

这些 handler 操作的是 desktop 自己的视觉状态，因此必须在 desktop 注册。

### 15.2 命令面板（CommandPalette）

CommandPalette 是 desktop 的 L3 组件，使用 `CommandRegistry` 提供的能力：

- 列出所有已注册命令（`registry.list()`）
- 按 fuzzy 匹配筛选（`logic.rs` 中的纯算法）
- 用户选择 → 派发 `(CommandId, CommandArgs::empty())`

命令的 `title` 通过 i18n 显示——见 15.5。

### 15.3 AI 意图到命令的翻译

`zom-ai::AiAction` 是 plain 意图（含 `command: String` + args）。desktop 组合根负责把它解析为 `(CommandId, CommandArgs)`：

```
AiProvider 返回 AiAction
    ↓
desktop 组合根的 AiActionTranslator
    ↓
(CommandId, CommandArgs)
    ↓
CommandQueue
```

`AiActionTranslator` 是 desktop 内的薄薄一层，捕获了"AI 知道的命令词表"。zom-ai 与 zom-command 仍然没有依赖边——它们只在 desktop 这里相遇。

### 15.4 键位三层模型

键位定义在 `settings.keymap`，desktop 解析后构造 `zom-command::Keymap` 实例。三层 dispatch 顺序：

```
1. 全局键位       [keymap]
                  不受 focus 影响

2. 上下文键位     [keymap.context.<component>]
                  组件 focus 时生效；目标必须是 Command

3. 文本输入 fallback
                  未被前两层捕获的可打印字符
                  转发给当前 focus 的文本输入目标
                  EditorView / 单行输入框 / 命令面板搜索框等共享
```

**上下文键位的目标也必须是 Command**——不允许绑组件本地 Rust 类型。组件如果想让某个局部行为可绑键位，必须先把它注册为 Command（如 `file_tree.expand-node`）。

文本输入 fallback：未匹配 keymap 的可打印字符，由 desktop 转换为 `editor.insert_text { text }` 命令（或同等的当前 focus 目标的命令），仍然走 `CommandQueue` 派发。**所有编辑动作都是命令**——这是 zom-command 的核心原则，desktop 不绕开。

### 15.5 命令的 i18n title

命令在用户界面显示时（命令面板、菜单、tooltip）需要 i18n title。desktop 维护一个 `CommandId → i18n_key` 表，由 desktop 的 `copy` 模块按 `cx.locale()` 解析：

```rust
// shell/commands/copy.rs
pub fn title_for(cx: &App, id: &CommandId) -> &'static str {
    match (id.as_str(), cx.locale()) {
        ("editor.save", Locale::ZhCN) => "保存",
        ("editor.save", Locale::EnUS) => "Save",
        ("panel.toggle.file_tree", Locale::ZhCN) => "切换文件树",
        ("panel.toggle.file_tree", Locale::EnUS) => "Toggle File Tree",
        // ...
    }
}
```

新增命令时 desktop 这里必须补翻译，否则 match 编译错——与第十章的"编译期穷举"一致。

底层 crate 的命令 title 由对应 catalog 维护；desktop 只负责把 keymap 反查结果和本地化展示接到 UI，不在组件里手拼命令字符串。

## 十六、事件与通信

本章规定 zom-desktop **内部**的"行为传递"机制。跨 crate 的领域调用（修改 buffer、操作 view、派发命令）走对应 crate 的 public API，不在本章范畴。

### 16.1 通信机制决策树

```
我要传什么？
├─ 用户可名、可绑键位的功能              → Command（zom-command；见第十五章）
├─ 父→子组件的直接行为                    → 回调注入（16.2）
├─ desktop 内跨多层 / 跨兄弟组件的事件    → Entity Event（16.3）
├─ desktop 全局视觉状态变化               → Observable（16.4）
├─ 修改 buffer / view                    → 派发 Command 或直接调底层 crate API
└─ 监听底层 crate 状态变化                → observe 底层 crate 提供的 Entity 句柄
```

GPUI Action **不出现在决策树里**——它是 zom-command 内 Keymap dispatch 的实现机制，组件作者不直接接触。

### 16.2 回调注入

L3 组件 Props 默认通过回调接收父级行为：

```rust
pub struct FileTreeProps {
    pub workspace: Entity<Workspace>,         // 来自 zom-workspace
    pub on_open: Box<dyn Fn(PathBuf, &mut App)>,
    pub on_request_command: Box<dyn Fn(CommandId, CommandArgs, &mut App)>,
}
```

判定准则：**父级想知道"子组件发生了某个具体动作"时用回调**。回调是显式的、类型安全的、可注入 mock 测试。

需要派发命令时，回调内调用调用方持有的 CommandQueue / CommandExecutor，而不是组件自己直接持有命令派发链路。

### 16.3 Entity Event

跨多层、跨兄弟组件通信时用 GPUI 的 Entity Event 机制：

```rust
pub enum FileTreePanelEvent {
    FileActivated(PathBuf),
}

impl EventEmitter<FileTreePanelEvent> for FileTreePanelState {}

cx.emit(FileTreePanelEvent::FileActivated(path));

cx.subscribe(&panel, |this, _, event, cx| { ... });
```

使用规则：

- **必须有明确的源 entity**：subscribe 时显式 `&entity_handle`，**禁止"无源订阅"**
- **事件携带 payload**：无 payload 用 Observable
- **Event 类型不跨 crate 暴露**：是组件实现细节；跨 crate 通信用 Command 或显式 Props

### 16.4 Observable

desktop 全局视觉状态变化用 observe：

```rust
cx.observe(&theme_registry, |this, _, cx| {
    cx.notify();   // 仅触发重渲染
});
```

判定准则：

- **有 payload 用 Entity Event**
- **无 payload、表达"状态变了、自己去读最新值"用 Observable**

例：主题切换 / locale 切换 / 字号变更都是 Observable。

底层 crate（workspace / view 等）的状态变化也以 observe 形式接入——desktop 把它们的 entity 句柄持有后 observe。

### 16.5 错误的呈现

底层 crate 的 `Display` / `Error` 是英文（见 10.5）。desktop 在呈现给用户时翻译：

```rust
fn translate_workspace_error(cx: &App, err: &WorkspaceError) -> String {
    match (err, cx.locale()) {
        (WorkspaceError::FileNotFound(p), Locale::ZhCN) =>
            format!("文件不存在：{}", p.display()),
        (WorkspaceError::FileNotFound(p), Locale::EnUS) =>
            format!("File not found: {}", p.display()),
        // ...
    }
}
```

呈现层级（toast / banner / dialog）由 desktop 决定。技术细节同时进日志（不依赖 i18n）。

### 16.6 硬禁止全局事件总线

任何形式的全局 EventBus / MessageHub / GlobalDispatcher 都**不允许**出现在 zom-desktop。

理由：难追踪、难测试、容易腐烂。

跨组件通信只允许：

- **Entity Event**：必须有明确的源 entity
- **Command**：用户语义的全局动作，由 CommandRegistry 集中维护

### 16.7 键盘输入完整路径

```
GPUI raw key event
    ↓
shell::platform::keyboard 解码为 KeyChord
    ↓
zom-command::Keymap::resolve（三层 dispatch）
    ├─ 全局键位匹配 → CommandQueue
    ├─ 上下文键位匹配 → CommandQueue
    └─ 都不匹配 → 文本输入 fallback
                  ↓
              desktop 把字符包装成 editor.insert_text 命令 → CommandQueue
    ↓
zom-command::CommandExecutor 排空队列，handler 执行
    ↓
handler 调用 Workspace / ViewSet / Engine API 修改状态
    ↓
对应 Entity notify
    ↓
观察该 Entity 的 L3 组件 re-render
```

整条路径里 GPUI Action 只在 Keymap 内部 dispatch 时作为实现细节出现，组件作者从头到尾不直接接触。

## 十七、错误处理

### 17.1 哲学

错误处理被切成两半：

```
底层 crate 错误（各自已定型，desktop 不重新发明）
  zom-engine     分层 thiserror（坐标 / 编辑 / 事务 / 存储 / 历史）
  zom-workspace  WorkspaceError / WorkspaceResult
  zom-command    CommandError
  zom-ai         AiError / ProposalRejected
        ↓ 通过 ? 上抛
desktop 的责任
  - desktop 自己的错误（settings 加载、theme 解析、I/O）
  - 把底层 crate 错误冒泡转化为用户可见呈现
  - panic hook + 数据救援
  - 日志（tracing）
  - i18n 化错误消息
```

desktop 只负责**中转、呈现、保护**，不重新定义错误模型。

### 17.2 错误风格

| 位置 | 风格 |
|---|---|
| 底层 crate | thiserror + 自定义 Error enum（已定，不动） |
| desktop 内部默认 | `anyhow::Result<T>` + `Context` |
| desktop 内工具模块 | 局部用 thiserror（如 `ThemeLoadError`、`SettingsParseError`、`KeymapParseError`），在 desktop 内被 anyhow 包装传播 |
| 跨 crate 转换 | 底层 Error 通过 `?` 自动 From 转入 anyhow，链路上下文保留 |

理由：desktop 是应用层，大部分错误只是"展示给用户"，弱类型 + 字符串链上下文足够；局部工具模块在 desktop 内仍想 match 分类处理时用 thiserror。

### 17.3 panic vs Result 的边界

| 场景 | 处理 |
|---|---|
| 编程错误（违反不变量、不可能状态、契约违反） | `panic!` / `unreachable!` / `debug_assert!` |
| 外部世界（文件、网络、解析、用户输入） | `Result` |
| 第三方 / 底层 crate 调用 | 必须 `?` 上抛或显式处理 |

**desktop 顶层（main）允许 panic**，但必须有 panic hook（17.6）。
**desktop 内部代码禁 `.unwrap()`**——测试代码、`// SAFETY:` 注释的"明确不可能"场景除外。CI 用 `clippy::unwrap_used` lint 强制。

### 17.4 用户可见错误的四级呈现

```
1. Inline    内联在相关元素旁、不打断
             例：保存按钮旁的"无效文件名"

2. Toast     窗口角落浮起、几秒后自动消失
             例：自动保存失败 / 主题加载 fallback

3. Banner    面板顶部常驻横幅，需用户主动关闭
             例：LSP 进程崩溃 / 文件被外部修改未同步

4. Dialog    模态对话框，必须用户操作
             例：未保存内容关闭确认 / 严重错误退出
```

判定准则：

- 阻塞继续操作 → Dialog
- 需用户知晓但可继续 → Banner
- 短暂提示、不关键 → Toast
- 与某个具体元素强绑 → Inline

四级呈现在 desktop 内各有 L2 / L3 组件支持：`InlineError` / `Toast` / `Banner` / `Dialog`。组件接收 `&str`（已 i18n 化的人话），不接收原始 Error 类型。

### 17.5 不静默原则

**任何错误必须留下痕迹**——至少一条 `tracing::warn!` / `tracing::error!`。

**禁止形式**：

```rust
let _ = risky_call();                                    // 禁
match risky_call() { Ok(_) => ..., Err(_) => () }         // 禁
risky_call().ok();                                        // 禁
```

唯一例外：明确写出 `// IGNORE_ERR: <原因>` 注释。例外用法稀有，code review 必看。

### 17.6 Panic hook 与数据救援

应用启动时安装 panic hook：

```
1. 完整记录 panic 详情到日志（含 backtrace、线程、文件位置）
2. 调用 Workspace::emergency_save_all
   ── 把所有 dirty buffer 直接 dump 到
      <cache_dir>/zom/crash-recovery/<timestamp>/
3. 退出进程
4. （第二版）显示崩溃对话框
5. （第二版）下次启动检测 crash-recovery 目录、提示用户是否恢复
```

第一版做 **1 + 2 + 3**：2 留接口，实现尽量简单（直接写文本）。第二版补 4 + 5。

panic hook 不依赖 desktop 的 GPUI 状态——hook 触发时 GPUI 可能已不可用，必须用纯 std I/O 完成数据保存。

### 17.7 错误的 i18n 化

底层 crate 的 `Display` 是英文（已隐含——它们没有 locale 概念）。desktop 在呈现给用户时翻译：

```rust
// shell/errors/translate.rs
pub fn translate_workspace_error(cx: &App, err: &WorkspaceError) -> String {
    match (err, cx.locale()) {
        (WorkspaceError::FileNotFound(p), Locale::ZhCN) =>
            format!("文件不存在：{}", p.display()),
        (WorkspaceError::FileNotFound(p), Locale::EnUS) =>
            format!("File not found: {}", p.display()),
        // ...
    }
}
```

每个底层 crate 一个翻译模块（`translate_workspace_error` / `translate_engine_error` / `translate_command_error` / `translate_ai_error`）。

**新增 Error 变体时 desktop 的 match 编译错**——强制补翻译，与第十章 i18n 的"编译期穷举"哲学一致。

技术细节同时进日志（保留英文原文），**日志不走 i18n**——日志面向开发者与机器，全英文便于检索、grep、贴 issue。

### 17.8 tracing 集成

第一版用 `tracing` crate。输出策略：

| 环境 | 输出目标 |
|---|---|
| 开发模式（`cargo run`） | stderr，彩色 |
| 发布模式 | 文件 `<cache>/zom/logs/zom-YYYY-MM-DD.log`，按日轮转，保留最近 7 天 |

跨平台 `<cache>` 路径走 `shell::platform::paths`（12.2）。

级别约定：

| 级别 | 用途 |
|---|---|
| `error!` | 用户或开发者必须知晓的错误 |
| `warn!` | 失败但已 fallback / 边界情况 |
| `info!` | 重要生命周期事件（启动、关闭、workspace 切换、theme 切换） |
| `debug!` | 开发期细节 |
| `trace!` | 极细节，仅 opt-in（`RUST_LOG=trace`） |

`tracing` 的 span 用于标记跨函数的操作上下文（如"打开文件 X"、"派发命令 Y"），便于日志检索。

### 17.9 错误处理的不变约束

| 约束 | 强度 |
|---|---|
| desktop 不重新定义错误模型 | 硬规则 |
| 底层 crate 的英文 Error 必须经翻译才呈现给用户 | 硬规则 |
| 任何错误必须至少一条 tracing 日志 | 硬规则 |
| desktop 内禁 `.unwrap()`（除测试与 `// SAFETY:` 注释） | 硬规则；CI lint 强制 |
| panic hook 必须救数据 | 第一版最低限度（dump dirty buffer） |
| 用户呈现走 inline / toast / banner / dialog 四级 | 推荐；新增级别需评审 |

## 十八、扩展性

### 18.1 第一版不做通用插件系统

zom-desktop 第一版**不发布**任何通用插件 API。理由：

- 插件 API 是**单向门**——1.0 发布后所有变更都要兼容旧插件
- MVP 阶段没有用户、没有插件作者
- 设计错误会污染整个核心架构，且无法事后剥离

通用插件系统推迟到**第三版及以后**。

### 17.2 但第一版就具备的"插件友好"基础设施

下列设施对第一版自己也有价值，同时为将来插件铺路：

- **命令系统**：`zom-command` 提供的 `CommandRegistry` 本身就是开放注册表（类型擦除 handler）。插件将来注册命令是同一个 API
- **键位外置**：用户已经能改键位、未来插件能注册键位
- **AI 意图入口**：`AiAction` 已经走"翻译为命令"的路径，与插件命令同形
- **主题驱动**：主题就是配置驱动的内容扩展（见第五章）
- **语言支持配置**：第二版将引入 `languages/<name>/` 目录配置

### 17.3 L3 形态：具体类型，不抽 trait

L3 视觉组件第一版采用**具体结构体**形态，在 app 层硬编码注册。**不为不存在的插件预先抽 trait + 注册表**。

```rust
// 第一版
pub struct FileTree { ... }
pub struct CommandPalette { ... }

// shell/workbench 层硬编码组装
fn build_workbench(...) -> Workbench { ... }
```

但 L3 的 **Props / 对外接口必须按 trait 思维设计**：命名清晰、参数稳定、不漏内部实现。将来加扩展时是机械重构。

### 17.4 长期：WASM 沙箱

第三版引入通用插件系统时，采用 **WASM 沙箱** 方案。

选 WASM 而非其他架构的理由：

| 候选 | 否决理由 |
|---|---|
| 动态库 (dylib) | 插件崩了带崩主进程；平台特定二进制 |
| 内嵌 Lua / JS | 被锁死在脚本生态；解释器内嵌增加二进制体积 |
| 子进程 IPC | 适合 LSP 这种重交互场景；通用插件开销太大 |
| **WASM** | **跨平台分发统一、强隔离、性能接近 native、语言中立、Zed 的实际选择** |

API 通过 WIT（WebAssembly Interface Types）定义、版本化。

### 17.5 插件能力锁定

无论何时引入插件系统，能力锁定在以下范围：

| 能力 | 是否允许插件 |
|---|---|
| 注册命令 | 允许 |
| 注册键位 | 允许（通过用户 settings.keymap 引用插件命令） |
| 注册语言支持（LSP / grammar） | 允许 |
| 编辑器装饰（诊断、inlay hint、代码动作） | 允许 |
| **注册自己的 dock panel** | **明确禁止** |
| **画任意 UI** | **明确禁止** |
| **修改外壳布局** | **明确禁止** |

理由：UI 是变化最快的层，锁定 UI 接口 = 主程序失去演化自由。允许的能力覆盖 80% 真实插件需求。

### 17.6 API 兼容承诺

- **第一版**：无公开扩展 API
- **第二版**：语言支持配置 schema 是稳定 API，遵循 semver
- **第三版**：WASM 插件 API 是永久承诺；破坏性变更必须主版本号 + 迁移期

## 十九、EditorView 设计

EditorView 是 desktop 最复杂的 L3 组件，串起四个底层 crate（engine / workspace / view / command）将文本编辑能力呈现给用户。本章定义其第一版最小可用形态，面向 TODO.md 中 P2 的"OS 按键 → KeyChord → keymap → 命令、删除、移动光标、撤销 / 重做"闭环；P3（搜索 / 折叠 / 投影）与 P4（AI 提案）的接入点留出明确扩展槽，但本章不规定其内部细节。

### 19.1 定位

```
EditorView (L4 in zom-desktop/src/shell/workbench/regions/editor_area/editor_grid.rs)
  ├─ 显示：透过 zom-view 的 ViewportState、zom-workspace 的 Buffer 内容渲染文本
  ├─ 输入：转 GPUI 事件为 zom-command 的 (CommandId, CommandArgs) 派发
  └─ 状态：自身只持 UI 局部状态（焦点、IME 缓冲、鼠标拖拽、字体度量缓存）
```

EditorView **不持有领域状态**：buffer 在 workspace、视图状态在 view、命令派发在 command。

### 19.2 持有的句柄与状态

```rust
pub struct EditorView {
    // 句柄（注入；参见第八章）
    workspace: Entity<Workspace>,
    view_set: Entity<ViewSet>,
    view_id: ViewId,

    // 行为通道（回调；参见 16.2）
    on_request_command: Box<dyn Fn(CommandId, CommandArgs, &mut App)>,

    // 自己的 UI 状态（局部、可序列化为 PreviewVariant）
    focus_handle: FocusHandle,
    composition: Option<CompositionUiState>,
    drag: Option<DragUiState>,
    metrics: FontMetricsCache,
}
```

EditorView 必须接受**最小子状态**：拿 `Entity<ViewSet>` 而非 `Entity<App>`；拿 `ViewId` 而非"由我决定哪个是活动 view"。

### 19.3 与 EditorGrid / ViewSet 的关系

- **EditorView 是叶子组件**——对应一个 `ViewId`。多视图（分屏）由 L4 `EditorGrid` 通过 split tree 装配多个 EditorView，每个实例持有不同 `ViewId`。
- **EditorView 不挑活动 view**——`active view` 状态由 `ViewSet` 维护。EditorView 获得 focus 时通过命令（如 `editor.activate_view`）通知 ViewSet 更新 active。
- **EditorView 不知道 split tree**——split 决策、尺寸分配、聚焦切换都在 `EditorGrid` L4 层。EditorView 内部只关心"我这一个视图怎么显示和响应"。

### 19.4 渲染策略（第一版最小可用）

第一版按 viewport 渲染：

```
1. 从 view_set 取出 view（ViewId 索引）
2. 读 view.ViewportState 决定可见行范围
3. 从 workspace 取 Buffer，调 zom-engine 的 viewport slicing API 取可见文本
4. 渲染层次（自底向上）—— 6 阶段绘制契约：
   1) 行背景        active line / diff hunk 整段背景
   2) 范围背景      selection / search match / AI 提案区间
   3) 字符层        字色 / 字重 / 斜体 / 下划线 / 波浪线
   4) 字符叠加      inline ghost text / inlay hint
   5) cursor / IME composition
   ─（与文本层并列的独立竖列）─
   6) gutter        行号 + 行级装饰图标（断点 / git diff / 诊断 glyph 等）
5. 字体度量缓存按 ui_font_size / buffer_font_size 失效
```

阶段顺序固定，阶段之间是绘制顺序（后画的覆盖前画的）；阶段内部不同 layer 来源之间才谈 z-order。

第一版必填：阶段 1（仅纯背景色 / 无 diff）、阶段 2 的 selection、阶段 3（仅字色 / 无字重斜体下划线波浪线）、阶段 5、阶段 6（仅行号 / 无装饰图标）。其余（搜索 / AI 区间、字符叠加、gutter 装饰图标）是 P3+ 扩展槽位，**槽位本身必须在第一版就留出**——第一版不实现，但渲染管线的 6 阶段结构不能等接入时再改。

所有装饰来源遵循"语义键 + theme 解析"契约：layer payload 只携带语义键（如 `SyntaxToken { kind }`、`DiagnosticMark { severity }`），desktop 侧统一查 theme 解析为颜色 / 字重 / 下划线 / inline 文本等具体绘制指令。换主题不重算 layer；跨平台（如未来的终端版）能复用同一份 payload。

**observe 哪些 entity 触发 re-render**：

- `workspace`（buffer 内容变化 + buffer 上挂载的 metadata layer 变化 + buffer.search 状态变化）
- `view_set`（光标 / 滚动 / fold 变化）

P3 接入 fold / projection 时，第 3 步从 `ViewportSlice` 升级为 `ProjectedRange`——这是一处单点替换。

### 19.5 键盘输入路径

```
GPUI key event
    ↓
shell::platform::keyboard 解码为 KeyChord（见 14.2）
    ↓
EditorView.on_key_down 接到 KeyChord
    ↓
向上派发：调用 on_request_command（实际由组合根的 Keymap 解析）
    ├─ 匹配 Command       → CommandQueue → handler
    └─ 不匹配 + 可打印字符 → 包装为 editor.insert_text 命令 → CommandQueue
    ↓
CommandExecutor 排空队列，handler 调 workspace/view/engine API
    ↓
对应 Entity notify
    ↓
EditorView observe 触发 re-render
```

**EditorView 不持有 Keymap 实例**——Keymap 是组合根服务（见 2.1），通过回调机制将 KeyChord 上抛后由组合根派发。

### 19.6 IME 接入

按 TODO.md 已规划的最小闭环：

| IME 事件 | 通道 |
|---|---|
| `start` | 命令 `editor.composition_start` |
| `update` | **直接通道**：EditorView 直接调用 `view.composition_mut().update(...)`；不走命令队列以避免每次按键都排队 |
| `commit` | 命令 `editor.composition_commit` |
| `cancel` | 命令 `editor.composition_cancel` |

GPUI IME event → `shell::platform::ime` 适配 → 上述命令 / 直接通道。

`CompositionUiState`（EditorView 自己持有的局部状态）只承载渲染所需的临时显示信息（如下划线区段）；权威的 composition 状态在 `zom-view::View` 中。

### 19.7 鼠标输入

第一版三类鼠标交互：

| 交互 | 通道 | 说明 |
|---|---|---|
| 点击 → 移动光标 | 命令 `editor.set_cursor` | 鼠标坐标 → 字符位置由 desktop 算（字体度量缓存） |
| 拖拽 → 选区 | 命令 `editor.set_selection`（高频可改直接通道，第一版先走命令） | drag 起始 / 终止位置打包 |
| 滚轮 → 滚动 | **直接通道**：EditorView 直接改 `view.viewport_mut()` | 与 IME update 同理，高频不走命令 |

**字体度量**：desktop 缓存当前 `buffer_font_size` 下的字符宽度表（等宽字体下是单一值；变宽字体需按 grapheme cluster 缓存）。字号变化时缓存失效。坐标 ↔ 字符位置转换抽到 `logic.rs`，可裸单测。

### 19.8 滚动权威

`view.ViewportState` 是**唯一权威**。GPUI 的 scroll handle 只是 UI 触发源。

```
用户滚轮  → GPUI scroll event → 直接通道改 view.ViewportState → re-render
命令 / 代码改 ViewportState → re-render → GPUI 渲染到新位置
```

不允许两个权威。GPUI 的内部滚动状态被 EditorView 视为"无状态的事件源"，所有"当前滚到哪了"的真相只在 view。

### 19.9 留给 P3 / P4 的扩展点

| 阶段 | 接入方式 | EditorView 侧的改动 |
|---|---|---|
| P3 fold / projection | viewport 切片从 `ViewportSlice` 改为 `ProjectedRange`（zom-engine 已有） | 19.4 第 3 步单点替换；新增 fold 命令 handler 不在 EditorView 写 |
| P3 语法高亮 | 宿主侧 highlighter（tree-sitter / LSP semantic tokens 等）异步算 tokens，通过 `MetadataLayer<SyntaxToken>` 挂到 buffer 上；payload 只携带语义键（`TokenKind::Keyword` 等），desktop 查 theme 解析颜色 | 阶段 3（字符层）按可见区间查 syntax layer，逐 glyph 应用解析后的字色 / 字重 |
| P3 搜索高亮 | 由 `WorkspaceBuffer.BufferSearch` 持有 query / `SearchResult` / current hit（per-buffer 共享，分屏看同一 buffer 时多 view 共用）；engine 仅提供纯查询 API（`search_in_text` / `SearchResult::try_remap`），不再用 `MetadataLayer::SearchMatch` 承载高亮。**重算时机**：编辑期间仅 `try_remap` 推进现存命中，不主动发现新命中；query 变化、或 find-next 发现 result 落后于当前 buffer.version 时才同步 re-run | 阶段 2（范围背景）从 `buffer.search().result.ranges()` 取可见命中绘制；current hit 加强调样式 |
| P3+ gutter 装饰 | 复用 `MetadataLayer`，行级用零宽锚点（行首 + `Stickiness::After`），多行用真实 range；失效策略 `invalidate_when_touched_by_deletion`；payload 只携带语义键 | desktop 维护"路由到 gutter 的 layer kind"硬编码常量表（`breakpoint` / `git-diff` / `diagnostic-mark` / `bookmark` 等），阶段 6 按表渲染图标 |
| P4 AI 提案预览 | 透过 `MetadataLayer` 承载 ghost text / diff hunks；payload 只携带语义键 | ghost text 落阶段 4（字符叠加）；diff hunk 整段背景落阶段 2；按 layer kind 路由 |

**第一版 EditorView 必须已具备这些扩展点**：

- viewport 切片是单点函数调用（19.4 第 3 步），不内联到 render
- 渲染层次允许新增装饰层（19.4 第 4 步是有序列表，新增层只是插入新项）
- selection 渲染按 `SelectionSet`（zom-engine 模型），天然支持多 cursor

### 19.10 与其他 L3 组件的协作

| 组件 | 协作形式 |
|---|---|
| `TabStrip` | EditorView 不直接知道。TabStrip 操作 ViewSet active view；EditorView 跟随 |
| `FileTree` | EditorView 不直接知道。FileTree 点击文件触发命令（`workspace.open_file` + `view.create_for_buffer` 等组合），由组合根 handler 完成 |
| `StatusBar` | EditorView 不直接知道。StatusBar observe `ViewSet` / `Workspace` 自行读取当前 view 的光标位置、文件 dirty 状态等 |
| `CommandPalette` / `FindReplace` 等 Surface | EditorView 不直接知道。Surface 通过命令派发；EditorView 因 Buffer / View 变化自动 re-render |

**所有跨 L3 协作都通过共享底层 entity 完成**——没有 L3 之间的直接调用，没有 EditorView 持有其他 L3 的句柄。

### 19.11 测试要求

按 11.2 / 11.4 的 L3 硬规则，EditorView 必须 `#[gpui::test]` 覆盖以下场景：

| 场景 | 验证 |
|---|---|
| 基本渲染 | 给定 Buffer + ViewportState，渲染输出包含可见行文本 |
| 光标移动命令 | 派发 `editor.move-left` → view 的 SelectionSet 更新 → EditorView 触发 re-render |
| 文本输入 | 派发 `editor.insert_text` → buffer 更新 → EditorView 显示新文本 |
| IME 闭环 | start → update → commit 后，buffer 包含提交文本，CompositionUiState 已清空 |
| 滚动 | 改 `view.ViewportState` 后渲染可见行范围变化 |

**字体度量、坐标 ↔ 位置转换**抽到 `logic.rs`，纯函数裸单测；不依赖 GPUI。

EditorView **不重测底层 crate 的领域逻辑**——SelectionSet 怎么 movement、Buffer 怎么 undo、Keymap 怎么解析，都是底层 crate 的 contract test 已覆盖的。

### 19.12 第一版不做的事

明确划掉，避免范围漂移：

- **分屏 split 内部布局**（属 L4 EditorGrid）
- **跨 view 的状态协调**（属 ViewSet / 组合根）
- **fold / 投影 / 语法高亮 / 搜索高亮 / gutter 装饰图标 / AI 提案的具体实现**（P3 / P4）
- **mini-map / 缩略图**（推迟）
- **行内插件 / 代码动作 UI**（推迟到插件系统）
- **代码折叠按钮 / gutter 装饰的扩展点**（与 P3 一起设计）

## 二十、Dock / Panel 实现

「桌面端布局模型」第 5 节已定面板模型语义（`PanelDescriptor` / `PanelPlacement` / `PanelStack` / `DockAreaId`）。本章规定 desktop 端如何把这套模型落到 L4 Region 与 L3 Composite。

### 20.1 整体落位

```
L4 Region        LeftDock / RightDock / BottomDock
                 容器：持有 PanelStack（panel id 列表 + active）
                 持有 Dock 自身的折叠 / 尺寸状态
                 按 active panel id 取实例渲染

L3 Composite     每个 Panel（FileTree / Outline / Search / Terminal / ...）
                 普通 L3 组件，遵循第 3.3 目录结构
                 不抽 trait（与 17.3 / 18.3 一致）

PanelHost        每窗口持有；保存该窗口所有 panel 实例（Entity）
                 由组合根创建；Dock 按 id 从此取实例
```

### 20.2 Panel 是 L3，不抽 trait

第一版 Panel 是普通 L3 组件。**不为不存在的插件预先抽 `PanelProvider` trait**。

Panel 的图标、命令与短 id 由 `PanelId` 集中维护，避免面板身份字符串散落：

```rust
// shell/features/panels/mod.rs
pub(crate) fn icon_path(self) -> &'static str {
    match self {
        PanelId::FileTree => "icons/panels/file_tree.svg",
        // ...
    }
}
```

PanelId 由 desktop 定义为闭合 enum；需要给命令系统传递短字符串时，通过 `PanelId::command_str_id()` 显式投影。

### 20.3 PanelHost：每窗口持有所有 panel 实例

```rust
// shell/features/host.rs
pub struct PanelHost {
    file_tree: Entity<FileTreePanel>,
    outline: Entity<OutlinePanel>,
    search: Entity<SearchPanel>,
    terminal: Entity<TerminalPanel>,
    // ... 第一版硬编码列表
}

impl PanelHost {
    pub fn panel_element(&self, id: PanelId, cx: &mut App) -> Option<AnyElement> { ... }
}
```

`PanelHost` 由 app 组合根在创建窗口时一次性实例化全部 panel。Dock 按 PanelId 从 PanelHost 取元素。

**不引入 `PanelRegistry` 动态注册表**——第一版面板列表硬编码；注册表是为不存在的扩展付费。将来插件系统真要 panel 扩展时（**目前 18.5 明确禁止**）再演化。

### 20.4 PanelStack：第一版单栈

第一版每个 Dock 用单栈模型：

```rust
pub struct PanelStack {
    panels: Vec<PanelId>,     // 该 Dock 持有的 panel 序列
    active: Option<PanelId>,  // 当前显示的（最多 1 个）
}
```

切换语义：

| 命令 | 行为 |
|---|---|
| `panel.toggle.<id>` | 若已 active 则置 None（关闭）；否则置 Some(id) |
| `panel.activate.<id>` | 无论之前是什么，置 Some(id) |
| `panel.close.<id>` | 若当前 active 是 id 则置 None；否则忽略 |

第二版升级为 `PanelGroup` tree（栈 + split），支持同 Dock 内多 panel 同时显示。

### 20.5 Panel 固定归属

第一版固定映射（用户不能拖动跨 dock）：

| Panel | 固定归属 Dock |
|---|---|
| FileTree | Left |
| VersionControl（第二版） | Left |
| Outline | Right |
| Search | Bottom |
| Terminal（第二版） | Bottom |
| Debug（第二版） | Bottom |

归属由对应 dock 模块声明：`left_dock.rs` 声明左侧 panel，`bottom_dock.rs` 声明底部 panel，`right_dock.rs` 声明右侧 panel。settings 可覆盖同 dock 内顺序，但不可改 panel 归属 dock（第一版）。

### 20.6 Dock 状态归属

| 状态 | 持有位置 |
|---|---|
| Dock 显隐（整个 Dock collapsed） | 每窗口（L4 Region 持有） |
| Dock 尺寸（宽 / 高） | 每窗口 |
| Dock 内 active panel | 每窗口（PanelStack 持有） |
| Dock 内 panel 顺序 | settings（用户级 / workspace 级覆盖） |

与 11.2 跨窗口共享规则一致：偏好类（panel 顺序）共享；"当前在做什么"（active panel / 折叠 / 尺寸）每窗口。

### 20.7 折叠与尺寸交互

- **折叠**：通过 `panel.toggle.<id>` 命令切换 active 为 None；Dock 检测到 active 为 None 时自动 collapse
- **尺寸**：拖拽 Dock 边缘——L4 Region 内部交互；**不走命令**（高频拖拽）；直接改 `WorkbenchController` 里的 size 状态

### 20.8 BottomBar 与 Panel 的关系

BottomBar **不是 Dock**——它是窗口级外壳（见「桌面端布局模型」4.1）。

BottomBar 里的"面板切换 slot"（`bottom-bar-file-tree` / `bottom-bar-outline` 等）是 `panel.toggle.<id>` 命令的视图：

```
用户点击 BottomBar 里的 file_tree icon
    ↓
派发 panel.toggle.file_tree
    ↓
zom-command handler：emit HostEffect::TogglePanel("file_tree")
    ↓
ShellView：交给 WorkbenchController 找到所在 Dock → 更新 PanelStack.active / collapsed
    ↓
窗口 refresh → re-render
```

**BottomBar 不知道 panel 是什么**——它只知道 CommandId。这条切割让 BottomBar 与 Dock 完全解耦。

### 20.9 EditorGrid 与 Dock 的边界

EditorGrid **不是 Dock**，不走 Panel 模型。它独占 CenterColumn 上半部（「桌面端布局模型」4.4）：

```
TopBar
─────────────────────────────────────────────
LeftDock │ EditorGrid              │ RightDock
         │ ─────────────────────── │
         │ BottomDock              │
─────────────────────────────────────────────
BottomBar
```

BottomDock 只占中间列下半部，不侵入左右 Dock。

EditorGrid 内部是 split tree + tab group（「桌面端布局模型」第 6 节），由 EditorGrid L4 自己实现。EditorView（第十九章）是 EditorGrid 内的叶子。

### 20.10 第一版具体 Panel 清单

| Panel | 固定归属 Dock | 第一版功能 |
|---|---|---|
| FileTree | Left | 显示 workspace 文件树；点击触发 `workspace.open_file` |
| Outline | Right | 占位骨架；LSP 接入后填充符号大纲 |
| Search | Bottom | 当前文件与跨文件搜索 UI（绑定 zom-engine 的搜索能力，P3） |

推迟到第二版及以后：VersionControl / Terminal / Debug / KeyboardShortcuts。

第一版完整实现的 Panel 数量保持小（3 个）；新增 Panel 不需要修改其他 Dock 的代码——只需在 PanelHost 加字段、在目标 dock 模块的 `PANELS` 列表加入归属、注册 `panel.toggle.<id>` 命令。

### 20.11 注册流程

每窗口创建时：

```
1. 实例化 PanelHost（含全部 panel）
2. 创建 WorkbenchController
3. 创建 LeftDock / RightDock / BottomDock（按各 dock 模块的 PANELS 装入 PanelStack）
4. 应用 settings 覆盖（panel 顺序、初始 active、初始折叠 / 尺寸）
5. 注册 panel 命令 catalog；handler 只 emit HostEffect
6. ShellView 收到 HostEffect 后更新当前窗口的 WorkbenchController
```

panel 命令的**解释**是窗口范围的：同名 `HostEffect::TogglePanel` 在不同窗口里操作各自的 `WorkbenchController`。

### 20.12 第一版明确不做

- panel 跨 dock 拖动
- panel 浮动（脱离 dock）
- 同 dock 多 panel 同时显示（PanelGroup tree）
- 用户自定义 panel（等插件系统；但 18.5 明确禁止）
- panel 内拆分布局

## 二十一、SurfaceLayer / BubbleLayer 实现

「桌面端布局模型」第 7 节定义 SurfaceLayer 语义、第 8 节定义 BubbleLayer 语义。本章规定 desktop 端实现：谁持有 / 怎样创建销毁 / 如何定位 / 与 L3-L4 的关系。

### 21.1 Surface 与 Bubble 的区分

Surface 中文称为 **浮面**，Bubble 中文称为 **气泡**。二者都属于悬浮层，但不是同一种组件：

- Surface 是可交互悬浮面板。框架只提供外壳能力：入口定位、层级、关闭策略与焦点归还；内容、状态、功能和焦点目标完全由打开方持有。
- Bubble 是轻量提示。框架统一它的内容模型、视觉样式与生命周期；调用方只提供文本、级别、少量动作和超时等数据。

| 维度 | Surface | Bubble |
|---|---|---|
| 可交互 | 是 | 否 |
| 承载焦点 | 是 | 否 |
| 关闭机制 | Esc / 显式 close / 失焦 | 自动 / 鼠标移开 / 超时 |
| 同时活跃 | 第一版最多 1 个 | 多个（不同类型可并存） |
| 例 | 命令面板、context menu、内联弹窗、inspector | tooltip、diagnostic hover、parameter hint、toast |

升级判定：Bubble 需要承载确认 / 表单 / 复杂交互时升级为 Surface。

### 21.2 渲染层次与 z-index

```
[10] WorkbenchFrame    含 TopBar / BottomBar / Body（Dock + EditorGrid + BottomDock）
[20] SurfaceShell      SurfaceManager 当前活跃的 Surface
[30] BubbleShell       BubbleManager 当前活跃的所有 Bubble
```

z-index 是 desktop 内固定常量，不暴露给 L3 组件。

### 21.3 SurfaceManager / BubbleManager

每窗口持有一对 Manager：

```rust
pub struct SurfaceManager {
    active: Option<ActiveSurface>,    // 第一版单 Surface 独占
}

pub struct BubbleManager {
    bubbles: HashMap<BubbleId, ActiveBubble>,   // 多 Bubble 并存
}
```

Manager 是 GPUI Entity；observe 触发对应 Shell re-render。

**第一版同时最多 1 个 Surface**——打开新 Surface 自动关闭旧的（"模态独占"）。第二版考虑允许嵌套，但需评估能否避免"无限堆叠"问题。

### 21.4 SurfaceShell / BubbleShell

两个 Shell 都是 desktop 内的特殊渲染层，挂在 WorkbenchFrame 之上：

- 从对应 Manager 读 active 状态
- 解析 invoker → 屏幕坐标
- 渲染 Surface / Bubble 实例

Shell 不是 L4 Region——它们不参与 WorkbenchFrame 的 layout，是独立 portal 层。

### 21.5 Surface 内容由调用方拥有

CommandPalette / QuickPicker / ContextMenu / InlinePopover / InspectorPopover 等都是普通 L3，按第 3.3 目录组织。**它们不知道自己是 Surface**——只是普通组件。

功能模块创建或复用这些 L3 实例，并提供 `SurfaceRequest`。`SurfaceRequest` 携带 id、召唤入口、placement 与最终要渲染的 element。SurfaceShell 不按固定枚举匹配业务内容，也不直接 import 某个 feature 模块。新增一种 Surface 不应修改 SurfaceShell。

Bubble 不走这条规则。Tooltip / Toast / DiagnosticHover / ParameterHint 由 BubbleManager 接收结构化数据，统一渲染为气泡。

### 21.6 Anchor 解析

「桌面端布局模型」定义 Surface 锚到召唤它的具体入口。desktop 实现：

| SurfaceAnchor | 屏幕坐标计算 |
|---|---|
| `Invoker(ElementId)` | 通过 anchor registry 查询该入口元素的渲染矩形 |

入口几何采集在 `shell/surfaces/anchor_registry.rs`，入口元素通过 `track_surface_anchor` 标记自己。SurfaceShell 只消费这些入口矩形，不要求 TopBar / BottomBar / Dock 依赖 Surface 语义。

Bubble 的位置规则（按「桌面端布局模型」8.x）：

| BubbleKind | 跟随 |
|---|---|
| Tooltip | hover 目标 element 附近 |
| DiagnosticHover | EditorPosition |
| ParameterHint | 当前光标位置（EditorPosition） |
| Toast | 窗口角落（固定，多 toast 纵向堆叠） |

### 21.7 Surface 生命周期

```
1. 派发命令 surface.<id>.open（如 command-palette.open）
2. handler 创建或复用 Surface 实例 → SurfaceManager.active = Some(...)
3. Manager notify → SurfaceShell re-render → Surface 显示并获得焦点
4. 用户交互
5. 关闭触发：
   - Esc 键（全局键位 → 命令 surface.dismiss）
   - 显式命令（如选择命令面板的某项后自派发 surface.dismiss）
   - 失焦（窗口失焦或点击 Surface 之外区域）
6. SurfaceManager.active = None → SurfaceShell re-render → Surface 隐藏
```

Surface 关闭时焦点回到先前 focus 目标（SurfaceManager 在打开时记录）。

### 21.8 Bubble 生命周期

| 触发 | 关闭 |
|---|---|
| Tooltip：hover 进入 element | hover 离开 |
| DiagnosticHover：鼠标停留在编辑器位置 N ms | hover 离开 / 光标移动 |
| ParameterHint：编辑函数调用括号内 | 光标退出参数区 |
| Toast：程序派发 `toast.show` | 超时（默认 3 秒）/ 显式 dismiss / 数量上限替换 |

### 21.9 与 GPUI 内建 Tooltip 的关系

zom-desktop 现有 Glyph tooltip 通过 GPUI 内建 `Tooltip` 实现。第一版**两套并存**：

| 场景 | 选择 |
|---|---|
| 图标 hover 短文本 | GPUI 内建 Tooltip |
| 跨函数生命周期 / 程序化触发 / invoker 解析 | BubbleManager |

第二版若 BubbleManager 稳定，再考虑统一。

### 21.10 与 EditorView 的协作

Surface 中与 EditorView 位置强绑的（如 InlinePopover、ContextMenu）通过对应的召唤入口获取屏幕位置；需要按编辑器位置召唤时，由 EditorView 或相关功能提供一个临时 invoker rect。

**EditorView 不知道 Surface 存在**——它只提供可被定位的入口或几何信息，Surface 侧按 request 消费。

### 21.11 第一版不做

- 模态独立窗口（与 Surface 不同；推迟）
- Surface 拖动 / 调整大小
- 同时多 Surface（嵌套）
- Bubble 之间的避让算法（位置冲突时简单覆盖）
- Surface 内嵌 Surface

## 二十二、资源管理 (assets)

### 22.1 资源根目录与组织

资源根目录：`zom-desktop/assets/`。

```
zom-desktop/assets/
  icons/
    app/               应用图标
    panels/            Panel 图标（与 PanelId::icon_path 对应）
    actions/           通用动作图标（close、settings、find/replace 等）
    navigation/        导航图标（chevron 等）
    files/             文件系统图标（file、folder 等）
    status/            状态图标（diagnostics、signal 等）
    window/            自绘窗口控制符号
    ...
  themes/
    dark.toml          内置主题（与第五章 schema 一致）
    light.toml
  fonts/               第一版为空；见 22.6
```

按**语义类别**分目录，与 9.2 的路径使用约定配合：资源目录不绑定具体出现位置，组件仍在本地声明或内联自己使用哪个路径。

### 22.2 第一版用 embedded asset

第一版资源**编译进二进制**（embedded）：用 `include_bytes!` / `include_str!` 把 assets 打包进 desktop 可执行文件。

| 优点 | 代价 |
|---|---|
| 单一可执行文件分发 | 二进制体积略增（SVG 多在 <1KB / 个，全集 <100KB） |
| 不依赖文件系统路径 | 资源改动需重新编译 |
| 加载零延迟、零失败 | 不支持运行时替换 |
| 用户无法误删 | |

**用户主题除外**——用户主题在文件系统（5.2 已定）。embedded 与文件系统并存：内置 asset embedded、用户产物在 `~/.config/zom/`。

### 22.3 GPUI AssetSource 接入

GPUI 通过 `AssetSource` trait 加载资源。desktop 实现一个 `EmbeddedAssetSource`：

```rust
pub struct EmbeddedAssetSource;

impl AssetSource for EmbeddedAssetSource {
    fn load(&self, path: &str) -> Result<Option<Cow<[u8]>>> {
        // 按 path 匹配 embedded bytes
    }

    fn list(&self, path: &str) -> Result<Vec<SharedString>> { ... }
}
```

启动时由 app 组合根注册到 GPUI App。所有 L3 组件通过 `svg().path("icons/...")` 等方式取资源，**不直接读文件**。

### 22.4 路径使用约定

图标路径用相对 assets 根的形式，**不带** `assets/` 前缀。多处复用的路径可以保留为组件本地常量；panel 图标由 `PanelId::icon_path()` 集中映射；只在一处使用的路径直接内联：

```rust
const FOLDER_ICON: &str = "icons/files/folder.svg";

svg().path("icons/actions/close.svg")
```

GPUI AssetSource 实现负责把 `"icons/..."` 路径映射到 embedded bytes。

### 22.5 资源命名

| 规则 | 例 |
|---|---|
| 文件名 snake_case | `file_tree.svg` |
| 按语义类别分目录 | `icons/panels/file_tree.svg` |
| 同图标多状态用后缀 | `chevron_right.svg` / `chevron_down.svg` |
| 不按视觉效果命名 | ❌ `red_circle.svg` ✓ `error_dot.svg` |
| 不按出现位置命名 | ❌ `topbar_settings.svg` ✓ `settings.svg` |

命名抗腐：将来同一图标可能被多处复用，按"是什么"命名不会过时。

### 22.6 字体策略

第一版**不内嵌字体**——使用系统字体。理由：

- 字体文件体积大（单个 1-10MB）
- 法律授权复杂（OFL / 私有协议各异）
- 用户对自己系统字体已熟悉

settings 提供字体配置，支持回退列表：

```toml
[ui]
font_family = ["Inter", "system-ui", "sans-serif"]

[editor]
font_family = ["JetBrains Mono", "Menlo", "Consolas", "monospace"]
```

GPUI 按列表顺序回退到第一个可用字体。

第二版可考虑内嵌 1-2 个推荐字体作为可选默认。

### 22.7 内置主题作为 asset

`themes/dark.toml` / `themes/light.toml` 是 embedded asset。ThemeRegistry 启动时通过 AssetSource 加载，与用户主题（文件系统加载）走相同 schema（5.2）：

```
内置主题   AssetSource → embedded bytes → toml::from_str
用户主题   fs 读取 → toml::from_str
```

加载后路径不再区分，统一进 `name -> Theme` 表。

### 22.8 资源版本管理

资源跟随 desktop 二进制版本——升级 zom 自动获得新资源。**不存在"资源版本与代码版本不一致"**。这是 embedded 的另一项收益。

升级新增的 icon、修改的 token 取值都不会撕裂运行环境。

### 22.9 第一版不做

- 用户自定义 icon 包
- 动态资源热重载（修改 SVG 后即时生效；第二版若需要可加 fs watch + 文件系统 asset source 双轨）
- 远程资源加载
- 资源压缩 / 优化构建步骤（SVG 已经够小，不优化）
- 多分辨率 icon（@1x / @2x / @3x）；SVG 已矢量

## 二十三、异步与后台任务

### 23.1 GPUI 提供的工具箱

desktop **不引入自己的 async runtime**——直接使用 GPUI 提供的执行器：

| API | 作用 |
|---|---|
| `cx.spawn(async \|cx\| { ... })` | 前台任务：在主线程 await，可直接 update entity；返回 `Task<T>` |
| `cx.background_executor().spawn(async { ... })` | 后台任务：worker pool 执行；不能直接持有 Entity |
| `cx.foreground_executor().spawn(...)` | 显式提交到主线程的 task |
| `Task<T>` | 任务句柄；drop 即 cancel |

desktop 不直接 `use tokio` 或 `use async-std`——所有异步走 GPUI 的执行器，避免运行时双栈。

### 23.2 前台 vs 后台的分工

| 任务类型 | 执行器 | 例 |
|---|---|---|
| 短小、需 await 后立刻改 UI | foreground（`cx.spawn`） | 等待用户选择对话框结果 / 派发命令链 |
| 长时计算 / I/O 密集 | background | 文件读写、项目索引、搜索 |
| 网络请求 | background | LSP（将来）、AI 调用 |
| 实时小高频更新 | 不走 task | 滚动、IME update 走直接通道（见 19.6 / 19.7） |

**判定准则**：会阻塞主线程超过 16ms（一帧）的事必须后台。

### 23.3 UI 状态修改的硬约束

后台任务**不能直接持有 GPUI Entity**——`Entity<T>` 是 `!Send`。后台结果必须通过 `cx.update_in` 切回主线程修改状态：

```rust
// 正确：后台读文件 → 切主线程更新 buffer
let task = cx.background_executor().spawn(async move {
    std::fs::read_to_string(&path)
});
cx.spawn(|workspace, mut cx| async move {
    let text = task.await?;
    workspace.update(&mut cx, |ws, cx| {
        ws.open_text(text, cx);
    })?;
    Ok::<_, anyhow::Error>(())
}).detach();
```

**禁止**：
```rust
// 错误：后台任务里直接 borrow entity
cx.background_executor().spawn(async move {
    workspace.update(&mut cx, ...);  // ← Entity 不能跨线程
});
```

### 23.4 取消语义

`Task<T>` drop 即 cancel。**取消的标准方式 = 让 Task 句柄随组件 drop**：

- L3 组件持有的 Task 在组件 unmount 时自动 cancel
- 显式取消：用户中断按钮 / Esc 时 drop 对应 Task

后台任务自身要写**取消检查点**——长循环要定期 `cx.background_executor().yield_now().await`，让 cancel 信号有机会传到。

```rust
for file in files {
    cx.background_executor().yield_now().await;   // 允许 cancel
    process(file);
}
```

### 23.5 超时

| 任务类别 | 超时策略 |
|---|---|
| 本地文件 I/O | 不主动超时（fs 本身有错误） |
| LSP 请求 | 默认 5s，可配置 |
| HTTP / AI 调用 | 默认 30s，必须 timeout，不允许无限等待 |
| 用户交互对话框 | 不超时（等用户） |

超时实现用 GPUI 的 `BackgroundExecutor::timer` 配合 `select!`，不引入 `tokio::time`。

### 23.6 并发限制

需要限制并发的场景用简单的 `Semaphore`（用 `tokio::sync::Semaphore` 或自实现的 GPUI 友好版本）：

| 场景 | 并发上限 | 理由 |
|---|---|---|
| 项目索引文件读 | 8（或 CPU 核数） | 防止打开过多 fd |
| LSP 请求（同一服务器） | 由 LSP 协议保证序列性 | 协议级 |
| AI 调用（同一 provider） | 1（顺序） | 防止配额耗尽 |
| 自动保存 | 1（按 buffer） | 防止重复保存 |

限制实现集中在各任务的入口处，**不引入全局任务调度器**。

### 23.7 错误传播

异步错误进第十七章的错误处理流程：

```
后台 Task 内部 Err
    ↓
.await? 上抛到调用方
    ↓
调用方在 cx.spawn 内部接收 Err
    ↓
按场景：toast / banner / dialog（17.4）
    ↓
同时 tracing::error!(?err) 进日志
```

**任何被 `.detach()` 的 Task 必须处理错误**——detach 让 Task 后台跑，但错误不能丢。模式：

```rust
cx.spawn(|this, mut cx| async move {
    if let Err(err) = do_work(&mut cx).await {
        tracing::error!(?err, "...");
        show_toast(&mut cx, &err);
    }
}).detach();
```

### 23.8 长任务的进度反馈

| 进度形态 | 用法 |
|---|---|
| 静默 | 短任务（<200ms），无需反馈 |
| Spinner（不定量） | 中等任务（200ms–几秒），状态栏角落 |
| Progress bar（定量） | 长任务（>几秒），状态栏或专用 banner |
| Toast 结束通知 | 用户感知关键的（如"项目索引完成"） |

第一版只做静默 + spinner；progress bar 与结束 toast 推迟到第二版。

### 23.9 第一版的具体使用场景

| 场景 | 实现 |
|---|---|
| 文件保存 | `cx.background_executor` 写文件；完成后切主线程更新 dirty 状态 |
| 文件加载 | `cx.background_executor` 读文件；完成后切主线程 `workspace.open_text` |
| Workspace 切换 | foreground spawn 串联清理旧 + 创建新；按需后台预热索引（第二版） |
| LSP（推迟到第二版） | 子进程 + stdio；接收 → background task → 切主线程更新 view metadata |
| AI 调用（推迟） | background HTTP；超时 30s；结果切主线程 |

### 23.10 不做的事

- 自定义 async runtime
- 引入 `async-trait` crate（如果必须 async fn in trait，第一版评估时再决定）
- 流式响应（除 AI 第二版必须时）
- 跨 task 的复杂数据流（用 channel + spawn 解决，不引入 stream 抽象）
- 全局任务调度器（每场景就地写 Semaphore 已够）

## 二十四、持久化与状态恢复

「桌面端布局模型」第 8 节给出持久化边界草案。本章把它落到 desktop 实现：文件位置、格式、时机、合并规则、跨版本兼容、与 crash-recovery 的协作。

### 24.1 持久化的两层

```
全局持久化层（跨窗口共享）
  └─ 用户偏好与会话级元数据
     - settings.toml             用户配置（第十二章已定）
     - recent_workspaces.toml    最近 workspace 列表
     - command_usage.toml        命令使用频率（用于命令面板 rank）
     - themes/*.toml             用户主题（第五章已定）

窗口持久化层（按 workspace 写）
  └─ <workspace_root>/.zom/layout.toml    本 workspace 的窗口布局快照
     - Dock 显隐 / 尺寸 / active panel / panel 顺序
     - EditorGrid 的 split tree
     - tab group 与 active editor
     - 每个 tab 的 buffer 路径、滚动位置、光标位置
```

`settings.toml`（已定）与 `layout.toml`（本章）**同目录但不同文件**：
- `settings.toml`：用户**意图**配置（要不要这个面板亮起、用哪个主题）
- `layout.toml`：当前**会话**布局快照（这次 dock 拖到了多宽、哪个 tab 是 active）

### 24.2 文件位置

全局持久化与 settings 同根（参见 12.2）：

| 平台 | 全局根目录 |
|---|---|
| macOS | `~/Library/Application Support/zom/` |
| Linux | `~/.config/zom/` |
| Windows | `%APPDATA%\zom\` |

跨平台路径走 `shell::platform::paths`。

完整文件清单：

```
~/.config/zom/
  settings.toml             第十二章
  recent_workspaces.toml    本章
  command_usage.toml        本章
  themes/*.toml             第五章（用户主题）
  logs/zom-YYYY-MM-DD.log   第十七章 17.8
  crash-recovery/<ts>/      第十七章 17.6
```

每窗口快照走 workspace 根：

```
<workspace_root>/.zom/
  settings.toml             第十二章（workspace 级 settings 覆盖）
  layout.toml               本章（窗口布局快照）
```

### 24.3 文件格式：统一 TOML

与 settings、主题保持一致：所有持久化文件用 TOML。写回时用 `toml_edit` 保留注释（与 12.8 一致）——尽管 layout.toml 多为程序生成，预留注释空间便于用户手改。

### 24.4 持久化时机

| 触发 | 行为 |
|---|---|
| 状态变化 | debounced 1s 后写（与 settings 一致） |
| Workspace 切换 | 强制写出旧 workspace 的 `layout.toml`，再加载新 workspace |
| 窗口关闭 | 强制写出该窗口的 layout |
| 应用正常退出 | 强制 flush 所有 pending 写 |
| Panic / 崩溃 | **不写**持久化文件（不安全）；只走 crash-recovery（17.6） |

debounce 与强制写都通过 `cx.background_executor` 调度，**不阻塞 UI 主线程**（与 23.3 一致）。

### 24.5 持久化范围

沿用「桌面端布局模型」第 8 节：

**持久化**：
- shell 级配置（TopBar / BottomBar，第一版基本固定）
- Dock 状态：显隐 / 尺寸 / active panel / panel 顺序
- EditorGrid 的 split tree、tab group、active group
- 每个 tab：buffer path、滚动位置、光标位置
- 全局：recent_workspaces、command_usage

**不持久化**：
- 当前打开的 Surface / Bubble
- 鼠标位置、hover 状态
- 字体度量等渲染缓存
- dirty buffer 的内容（走 crash-recovery，见 24.9）
- IME composition 临时状态

### 24.6 强 schema + 跨版本兼容

layout.toml 也是 Rust struct + serde，规则与 settings（12.6）一致：

- 未知字段警告不阻塞（旧版 zom 能读懂新版生成的 layout）
- 缺失字段用默认值
- 破坏性字段重命名：旧版字段名保留并标 deprecated，新版双名读取至少一个大版本
- schema 内嵌 `schema_version: u32`（第一版 = 1），将来重大变更可按版本走 migration 函数

### 24.7 PersistenceRegistry

与 SettingsRegistry / ThemeRegistry / LocaleRegistry 结构平行：

```
启动时
  - 加载 recent_workspaces / command_usage（全局）
  - 加载首个 workspace 的 layout.toml（按 settings 决定首个 workspace）
运行时
  - observe 各组件状态变化 → debounced 写
切换 workspace 时
  - flush 旧 layout
  - 加载新 workspace layout
  - 触发 observable（panel / editor 跟随）
关闭窗口时
  - flush 本窗口 layout
```

`PersistenceRegistry` 是 GPUI Entity，每窗口持有自己的 layout 快照；全局 registry 持有跨窗口共享的内容。

### 24.8 失败处理

| 失败 | 处理 |
|---|---|
| layout.toml 不存在 | 使用内建 panel 固定归属与空窗口运行态；不报错（第一次打开 workspace 的正常状态） |
| layout.toml 解析失败 | 使用内建 panel 固定归属与空窗口运行态 + 一次性 toast + 日志（包含 backtrace） |
| 写失败（磁盘满、权限） | `tracing::error!` + 应用继续；不阻塞 UI |
| 跨版本 schema 不兼容 | migration 函数尝试转换；失败则用默认 + toast 通知 |

**持久化失败绝不影响关键路径**——持久化是优化，失败应用仍能跑。

### 24.9 与 crash-recovery 的关系

```
crash-recovery（17.6）        dirty buffer 文本内容
                              panic hook 紧急 dump
                              下次启动检测并提示恢复（第二版）

持久化（本章）                布局元数据 + 已保存文件的元信息
                              正常运行时 debounced 写
                              下次启动恢复布局
```

互补，不冲突。下次启动顺序：

```
1. PersistenceRegistry 加载 layout（恢复布局、打开上次 tabs）
2. CrashRecoveryRegistry 检查 crash-recovery 目录
   - 若有未消费的 dump → 提示用户"上次崩溃了，是否恢复未保存内容"
   - 用户同意 → 把 dump 内容载入新 buffer（不绑文件）
   - 消费后清理目录
```

### 24.10 buffer 内容不属于 desktop 持久化

打开的文件**内容**的持久化是 `zom-workspace` 的"保存"概念（已存盘的 buffer）。desktop 的 layout.toml **只存 buffer 路径**，不存内容。

dirty buffer 的两种归宿：

- 用户主动保存 → 落到磁盘的对应文件
- 崩溃前未保存 → crash-recovery dump（17.6）

desktop 持久化层**不复制 buffer 内容**——避免与 workspace 重复、避免泄漏未保存数据。

### 24.11 第一版不做

- 跨设备同步（云持久化）
- 持久化文件加密
- 持久化版本管理（git-like 多版本回滚）
- 多布局快照（用户切换不同"工作模式"）
- crash-recovery 的下次启动恢复提示（推迟到第二版，对应 17.6 的第 5 步）

## 二十五、生命周期

第二章 2.2 已规定启动序列。本章补关闭、workspace 切换、资源清理、系统信号——围绕"用户的工作不丢失"展开。

### 25.1 触发关闭的入口

下列入口都派发同一个命令 `app.quit`，由唯一 handler 走完整流程：

| 入口 | 触发条件 |
|---|---|
| 命令面板 `app.quit` | 用户显式触发 |
| 全局键位 `mod-q` | macOS Cmd-Q / 其他平台 Ctrl-Q |
| 关闭最后窗口 | 11.5；macOS 例外（保持进程） |
| 系统信号（SIGINT / SIGTERM） | 见 25.5 |
| 平台 quit 事件 | macOS Dock quit / Windows shutdown |

收敛到单一命令避免多份关闭逻辑分叉。

### 25.2 关闭流程

```
app.quit handler
  1. 标记 quitting 状态（防止重入；二次触发直接 return）
  2. 收集所有窗口的所有 dirty buffer 清单
       若有 → 显示 SaveBeforeQuitDialog (Surface)
         - "保存所有" → 派发 editor.save_all → 等待完成
         - "全部丢弃" → 跳过
         - "取消"   → 解除 quitting 标记、中止流程
  3. flush PersistenceRegistry（写 layout / recent / usage）
  4. flush SettingsRegistry（确保 settings 已写）
  5. 关闭所有窗口（GPUI Window drop）
  6. 销毁每窗口 PanelHost / SurfaceManager / BubbleManager
  7. 关闭 LSP 子进程（第二版有 LSP 时）
  8. tracing::info!("zom shutdown complete")
  9. 进程退出
```

**幂等**：第 1 步的 quitting 标记保证重复触发不会重复弹 dialog 也不会重复 flush。

### 25.3 Workspace 切换

两个命令对应两种切换：

| 命令 | 行为 |
|---|---|
| `workspace.open` | 在**当前窗口**替换 workspace |
| `workspace.open_in_new_window` | 在**新窗口**打开；当前 workspace 不动 |

`workspace.open` 流程：

```
  1. 收集当前 workspace 的 dirty buffer
     若有 → 弹 Dialog 询问（同 25.2 第 2 步）
  2. flush 当前 workspace 的 layout.toml
  3. 销毁当前 Workspace / ViewSet（GPUI Entity drop）
  4. 创建新 Workspace 实例
  5. SettingsRegistry 重 merge 新 workspace 的 .zom/settings.toml
       触发 observable → 主题 / 字号 / locale 跟着切（若 workspace 覆盖）
  6. PersistenceRegistry 加载新 workspace 的 layout.toml
  7. 创建新 ViewSet（按 layout 恢复 split tree / tabs / 光标位置）
  8. WorkbenchFrame re-render
```

`workspace.open_in_new_window` 跳过 1-3 步，直接走 4-8 步（在新窗口）。

### 25.4 资源清理与 RAII

GPUI Entity 自动管理生命周期。desktop 不手动 Drop 大部分资源。

必须显式管理：

| 资源 | 显式处理 |
|---|---|
| LSP 子进程（第二版） | 显式 kill，避免 zombie |
| 文件 watcher | 随 Workspace Entity drop 自动释放 |
| 后台 Task | 组件 drop 即 cancel（与 23.4 一致） |
| 异步写文件的 pending flush | app.quit 第 3-4 步强制 await |

panic hook **不依赖 RAII**——崩溃时 GPUI 可能已不可用，必须用纯 std I/O 完成救援（17.6）。

### 25.5 系统信号

跨平台信号处理收纳在 `shell::platform::signals`（与 14.4 边界一致）：

| 信号 / 事件 | 处理 |
|---|---|
| SIGINT（terminal Ctrl-C） | 派发 `app.quit` |
| SIGTERM | 派发 `app.quit` |
| SIGKILL | 无法捕获；依赖下次启动 crash-recovery |
| macOS Cmd-Q / Dock quit | 派发 `app.quit` |
| Windows close 按钮 / shutdown 信号 | 关闭按钮 → `window.close`；最后窗口 → `app.quit` |
| Linux desktop session 结束 | 派发 `app.quit` |

信号 handler 必须 async-signal-safe——只做"把事件丢给主线程"，实际处理在 `app.quit` 命令 handler 内。

### 25.6 首次启动的特殊处理

首次启动（用户级配置目录不存在）：

```
1. 创建配置目录 ~/.config/zom/（或平台等价）
2. 不主动创建 settings.toml（与 12.7 一致：用户首次改设置才创建）
3. 加载内置默认（dark 主题 / zh-CN locale / 默认字号）
4. 首个 workspace 来源决策：
   - CLI 参数指定 → 打开该路径
   - 否则 → 默认空 workspace（unnamed scratch buffer）
5. 启动后续步骤照常（2.2 启动序列）
```

第二版可补"首次启动欢迎页"（推迟）。

### 25.7 第一版不做

- 优雅重启（关闭并自动重启进程）
- 系统 sleep / wake 时的 buffer 保护
- 多用户切换处理
- 子进程清理超时强杀（第二版与 LSP 一起补）
- 关闭过程中的"取消未保存写"中断（assume flush 总能在合理时间完成）

## 二十六、CLI 入口

zom-desktop 作为桌面应用，同时是命令行可调用的工具。本章规定 CLI 参数模式、路径解析、实例策略与平台集成边界。

### 26.1 第一版 CLI 参数

```
zom                              空 workspace 启动（默认 unnamed scratch buffer）
zom <path>                       打开文件或目录
zom <path1> <path2> ...          多目标（详见 26.2）
zom --new-window [path]          强制新窗口；与 25.3 的 workspace.open_in_new_window 等价
zom --version                    输出版本号后退出
zom --help                       输出帮助后退出
```

参数解析用 `clap`（或同类成熟 crate），**不自己手撸 parser**。

### 26.2 路径解析规则

| 输入 | 解析 |
|---|---|
| 单个目录 | 当 workspace 根打开；首个 buffer 由 layout 恢复（若有）否则空 |
| 单个文件（已存在） | workspace 根 = 文件所在目录的最近 git root；若无 git root → 文件所在目录；该文件作为初始 buffer 打开 |
| 单个路径（不存在） | 视为"新建文件"意图；workspace 根 = `cwd`；buffer 绑该路径但 dirty 直到首次保存 |
| 多个路径 | 第一个决定 workspace 根（按上述规则）；其余作为文件打开 |

**workspace 根判定的优先级**：CLI 显式 > 文件最近 git root > 文件所在目录 > cwd。

### 26.3 实例策略：第一版多实例

第一版**每次 `zom` 启动新进程**——多个进程独立运行、各自持有 settings/theme/locale 的拷贝（但全局共享的语义靠 OS 文件 inotify 自动同步，见 12.8）。

理由：

- IPC 实现跨平台复杂（macOS URL handler / Linux socket / Windows named pipe）
- 第一版用户量小，多实例性能成本可接受
- 让 desktop 第一版聚焦核心

第二版升级**单实例 + IPC**：

- 第一个进程是主进程
- 后续 `zom` 调用通过 IPC 把"打开 X"请求转给主进程
- 主进程决定走新窗口还是追加 tab

**CLI 表面在升级前后不变**——`zom <path>` 始终能工作，只是底下是否复用进程的差异。

### 26.4 退出码

| 码 | 含义 |
|---|---|
| 0 | 正常退出 |
| 1 | 内部错误（panic hook 设置；包括崩溃恢复后退出） |
| 2 | CLI 参数错误（clap 自带） |
| 3 | 配置文件严重错误且无法用默认（罕见；通常 settings 失败会走 12.7 fallback） |

### 26.5 平台集成（第一版只保命令行）

| 平台 | 第一版状态 | 第二版规划 |
|---|---|---|
| macOS | 命令行可用；Bundle 内不预注册文件类型 | Info.plist 注册文件类型；NSApplicationDelegate 处理 openFiles |
| Linux | 命令行可用；不自动注册 .desktop | .desktop 文件注册 MIME |
| Windows | 命令行可用；不自动改注册表 | 注册表关联文件类型 + cmd handler |

第一版用户想要"双击文件用 zom 打开"自己在系统设置里关联。

### 26.6 URL handler（推迟）

`zom://` 协议用于深链接（"打开远端文件"、"跳转到符号"、"插件入口"）推迟到第二版。届时设计：

```
zom://open?path=/abs/path&line=42
zom://workspace?root=/abs/workspace
```

第一版不实现；CLI 已覆盖大多数本地场景。

### 26.7 stdin / pipe（推迟）

第一版**不支持** `cat file | zom` 这类 stdin 输入。理由：

- 编辑器不是流式工具，pipe 输入语义模糊（要不要可编辑？保存到哪？）
- 命令行场景已被 `zom <path>` 覆盖

第二版可考虑 `zom --stdin` 显式接收 pipe 为只读 / 临时 buffer。

### 26.8 第一版明确不做

- 单实例 + IPC（第二版）
- URL handler `zom://`（第二版）
- stdin pipe（第二版）
- shell completion（`zom completion bash` 等；第二版）
- 文件关联自动注册（用户手动配；第二版可考虑安装脚本）
- macOS Quick Look 扩展
- 服务端模式（`zom --server`）

|---|---|---|

| 国际化 | 第一版立刻做接口；分散式 + enum locale + match；zh-CN / en-US 同步填写；只影响 desktop 层 | 十 |

| 设置文件 | 单文件 TOML；用户级 + workspace 级（覆盖语义）；强 schema；写回保留注释 | 十二 |
| Workspace 信任 | 第一版信任所有；trust 机制延后到第三版 | 12.11 |
