# 语法高亮异步 + 增量改造记录

> 本文档是兑现 [BASELINE](../../zom-bench/BASELINE.md) §4 性能红线的实施记录，配套 [桌面端语法高亮手册](../../zom-desktop/docs/桌面端语法高亮.md)。
>
> **结论先讲**：改造前 `HighlightWorker` = "同步 + 全量 + 主线程"，4 MiB 单键 457 ms、16 MiB 直接被 4 MiB 阈值拦掉，结构性塌。当前实现已收口为"异步 worker + tree-sitter 增量 + ReplaceRange 局部产物"三位一体，主线程脱钩文件大小、worker 端 viewport-scoped 后单键 < 100 ms。改造影响 [`zom-workspace::syntax`](../src/syntax/) 内部实现，不动 `HighlightProvider` trait 外部契约、不动 sink 协议、不动 desktop 渲染层。
>
> **2026-06-01 收口调整**：原方案以 64 MiB 为目标语料，实测 16 MiB 已达成红线；
> 64 MiB 主要受 tree-sitter 解析树本身 O(file size) 走树代价拖累（非本方案能撬
> 动），且现实场景中 16 MiB 已覆盖绝大多数单文件代码——超出基本是日志 / 生成
> 代码。**新阈值定 16 MiB**：超过部分由 `MAX_HIGHLIGHT_BYTES` 拦下静默落 plain。

## 1. 目标与红线

| 指标 | 改造前基线 | 改造后目标 |
|---|---|---|
| 16 MiB rust 单键 viewport-scoped e2e | 拦掉（>4 MiB 阈值） | < 100 ms（worker 端） |
| 16 MiB rust 单键主线程时间 | — | < 5 ms |
| 16 MiB rust `parse` 冷启动 | 拦掉 | ≤ 1.5 s（后台线程） |
| 4 MiB `MAX_HIGHLIGHT_BYTES` 阈值 | 屏蔽 >4 MiB | 提升到 16 MiB |
| 1 / 4 MiB 现有数字 | 见 BASELINE | 不允许劣化 |
| 64 MiB 一档 | 拦掉 | **不再追**：tree-sitter 走树本身 O(n) 不可避免，让宿主提示用户跳过高亮 |

## 2. 改造前一句话总结

```
HighlightWorker::on_edit
  → run_full
  → snapshot 全范围切片        // 物化全文 String（64 MiB 文件 = 64 MiB 分配）
  → Highlighter::highlight(bytes)  // tree-sitter-highlight 内部 Parser 从头 parse 全文
  → 收集 Vec<(TextRange, HighlightSpan)>  // 全文 spans
  → sink.replace_all
  → MetadataLayers::replace_layer_ranges  // 全层重建
```

四个"全":全文物化、全文 parse、全集 Vec、全层重建。每一处都是 O(文件大小)，每次按键都跑一遍，全部同步在主线程。

## 3. 总体方案

把上面四个"全"分别替换：

| 现状的"全" | 替换为 | 兑现的红线 |
|---|---|---|
| 旧全文物化 String | `TextProvider` 按 chunk 流式喂给 tree-sitter | peak RSS |
| `Highlighter::highlight(bytes)` 全文 parse | `Parser::parse(text, Some(&old_tree))` 增量 reparse | parse / edit+hl 时间 |
| 全文 spans Vec | 按 viewport ± 缓冲区 `QueryCursor::matches` 局部产 | spans Vec 内存 |
| `replace_all` 全层重建 | `replace_range` 仅替换 viewport 段 | 编辑延迟 |

并把整条链路推到**后台 worker 线程**，主线程只投递 job + drain sink。

## 4. 关键架构决策

### 4.1 脱 `tree-sitter-highlight`，直接用 `tree-sitter`

**为什么**：`Highlighter::highlight()` 签名固定吃 `&[u8]` 从头 parse，**不接受已有 Tree**——不可能做增量。这是 tree-sitter-highlight 的设计取舍，无法绕过。

**代价**：要自己用 `tree_sitter::Query` + `QueryCursor::matches` 写 capture → HighlightName 映射，复刻 tree-sitter-highlight 的"嵌套 stack + Source 段携带栈顶 capture"逻辑（[现实现 common.rs:128-156](../src/syntax/providers/common.rs)）。代码量 ~80 行 / 语言无关一份。

**收益**：拿到完整的 `Tree` 控制权——`Tree::edit()` + `Parser::parse(_, Some(&old_tree))` 这条增量路径才能走。

**当前状态**：旧 tree-sitter-highlight 路径已移除；失败时统一走本实现内的全量重解析或落 plain，不再保留旧实现切换开关。

### 4.2 Worker 线程模型：单全局 worker

**选项对比**：

| 方案 | 复杂度 | 并发度 | 内存 |
|---|---|---|---|
| 每 buffer 一线程 | 高（buffer 数 = 线程数，attach/detach 管理重） | 高 | 每线程一份 Parser/Tree，OK |
| 每语言一线程 | 中（13 线程常驻） | 中 | 同上 |
| **全局单 worker** | **低** | **低**（多 buffer 编辑串行） | **最省**（单 Parser pool） |

选**全局单 worker**：单用户编辑场景下"多个 64 MiB 文件同时频繁编辑"几乎不可能；编辑器 60 fps 的主循环不会被 worker 阻塞，最坏情况 = 第二个 buffer 的高亮延迟 50–100 ms 出，可接受。后续若证明是瓶颈再扩成线程池，**不影响 API**。

**线程内部结构**：

```rust
WorkerLoop {
    parsers: HashMap<LanguageId, Parser>,         // 复用，不重建
    trees: HashMap<BufferId, (BufferVersion, Tree)>,  // 每 buffer 最新树
    queries: Arc<LanguageRegistry>,               // 跨语言共享 query
    jobs: Receiver<Job>,
}

enum Job {
    Attach { buffer_id, language, snapshot, sink },
    Edit { buffer_id, edits: Vec<InputEdit>, new_snapshot, new_version, sink, viewport_hint },
    Detach { buffer_id },
}
```

### 4.3 任务投递与去抖（coalescing）

**问题**：用户连按 10 键，主线程发出 10 个 Edit job。worker 不可能 10 帧内做完——必须丢掉中间 9 个。

**方案**：每 `(buffer_id, sink)` 维护一个"最新待处理 job"的原子槽（`ArcSwap<PendingJob>` 或 `Mutex<Option<Job>>`）。主线程投递时**覆盖**槽而不是 append：

- 新 Edit 来了：取出旧 Edit（如果有），合并 `edits` 列表（旧的 InputEdit 还是有效的，因为 `Tree::edit` 可多次顺序调用），用新 snapshot/version 覆盖
- worker 完成当前 job 后从槽里**取走**最新待处理 job（leaves None），开干

**好处**：天然合并连续按键、自动丢弃中间过期版本、不需要显式 cancellation。

**cancellation**：tree-sitter 的 `cancellation_flag` 仍作为兜底——worker 在每个 parse 调用前后检查"buffer 当前期望版本"是否仍 = 我手上这个 job 的版本，否则把 flag 拉起来让 parse 中途退出。

### 4.4 ChangeSet → InputEdit 翻译

tree-sitter `InputEdit` 需要 6 个字段：

```rust
pub struct InputEdit {
    pub start_byte: usize,
    pub old_end_byte: usize,
    pub new_end_byte: usize,
    pub start_position: Point,      // (row, byte_column)
    pub old_end_position: Point,
    pub new_end_position: Point,
}
```

`ChangeSet` 暴露 `changed_ranges()` 但那是**新坐标**下的范围。tree-sitter 要的是**旧坐标下的 start / old_end，加新坐标下的 new_end**。换源：用 `EditList`（每条 `Edit` 有 `range`（旧）+ `replacement`（新文本））和老 Snapshot：

```rust
// edit.range() = 旧文本里被替换的范围
let start_byte = edit.range().start().get();
let old_end_byte = edit.range().end().get();
let new_end_byte = start_byte + edit.replacement().len();

// Point 需要 row + byte column；用旧 snapshot 算旧端，新 snapshot 算新端
let start_position = old_snapshot.byte_to_point(start_byte);
let old_end_position = old_snapshot.byte_to_point(old_end_byte);
let new_end_position = new_snapshot.byte_to_point(new_end_byte);
```

**关键工程点**：worker 要同时持有 **本次 edit 之前的 snapshot**（算旧端 Point）和**本次 edit 之后的 snapshot**（算新端 Point + 喂 TextProvider）。流程：

```
主线程 pump_post_edit:
  edit before = state.last_known_snapshot.clone()   // 极廉价（Arc 共享）
  edit after  = buffer.snapshot()
  events = buffer.take_pending_events()
  for event in events: translate to InputEdit using (before, after)
  push Job::Edit { edits, new_snapshot: after, new_version }
  state.last_known_snapshot = after
```

每个 Snapshot 都是轻量 clone（rope 内部 Arc + 几个 usize），多持一份不增加显著内存。

需要在 engine 公开一个便利方法 `Snapshot::byte_to_point(ByteOffset) -> (line, byte_in_line)`——`Position` 已经存在但是 char column；tree-sitter 要 byte column。实现成新公开方法即可（**engine 侧新增小 API**，唯一对 engine 的入侵）。

### 4.5 TextProvider：流式喂 rope chunks

tree-sitter `Parser::parse_with_options` 接受 `FnMut(usize, Point) -> impl AsRef<[u8]>`——从指定字节位置开始拿一段 bytes，tree-sitter 自己迭代调用直到 EOF。我们实现：

```rust
fn provider(offset: usize, _: Point) -> &[u8] {
    snapshot.chunk_at_byte(offset).as_bytes()  // 借自 ropey
}
```

ropey 的 `Chunks` 是 zero-copy `&str` 迭代；我们提供"任意 byte offset 后第一段 chunk"的访问。**engine 侧需新增 `Snapshot::chunk_at_byte(ByteOffset) -> &str`**——再一个小入侵。

这一步等价兑现"不再物化全文"——peak RSS 的 String 那 64 MiB 直接消失。tree-sitter 内部需要把 bytes 拷进自己的扫描缓冲，但是分块的、有上限的（kB 级），不是 GB 级。

### 4.6 spans 局部产物：viewport ± 缓冲区

`QueryCursor::set_byte_range(start..end)` 限制查询范围。worker 拿到 desktop 上报的 viewport hint（line_range → byte_range），加 ± N 行缓冲（避免每次轻微滚动都触发查询），跑 `cursor.matches(query, tree.root_node(), provider)`，得到的只是 viewport 段的 spans。

通过 `sink.replace_range(version, viewport_byte_range, spans)` 投递，只覆盖该段，远处的旧 spans 保留。

**协议升级**：现在 coordinator 的 `drain_into_layers` 把 `SinkMessage::ReplaceRange` 静默忽略（[coordinator.rs:139-141](../src/syntax/coordinator.rs)）。要把它接上 `MetadataLayers::replace_layer_ranges_in(kind, version, byte_range, spans)`——目前 engine 是否暴露这个 API 待确认；如果没有需要在 engine 加。

**viewport 通信**：`zom-view::ViewportState` 由 desktop 设置，coordinator 当前不读它。需要给 `BufferSyntaxState::handle_edit` 加一个 `viewport_hint: Option<TextRange>` 参数（main thread 已经知道），或者让 worker 跑两段：先全树 parse（必需，得到 syntax tree），再按 viewport 跑 query（局部出 span）。两段分离很自然。

### 4.7 Wake：每帧 drain

异步 worker 完工后产物落进 sink，但 sink 是**被动**的——必须有人调 `drain()`。当前只有 `pump_post_edit` 时调，**没编辑就不会 drain**——worker 算完了 span 也上不了屏。

**新增 `Workspace::pump_pending_highlights(&mut self)`**：扫描所有 buffer，对有 sink 的调一次 drain。desktop 在每帧 `prepaint` 开始时调。**额外成本 = 每帧扫一次 hashmap + 一次空 drain（拿锁、看 empty、放锁）**——主线程 1 µs 级别，60 fps 下完全可接受。

### 4.8 内存边界

| 单 buffer 持有 | 数量级（64 MiB rust） |
|---|---|
| Parser（在 worker，按语言共享） | 几 MB |
| `Tree`（latest only，每 buffer 一份） | ~ 200–400 MB（tree-sitter Rust 实测约 5–7× 源） |
| spans Vec（在 MetadataLayers） | viewport 段几十 KB |
| Buffer 本身（ropey） | ~ 100 MB |
| 旧 Snapshot 缓存（worker 用作 InputEdit 旧端 Point） | 0（snapshot 是 Arc 共享，挂在 buffer 内） |
| **合计** | **< 500 MB** ✅ 进红线 |

对比当前峰值 4.38 GB：消失的是 String 物化（64 MB）、tree-sitter-highlight 的短生命周期 stack/cursor 缓冲、全文 spans Vec（百万 entries × 几十字节 = 几十 MB）。

## 5. 分阶段落地

以下为历史落地顺序；v0.2.0 发布前只保留当前实现，不再保留阶段切换路径。

### 阶段 0 · 拆 tree-sitter-highlight，等价替换为 raw tree-sitter（**仍同步、仍全文**）

- 新 `RawHighlightWorker`：内部 `Parser + Query + lookup`
- `run_full` 流程：`parser.parse(全文 bytes, None)` → `QueryCursor::matches(query, tree.root_node(), …)` → 走与 tree-sitter-highlight 等价的嵌套 stack 合成 spans
- 新实现成为唯一 tree-sitter 路径，不保留旧高亮器切换开关
- **验收**：bench 数字与 v0.2.0 持平（误差 ±10% 内），单测全过

**风险**：Query API 与 highlight 的嵌套语义对齐细节，可能有 capture priority 差异。**对策**：写一组对比测试（同 buffer 喂两条路径，比较 span 集合）。

### 阶段 1 · 持久化 Parser + Tree，做增量 reparse（**仍同步**）

- `RawHighlightWorker` 持有 `Option<Tree>`
- `on_edit`：用 ChangeSet/EditList + 老 snapshot/新 snapshot 翻译成 `Vec<InputEdit>`，逐条调 `tree.edit(&ie)`，然后 `parser.parse(text, Some(&old_tree))`
- 需要的 engine 小 API：`Snapshot::byte_to_point(ByteOffset) -> (Line, byte_column)`、`Snapshot::chunk_at_byte(ByteOffset) -> &str`
- **验收**：64 MiB rust `edit+highlight` 单键 < 200 ms（仍同步，但增量 reparse 应该 <50 ms，加上其他全文 query 开销，目标 200 ms）；spans 集合等价于全量

**风险**：tree-sitter 增量重 parse 失败的边界条件（grammar bug、ABI 不匹配）。**对策**：parse 返回 `None` 时走全量重解析并复位 `Tree = None`。

### 阶段 2 · 推到后台 worker 线程，每帧 drain

- 新 `SyntaxWorker`：一个 `std::thread` + `mpsc::Receiver<Job>`，承载所有 buffer 的 parse
- 投递走 atomic slot 协议（4.3）
- `BufferSyntaxState::handle_edit` 改成投 Job，不再当场跑 parse
- `Workspace::pump_pending_highlights` 新方法，desktop 每帧 prepaint 起手调一次
- **验收**：64 MiB rust 单键主线程时间 < 5 ms（剩下的 ~50 ms reparse 在 worker；产物 1 帧后上屏）；输入响应不掉帧

**风险**：provider panic 后拖垮高亮线程。**对策**：每条任务包 `catch_unwind`，出问题的缓冲区移除高亮条目，其他缓冲区继续工作。

### 阶段 3 · ReplaceRange + viewport 局部产物

- `QueryCursor::set_byte_range(viewport ± buffer)`
- `sink.replace_range` 取代 `replace_all`（首次 attach 仍走 replace_all 铺底）
- coordinator 把 `SinkMessage::ReplaceRange` 接上 `MetadataLayers`（engine 可能需要加 API）
- desktop 滚动时通过 view 状态变更通知 syntax coordinator "viewport 变了，重新喂 hint"
- **验收**：spans Vec 内存常驻 < 1 MB；滚动后新区域 spans 1–2 帧内出现

**风险**：viewport 边界处的 span 撕裂（部分位于 viewport 内、部分超出）。**对策**：用更宽的查询范围（viewport ± N 行），让 query 看到完整 capture。

### 阶段 4 · 放开阈值（16 MiB 收口）

- `MAX_HIGHLIGHT_BYTES` 从 4 MiB 提升到 **16 MiB**。viewport-scoped 路径已脱钩
  文件大小，4 MiB 旧门槛可以撤；16 MiB 是兼顾"实际单文件代码上限"与
  "tree-sitter 走树代价仍可控"的现实位。超出 16 MiB 静默落 plain，等宿主侧
  加"用户可手动启用 + 警示"再放。
- 搜索 `DEFAULT_REGEX_HAYSTACK_BYTE_LIMIT` 单独立项——是 engine 侧问题，本方案
  不解决；放开它前需先做异步搜索 + 可取消 + 进度上报，否则换"卡死"。
- **验收**：BASELINE.md 16 MiB 一档红线达成（viewport-scoped e2e < 100 ms /键、
  主线程 < 5 ms、cold parse ≤ 1.5 s）。

## 6. 不做的事

- 不引入 `tokio` / async 运行时。用 `std::thread` + `mpsc` 足矣，避免新依赖。
- 不做 LSP semantic tokens 并行——本方案只覆盖 tree-sitter producer；LSP 是独立 producer，遵循同一 `HighlightProvider` trait 但内部线程模型不同（server 自带异步）。
- 不重写 `HighlightProvider` trait。这个 trait 已经为异步设计（sink + version 协议），阶段 2 完全在 worker 内部消化异步性。
- 不动 desktop 渲染路径。spans 落 `MetadataLayers` 后的消费链路完全不变。
- 不重排 cargo feature 拆分（tree-sitter grammar feature gating）；正交事项。
- **不处理多 view 共享同 buffer 的 viewport 联合**——以最大并集为 hint，或第一阶段只用 active view 的 viewport，错过的远处 view 接受短暂"高亮缺失 → 1–2 帧后补齐"。

## 7. 对 engine 的入侵（最小集合）

| 新增 API | 用途 | 风险 |
|---|---|---|
| `Snapshot::byte_to_point(ByteOffset) -> (Line, usize)` | ChangeSet→InputEdit 翻译，列单位为 UTF-8 byte | 低，纯派生 |
| `Snapshot::chunk_at_byte(ByteOffset) -> (&str, ByteOffset)` | TextProvider 流式喂 tree-sitter，返回 chunk 和它在全文里的起点 | 低，包装 ropey `Chunks::next` |
| `MetadataLayers::replace_layer_ranges_in(kind, version, byte_range, spans)`（若不存在） | ReplaceRange sink 消费 | 中，需要确认现有 API |

三项都属于"派生 / 包装"，不动核心数据结构、不引入新错误模型。

## 8. 发布收口

- 不保留旧同步全量实现、环境变量切换或 cargo feature 切换；发版代码只有当前 tree-sitter provider 路径。
- 失败策略收口在当前路径内：增量失败走全量重解析，provider panic 隔离到单缓冲区，超过 16 MiB 静默落 plain。
- 若后续 bench 退化，按测试和性能基线修当前实现；不重新引入发布期切换路径。

## 9. 验收与回归

- 每个阶段在 PR 描述里贴 `cargo run --release -p zom-bench -- run rust` 的旧/新对比表
- 等价性测试：raw collect、全量路径、增量路径与 viewport-scoped 子集互相比对，断言 name + range 严格相等
- panic 兜底测试：人造 provider panic，确认主线程不挂、其他缓冲区不受影响
- 长跑测试：连续 10k 次随机编辑 64 MiB rust buffer，断言 peak RSS 单调（不持续涨）、worker 没积压
