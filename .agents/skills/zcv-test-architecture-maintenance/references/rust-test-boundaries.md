# Rust 测试边界

## 编译边界

单元测试通常与被测模块一起编译，因此生产源文件中的 `#[cfg(test)]` 模块可以访问该模块的私有实现。

集成测试把生产 crate 当作普通依赖编译。生产 crate 编译为集成测试依赖时，不应假设其中的 `#[cfg(test)]` 会自动启用。因此，跨模块共享的测试能力不能依赖“生产 crate 内部测试模块会被集成测试看见”这一前提。

## 放置决策

| 场景 | 首选位置 | 判断依据 |
| --- | --- | --- |
| 只服务一个私有模块的辅助函数 | 相邻测试模块或 `test` 文件 | 不需要成为生产 API |
| 多个测试共享 fixture | 测试支持模块或独立 `test-support` crate | 共享的是测试资源，不是产品状态 |
| 需要访问私有实现的单元测试 | 就近单元测试 | 私有访问是单元测试边界的一部分 |
| 验证用户可见行为 | 通过产品正式入口 | 不应依赖测试专用后门 |
| 构造非法或不可达生产状态 | 测试支持工厂，或改为测试合法行为 | 不应放宽生产不变量 |

## 常见误判

- 被测试读取的字段不一定是测试专用字段；如果字段表达真实产品状态，应保留并从行为验证。
- `#[cfg(test)]` 不是迁移目标本身。它可能已经是正确的单元测试边界。
- `test-support` feature 只能显式启用，不能进入默认 feature 或发布构建；跨多个 crate 共享时，独立测试支持 crate 通常更清晰。
- 不要为了让集成测试访问私有状态而把字段改成 `pub`，也不要增加只为测试存在的 getter。
