# Zcv 架构维护

围绕真实依赖和当前需求维护 Zcv 的架构边界。先区分用户要的是只读审计还是明确修改；审计请求不授权改代码，清理、精简、重构等明确修改请求才授权在指定范围内实施。

## 选择工作模式

- 可见性、重导出、公开模块、规范导入路径：读取 [references/visibility-cleanup.md](references/visibility-cleanup.md)。
- 架构体检、边界审查、所有权或数据流审计：读取 [references/architecture-audit.md](references/architecture-audit.md)。
- 架构减法、删除错误抽象、兼容层或重复状态：读取 [references/architecture-subtraction.md](references/architecture-subtraction.md)。
- 组合任务只读取涉及的参考；通常先体检确定问题，再做减法，最后收紧可见性。

## 共同工作准则

1. 完整读取仓库与目标目录中的 `AGENTS.md`，再按修改范围读取直接相关的架构文档和模块实现；不要无条件读取整个 `docs/`。
2. 开始前检查工作树，保留用户已有修改。先确定目标模块的职责、调用方、真实消费方、状态所有者、生命周期和权威数据源。
3. 涉及成熟编辑器能力时研究 `/Users/liuyuan/project/zed` 的对应实现，理解设计和边界条件；只采用与 Zcv 当前目标一致的部分。
4. 用代码搜索、依赖清单、类型和测试证明结论。名称相似、代码行数、个人偏好或“以后可能需要”都不是架构证据。
5. 将发现区分为局部实现错误和底层抽象错误。底层抽象错误应修正唯一正确路径，不叠加特殊分支、回退、双写或兼容层。
6. 遵守 Zcv 当前范围：不引入实时协作、远程开发或 LSP；语法能力优先使用 Tree-sitter。
7. 只处理用户指定范围。若正确修复需要明显扩大范围、删除大量代码，或存在无法由现有设计判断的架构方向选择，停止并请求确认。

## 跨平台架构

跨平台重构的目标是统一语义流程和生命周期，而不是消灭所有平台差异或增加一层万能转发。

1. 先按能力域建立统一入口：调用方表达能力语义，不直接处理 `cfg`、平台路径、系统命令、平台资源布局或平台错误细节。
2. 将真实的系统差异放入能力域内部的私有平台后端；后端负责系统调用、路径布局、权限、进程模型和资源释放。
3. 共享平台无关的状态机、事务协议、错误语义和生命周期。不要为 macOS、Windows 等平台复制完整业务流程，也不要让平台后端决定上层业务策略。
4. 不默认创建全局 `Platform` trait、`zcv-platform` crate 或聚合所有系统能力的模块。只有多个能力域拥有相同且稳定的语义契约时，才提取共享原语；单一消费方的后端留在消费方附近。
5. 检查同一事实是否被多个层重复保存，例如应用路径、进程标识、当前平台键和更新事务状态。选择唯一所有者，其余位置只读取或派生。
6. 跨平台测试分为两层：平台无关测试证明共同语义和状态转移；平台测试证明后端对系统边界的适配。无法运行目标平台时，必须明确记录未验证的运行时行为。

典型边界应遵循以下形态：

```text
调用方 / UI
    ↓ 稳定语义入口
能力域核心流程、状态机和错误契约
    ↓ 私有平台后端
macOS / Windows / Unix / Linux 的系统适配
```

评审跨平台代码时，重点检查：统一入口是否真的统一了流程；平台 `cfg` 是否只出现在后端边界；平台后端是否拥有相关资源的完整生命周期；新增平台是否只需增加后端而无需复制业务流程；共享抽象是否有真实的多个消费方。

## 证据与交付

每个架构结论至少说明：

- 位置与实际依赖证据；
- 当前职责或数据流；
- 违反的边界及实际影响；
- 最小且完整的修正方向；
- 能直接证明结果的验证方式。

只读体检按影响排序报告发现；没有证据的问题不列为“可能风险”。修改任务应同步更新所有调用方、测试和受影响文档，删除被本次修改淘汰的路径，并运行与行为、类型、格式和 Lint 风险相匹配的最小验证。明确区分已验证、未验证和环境限制。

## 导入路径清理

项目级清理不能只针对当前暴露问题的 crate；应搜索所有 `zcv_*::` 等 crate 限定路径，并逐处判断是否确有必要。

- 已通过 `use` 导入且在同一文件中重复使用的模块、类型、函数或常量，统一采用导入后的短名称。
- 同名冲突、职责边界、文档链接、属性宏和单次使用路径，可以保留 crate 限定形式。
- 不要为了缩短路径盲目增加只服务一次调用的导入，也不要删除表达跨 crate 所有权或协议边界的限定。
- 清理完成后再次进行项目级搜索，确认剩余限定路径都能说明保留理由，并删除本次清理产生的无用导入。
