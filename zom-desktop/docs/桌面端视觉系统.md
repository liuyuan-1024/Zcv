# 桌面端视觉系统

> 本手册规定 `zom-desktop` 视觉令牌的全部规则：颜色、主题、尺寸、文案与图标、国际化。视觉的具体数值（色板、节拍刻度）以单独的 token 清单为准，本手册只规定它们的命名规则与归属规则。

## 一、颜色系统

### 1.1 两轴正交：色相 × 档位

颜色 token 由两个正交维度决定：

```
轴 A  色相 hue     gray | blue | yellow | red | green
轴 B  档位 step    01..09，跨色相含义固定（见 1.2）
```

token 命名形如 `hue.sNN` / `hue.aNN`，例：

```
gray.s01     app 底面背景
blue.s07     实心强调色（caret、按钮品牌色）
blue.s06     焦点边框
blue.a04     active UI 背景（半透明，叠在文本上）
yellow.a05   次级强调高亮（半透明）
```

**关键设计**：**档位 step 跨色相含义固定**。`blue.s07` 与 `red.s07` 都是"该色相的实心强调档"——色相决定语气，档位决定角色。组件按"我要哪种视觉角色"反查档位，按"是不是要强调 / 是不是危险态"选择色相；两个维度独立做决定。

**不引入 usage 轴**。先前把"用法"作为命名维度（`xxx.fill` / `xxx.text` / `xxx.border`）的设计撤掉——usage 不是颜色的属性，是消费方的事；档位 step 已经隐含了该用在哪类元素上（见 1.2 表）。

### 1.2 9 档功能语义表

每个色相提供 9 档；档位**严格跨色相对齐**：

| 档 | 角色 | 典型用法 |
|---|---|---|
| 01 | app background | 最深底面（编辑区底） |
| 02 | surface | 抬升面（浮层底、bars 底） |
| 03 | ui-bg | UI 元素背景（常态） |
| 04 | ui-active | UI 元素背景（active / selected / hover 后） |
| 05 | border-subtle | 次级边框、分隔线 |
| 06 | border-focus | 焦点强调边框、hover 边框 |
| 07 | solid | 实心强调（caret、按钮 bg、链接色、品牌色填充） |
| 08 | text-muted | 次级 / 弱化文字 |
| 09 | text | 正文 / 强调文字 |

**档位含义不可更改**。一旦发布，每个数字代表的视觉角色就是用户主题作者的隐式 API（详见 2.6）——改它就破坏所有用户主题。

**关于 text 的强弱**：第一版只有 08 / 09 两档文字色。需要"比正文更强"的对比时，**靠 font_weight，不靠色阶**——给文字加 token 是逃避排版规则。

**gray 的 06/07 档**：填值以保持跨色相对称（无障碍 / 中性 solid 场景可能用到），但调用时优先考虑能否用 accent 色相。"中性焦点框"是 gray.s06 的少数合法场景；多数 focus / solid 应该走 blue。

### 1.3 solid 与 alpha 双阶梯

每个色相提供两条并行阶梯，档位语义同步：

```
hue.sNN    solid    不透明 RGB；用于边框、文字、实心填充
hue.aNN    alpha    半透明 RGBA；叠加在底色上的色块，让下层透过
```

| 形态 | 适合 | 不适合 |
|---|---|---|
| `sNN` | 文字、1px 边框、caret、按钮 bg、图标 | 跨文本的色块（会盖住 syntax 字色） |
| `aNN` | 选区背景、搜索高亮、hover 高亮、AI 提案区间 | 文字色（alpha 文字对比度不稳） |

**取色三步**：先选色相（语气）→ 再选档位（角色）→ 最后选 solid / alpha（叠加方式）。三个维度有清晰先后，调用方不需要"凭审美挑步数"。

举例：

```
caret 实心竖条        blue.s07    （蓝色相 × solid 强调档 × 不透明）
选区背景色块          blue.a04    （蓝色相 × active UI 档 × 半透明）
搜索普通命中          blue.a05    （蓝色相 × border-subtle 档 × 半透明）
搜索当前命中          yellow.a05  （黄色相 × border-subtle 档 × 半透明）
错误文字              red.s07     （红色相 × solid 强调档 × 不透明）
危险按钮 hover 边框   red.s06     （红色相 × focus 边框档 × 不透明）
```

注意搜索两个命中**共用 a05 档**——同视觉角色，色相区分；这正是档位含义跨色相对齐的红利。

### 1.4 命名硬规则

1. **永远不按组件命名颜色**。`topbar_bg`、`status_item_color`、`caret_color` 都属于禁项。
2. **永远不按用法命名颜色**。`selection_bg`、`focus_border`、`link_text` 都属于禁项——用法在档位 step 里。
3. **永远只按"色相 + 档位"命名**。组件按视觉角色反查档位、按语气反查色相。
4. **组件本地色是例外、不是常态**。能进 token 的不进本地；进本地的必须在组件 doc 里写明"为什么不能复用 token"。

### 1.5 档位与色相的冻结纪律

档位含义（1.2 表）与色相列表（1.1）一旦发布即冻结：

- **不能改某档位的语义**。比如把 `s07` 从"solid 强调"改成"次强调"，会同时改写所有 5 个色相的同一档语义——这是用户主题作者的契约破坏。
- **新增档位是不可逆操作**。9 档之外要加（如 `s10`），所有内置 + 用户主题都得补值；走 2.6 deprecation 流程。
- **新增色相不影响档位语义**。要加 `purple` / `cyan` 等新色相时，按 9 档语义表完整填值就行——这是档位语义跨色相对齐的红利。
- **删除色相或档位是破坏性变更**。

### 1.6 颜色 token 的 API 形态

token 必须以函数形式暴露而非常量。函数签名固定为：

```rust
pub fn s07(cx: &App) -> Rgba { cx.theme().blue.solid.s07 }
pub fn a04(cx: &App) -> Rgba { cx.theme().blue.alpha.a04 }
```

组件代码不允许出现 `const BLUE_S07: Rgba = ...`，也不允许出现不接受 `cx` 的零参 token 函数。这是主题切换得以运行时生效的前提。

调用形如 `color::blue::s07(cx)` / `color::yellow::a05(cx)`——色相是模块、档位是函数。括号始终在最后，与"组件 → 取色 token"的语法心智一致。

### 1.7 与主题的关系

颜色 token 的**集合定义**（5 色相 × 9 档 × 2 阶梯 = 90 个 token）由本章规定，**取值**由主题决定。换主题只能改取值，不能改集合。第二章规定取值如何被填充和切换。

第一版不区分"品牌色"。所有颜色 token 都参与主题切换。

## 二、主题系统

### 2.1 定位

主题是颜色 token 集合的一次完整填充。**主题不增减 token**，只决定每个 token 的具体取值。

只有颜色参与主题切换。**尺寸、字号、圆角、间距不参与主题**。

### 2.2 主题来源

```
内置主题   embedded 在二进制里
           themes/dark.toml
           themes/light.toml

用户主题   从用户目录加载
           ~/.zom/config/themes/*.toml（具体路径按平台规约）
```

第一版提供两套内置主题：`dark` 与 `light`。用户主题第一版即支持加载。

### 2.3 配置格式：TOML

主题文件采用 TOML。每个色相一个表，下分 `solid` / `alpha` 两个子表（对应 1.3 的双阶梯）：

```toml
name = "dark"
extends = "dark"   # 可选；继承的基底主题名

[gray.solid]
s01 = "#0d0f12"   # app background
s02 = "#13161b"   # surface
s03 = "#1b1f26"   # ui-bg
s04 = "#252a33"   # ui-active
s05 = "#3a4050"   # border-subtle
s06 = "#4a5266"   # border-focus
s07 = "#5e6678"   # solid
s08 = "#a8b0c0"   # text-muted
s09 = "#f2f4f8"   # text

[gray.alpha]
a01 = "#0d0f1219"   # alpha 各档对应 solid 同档语义，叠在背景上
a02 = "#13161b26"
# ... 9 档全填

[blue.solid]
s01 = "..."
# ... 9 档全填
s06 = "#5a8fd6"   # border-focus（焦点边框）
s07 = "#74ade8"   # solid（caret、品牌色）

[blue.alpha]
a04 = "#74ade83d"   # ui-active 档：选区色块
a05 = "#74ade866"   # border-subtle 档：搜索普通命中
# ... 9 档全填

# yellow / red / green 同结构
```

颜色值统一用 `#RRGGBB` 或 `#RRGGBBAA`。**禁止**在主题文件里出现 token 名以外的自定义键。**每个色相的 solid 与 alpha 两套阶梯都必须各填 9 档**（除非 `extends` 覆盖，见 2.4）。

### 2.4 继承语义

用户主题通过 `extends` 字段声明基底，**只列要覆盖的差异**：

- `extends` 缺省时，主题必须**完整定义**所有 token；加载时若有遗漏直接报错并拒绝加载。
- `extends` 指向另一个主题时，缺失字段从基底继承；显式给出的字段覆盖基底同名值。
- 继承只允许一级，不允许链式。
- 基底只能是**内置主题**。强制内置主题永远是完整定义、永远是稳定锚点。

### 2.5 切换路径

```
settings.theme 改变
    ↓
ThemeRegistry 重算 active theme（解析 extends、合并字段）
    ↓
全局 observable 触发
    ↓
所有调用过 cx.theme() 的组件 re-render
```

组件**完全不感知主题切换**——只通过 `cx.theme()` 取值，GPUI observe 负责传播。主题加载失败一律 fallback 到 `dark`，**绝不静默忽略**。

### 2.6 主题作者的隐式 API

**token 命名与档位语义都是用户主题作者的 API**——一旦发布就极难改名 / 改义。这反向约束 1.1 的命名规则与 1.2 的档位语义：

- token 命名必须可读、稳定、与组件解耦
- **档位 step 的视觉角色含义不可悄悄改**——改 `s07` 的语义会同时改写所有色相的同一档
- 新增色相 / 档位是不可逆操作（用户主题不会自动覆盖新 token）
- 删除或重命名色相、档位是破坏性变更，需走显式 deprecation 流程

第一版起就要为 token 写一份"主题作者参考"——列出 5 色相 × 9 档 × 2 阶梯每个 token 的功能含义与示意取值。本文档不重复该清单。

## 三、尺寸系统

尺寸系统分为两个独立子系统：**距离类节拍尺**（固定）与**字号**（用户可配）。二者解耦。

### 3.1 距离类节拍尺

间距、圆角、icon 尺寸、控件 padding 必须落在同一根节拍尺上：

```
基础节拍 = 4px
半节拍   = 2px（仅供 hairline / 描边 / 圆点直径微调）
合法步长 = 2, 4, 6, 8, 12, 16, 20, 24, 32, 40, 48
```

距离类 token **完全固定**，不参与字号变化、不参与任何系数。字号变化只让"文字行高自然变大"，节拍尺保持纯净。

### 3.2 命名风格：绝对像素

```
space.s2 / space.s4 / space.s6 / space.s8 / space.s12 / space.s16 ...
radius.r2 / radius.r4 / radius.r6 / radius.full
icon.i12 / icon.i14 / icon.i16 / icon.i20
```

相对档位命名抗腐性差。绝对像素命名看名字就知数值、不会膨胀。

允许在底层之上引入语义别名（`gap.inline = space.s4`），但别名永远是底层 token 的 alias、不允许独立赋值。

距离类 token 函数签名可以零参：

```rust
pub fn s8() -> Pixels { px(8.0) }
```

### 3.3 字号系统

字号是**唯一**对用户可配的尺寸维度。zom 不引入密度系统、不引入整体缩放。

字号分为两组独立可配的基础值：

```
ui_font_size       桌面外壳与所有 L2/L3 组件的基础字号，默认 13
buffer_font_size   编辑器缓冲区字号，默认 14
```

二者完全解耦。其他字号档位以基础值为锚点派生：

```
text.caption(cx)   ui_font_size - 1
text.body(cx)      ui_font_size
text.title(cx)     ui_font_size + 1
text.large(cx)     ui_font_size + 3

editor.body(cx)    buffer_font_size
editor.gutter(cx)  buffer_font_size - 1
```

字号 token 必须接受 `cx`，从 `cx.fonts()` 取基础值。

### 3.4 行高的派生

行高**不暴露为独立 token**，从字号按固定比例派生：

```
ui 行高     = ui_font_size × 1.5
editor 行高 = buffer_font_size × 1.4
```

行距比例是文档级常量，组件不感知。派生而非独立暴露的理由：行高与字号绑死才能保证视觉协调。

### 3.5 不引入密度系统

zom 明确不引入独立密度系统（无 compact / normal / comfortable 档位、无 density scale 系数）。理由：

- 用户调字号 → 行高跟着变 → 文字行天然变紧/变松 → 已覆盖大多数"密度感"需求
- 间距类完全脱钩字号变化 → 节拍尺保持纯净 → 视觉对齐永远精确到像素
- icon 尺寸固定 → 跨字号下控件结构稳定

**未来约束**：即使将来引入密度系统，作用域也只允许**全局一档**——禁止局部分区。理由是局部分区会让节拍尺失去"窗口内统一"的保证，且会让组件知道自己在哪种密度上下文里，污染分层。

### 3.6 组件内禀尺寸

组件自身的"为什么是这个值"是组件设计决策，应当写在组件本地常量里，不进 token。例：红绿灯直径、品牌徽标尺寸、特殊图形几何参数。

## 四、文案与图标

### 4.1 文案

组件专属文案以函数形式写在组件本地 `copy.rs`，每条通过 `match cx.locale()` 给出多语言文本。详见第五章。

跨组件复用的标准文案（如"取消"、"确定"、"关闭"）下沉到 `shell::copy` 模块，按动作语义命名，不按出现位置命名。

### 4.2 图标

资源文件（svg）由根 `assets/` 统一管理，按语义类别分目录。组件只持有自己需要的相对路径，不带 `assets/` 前缀。

```rust
svg().path("icons/actions/close.svg")
```

多处复用的图标路径可以保留为组件本地常量；panel 图标统一由 `PanelId::icon_path()` 映射。只在一处使用的图标路径直接内联。

## 五、国际化

### 5.1 哲学

zom-desktop 第一版即引入 i18n 接口。理由：从字符串直接量迁移到 i18n 是机械重复但工作量巨大的事；"先做接口、再补翻译"的 ROI 远高于"先做直接量、将来全局替换"。

i18n 实现采用最轻量方案：**分散式 + enum locale + 零外部依赖**。不引入 fluent / gettext / rust-i18n 等库。

i18n 只影响 desktop 层。底层 crate 的 `Display`/错误消息**用英文**，由 desktop 在呈现时翻译为 locale 文本（每个底层 crate 的英文 Error 在 desktop 内有专门的翻译模块，新增 Error 变体编译期强制补翻译）。

### 5.2 Locale 与切换

```rust
// shell/i18n.rs
#[derive(Clone, Copy, PartialEq, Eq)]
pub enum Locale {
    ZhCN,
    EnUS,
}
```

第一版固定支持 `ZhCN` 与 `EnUS`。每条文案两种语言都必须填写——`Locale` 是 enum，`match` 强制穷举，缺翻译直接编译错。

默认 locale 为 `ZhCN`。locale 通过 `settings.locale` 配置，运行时切换，机制与主题完全相同。

### 5.3 组件文案的写法

```rust
// shell/features/panels/file_tree/copy.rs
use crate::i18n::Locale;
use gpui::App;

pub fn empty(cx: &App) -> &'static str {
    match cx.locale() {
        Locale::ZhCN => "暂无文件",
        Locale::EnUS => "No files",
    }
}
```

调用方：`div().child(copy::empty(cx))`。

### 5.4 含变量的文案

涉及插值的文案用 `format!()`，返回 `String`：

```rust
pub fn found_n(cx: &App, n: usize) -> String {
    match cx.locale() {
        Locale::ZhCN => format!("找到 {n} 个匹配项"),
        Locale::EnUS => format!("Found {n} match{}", if n == 1 { "" } else { "es" }),
    }
}
```

复数 / 性别 / ICU 高级语法第一版不引入。

### 5.5 不翻译的内容

- 产品名（`zom`、`zom-desktop`）
- 技术专有名词（`LSP`、`Workspace`、`Editor`、`Panel`）
- 文件路径、命令 ID、快捷键文本
- 代码 / 标识符
- 底层 crate 的英文 Display 消息（直接在日志、技术对话框中保留原样）

判定准则：**翻译后用户更难看懂的，不翻译**。

### 5.6 跨组件标准文案

跨组件复用的标准文案下沉到 `shell::copy` 模块：

```rust
// shell/copy.rs
pub fn cancel(cx: &App) -> &'static str {
    match cx.locale() {
        Locale::ZhCN => "取消",
        Locale::EnUS => "Cancel",
    }
}
```

命名按动作语义，不按出现位置。

### 5.7 为什么不用 i18n 库

- **编译期穷举**：i18n 库走运行时表，缺 key 只有运行时暴露；enum match 缺翻译直接编译错
- **翻译跟随组件**：组件删除时翻译自然移除，不会留下"30% 死翻译"的腐烂表
- **零工具链**
- **重构友好**

代价是不支持第三方翻译平台。将来确需走 Crowdin / POEditor 时再迁移到集中式表，接口 `copy::xxx(cx)` 不变。
